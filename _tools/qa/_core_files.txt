# SOrders **核心区**文件清单（2026-09-21 用户定准则：核心逻辑不要乱动、核心不要变）
#
# 「核心」＝**动一下就会让钱算错、状态走错、权限漏掉、或者历史数据变样**的那几处。
# 其余一切（新功能 / 新页面 / 新动作 / 新端点 / 新检查）都按**插件式**扩展：
#   能调方法就调方法、能继承就继承、能调 API 就调 API —— 见 docs/CORE_AND_EXTENSION.md。
#
# ## 规矩（改核心文件的人必须做的一件事）
# 在 `docs/AI_WORK_CLAIM.md` 的「## 进行中」一节里写一行：
#
#     核心改动：<这个文件的路径> —— 为什么必须动核心：<一句话>
#
# ⛔ 没有这一行而工作区里又改了核心文件 → `python _tools/qa/_check_core_freeze.py` 当场报红。
#    （判据只看**未提交**的改动：提交之后就进了 git 历史，那时声明页已经不是唯一记录了。）
#
# 格式：`路径|为什么它是核心（一句话）`；`#` 开头是注释，空行忽略。
# ⛔ 不许为了让检查变绿而删条目：脚本里有一条"骨架判据"钉着必须存在的那些（`_SKELETON`）。
#
# ## ⭐ 核心区**不是永久禁止修改**：它只能被「证据触发的例外」修改（R4-00，2026-09-27）
#
# 用户 2026-09-26 拍板（R3-06 生产 Drill C 抓到 P1 之后）：冻结的**目的不是让核心永远不变**，
# 而是让每一次改动**必须有一个已经发生过的事实当理由**。例外要同时满足三件事：
#
#   ① **有证据** —— 不是"我觉得这样更好"，而是生产演练 / 线上原始输出 / 失败用例里拿到的**原始证据**。
#      （R3-06 那次的证据是：停 Redis 时一条真实业务写入的发件箱事件被记成 `sent attempts=0`，
#        而同一次演练的日志里有 16 条 `Cannot publish to redis... giving up`。）
#   ② **只治那个病** —— 改动范围由证据界定的**那一条链**决定。
#      ⛔ "顺手"做的重构 / 换实现 / 加抽象层**不算例外**：那属于新的一轮，要另行立项，
#      不许借这个口子进来（用户 R3 的原话：「这次只治一个病」）。
#   ③ **写下来** —— 在 `docs/AI_WORK_CLAIM.md` 的「进行中」写一行
#      `核心改动：<路径> —— 为什么必须动核心：<一句话>`，并在报告里留一条
#      「**演练 → 缺陷 → 修复 → 重跑**」的证据链（R3 的样子见 `docs/R3_FAILURE_DRILL_EVIDENCE.md`
#      与 `docs/RECTIFICATION_REPORT_R3.md` §2.7）。
#
# ⛔ 反过来同样成立：**没有这三件事就不许动核心**。
#    判据 `_check_core_freeze.py` 的第 3 条（未提交）与第 4 条（HEAD 那个提交）就是这句话的机器形态；
#    规则本身写在 `docs/CORE_AND_EXTENSION.md` §2.1。
