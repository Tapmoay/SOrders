# SOrders AI 能力方案：垂直工具型 Agent + 长期记忆

> 定位：**这份是方案，不是实现。** 不涉及任何代码改动。
> 基线：`android/app/src/main/java/com/tapmoay/sorders/ai/`（20 文件）、`docs/ai/ai_toolmap.json`（127 端点）。
> 参考：`ref-operit-*.md` 三份（Operit 调研）。

---

## 0. 结论摘要

**目标口径**（用户原话）：不需要跟通用智能对齐，核心目标是**把 App 原本的功能做到让 AI 全部了解、全部使用**，用户只要通过 AI 就能完成所有功能。

按这个口径衡量，现在的 AI 是**一个做得很扎实的「查询助手」，还不是「办事助手」**：

| 维度 | 现状 | 目标 | 差距 |
|---|---|---|---|
| **读** | 36 / 49 只读端点 | 49 | 小 |
| **写** | **0 / 78 写入端点** | 78 | **决定性缺口** |
| **记忆** | 仅行为统计（AiHabit） | 事实 + 习惯 + 会话三层 | **决定性缺口** |
| Agent 循环 | 已有，质量高 | 复用 | 无 |
| 上下文管理 | 已有自愈机制 | 复用 | 无 |

**一句话**：现在 AI 只能"看"，不能"做"，也"记不住"。这两个缺口就是方案的全部内容。

### 0.1 为什么不能拿 Operit 当标尺（但可以当参考）

| | Operit | SOrders（本项目） |
|---|---|---|
| 定位 | **通用** Android Agent | **垂直** 派单业务 Agent |
| 工具数 | **180 个**（实测 `ToolRegistration.kt`） | 6 个 |
| 能力域 | 蓝牙16 / 浏览器22 / 文件15 / 角色卡9 / 聊天9 / 工作流8 / 终端8 / 记忆7 / 音乐7 / UI自动化 / 沙箱 / … | 业务读 6 |
| 评判标准 | 能做的事越多越好 | **App 功能覆盖率** |

> **关键判断**：Operit 的 180 个工具里，绝大多数是「操作系统能力」（蓝牙、浏览器、音乐、终端），**SOrders 一个都不需要**；反过来，SOrders 最需要的「业务写入」，Operit 根本没有对标物（它不对接任何业务系统）。
>
> **所以：工具数量不是目标，功能覆盖才是。** 本项目的工具数应该收敛在 **25 个左右**（6 读 + ~20 写），而不是去追 180。Operit 值得抄的是**机制**（风险分级、权限模式、工具暴露裁剪、结果回灌规范），不是**清单**。

### 0.2 顺带发现的一个可直接改的点：工具定义「单一出处」

Operit 的工具定义是**一份数据同时供给两处用**（`data/model/ToolPrompt.kt`）：

```kotlin
data class ToolParameterSchema(name, type, description, required, default)
data class ToolPrompt(name, description, parametersStructured, details, notes)
```

`parametersStructured` **既渲染成给模型看的提示词文本，又直接转成 function-calling 的 JSON schema**——所以两者不可能不一致。

**SOrders 现状是三处各写一遍**（`AiTools.kt`）：
| 用途 | 位置 | 例子 |
|---|---|---|
| function-calling schema | `SCHEMAS`（JSON） | `put("description", "货主姓名或手机号…")` |
| 给模型的描述 | `DESCRIPTIONS` | `"按姓名或手机号查找货主…"` |
| 设置页文案 | `TITLES` / `HINTS` | `"查货主"` / `"按姓名或手机号找货主…"` |

三处描述同一件事，**改一处忘一处**就会出现「设置页说 A、模型看到 B」。工具数从 6 涨到 26 之后，这个风险会放大。

**建议**：收敛成一个 `ToolSpec` 数据类（name / 标题 / 一句话说明 / 给模型的描述 / 结构化参数 / 风险级别），三处都从它派生。这与 §2.3 的「风险分级写进代码常量」是同一件事的两面——**工具的元数据应该只有一份**。

> ⚠️ **补正（读完 Operit 工具体系报告后）**：Operit 在这一点上**只是做对了一半**，别把它当标杆。
> 它的 `parametersStructured` 确实同时供给"提示词文本"和"function-calling schema"（必然一致），**但注册表 `ToolRegistration`（185 次 registerTool）与提示词表 `SystemToolPrompts` 仍是两处手写**——工具名拼错**不会有编译错误**。代价是项目里存在一份 200 行的「改工具参数必改 8 处清单」（`docs\doc-src\architecture\DEFAULT_TOOLS_ARCH.md:25-201`）。
> **所以目标不是"像 Operit"，而是"让拼错工具名编译不过"。** 生成式单一出处 > 手写多处 + 人工 checklist。

## 1. 现状诊断

### 1.1 已经做对的，不要推倒

这几处质量很高，方案是在其上叠加，不是重写：

| 资产 | 文件 | 为什么好 |
|---|---|---|
| agent 循环 | `AiAgentLoop.kt` | 8 步硬上限、取消穿透、tool_call_id 兜底、工具往返不入历史（`sanitizeHistory`） |
| 通用读通道 | `AiReadService.kt` + `AiReadCatalog.kt` | 一个工具 + `action` 枚举 + 编译期白名单，规格常量级；`ignored_filters`/`assumed_filters` 如实回报 |
| **名字→编号解析** | `AiReadService.resolveId()` | **这是写入能力的地基，已经有了一半** |
| 字段过滤红线 | `AiRowShaper.kt` | 单一出处，剔 `id`/`*_id` + `cost*`/`profit`/`margin` |
| 上下文自愈 | `AiContext.kt` | 窗口按模型名猜 + 撞 400 读端点自述上限 + 成功率反推长大 |
| 压缩 | `AiCompactor.kt` | 摘要保留筛选条件；压缩后只留 user/纯文本 assistant（避免拆散工具对） |
| 行为统计 | `AiHabit.kt` | 注入三纪律（只作默认值/必须说明范围/样本不足不注入） |
| 配置存储 | `AiKeyStore.kt` | API Key AndroidKeyStore AES-GCM；**学到的窗口与"不支持思考的主机"会持久化** |

> 最后一条特别值得注意：`learned_windows` / `no_thinking_hosts` 这种「**错了自己能修并记住**」的模式，正是记忆系统该有的形态。方案 B 直接沿用这个思路。

### 1.2 三个缺口

**缺口 A（决定性）：写入能力 0/78。**
78 个写端点里有 20 个是订单/派单——**恰好是派单员的主职**。现在 AI 明确写着自己「只有只读能力：不能下单、派单、改价、删除、撤销」（`AiAgentLoop.kt:252`）。用户说「把这单派给张师傅」，AI 只能让他自己去点。

**缺口 B（决定性）：没有长期事实记忆。**
`AiHabit` 记的是「他常用哪几个工具、常用哪个时间范围、最近问了什么」——是**行为统计**，不是**业务事实**。
它记不住「城东水果批发 = 张老板，习惯月结」「金龙鱼调和油走 5L 箱装」「王师傅只跑城西线」。
每次对话都要重新问、重新查。

**缺口 C（次要）：只读覆盖 36/49**，缺 13 个（详见 §4）。

## 2. 方案 A：写入能力（P0，最高 ROI）

### 2.1 为什么不能把 78 个端点变成 78 个工具

两个理由：

1. **端点 ≠ 用户动作**。用户说「把这单派给张师傅」是一个动作；后端需要的是 `POST /orders/{id}/assign` 加一个 `driver_id`。78 个端点是 **API 视角**，不是**用户视角**。
2. **工具数上升会杀死选工具准确率**。`AiReadService.kt:216` 的注释已经把这个判断写下来了（"36 个工具定义会塞满每一次请求…模型的选工具准确率会随工具数下降"）。写侧更该守这条。

→ **按「业务动作」聚合，不按端点聚合。**

### 2.2 聚合草案：78 端点 → 约 18 个业务工具

按模块聚合，每个工具对应「用户会说的那句话」：

| # | 工具（草案名） | 覆盖端点 | 用户会这么说 |
|---|---|---|---|
| 1 | `create_order` | create_order, create_order_product ×N | 「给城东水果批发下一单：金龙鱼 10 箱，送到…」 |
| 2 | `assign_order` | assign_order, batch_assign_orders | 「把这单派给王师傅」/「把待派池里的都派给王师傅」 |
| 3 | `update_order` | update_order, patch_order_exception, update_order_freight | 「这单地址改成…」「标记为货损」「运费改成 80」 |
| 4 | `cancel_order` | cancel_order, recall_order | 「撤销这单」/「把派给王师傅的那单收回来」 |
| 5 | `complete_order` | complete_order, complete_order_with_upload, pay_order, charge_order, upload_delivery_photos | 「这单送到了，收现金」/「挂到城东水果批发账上」 |
| 6 | `delete_order` | delete_order, delete_cancelled_order, restore_order | 「删掉这单」/「恢复刚才删的那单」 |
| 7 | `split_order` | split_order_endpoint | 「这单拆成 3 份」 |
| 8 | `manage_product` | create/update/delete_product, upload_product_image | 「新增商品…」「把金龙鱼的库存改成 50」 |
| 9 | `manage_inventory` | create_movement | 「入库 20 箱金龙鱼」 |
| 10 | `manage_ledger` | create/update/delete_entry, create_receipt, sync_ledger | 「记一笔支出 300 元油费」「城东水果批发还了 5000」 |
| 11 | `manage_user` | create/update/delete_user, swap_shipper_driver | 「新增一个司机…」「把张三改成货主」 |
| 12 | `manage_price_rule` | create/update/delete/batch_price_rules | 「给城东水果批发设专属价」 |
| 13 | `manage_address` | shipper 模块 11 个 | 「给城东水果批发加个新地址」 |
| 14 | `manage_arrears_unit` | arrears 3 个 | 「新增一个挂账单位」 |
| 15 | `manage_expense` | create_expense | 「记一笔…」 |
| 16 | `manage_vehicle` | create/update_vehicle | 「新增一辆车」 |
| 17 | `manage_template` | freight_templates 3 个 | 「加一个运费模板」 |
| 18 | `settle_driver` | generate_bills, create_settlement, settlement_action | 「给王师傅结算这个月的运费」 |
| 19 | `manage_notification` | notifications 7 个 | 「把消息都标成已读」/「给王师傅发个通知」 |
| 20 | `resolve_exception` | resolve_exception_order | 「这个异常单处理完了」 |

> `auth` 那 4 个（登录/注册/发短信）**不该给 AI**——它们是"进门"的动作，不是业务动作。
> `customers.merge_customers` 是高风险合并，建议**先不开放**。

### 2.3 风险分级与确认策略（这是写侧的核心设计）

78 个写端点的后果差别巨大。**分级的意义是让「绝大多数操作不打断用户」**：

| 级别 | 判据 | 例子 | 交互 |
|---|---|---|---|
| **L0 无痕** | 不改业务数据本质 | mark_read, driver_ack_view | 直接执行 |
| **L1 可自助撤销** | 自己就能改回来 | update_order, update_remark, 通知类, create_expense | 直接执行 + **结果卡带「撤销」** |
| **L2 需确认** | 产生新业务对象 | create_order, create_user, create_product, manage_address, create_entry | **执行前弹确认卡** |
| **L3 敏感不可逆** | 影响钱/账/派单/删数据 | assign_order(批量), complete_order, pay_order, charge_order, cancel_order, delete_*, settle_driver, price_rules, merge_customers | **执行前确认 + 二次核对（金额/单数/对象名）** |

**关键**：分级表要**显式写进代码常量**（像 `AiHabit.MIN_SAMPLES` 那样），而不是散在提示词里。提示词叮嘱会漏，代码常量不会。

### 2.4 引用方式：编号依然不进模型（复用 resolveId）

**这是整个方案最关键的复用点。** 现有红线是「AI 不许看到编号」，而写入又必须指定对象——看似矛盾，其实已经有解：

| 对象 | AI 用什么引用 | 为什么可行 |
|---|---|---|
| 订单 | **`order_no`**（用户可见） | `AiReadService.kt:369` 注释已写明「订单号是**用户看得见**的编号（和内部主键不是一回事），所以可以按它反查」；`OrderOut.order_no` 存在；`AiRowShaper.isHiddenField` 只拦 `id`/`*_id`，**`order_no` 能通过** |
| 人（货主/司机/客户） | **名字** | `resolveId()` 已实现，含「精确匹配优先，再模糊」两级 |
| 商品 | **商品名** | 同上 |
| 挂账单位 | 名字 | 已有 `arrears_unit_name` 在 `OrderOut` 里 |

**所以写工具的参数一律是「订单号 + 名字 + 业务字段」，绝不出现 ID。** 编号只在工具内部那一次 HTTP 里短暂存在，用完即弃（沿用 `resolveId` 注释里的原则）。

**必须补的一件事：歧义处理。** 现在是 `firstOrNull`——**重名会静默选错人**。读侧选错只是看到错数据，写侧选错就是**把单派给了别人**。所以写侧要求：

- `resolveId` 增加**写入专用的严格模式**：命中 0 个 → 报错；命中 ≥2 个 → **不猜**，返回候选列表让模型反问用户（「有两位叫王师傅的：王建国/王建军，是哪位？」）
- 这条是 L3 级工具的前置条件，不可省

### 2.5 两段式：先预览，后执行

L2/L3 工具建议走**两个工具**而不是一个：

```
preview_assign_order(order_no, driver_name)
   → {"preview": "把订单 SO20260914001（城东水果批发，3 件，送到…）派给司机王建国",
      "token": "pv_7f3a", "warnings": ["王建国今日已完成 12 单"]}

execute_assign_order(token="pv_7f3a")
   → 真正执行
```

好处：
1. **确认卡的内容由工具生成，不由模型编**——模型可以把预览文案写错，但执行的是 token 指向的那个动作，**所见即所执行**
2. token 一次性、有有效期（如 5 分钟），防重放
3. UI 上就是一个确认卡片，用户点「确认」调 execute

> 对比方案：让模型直接调用并用 App 拦截弹窗。问题是模型可能一次并发调好几个写工具，拦截层要处理"部分确认"，复杂度反而高。两段式把确认权交回给 UI，模型只负责"提议"。

### 2.6 幂等

写工具必须带 `client_token`（App 生成 UUID，随请求发给后端）。用户的网络是手机网络，**超时重试是常态**；没有幂等键，一次「派单」超时重试就可能派两次。

> 待确认：后端是否已有幂等支持。若没有，这是**后端要配合改的第一件事**（见 §7 待验证）。

### 2.7 权限与角色

- 写工具**必须复用后端的权限判定**（现有 `humanError` 已把 403 转成「当前登录账号没有权限」）
- 建议：**按角色裁剪写工具集**。司机端不该看到 `assign_order`，货主端不该看到 `settle_driver`
  - 现有 `AiTools` 已有 `enabledNames` 回调机制，扩展成「角色默认集 × 用户开关」即可
- L3 工具建议默认**关闭**，由用户在设置页显式打开（沿用「高级能力默认关闭」的既有惯例）

### 2.8 设置页改动

现状（截图确认）：设置页那一栏标题是 **「工具（只读）」**。

方案后的形态：

```
工具
  ├─ 查询（36 项，按模块开关）        ← 现有，标题从「工具（只读）」改上去
  └─ 操作（20 项，默认只开 L1）
       ├─ [L1] 改订单备注 / 标记已读 / 记支出      ← 开关
       ├─ [L2] 下单 / 新增人员 / 新增商品          ← 开关
       └─ [L3] 派单 / 送达收款 / 撤销 / 删除 / 结算 ← 开关（默认关，开启时二次确认弹窗）
```

## 3. 方案 B：长期记忆（P1，用户明确想要）

### 3.1 Operit 的启示与**降维**

Operit 的记忆是**图谱 + 四路召回打分 + LLM 结构化提取 + 有序写回**（见 `ref-operit-memory.md`）。

**结论：不要照搬。** 理由：

| Operit 的做法 | 为什么 SOrders 不需要 |
|---|---|
| 知识图谱（节点+边+传播打分） | Operit 是通用助手，用户什么都聊；SOrders 的实体关系**后端数据库里已经有了**（订单↔货主↔司机），再建一张图是重复建设 |
| 向量检索 + HNSW 索引 | 垂直场景实体名明确（货主名/商品名/订单号），**关键词+实体匹配就够**；向量反而引入云端 embedding 依赖和不确定性 |
| LLM 提取（每 5 条候选批量调模型） | 烧 token 且不可控。**SOrders 有更便宜、更准的来源：业务动作本身** |

**该抄的是这四条**（真正值钱的部分）：
1. **「错了自己能修并记住」**——`AiKeyStore.learned_windows` 已是这个形态，推广到记忆
2. **抗膨胀闸门**：只存「用户特定的可复用知识」、**不存常识**、**不存未来/推测项**、无价值就什么都不写
3. **`update`/`merge` 优先于 `new`**、新条目有上限——直接对抗"记忆越用越膨胀"
4. **注入时带约束**：只作默认值 + 必须说明用了什么 + 样本不足不注入（`AiHabit` 三纪律已具备）

### 3.2 三层记忆模型

```
┌─ 会话记忆（已有）AiCompactor + AiConversation   短期，一次会话内
├─ 行为记忆（已有）AiHabit                          中期，本机统计，跨会话
└─ 事实记忆（新增）AiMemory                        ★ 长期，业务事实，跨会话
```

**`AiMemory` 存什么**（严格限定，这是抗膨胀的关键）：

| 类别 | 例子 | 来源 |
|---|---|---|
| **别名/称呼** | 「张老板」= 城东水果批发 | 用户说 + 动作确认 |
| **稳定属性** | 城东水果批发月结；王师傅只跑城西线 | 用户说 + 动作统计 |
| **操作偏好** | 下单默认送到后门；运费按 5L 箱装算 | 用户说 + 动作观察 |
| **异常/坑** | 这个地址导航会错，要导旁边加油站 | 用户说 |

**明确不存**：任何金额/单量等**业务结果**（那在数据库里，查得到）；常识；推测；临时要求。

### 3.3 记忆怎么产生（按 ROI 排序，这是关键取舍）

Operit 走的是「对话后 LLM 提炼」。**SOrders 应该反过来：先做前两个免费的，LLM 提炼放最后。**

| 优先级 | 来源 | 成本 | 可靠性 | 说明 |
|---|---|---|---|---|
| **① P0** | **用户显式指令** | 0 | 最高 | 用户说「记住：城东水果批发是月结」→ 直接写。需要一个「记住」的表达约定 + 确认卡 |
| **② P0** | **业务动作回填** | 0 | 高 | 派单成功后自动记「SO20260914001 → 王建国」？**不，这属于业务结果不该存**。真正该存的是**动作里暴露的稳定映射**：用户选了"张老板"这个联系人 → 记「张老板 = 城东水果批发」；用户给某地址传了照片 → 记「这个地址有参考图」 |
| **③ P1** | **重复模式统计** | 0 | 中 | 沿用 `AiHabit` 的模式：同一货主反复用同一地址 → 该地址是它的常用地址（**由数据本身统计，不调模型**） |
| **④ P2** | **LLM 提炼** | 高 | 中 | 只在①②③都不够时做；且要批处理 + 门槛 + 严格 schema（抄 Operit 的 `{}` 空返回约定） |

> **我的建议：先只做 ①②③，把④无限期推后。** 你们的场景里，用户明确说一句「记住…」的 ROI 远高于花 token 猜。等记忆库真的攒起来、有真实使用数据了，再决定要不要上④。

### 3.4 记忆怎么用（复用已有通道）

**好消息：注入通道已经存在。** `AiAgentLoop.run(systemExtra:)` 就是为此设计的（现在传的是 `AiHabit.promptHint` + 摘要）。

改法：`systemExtra` 变成**拼接**——习惯 + 事实记忆 + 摘要，各自带自己的约束段。

**检索**：不需要向量。按**当前问题里出现的实体名**做匹配：
- 问题里出现「城东水果批发」→ 取出所有以它为键的记忆条目
- 问题里出现「王师傅」→ 取出别名指向的记忆

这比 Operit 的 RRF 打分简单得多，但**在垂直场景里够用且可解释**。

**预算**：记忆注入要**限条数 + 限字数**（建议 ≤ 15 条 / ≤ 800 字），并在超预算时按「最近用到 / 用得最多」淘汰。否则记忆会慢慢吃掉上下文——这是所有记忆系统的通病。

### 3.5 存储与安全

沿用 `AiConversationStore` 已经验证过的四条做法：
1. **App 私有目录**（`filesDir`），刻意不用外部存储（里面有客户名）
2. **先写 `.tmp` 再 `renameTo`**（原子，不会半截）
3. **坏文件改名留证**，不静默覆盖
4. **任何异常都不抛**（记忆丢了不影响主流程）

### 3.6 配置面

```
AI 助手设置
  └─ 记忆
       ├─ 事实记忆（列表，可查看/编辑/删除单条）   ← 必须可编辑，否则错了没法纠
       ├─ 本机统计（现有 AiHabit，可清空）
       ├─ 「记住这句话」开关
       └─ [清空全部记忆]
```

**「记忆可查看可编辑」是硬要求**——不可见的记忆等于不可控的行为，用户会不信任。

## 6. 风险与红线

| 风险 | 对策 |
|---|---|
| **AI 派错单**（最严重） | 两段式确认 + 歧义不猜 + L3 默认关闭 + 预览文案由工具生成而非模型编 |
| **重试导致重复写入** | 幂等键（需后端支持） |
| **成本价泄露** | 现有 `AiRowShaper` 已守住；**写工具的返回体必须同样过它**（写操作的响应也会带完整对象） |
| **编号泄露** | 写工具参数/返回一律无编号；`preview` 文案也只用人名/订单号 |
| **记忆越长越膨胀** | 存入门槛 + 条数/字数预算 + `update` 优先 + 可查看可编辑可删 |
| **模型幻觉出没发生的操作** | 写工具**只返回后端真实结果**；未执行成功绝不回「已完成」 |
| **权限越界** | 按角色裁剪工具集 + 复用后端 403 |
| **⚠️ 权限判定建立在模型可控文本上** | 见下方「反面教材」——**这是本次调研发现的真实缺陷，必须避免** |

### 6.1 反面教材：Operit 的权限可被模型绕过

调研 Operit 工具体系时发现一处真实缺陷（`api\chat\enhance\ToolExecutionManager.kt:459`）：

```kotlin
hasPromptForPermission = !invocation.rawText.contains("deny_tool")
```

即：**模型只要在自己输出的工具调用原文里带上 `deny_tool` 这个字符串，就能跳过权限询问、直接被记为 granted**（`:488-493`）。

**教训：权限判定绝不能建立在"模型可控的文本"上。**

这条直接印证了 §2.5 两段式设计的必要性：
- ❌ 「让模型直接调用写工具，App 拦截弹窗」——**拦截逻辑要读模型给的参数来判断风险，就落进了同一个坑**
- ✅ 「模型只产出 preview 文本 → App 生成 token → 用户确认 → execute(token)」——**风险等级与确认由 App 按工具名查表决定，模型碰不到判定依据**

### 6.2 反过来：这两点 SOrders 已经领先 Operit

| 维度 | Operit | SOrders |
|---|---|---|
| **最大工具轮数** | **没有**——`api\chat\` 全目录无 `maxIterations`/`MAX_TOOL_ROUNDS`，循环是递归的，只有三条终止路径（模型不再调工具 / token 超阈值 / 外部取消） | ✅ `AiAgentLoop.DEFAULT_MAX_STEPS = 8` 硬上限 |
| **参数校验** | `ToolExecutor.validateParameters` **默认恒真**（`AIToolHandler.kt:488-490`），原生工具默认无类型/必填校验，只能各 executor 手写 | ✅ `ToolArgException` + 逐工具显式校验 + 日期格式校验 |

> **别因为 Operit 有 180 个工具就默认它更成熟。** 在「Agent 循环纪律」和「参数校验」这两件最要命的事上，SOrders 做得比它好。方案是在你们的正确基础上叠加，不是推倒重来。

## 7. 假设核验结果

### ✅ 已核验（本轮已在代码中确认）

| 假设 | 结论 | 证据 |
|---|---|---|
| **`order_no` 是否全局唯一** | **是，可安全作为引用键** | `backend/app/models/order.py:21`：`order_no: Mapped[str] = mapped_column(String(32), unique=True, index=True)` |
| **订单号格式与可读性** | `SO{YYYYMMDD}{10位随机}`，如 `SO202609141234567890` | `backend/app/services/auth_service.py:50 new_order_no()` |
| **拆单子单号是否也唯一** | 是，父单号 + `-N` 后缀 | `backend/app/services/order_flow.py:120`：`order.order_no + "-" + str(idx + 1)` |
| **人是否有重名风险** | **有，`full_name` 无唯一约束** | users 模型中 `full_name` 无 unique/index 约束 |
| **`order_no` 是否会被 `AiRowShaper` 过滤掉** | 不会——过滤器只拦 `id` 与 `*_id` | `AiRowShaper.isHiddenField()`：`k == "id" \|\| k.endsWith("_id")` |
| **名字→编号解析是否已存在** | 已存在，且订单分支已支持按订单号反查 | `AiReadService.resolveId()`，含 `IdKind.ORDER` 分支 |

> **结论**：§2.4 的「编号不进模型」方案**完全可行**，且地基已在代码里。
> **结论**：重名风险**真实存在**，§2.4 的「歧义不猜、返回候选让模型反问」**是必需项，不是优化项**。

### ⚠️ 仍需确认（动手前）

1. **后端是否支持幂等键**？——决定 §2.6 能否落地。若不支持，这是**后端第一优先改动**。
2. **78 个写端点里，哪些实际上只有特定角色能调**？——决定 §2.7 的角色裁剪表。`docs/PROJECT_MAP/08A_ENDPOINT_INDEX.md` 有授权列，需逐条对齐。
3. **后端写操作返回体是否带完整对象**——影响返回体过滤与「撤销」能力的实现方式。
4. **用户对「AI 能改数据」的接受度**——建议先在一个角色（派单员）灰度。
5. **生产数据里货主/司机重名的实际比例**——决定歧义处理 UI 的紧迫度（假设①已证明风险存在，但不知频率）。
