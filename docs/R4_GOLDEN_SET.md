> 用户 2026-09-27 §11：

## §1 它比的是什么

| | 是什么 |
| --- | --- |
| **Legacy** | 核心的价目匹配 `services/freight_pricing.quote_for`（**生产今天真的在跑的那一版**） |
| **Extension** | `backend/app/extensions/pricing/freight_template.py`（R4-16 新增：把同一套挑选规则**原样搬进契约**） |

同一份「输入世界」喂给两边，逐笔比**结论**（算出哪一条价目、多少钱、是不是「不猜」）。

⭐ 这正是用户 §12 那条链要的验收方式：

    Order → PricingContext → PricingContract → implementation → Money

⛔ 注意：**核心照样是 Legacy**。这一轮**没有接线** —— 先把「候选算得跟生产一模一样」证出来，
接线（Shadow / Canary）是后面几格的事。

## §2 两份东西（⛔ 别把它们混成一份）

| | 在哪 | 谁写的 |
| --- | --- | --- |
| **语料** | `_tools/qa/_golden/freight_pricing.json` | **人写的**：世界 + 期望 + `why`（每一条都要说清它为什么在这儿） |
| **比对器** | `_tools/qa/_check_golden_set.py` | 机器：现建临时库 → 跑 Legacy → 跑 Extension → 比 |

**三种结论**：

- `match`：金额（两位小数口径）与「哪一条价目」都对上；
- `mismatch`：**任何一处对不上就报红** —— 用户原话「不要立刻说差一点点没关系，尤其是钱」；
- `known-diff`：写在语料里的已知差异，每条必须带理由（**现在是 0 条** —— 表空着是结论，不是漏了）。

⭐ 判据还核一件事：**语料里「人写的期望」必须和「核心算出来的」一致**。
只有核心那一栏的话，这份语料的结论就只是「候选像核心」，而不是「候选对」—— 这两件事差别很大。

## §3 覆盖（用户点名的十一个桶，逐条对账）

| 桶 | 样例 | 说明 |
| --- | --- | --- |
| 普通订单 | `normal-route-hit` / `normal-route-id-hit` | 终点逐字相同 / 靠**线路编号**命中（写法不同也算） |
| 边界 | `boundary-template-no-category` / `boundary-category-mismatch` / `boundary-order-no-category` / `boundary-route-miss` / `boundary-no-address` | 通用兜底 / 分类对不上 / 这一单没分类 / 路线没价目 / 没有地址 |
| 零值 | `zero-fee` | 0.00 是一条**真的价格**，⛔ 不是「没定价」 |
| 小数 | `decimal-fee` | 88.88 |
| 最大值 | `max-fee` | 9999999999.99（金额列上限） |
| 不同计价类型 | `pricing-kind-ambiguous` / `pricing-kind-not-mine` | 同一档多条 → **不猜** / 快照点名别的 kind → 这个实现不认领 |
| 四舍五入边界 | `rounding-3dp` | 见 §4 —— 这一格**证伪了一个猜想** |
| 异常输入 | `error-driver-no-rule` / `error-rule-without-templates` | 司机没挂规则 / 规则没勾价目 |

⛔ **三个桶明确「不适用」**（写在判据的 `NOT_APPLICABLE` 里，每条带理由，⛔ 不许安静地少一个）：

| 桶 | 为什么不适用 |
| --- | --- |
| 不同单位 | 承运运费是「一条路线一条价」，**不按件、不按斤** —— 单位只影响商品行（`quantity × unit_price`）。要按量计价是**另一个计价方式**（扩展里的 `per_quantity` / `tiered` 就是） |
| 折扣 | 当前承运运费的模型里**没有折扣这一维**（价目就是最终金额）。⛔ 造一个「打折的价目」出来，比的就成了我编的规则，不是生产 |
| 附加费 | 同上。要加是**新能力**，得先有产品口径，再进语料 |

## §4 一条被数据**否掉**的猜想（⭐ 这一节比结论本身值钱）

我原本的判断是：**价目表里存三位小数时，核心会原样给出 12.345，只有候选实现才量化成 12.35**
—— 于是我在语料里把这两件事分别写成了期望。

实测：**两边都是 12.35**。量化发生在**读库那一步**（SQLAlchemy 的 `Numeric(12,2)`
结果处理器），两条路都经过它。

⇒ 「核心不量化」这个担心在当前实现下**不成立**。这条语料把它钉住了，
而且它当场说明了一件事：**Golden Set 的价值不只是「回归」，还是「证伪」** ——
一个听起来很对、也没人会去查的猜想，被一行真实输出否掉。

## §5 ⛔ 这份语料**证不了**什么（如实列着）

1. **不证明「核心是对的」**：它证明的是「候选与核心逐笔一致」。
   核心自己错的地方，两边会**一起错**，而这份语料看不出来。
   （真实样本那一栏尤其如此 —— 期望值就是核心算的。）
2. **不是真实生产数据**：§3 的「世界」是**构造**的（一条路线、一两条价目、一个司机）。
   ⛔ 脱敏真实样本、以及对**生产订单**的逐笔比对，是 ⑤ Shadow 那一格的事。
3. ✅ **曾经最大的一处残余风险，已经消掉**（2026-09-27 当天，R4-17）：
   喂给候选实现的那份快照原来是**我照着 `quote_for` 的读法转录的**（`snapshot_from_db`），
   ⛔ 不是核心导出的 —— 转录错了这份语料照样全绿。
   现在它换成**核心自己导出的那一份**（`services/freight_pricing.freight_snapshot_of`，
   与 `quote_for` 共用 `driver_template_ids` / `route_ids_of` / `candidate_templates`）。
   ⭐ 换完之后**仍然是 15/15、mismatch 0** —— 既说明那份转录忠实，也说明风险**从构造上消失**。
   ⇒ 这条风险不再靠"我保证我抄对了"，而是靠"两边根本是同一份代码读出来的"。
4. **不覆盖别的计价方式**：按量计费 / 阶梯价 / 多币种都没有进这份语料
   （它们是别的 `pricing_kind`，各有各的语义）。
