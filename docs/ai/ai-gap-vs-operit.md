# SOrders AI vs Operit：差距对照与优化清单

> 用途：回答「对比 Operit，我们还在缺什么、哪里可以优化」。
> 基线：`android/app/src/main/java/com/tapmoay/sorders/ai/`（20 文件）；Operit HEAD `b2c7610`。
> 配套：`ai-vertical-agent-plan.md`（怎么做）、`ref-operit-*.md` ×4（参照物）。

---

## 一、总览

按**「垂直工具型 Agent + App 功能全覆盖」**这把尺子量，差距分三类：

| 类别 | 数量 | 说明 |
|---|---|---|
| 🔴 **真缺口** | 5 项 | 影响"能不能用 AI 办完事" |
| 🟡 **可优化** | 6 项 | 不影响正确性，影响体验/可维护性/成本 |
| 🟢 **已领先** | 3 项 | 比 Operit 做得好，**别改** |
| ⚪ **不该学** | 5 项 | Operit 有但我们不需要（防过度对齐） |

## 二、🟢 先说已领先的（别动）

| 维度 | Operit | SOrders | 证据 |
|---|---|---|---|
| **最大工具轮数** | **没有**——`api\chat\` 全目录无 `maxIterations`/`MAX_TOOL_ROUNDS`，递归循环，只靠三条路终止 | ✅ `DEFAULT_MAX_STEPS = 8` | `AiAgentLoop.kt:336` |
| **参数校验** | `validateParameters` **默认恒真**，手写的 schema 只喂模型、不用于运行时校验 | ✅ `ToolArgException` + 逐工具显式校验 + 日期格式校验 | `AiTools.kt:298-305,629` |
| **成本意识** | 无特殊设计 | ✅ 不做自动重试（"重试会把费用翻倍"）、压缩时关思考省 token | `LlmClient.kt:271`、`AiCompactor.kt:97-99` |

> 这三条说明你们的取舍是清醒的。**优化时不要为了"对齐 Operit"而放弃它们。**

## 三、🔴 真缺口（5 项，按优先级）

### 缺口 1｜写入能力 0 / 78 ★★★★★
**已详述于 `ai-vertical-agent-plan.md` §2**，此处只记结论：
后端 127 端点 = 49 读 + **78 写**，现在写了 0 个。20 个订单/派单写入恰好是派单员主职。
系统提示第 4 条明写「你只有只读能力」，设置页标题就是「工具（只读）」。

### 缺口 2｜没有长期事实记忆 ★★★★★
**已详述于 `ai-vertical-agent-plan.md` §3**。`AiHabit` 是行为统计（工具次数/时间范围/最近问题），**不是业务事实**。

### 缺口 3｜**非流式输出** ★★★★☆ ← 本轮新发现

**这是最直观的体验缺口，而且成本最低。**

| | Operit | SOrders |
|---|---|---|
| 流式 | ✅ 自研 `Stream` 抽象 + SSE 逐块 `emit`，UI 逐字出字 | ❌ `val stream: Boolean = false`（`LlmClient.kt:174,580`） |

直接后果：**用户提问后，在整轮跑完之前看不到任何文字**——包括 8 步工具循环里的每一轮。UI 只能显示「正在思考…」（`AiChatScreen.kt`）。

代码里已写明现状与原因（`LlmClient.kt:266-271`）：
> 「第一版用非流式（stream=false）…流式 SSE 要自己解析 `data:` 分片、`[DONE]`、以及把增量 tool_calls 按 index 拼起来，而 okhttp-sse 官方自述 experimental。先跑通再优化」

**架构已为流式留好口子**：`AiEvent.TextDelta` 的注释明确写着「非流式实现下只会在最后一次一次性给出完整文本…**以后换成流式时这个事件可以连续触发，聊天页不用改**」。

→ **这是一次低风险高收益的改动**：换 `LlmClient` 内部实现 + `AiEvent.TextDelta` 改为连续触发，UI 层不用动。

### 缺口 4｜无工具权限询问机制 ★★★☆☆

现在全部只读，所以不需要。**但写侧一上就必须有**：

| | Operit | SOrders |
|---|---|---|
| 权限档位 | 3 档（ALLOW / ASK / FORBID）× 2 层（全局默认 + 单工具例外） | 仅**开关**（`enabledTools` / `enabledReadModules`） |
| 询问 UI | WindowManager 悬浮窗 + 60s 超时 + `ALWAYS_ALLOW` 记忆 | 无 |
| 存储 | DataStore，`overrideLevel ?: masterSwitch` | prefs 字符串集合 |

> ⚠️ 但**别照抄 Operit 的实现**——它有权限旁路缺陷（见 §5）。SOrders 的写侧应该走 `plan §2.5` 的两段式（App 生成 token，模型碰不到判定依据）。

### 缺口 5｜工具结果无统一截断策略 ★★☆☆☆

| | Operit | SOrders |
|---|---|---|
| 单条结果上限 | **64,000 字符**硬上限 + `[工具结果过长，已截断]` 后缀 | 仅按**行数**限（`DEFAULT_ROWS=20 / MAX_ROWS=50`） |
| 危险 | — | **单行可能极大**（如 `remark`/`internal_notes` 长文本、`order_products` 嵌套数组） |

20 行 × 每行很长的 JSON 仍可能吃掉大量 token。建议加一道**字符级预算**，与行数限制并存。

## 四、🟡 可优化（6 项）

| # | 项 | 现状 | 建议 | 收益 |
|---|---|---|---|---|
| 1 | **工具元数据三处手写** | `SCHEMAS` / `DESCRIPTIONS` / `TITLES+HINTS` 各写一遍 | 收敛成 `ToolSpec` 一处，三处派生（`plan §0.2`） | 6→26 工具后**必然**出错，早改早省 |
| 2 | **无并行工具执行** | `AiAgentLoop` 里 `for (call in normalized)` **顺序**执行 | 只读工具可并发（Operit 白名单 12 个） | 多工具查询延迟从 N×RTT 降到 ~RTT |
| 3 | **厂商预设仅 3 家** | DeepSeek / 豆包 / 千问（`AiProviders.kt:64`） | 按用户实际用到的补；不建议追 39 家 | 低优先级，够用即可 |
| 4 | **无用量可见性** | 刻意不显示（`AiContext.kt:239-241` 注释：用户明确说不要看数字） | **保持不显示给派单员**；但建议在**设置页深处**给管理员一个统计入口 | 排障与成本控制 |
| 5 | **无「知识/规则」注入机制** | 只有 system prompt 硬编码 9 条规则 | 参考 Operit 的 **Skill 思路**：纯提示词注入，不注册工具 | 难以做成工具的业务规则（如"货损判定口径"）可做成文档注入 |
| 6 | **历史清洗后工具往返全丢** | `sanitizeHistory` 只留 user/纯文本 assistant | 这是**正确**的（避免 400）；可考虑把**上轮工具结论**并入摘要 | 减少重复查询 |

## 五、⚪ 不该学的（防止过度对齐）

| Operit 有 | 为什么 SOrders 不需要 |
|---|---|
| **180 个工具**（蓝牙 19 / 浏览器 22 / 音乐 / 终端…） | 全是 OS 能力，与派单业务无关。**目标是 App 功能覆盖率，不是工具数量** |
| **知识图谱 + 向量检索 + RRF 打分** | 实体关系后端库里已有；垂直场景实体名明确，关键词+实体匹配够用且可解释 |
| **39 种厂商 + 密钥池 + 限流** | 你们只有 3 个预设且用户是派单员，不是开发者 |
| **CLI 降级**（弱模型只给 2 工具） | 你们硬性要求模型支持 function calling（`AiProviders.TOOL_CALLING_REQUIREMENT`），不需要为弱模型设计 |
| **插件生态**（ToolPkg / MCP / Skill 市场） | 封闭业务 App，没有第三方开发者 |

> **⚠️ 特别提醒：Operit 的权限实现有真实缺陷，绝不能抄。**
> `api\chat\enhance\ToolExecutionManager.kt:459`：
> ```kotlin
> hasPromptForPermission = !invocation.rawText.contains("deny_tool")
> ```
> **模型只要在输出里带上 `deny_tool` 字符串就能跳过权限检查。**
> 教训：**权限判定不能建立在模型可控的文本上。** 这正是 `plan §2.5` 两段式设计（App 生成 token）要规避的。

## 六、建议动作清单（按性价比排序）

| 优先 | 动作 | 工作量 | 依赖 | 为什么不排后面 |
|---|---|---|---|---|
| **1** | **改流式输出**（缺口 3） | 中 | 无 | 收益最直观、架构已留口子、UI 不用改 |
| **2** | **`AiMemory` 存储 + 注入 + 可查看可编辑**（缺口 2 的 P1-a） | 中 | 无 | **记忆先于业务铺开**：早期样本少、错了代价小 |
| **3** | **写工具框架**（缺口 1 的 P0-a）：风险分级常量 + 两段式 + `resolveId` 严格模式 + 幂等 | 大 | 后端幂等键 | 先用 1 个 L1 工具打通全链路 |
| **4** | **工具元数据收敛**（可优化 1） | 小 | 无 | 越晚改越贵（工具数在涨） |
| **5** | **记忆来源①②**（用户说"记住" + 动作回填） | 中 | 动作 2、3 | — |
| **6** | **L1+L2 写工具**（约 10 个） | 大 | 动作 3 | — |
| **7** | **工具结果字符级截断**（缺口 5） | 小 | 无 | 可与动作 3 合并做 |
| **8** | **工具权限询问**（缺口 4） | 中 | 动作 3 | 写工具上线的**前置条件** |
| **9** | **并行只读工具**（可优化 2） | 小 | 无 | 纯提速 |
| **10** | **L3 敏感写工具**（派单/送达/收款/撤销/删除/结算） | 大 | 动作 6、8 | 需灰度 |
| 11 | 只读补齐 / 厂商预设 / 用量统计 / 知识注入 | 小 | — | 有余力再说 |

> **顺序里最有信息量的是第 1 和第 2**：
> - 把**流式**排第一——因为它**不改架构**（`AiEvent.TextDelta` 注释已声明"聊天页不用改"），却直接影响用户每次使用的第一印象；
> - 把**记忆存储**排在**写工具**之前——写工具铺开后每个动作都要考虑"要不要回填记忆"，反过来会返工。

## 七、一句话总结

**你们缺的不是"更聪明的 AI"，是三件事：**

1. **让它能动手**（78 个写端点 → 约 20 个业务动作工具）—— 最大的功能缺口
2. **让它记得住**（三层记忆，先做免费的显式指令与动作回填）—— 你明确想要的
3. **让它答得快点**（流式输出）—— 最便宜、最直观的体验提升

其余的都是细节打磨或**不该学的东西**。Operit 有 180 个工具、知识图谱、39 家厂商、插件生态——那些是**通用 Agent 的答案，不是你们的**。
