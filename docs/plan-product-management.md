## 0. 一句话结论

那套 POS 真正值得抄的**不是它的功能**，而是**它把同一件事复用到了三处**：

| 它的复用 | 具体表现（截图编号） |
|---|---|
| ① **一份名册 = 三种用法** | 「管理分组」= 「排序」= 「新建子分组」弹窗（图 3 / 4 / 5），同一个列表的三种状态 |
| ② **商品外观只有一个** | 在售列表（图 1）、选择商品（图 12）、排序列表（图 2）里的商品行是**同一个** |
| ③ **选择商品只有一个** | 批量操作（图 10/11）→ 选择商品（图 12）→ 加料/属性里还是它 |

**而我们的数据层与规则层早就做到了同样的复用**——`商品/运费/开销/地点` 四个分类名册共用
一套 ViewModel（`ui/common/CategoryRosterViewModel.kt`，221 行）与一套后端判据
（`backend/app/services/category_order.py`）。**缺的正是界面层**：名册页 4 份、商品外观 3 份。

所以这份方案里 **P1/P2 是"把我们已经写对的东西收口到界面"**（0 后端改动），
**P3/P4/P5/P7 是"抄它的排版与交互"**（P7 = 新增/编辑商品页，你这一轮点名要的那个"太乱"的屏），
**P6 是我们自己的真缺口**（商品顺序现在由 `id desc` 决定，用户管不了 —— 只有它要动数据库）。

## 3. 方案（P1–P7）

### P1 · 名册页收成**一个**组件（最值钱的一条）

**抄什么**：图 3/4/5 是同一个列表的三种状态（管理 / 排序 / 新建子分组）。
**落点**：新文件 `ui/common/CategoryRosterScreen.kt`。

```kotlin
// 现有基类已经是泛型的（ui/common/CategoryRosterViewModel.kt），页面直接跟着泛型走
@Composable
fun <T : Any> CategoryRosterScreen(
    vm: CategoryRosterViewModel<T>,
    spec: RosterSpec<T>,
    onBack: () -> Unit,
)

data class RosterSpec<T>(
    val title: String,                       // 「商品分类」/「运费分类」/「开销分类」
    val accent: Color,                       // 模块语义色（一色一功能）
    val hint: String,                        // 那一段"这一列是什么"的说明
    val rowSubtitle: (T) -> String,          // 「30 个商品」/「价目 3 条 · 规则 2 份」
    val renameNotice: (String) -> String,    // 是否级联、级联到哪
    val deleteMessage: (T) -> String,        // 「还有 N 个挂着，删不掉」的那句话
    val sortMode: SortMode = SortMode.DRAG,  // DRAG（商品/运费/开销）/ ARROWS（上下移）
    val embedded: Boolean = false,           // 面板形态（地点那种"抽屉里的第二层"）
)
```

**收益（可量化）**：4 个页面 ≈1116 行 → 1 个组件 ≈350 行 + 4 个壳（每个 ≈30 行）。
**更重要的收益**：那三条已经走散过的规则（只提交名册里的行 / 撤销不能丢新建的 / dirty 判据）
从此**物理上只有一处**。第 2 行的"丢行"故障不可能再出现。

**分批**：第一轮**先收 3 页**（商品 / 运费 / 开销），**地点那页保持独立** ——
它是"抽屉里的第二层面板"且用户为它推翻过一次独立路由，模式稳定之后再评估（不要一次追求到位）。

**验收**：新增 `_tools/qa/_check_roster_single_source.py`：断言「保存顺序」「撤销」这两个字面量、
`moveItemTo` 的调用、以及那段 dirty 提示条**只许出现在组件文件里**；配反向验证（把某一页改回本地实现 → 必须红）。

### P2 · 商品外观收成一套**零件**（⚠️ 第三批起：**也抽了行主体**，见 §10）

> ⚠️ **2026-09-21 第三批改口径**：这一节原来写的是"**刻意不造**整张卡、只抽三段零件"。
> 用户看完第一轮之后明确要求「**全部做深**…其他地方你也得改，最好是采用（通）用的继承，
> **上次你改一个地方，它就其他跟着改了**」→ 所以**又抽了一层** `ProductLine`（行/卡主体，槽位式）
> 与 `productFacts()`（事实构造器）。下面这段保留原文，是因为"为什么当时不敢抽"这个判断**并没有错**
> —— 它换来的做法是：**槽位 + 一个 `dense` 开关**，而不是"传 12 个参数的万能卡"。
> 结论以 **§10** 为准。

**抄什么**：图 1/2/12 里商品行是同一个。
**落点**：新文件 `ui/common/ProductCardKit.kt`。

⛔ **先说不做什么**：三处卡片的差异是**真实的**——
管理态是"两行事实 + 右侧一列（⋮/改价）"；选择态是"价格行 + 已选 N + 右侧 ＋"；
库存态是"库存行 + 下面一整行两个按钮"。
把它们硬塞进一张 `ProductCard(12 个参数)`，就是"参数比内容还多"的失败模式
（也正是用户说的「以插件的形式，能调方法调方法」的反面）。
所以**抽三段零件，不抽整张卡**：

```kotlin
// ① 缩略图：有图用图、没图用名称色块 + 图标（现在这一套三段各写了一遍）
@Composable fun ProductThumb(imageUrl: String?, nameColor: String?, size: Dp)

// ② 事实行：**数据驱动**，一个一行（设计规范 §4.1 的既定规矩，原样搬进来）
data class ProductFact(val icon: ImageVector, val label: String, val value: String, val color: Color)
@Composable fun ProductFacts(facts: List<ProductFact>)

// ③ 外壳：圆角 / 描边 / padding；尾部动作与底部动作都是**插槽**（不是参数）
@Composable fun ProductCardShell(
    trailing: (@Composable () -> Unit)? = null,
    footer: (@Composable () -> Unit)? = null,
    content: @Composable ColumnScope.() -> Unit,
)

// ④ 库存配色判据（现在在 ProductsScreen 里，是"这个数字要不要你处理"的信号）
fun stockColorOf(stock: Int, lowStockAlert: Int): Color
```

三页各自组装：管理页 `ProductFacts(售价+库存)` + `trailing = 那一列(⋮/改价)`；
选品页 `ProductFacts(价格)` + `trailing = ＋按钮`；库存页 `ProductFacts(库存/在途)` + `footer = 出入库两个按钮`。

⛔ **顺手加字段是这一条最容易犯的错**：设计规范 §4.1 是用户拍过板的
（**卡片上只有两个数字、一个一行、成本不在卡上、分类不在卡上**）。
抽组件时把它们从"注释里的约定"变成"零件的签字约束"，**不许因为好写就加**。

**唯一一个值得加的东西**（可选、可砍）：卡片上商品名后面那个小标签位（现在是「已下架」），
可以按优先级放 **`已下架` → `有 N 家批发商专属价`**。
第二个是我们自己的信息、而且可动作：**没设专属价的批发商下单时按默认售价走**，
派单员扫列表就能看出"这个商品有 3 家拿到专属价、2 家没有"。
⚠️ 它要**只对派单员下发**（挂在 `backend/app/api/v1/products.py::product_out` 那个已有的裁剪点上，
与 `cost_price` 同一处），且**只加一个计数字段**。
**两个被否掉的候选**：「未分类」——与 §4.1「分类不上卡」冲突；「缺货」——库存那个数字已经变红了，
同一件事说两遍（§4.1 也警告过重复表达）。

**验收**：`_check_product_card_single_source.py`：① 商品图的渲染（`AsyncImage`+`resolveStaticUrl`+色块兜底）、
② 售价文案的拼法、③ 库存配色判据，**三样都只许出现在 Kit 里**；三页都必须 import 它。
配注入反向验证（把某一页改回本地写法 → 必须红）。
外观验收：三页改前/改后**截图对比**（逐页人工确认"一个字都没变"）。

### P3 · 选品组件加一个「多选模式」

**抄什么**：图 12 的 `本组全选 / ☐全选 / 已选 N 个 / 确定`。
**落点**：`ui/common/ProductPicker.kt`（**现有文件，加参数**，不是新页面）。

```kotlin
enum class PickerMode { ADD_QTY, MULTI_SELECT }

fun ProductPickerBody(..., mode: PickerMode = PickerMode.ADD_QTY)
```

- `ADD_QTY`（**现状，一个字不改**）：下单用（`OrderCreateScreen.kt:430`）、账本「记一笔账」用（`LedgerCreateScreen.kt:585`，`single=true`）。
- `MULTI_SELECT`（新）：行尾是复选框而不是 ＋；顶部「本组全选」；底部 `☐全选 / 已选 N 个 / [确定]`；
  顶上带搜索（图 12 右上角那个「筛选」，我们换成已有的分类栏 + 搜索框，不新增概念）。

**⛔ 硬约束：不许出现第二份选品页。** 红线 §30 已经钉着"分类判据只有一份"，
这里同理 —— 批量选择、下单选择、账本选择**必须**是同一个组件。
`single` 参数已经在把这一页往多形态推，加 `mode` 是顺着它走，不是另起一页。

### P4 · 批量操作（底部三格 + 批量页 + 逐条执行）

**抄什么**：图 1 的底部三格、图 10/11 的批量操作列表（含"选择多个操作"的复选态）。
**落点**：`ProductsBottomBar` 改三格；新 `Routes.PRODUCTS_BATCH`、
`ui/dispatcher/ProductBatchScreen.kt` + `ProductBatchViewModel.kt`。

**(a) 底部三格 —— 用户 2026-09-21 拍板：「底部栅格组排直接照抄，他怎么搞我们就怎么搞」**

```
┌────────────────┬──────────────────┬────────────────┐
│      ▤         │      ( ⊕ )       │       ☰        │
│   分类管理      │    商品新增       │    批量操作     │
└────────────────┴──────────────────┴────────────────┘
   图标+文字           56dp 圆钮+文字         图标+文字
   无边框格子           语义色实底           无边框格子
```

**照抄的是形态，不只是位置**：左右两格是**无边框的"图标 + 文字"格子**（不是现在的
`OutlinedButton` 描边按钮），中间是**语义色圆钮**（`FilledIconButton` + 白 `+`）+ 下方一行文字。
理由（都是图 1 里能直接看到的）：描边按钮在三格里会变成三个并排的框，而"图标 + 文字"的格子
天然分得清主次、也把中间的圆钮衬出来。

⚠️ **两条已定的规矩会被这一条取代，落地时必须一起改文档**（否则下一个人照着旧规矩把它改回去）：
1. 设计规范 §4.3 写的「一个页面有两个并列入口 → 底部一条栏（**一实一虚**）」→ 补一句
   **"三个动作时用三格、主操作居中（圆钮）"**（两格时仍是一实一虚）。
2. §5「添加类表单用抽屉」→ 见 P7。

⚠️ 当年删掉右下角悬浮球的理由是"**它压着列表最后一张卡**"（列表尾部还因此留过 `Spacer(72.dp)`）。
**坐在栏里的圆钮不压任何东西** —— `Scaffold` 会把栏高扣掉，这正是 §4.3 记着的那条判据，
所以那个理由在这里不成立（`bottomBar` 里也不许再出现悬浮球）。

**(b) 批量操作列表 —— 只放我们真有的动作**

| 动作 | 走哪个接口 | 说明 |
|---|---|---|
| 批量改分类 | `PATCH /products/{id}` `{category}` | 后端在改商品时会**自动补进分类名册**，所以不会造出"名册外的分类" |
| 批量上架 / 下架 | `PATCH /products/{id}` `{is_active}` | 不动库存、不动钱 |
| 批量删除 | `DELETE /products/{id}` | **软删**。⛔ 必须和 (d) 一起做 |
| 批量改单位 | `PATCH /products/{id}` `{unit}` | 要等 **P5 的单位选择页**做出来（否则批量页里没有"选哪个单位"的地方） |
| 批量调价 | 已有 `BatchPriceSheets.kt` | **指过去，不重做** |
| ⛔ 批量改库存 | —— | **绝不做**：库存只能走出入库流水（`inventory_service` 的 `UPDATE ... WHERE stock + delta >= 0`）。批量改数字 = 账实不符且**整套流水对不上**，这是核心区 |

**(c) 执行通道 = 逐条调已有端点**（**不新增后端端点**）

- 不需要新端点 ⇒ **不碰核心区、不用改 `_write_coverage.py` 的覆盖表**，而且每条改动都由后端
  各自写一行 `operation_logs`（与人工逐条操作同形，可回查 —— 这正是用户对"调价必须留痕"的要求）。
- 界面必须：**先看到清单 → 确认一次 → 进度 + 逐条结果 + 可中止**。
  汇报格式照抄 AI 那边的经验（`AiWriteHandler.commitNote` 的由来）：
  **"成功 18 / 失败 2"**，并把失败的那两条**点名 + 原因**，绝不用一句"已完成"盖住。
- 代价（如实说）：逐条 = N 次请求。用户上一轮已经表过态（「如果用户说全部都做的话…可以搞几分钟」
  「如果他说就做这 50 个，那可能其实很快了」）⇒ **不做条数上限**，用进度条 + 可中止来消化。
- ⚠️ **不共用 AI 的确认卡**：AI 那张卡带一次性 token 与 5 分钟有效期，是聊天页的机制；
  页面里的确认就是页面里的确认。两边**共用同一批接口**（`repo.updateProduct/deleteProduct`），
  **不共用**确认机制 —— 这条要写进注释，否则下一个人会问"为什么两套确认"。

**(d) 「回收站」+ 恢复入口 —— 这一条是补**现有缺口**，不是新功能**

`GET /products` 恒过滤 `is_deleted=false`（`products.py:91`），而 `POST /products/{id}/restore`
**在 App 里一个入口都没有**（只有 AI 的撤回卡）。这**违反了用户 2026-09-20 定的硬规矩**。
批量删除会把这个缺口放大 200 倍（一次点掉 200 个商品、界面上再也找不回来）。

→ 顶栏那一段状态分段做成**三段**：`在售 / 已下架 / 回收站`（对应图 1 的两段，我们多一段）。
回收站里每行一个「恢复」。后端只需给 `GET /products` **加一个查询参数** `deleted_only`（不是新端点）。

## 4. 明确不抄（截图里有、我们不做）· 附理由

| 它的功能 | 我们为什么不做 |
|---|---|
| 套餐 / 加料 / 属性 / 多规格(SKU) | 我们的一个商品 = **一个单位 + 一个价 + 一个库存**。多规格会让"订单行单位""成本快照""库存流水"三处同时变复杂 —— 上一轮刚删掉的「批发价档位」就是同一个教训：**看着像价、下单时谁都不照它走** |
| 会员价 / 积分 / 划线价 | 我们的"第二个价"是**批发商专属价**（`price_rules`，按 批发商×商品 存，**真的会生效**）。多加一个"会员价"就又多一个"看着像价、其实不生效"的字段 |
| 门店成本价 + 仓库成本价（两个） | 我们只有一个成本价 + **生效区间历史**（`ProductCostHistory`，用户点名要的"从什么时候到什么时候"），毛利口径已经收口在 `cost_basis.py` |
| 库存扣减方式（扣商品/扣原材料/不维护库存） | 我们的库存只有一条线：**订单联动**（派单预占→送达实扣→撤销释放）+ **到仓自动入库**那条独立线（`warehouse.py`，用户原话「再开一条计算线」）。再多一个开关就是改账 |
| 沽清 / 取消沽清（作为独立状态） | 我们不需要第三个状态：**库存归零就是"卖完了"**，卡片上那个数字已经变红（§4.1）。多一个状态就多一个"为什么这件商品既不显示缺货又不可售"的追问 |
| 后厨打印机 / 档口 / 打印标签 / 销售时段 | 餐饮门店作业，我们发货靠**送货单与司机任务** |
| 供应商 / 产地 / 采购单位 | 进货只记**数量 + 进货价**（`inventory_movements`），供应商不入库。⚠️ "采购单位 × 换算率"是唯一一个真有可能有用的（进货按箱、销售按件）——但它**会动库存与成本两处核心**，要做必须单独立项，不夹在这里 |
| 条码生成(13/7位) / 扫码 | 我们没有扫码枪、也没有线下收银台 |
| 称重单位 | 同上：重量对我们的意义是"整车/整件"，不是电子秤读数 |
| 金融分组 | 我们的"钱归哪一类"由**账本分类**（`ExpenseCategory` 名册）表达，已经在账本/开销那边了 |
| 小程序启停售 / 收银机启停售 | 我们只有一个客户端：**上架/下架**（`is_active`）就是对全部渠道说的 |
| 二级子分组（图 5 的新建子分组） | 我们的分类是"这批货归哪一块"，做成树会让**下单页左栏**变成可展开的树（现在是一列 96dp 的平铺）。96 个商品 4 个分类不需要树；**真要做是另一轮**（新列 `parent_id` + 左栏树形 + 选品页跟着改） |
| 卡片上那两个显式按钮（沽清 / 编辑） | 设计规范 §4.2 是用户拍过板的：**三个以上收进 ⋮**；只有单个主操作才用显式按钮。我们的卡上动作有 5 个（各批发商价格/上下架/成本价历史/编辑/删除）+ 改价 |
