## §1 施工纪律（怎么保证「说改好了」不是自说自话）

1. **一个事项一个编号**：走查的每条发现都落成 `BUG-xxxx` 或 `CHG-xxxx`，并写立项文档 `docs/changes/<ID>.md`（我要解决什么问题 / 现状是什么 / 什么变了 / **什么明确不能变** / 属于 Core-Extension-Infrastructure 哪一层 / 什么证据算完成）。
2. **两条腿的证据**：**判据** `_tools/qa/_check_<topic>.py`（机器可跑，逐条打 `[OK]` / `[FAIL]`）＋ **反向验证** `_tools/qa/_reverse_verify_<topic>.py`（把源码逐处改坏，判据**必须**报红；跑完逐字节还原并核对文件指纹）。
3. **提交纪律**：实现一笔、归档一笔；归档只动三份文档（`docs/AI_WORK_CLAIM.md` / `docs/changes/README.md` / `docs/changes/<ID>.md`）。⛔ 暂存逐条列路径，不用 `git add -A`；⛔ 永不提交工作区里脏的 `backend/app/services/reports/loader.py`，也不提交 `_tmp/` 与 `exports/`。
4. **用户口径的禁做清单**：**不得放宽测试断言、不得删用例、不得只改测试数据绕过问题**；走查已核实「不是 bug」的行为保持原样（§4）。
5. **真机**：三台模拟器 `emulator-5554` 派单员 13800000001 陈国强 / `emulator-5556` 货主 13800000002 永盛食品 / `emulator-5558` 司机 13800002345 王强（口令 `123456`）；全程 adb 真人手法（tap / input / swipe / input text），截图与连拍存 `_tmp/`。

## §3 机制性发现：Hint 说明系统

走查 §六：新装默认**关闭**说明，首次登录那一轮显示、下一次冷启动自动关掉（`core/HintRound.kt:33-61`），开关在「我的 → 提示」且是否定式「不显示说明」；后果是**解释句根本不渲染**（这就是 P25 的成因）。

本轮的处理：

- **机制本身不动** —— 改默认值会改变「新装首次登录之后」的用户可见行为，属于产品口径，不是缺陷；CHG-0026 的 Must Not Change 里写死「提示开关机制与『首次登录那一轮开、之后默认关』的行为（`core/HintPrefs.kt` 一行未动）」。
- **被点名的那一句按个案处理** —— P25 那句口径说明改成**常显**（源码里留了注释：口径句**常显**，⛔ 不许改成 `Hint`），并给判据加了「不许退回 Hint」的反向注入。
- 留一条规矩：**关键解释句不许只活在 Hint 里**（`docs/HINT_STYLE.md` 与 `_check_hints.py` 仍在日常静检里跑）。

## §5 判定不修 / 另立事项（写明理由）

### 5.1 P6 历史脏数据与「??????」那张地点卡 —— **不修**

- **是什么**：走查在地址页看到一张名字与地址都渲染成 `??????` 的地点卡。报告当时的判词：「这是**测试环境数据卫生**问题，不算产品缺陷；但说明**异常字符没有兜底显示**，建议加降级文案」。
- **查了什么**：探针 `_tmp/_probe_pl.py`（只读 sqlite）扫了 `contact_categories` / `place_categories` / `place_user_usage` / `places` / `shipper_addresses` / `shipper_contacts` / `shipper_locations` 七张表，只有 `shipper_locations` 命中一行：`(94, '??????', '')` —— 库里存的**就是六个问号本身**，联系人字段是空串。别的表 0 行。
- **为什么判「不修」**：① 数据是坏的（写入端把编码丢成了 `?`），不是显示端丢字；② 客户端无法区分「数据坏了」与「名字本来就这样」，加「疑似乱码就降级」的启发式会把真实姓名也一起兜掉，属于用显示层补丁掩盖写入端缺陷；③ 走查报告自己就已经把它定性为数据卫生问题。
- **真正该做的（建议，本轮不执行）**：在**写入端**加编码校验（拒绝/转义不可显示的替换字符），并清掉 `shipper_locations` 里那条 `id = 94` 的测试数据 —— 删数据是不可逆动作，请用户在确认后执行。

### 5.2 消息提醒默认值按角色不一致（走查 `:178`）—— **另立事项**

- **现象**：货主端默认「仅前台接收」，派单员 / 司机端默认「语音 3 次 · 后台接收」。
- **为什么不本轮改**：这不是「哪一行写错了」，而是**哪个默认值是对的**需要拍板 —— 货主只在用 App 时需要提醒、司机离屏也要听见，两种设定都可能是有意为之；改动会落到三端的通知偏好默认值与设置页，属于产品口径。本轮不擅自替用户决定「统一成哪一个」。
- **下一步**：用户在「统一为语音 3 次 · 后台接收」与「按角色保留（但在设置页写清为什么）」之间拍一句，即可立 CHG 收口。

### 5.3 `GET /api/v1/unit-conversions` 返回 403 的后台噪声（走查 §八 ①）—— **只记录不修**

- 走查当时记录：13:14:08 / 13:15:59 / 13:32:23 / 13:33:27 四次 403，而**手动打开单位换算页一切正常**（正常空态），疑似工作台的后台预取。
- 为什么不修：这是**日志噪声**，没有可复现的用户可见后果；要定位得先抓到发起者（抓包或临时日志），属于排查任务而不是修复任务。留在未覆盖清单里（§6）。

- **根因与修法**（权威版见 `docs/changes/BUG-0007.md`）：同一个账期有**两套取数口径** —— 建单时现算一遍、确认时又按单号重算一遍，中间明细有增删就漂移。修法：取数收成 `settleable_bills` 一处；建单当刻把明细 id 锁进 `driver_settlements.bill_ids`；确认与付款都按锁定集合认账，少了就明确报错；恒等式 `amount == 明细合计 + adjustment`。证据：判据 40/40 ＋ 反验 17/17 ＋ 全量 pytest 1235 passed/0 failed ＋ 模拟器真机（生成 → 确认 → 付款）。
- **教训（写给下一个人）**：「走查报告里查不到证据」**不等于「没有问题」** —— 当时只检索了报告原文里的两个数字，没有去核账目本身。**用户手上的页面事实优先于报告里的检索结果**；下次遇到类似的「对不上」，第一步应当是去核那条不变式（这个仓库里就是那些长期红的用例），而不是先判不采纳。
