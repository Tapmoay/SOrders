## 0. 结论先行

1. **CLI 还是 MCP？两个都不用。** 它们是"给外部客户端/开发者"的接口形态；你要的是手机 App 内置功能。安卓上跑不了 CLI 子进程，MCP 也不是给 App 用的。
2. **运行时用安卓原生 Kotlin**（你已拍板）。DSH 有 linux-arm64 产物，但构建目标里**没有 android**，产物**动态链 glibc**，安卓是 bionic + W^X——见 §2。
3. **⚠️ 但"要不要做 agent"这件事，v1 的答案是错的。** 独立审查用一条底层推翻了 v1 的方案主体，我核对后**认同**（§16-D）：
   > 派单员的动作只有三类——**读**（筛/查/汇总）、**状态迁移**（派单/撤回/撤销/运费）、**录入**（记账/地址）。**AI 的唯一增量是"自然语言 → 参数"的翻译**，它不产生任何新业务能力。
   > 那么：**翻译收益 × 频次 − 运行时成本 − 误操作风险**。
   > 而**状态迁移和录入本来就是零成本的结构化表单**（待派池点选 + 按钮，已有确认弹窗、状态前置校验、`operation_logs` 留痕）——翻译收益 ≈ 0，风险却最高。
4. **所以只剩两件事值得做，而且是同一件**：
   - **第 1 步（1~2 周，纯后端，不写 App）**：用**真实派单员的 30 个问题**去测——**这些问题里有几个是现有搜索/页面真的答不了的？** 判据写死在 §3.3（跨模块且需 ≥3 步的占比 ≥25% 才继续）。
   - **如果继续**：答案很可能是**扩 `GET /orders` 的查询参数** 或 **一个聚合端点**，而**不是**一个 agent。§4.1 的决定性发现是：连"老王家是谁"这种实体解析，`?q=` 都早就做了。
5. **我在这一轮里推翻了自己两次**：v2 初稿推荐的"表单预填"（第 2 步）被 §4.1 推翻；v2 一度写下的"'老王家'需要新建客户名索引"也被 §4.1 推翻。**两处都保留在文档里**（§4.3、§5），因为判断对错只取决于一个 5 分钟能读代码验证的事实——这正是这份文档该有的样子。
6. **key 只存手机、后端不接触**（你定的）——但这条有个**副作用必须先解决**：§8 的"没有人能查用户的调用与费用"。
7. **v1 里我标为"最大隐藏工作量"的三件事，实际只有一件成立**（审查推翻，我已核实）：记账**已有**推送链路、AI 审计动作**零迁移**；唯一真缺口是**地址/联系人无推送**。见 §7.3。

## 1. 范围与底层逻辑

### 1.1 本轮范围

| 项 | 决定 |
|---|---|
| 角色 | **仅派单员（DISPATCHER）** |
| key | 用户自带（BYOK），**只存手机**（本轮验证不走手机，见 §3.1） |
| 运行时 | **本轮：无代码。** 若验证通过且真要给用户用，才做安卓原生 Kotlin |
| 不做 | 货主端、司机端、本地模型推理、离线执行写操作 |

### 1.2 底层逻辑（这是全案的判据，比任何技术选型都重要）

```
派单员的动作 = 读 + 状态迁移 + 录入
                    │
    ┌───────────────┴───────────────┐
    │                               │
 已经零成本（结构化表单）        尚未零成本
 状态迁移：待派池点选+派单按钮    跨模块只读聚合
 录入：记账/地址表单              （"上月挂账超5000且未结"）
 单页筛选：状态分段导航           ↑ 正解 = 后端一个聚合查询
    │                              不是让 LLM 串 3 个工具再口算
    └──────── 收益 ≈ 0 ────────────┘
                    │
        AI 的增量只有"自然语言→参数"翻译
                    │
   价值 = 翻译收益 × 频次 − 运行时成本 − 误操作风险
```

**两条推论：**
- **推论 A**：在"已经是零成本表单"的动作上加 AI，**净收益为负**（更慢、更贵、还可能错）。
- **推论 B**：唯一正收益区是**跨模块只读聚合**，而它的**正解是后端一个聚合 SQL**，不是 agent 串工具。**LLM 做数字汇总不可靠、更慢更贵。**

**所以本方案不做"万能 agent"，先做"能验证的实验"。**

### 2.2 R1 的真正障碍（收敛为四条，全部与 Landlock 无关）

| # | 障碍 | 性质 |
|---|---|---|
| 1 | **无 Node 运行时**：DSH 要 Node ^22.19 或 ≥24，安卓无官方 Node | 平台事实 |
| 2 | **bionic ≠ glibc**：产物动态链 glibc 2.28+，安卓无 glibc | 平台事实 |
| 3 | **W^X 强制（API 29+）**：禁止从 App 私有目录执行 ELF；本项目 `minSdk=26`/`targetSdk=35`（`android/app/build.gradle.kts:25-26`） | 平台事实 [待验证一手来源，见 §14 V1] |
| 4 | **上架合规**：要跑通需 Termux 或 proot Linux 用户态（数百 MB、后台不稳），**基本不可能走应用商店** | 工程事实 |

### 2.3 R2：Termux / proot Linux（**已有一手来源，路线基本被官方立场堵死**）

| 事实 | 来源（研究 agent 实测取证） |
|---|---|
| 安卓 C 库是 **bionic**（非 glibc 非 musl）；shell 是 **mksh**、命令由 **toybox** 提供，**无 bash、无完整 coreutils** | [aosp-mirror/platform_bionic](https://github.com/aosp-mirror/platform_bionic)、[shell_and_utilities/README.md](https://github.com/aosp-mirror/platform_system_core/blob/master/shell_and_utilities/README.md) |
| **targetSdk ≥ 29 禁止对 `filesDir`/`cacheDir` 内的文件直接 `execve`**（官方要求二进制随 APK 分发） | [Android 10 行为变更（官方）](https://developer.android.google.cn/about/versions/10/behavior-changes-10) |
| **Termux 官方立场：包可以用，但"不能使用我们的包仓库，须自行编译并自建托管"**；跨 App 唯一官方接口是 `RUN_COMMAND` intent（需权限+用户授权+`allow-external-apps`） | [Termux FAQ](https://wiki.termux.dev/wiki/FAQ)、[RUN_COMMAND Intent](https://github.com/termux/termux-app/wiki/RUN_COMMAND-Intent) |
| **Termux 自身 targetSdk 锁在 28** 以绕开 Android 10 的 execve 限制，代价是放弃 Google Play 更新 → **它不是可打包的库** | 同上 FAQ |
| 维护者对"打包内置"的答复："unsupported case；**Termux executables are not portable**"，须自定 prefix、全量拷依赖、targetSdk ≤ 28 | [termux-packages Discussion #27652](https://github.com/termux/termux-packages/discussions/27652)（官方仓库，权威二手） |
| proot = 用户态 chroot，依赖 **ptrace**；无需 root，但"伪造 root ≠ 提权" | [proot-me.github.io](https://proot-me.github.io/)、[Termux Wiki: PRoot](https://wiki.termux.com/wiki/PRoot) |
| **确实有自包含分发先例**：UserLAnd（README 自述 runs full distributions、No root required、上架 F-Droid/Play） | [CypherpunkArmory/UserLAnd](https://github.com/CypherpunkArmory/UserLAnd) |

**结论**：Termux **不能被合法内置**（官方明确不支持）；proot 路线可行（UserLAnd 是活证据）但代价是**数百 MB 的 Linux 用户态 + ptrace 性能损耗 + 后台存活不稳 + 上架合规风险**——而换来的 bash/文件系统能力，**派单员一样都用不到**（§2.4）。

### 2.4 R3：原生 Kotlin（**选定**）

| 判据 | R1 | R2 | **R3** |
|---|---|---|---|
| 可上架 | 否 | 否 | **能** |
| 包体增量 | 数十~数百 MB | 数百 MB | **< 1 MB** |
| 安卓兼容风险 | 高 | 中高 | **低** |
| 复用现有 repo/API/token | 要自己接 | 要自己接 | **直接复用** |
| 生态（第三方 skill/插件） | 强 | 强 | 弱（见 §10） |

**R3 的代价（必须说清）**：没有现成的安卓 agent SDK；模型调用循环、工具 schema、流式解析都要自己写；且**模型选型被限制在"支持 OpenAI 兼容 function calling"的厂商**。

## 3. 本轮唯一要动手的事：用真人问题验证价值前提（**产出不是代码**）

### 3.1 它是什么

```
派单员在电脑/手机浏览器打开一个内部页面（或你在微信里转发问题给我们）
        │  自然语言问题
        ▼
POST /api/v1/ai/query        ← 新增，**唯一新端点**
   ├─ 服务端持 key（第 1 步用你自己的 key，不涉及用户 key）
   ├─ LLM：自然语言 → 白名单查询 DSL（**不生成 SQL**）
   ├─ 执行：只读查询，**只走 4 个聚合端点**（§3.2）
   ├─ 返回：结构化结果 + **生成该结果的筛选条件摘要**（可核验）
   └─ 写 operation_logs(action="AI_QUERY")  ← 零迁移，见 §7.2
        │
        ▼
输出：结果 + "我是这样查的：状态=已送达，日期=2026-08-01~08-31，按货主聚合"
```

**为什么这一步不做 App**：App 界面、聊天页、KeyVault、Room 四张表加起来是**几周工作量**，而它验证的东西（模型能不能把中文口语翻译成正确参数）**用一个脚本 + 真人问题就能验证**——我已经用 `_ai_p0_probe.py` 做到了（§3.5）。先花 1~2 周买一个"要不要继续"的决定，而不是花 6 周买一个可能错的方向。

### 3.2 允许碰的数据（只读，4 个聚合端点）

| # | 端点 | 位置 | 授权真相 | 为什么选它 |
|---|---|---|---|---|
| 1 | `GET /api/v1/orders` | `orders.py:163` | 仅登录 + 体内含角色判断（需读源码） | 订单筛选/计数（**注意它自带 `?q=` 跨 7 字段模糊匹配**，见 §4.1） |
| 2 | `GET /api/v1/ledger/accounts?kind=shipper\|member` | `ledger.py:86` | 仅登录 + 体内仅允许派单员 | 货主/批发商账（跨模块聚合的正主） |
| 3 | `GET /api/v1/reports/turnover` | `reports.py:211` | 权限:ORDER_DISPATCH | 营业/毛利（**必须带覆盖率说明**） |
| 4 | `GET /api/v1/stats/driver-performance` | `stats.py:73` | 权限:STATS_READ | 司机表现/待结运费 |

> **这一步刻意不做**：任何写操作、任何多轮对话、任何手机端代码、任何"AI 自己解析实体"（`?q=` 已覆盖，§4.1）。

### 3.3 成功/失败判据（**先写死，跑完不许改口径**）

| 指标 | 通过线 | 不过怎么办 |
|---|---|---|
| 端点/参数选择正确率 | ≥ 90%（27/30） | 换模型或换 prompt，最多试 3 轮 |
| **筛选条件语义一致率** | ≥ 95%，且**每一条不一致都要能解释** | 换模型；或把该问题类型改为"扩查询参数"来做 |
| **静默降级检出率**（最重要） | 模型对"它答不了的条件"必须**显式说出"我没包含 X"**，而不是安静地返回一个漏条件的查询 | 检出率低 → 该问题类型**不做 NL 入口**，改扩 `GET /orders` 参数 |
| **「现有搜索/页面真的答不了」的问题占比** | **≥ 25%**（"答不了"= `?q=` + 状态 + 日期 + 现有页面点 ≤2 步 都覆盖不到） | **< 25% → 停，不做 AI，只扩查询参数** |
| 派单员真的在用它 | 30 个问题里 ≥10 个是他**主动**问的 | 需求不真 |

> ⚠️ **v2 初稿这一行写的是"数字与手算一致率 = 100%"，第二轮审查指出它是空指标**：既然聚合已在后端算，就不存在独立的"手算"参照，它恒等于 100%，等于没测。**已改为上面两条**——用"筛选条件语义是否一致"和"答不了时会不会明说"来测，这两条才测得到真东西。

> ⚠️ 第三条判据在 v2 定稿时被**收紧**了：因为 §4.1 发现 `?q=` 已覆盖实体解析，"能不能翻译成人名"不再是难题——**难题只剩"现有查询表达不了的聚合与多约束组合"**。判据必须按这个来，否则会被"翻译人名成功"的假阳性骗过去。

### 3.4 30 个问题从哪来（这是实验的命门）

**不能由我编**——我编的问题会自带"适合 AI 解决"的偏差。做法：
1. 找 2~3 个真实派单员，说一句话："**接下来两周，你平时要翻几个页面才能查到的东西，直接发微信问我**"；
2. 原样记录 30 条（不许我改写措辞）；
3. 标注每条：现有页面点击步数、能否用 `?q=` + 状态 + 日期直接答。

### 3.5 ⚠️ 已经跑过一次：**11 题 10 通过，但这个数字证明不了任何事**

我把实验工具写出来了（`_ai_p0_probe.py`，只读、可重跑），用本地库真实数据 + DeepSeek 跑了 11 道**我自己写的**模板题：

| 结果 | 数值 |
|---|---|
| 通过 | **10 / 11**（91%） |
| 失败 1 题的原因 | **我的判分器写错了**（"昨天派出去的 3 单"我期望 `status=DISPATCHED`，模型给的是昨天的 `date_from/date_to`——**模型是对的**，已修正判分） |
| 模型表现好的地方 | 时间词（"这个月/上个月"）→ 日期区间 100% 正确；`kind=shipper` vs `member` 分得清；会主动挑专用工具（`pending_dispatch_count`）而不是拿 `list_orders` 硬凑 |
| 模型表现差的地方 | **看不出来**——见下 |

**必须说清这个数字的局限（否则它会误导决策）**：

1. **题目是我写的，而我知道有哪些工具** → 这 11 题天然只包含"6 个工具能答"的问题。**它不是价值验证，是自证。**
2. **判分只校验"工具 + 少数参数"，不校验答对没有。** 例如 Q11（"已派单但司机三天没接的有几单"）模型给的是 `{status: DISPATCHED}`——**这答不出问题**（缺"未接单"和"超 3 天"两个条件），但按我的判分器它 PASS 了。
3. 所以 **91% 的真实含义是："模型会把中文问题正确映射到这 6 个工具的粗粒度参数上"**，而不是"派单员的问题能被回答"。

**这次跑出来的真正有用信息**：Q11/Q12 这类"**带缺失条件的多约束问题**"会**静默降级**——模型不会说"我做不到"，它会返回一个**看起来对但漏了条件**的查询。对一个要拿去做决策的派单员，这比明确报错更危险。（这属于 §13 风险 R3 的实例。）

> 📌 **结论：判据仍以"真人真问题"为准（§3.4）**。这次只证明了工具链能跑通、以及"多约束缺失条件"是**已验证的失败模式**。

**这次还踩到一个必须记下来的坑（它本身就是一个论据）**：写 `_ai_p0_probe.py` 时，我的 `ledger_accounts` 工具用了 `SUM(ledgers.amount)` —— **`ledgers` 表根本没有 `amount` 列**（实际是 `total`），且真实实现用 `entry_date` 过滤而写成了 `created_at`。**它不报错，只是安静地算错。**
> 所以：**任何"本地重实现一遍工具"的做法都会漂**（这正是审查质疑"客户端做工具层"的深层理由）。本工具只用于**测模型选什么**，**绝不能**用来验证后端行为；工具语义必须 1:1 对照真实端点（本文件已在 `TOOLS[i]["endpoint"]` 里标注映射，并已按 `ledger.py:86-136` 修正）。

## 4. 实体解析（唯一必须现在就想清的技术风险）

派单员说的是"老王家""娃哈哈水""李四那 3 单"。**AI 必须落到真实 ID，不能猜。**

### 4.1 `?q=` 已经解决了**一部分**实体解析（但**不是全部**，v2 初稿在这里又过了一次头）

`GET /api/v1/orders` 的 `q` 参数**已经是一个能用的模糊匹配器**（`backend/app/api/v1/orders.py:193-203`）：

```python
# 派单员带 q 时，一次 LIKE 同时匹配 7 个字段：
or_(
    Order.order_no.like(term),            # 单号
    shipper_u.full_name.like(term),       # 货主姓名     ← "老王家"
    shipper_u.phone.like(term),           # 货主电话
    Order.temp_shipper_name.like(term),   # 临时货主名   ← 无账号客户
    Order.address_detail.like(term),      # 收货地址     ← "老王家" 也能从地址命中
    driver_u.full_name.like(term),        # 司机姓名
    driver_u.phone.like(term),            # 司机电话
)
# 且可与 status / date_from / date_to / shipper_id 组合（:206-225）
```

**所以"AI 需要自己解析人名"这个前提基本不成立**——派单员现在输入 `老王` 就能跨"姓名+临时名+地址"一次命中。

**但第二轮审查实测出三个缺口（我认同，这三点决定了还不能把 `?q=` 当成"实体解析已完成"）：**

| # | 缺口 | 实测证据 | 影响 |
|---|---|---|---|
| 1 | `q` 是**订单搜索**，不是实体搜索 | 66 个 SHIPPER 里**只有 36 个有订单** → **30 个（45%）永远搜不到** | 新客户/沉睡客户无法用它定位 |
| 2 | **`contact_boss_phone` 不在那 7 个字段里** | 147 单有该字段，其中 **16 单的老板电话 ≠ 货主账号电话** → 按老板电话搜是 **0 命中**（另 131 单因两号相同侥幸命中） | "按电话找单"会静默漏 |
| 3 | `q` **不返回实体 id**，只返回订单 | — | §4.4 要的"复述姓名+脱敏电话"、以及表单预填要的"带经纬度的地址对象"都拿不到 |

**缺口 2 的修法是两行代码**（把 `Order.contact_boss_phone`、`Order.contact_dongjia_phone` 加进 `or_()`）——**这是本案里"投入产出比最高的一处改动，且与 AI 无关**。

> 结论修正：`?q=` = **订单搜索可用，实体解析只覆盖 55% 的货主、且漏电话维度**。所以正确的表述不是"实体解析已经完成"，而是"**大部分场景已经有现成实现，剩下的缺口里有两条是两行 SQL 能补的**"。

### 4.2 这把 AI 的剩余价值压缩到**两个真空白**

| # | 真空白（`q` + 现有页面做不到的） | 例子 | 正解是什么 |
|---|---|---|---|
| 1 | **跨模块聚合 + 算术** | "上月哪些货主挂账超 5000 且还没结清"（要 join 账本×挂账×逾期天数） | **后端一个聚合端点**（不是 LLM 串工具口算） |
| 2 | **多约束组合筛选**（`q` 只支持单关键字 + 单状态 + 时间 + 单货主） | "已派单但司机 3 天没接单的、运费还没定价的、货主是批发商的" | 要么扩 `GET /orders` 的查询参数，要么一个聚合端点 |

**除此之外，AI 的全部增量 = "把自然语言翻译成 `q`/status/日期参数"——而这三个参数派单员在现有界面上点两下就有。**

### 4.3 ⚠️ 但"聚合下沉到后端"**没有消除风险，只是换了位置**（第二轮审查提出，我认同）

朴素的想法是："让后端算数、模型只出参数，就不会算错了。" **这个想法是错的。**

- 真实失败模式（§3.5 实测）是**带缺失条件时静默降级**：用户问"已派单但 3 天没接的有几单"，模型给 `{status: DISPATCHED}`——**条件漏了一半，但它不说**。
- 聚合下沉之后，这个错误的表现变成：**后端用正确的 SQL 算了一个错误范围的数**。而且因为它出自后端，**看起来更权威**（"系统算的，不会错"）。
- 所以下沉改变的是**错误的可信度**，不是错误的概率。**它让错误更危险。**

**必须同时做两件事才敢上**：
1. **否定式回显**：结果里必须写明"我**没有**包含哪些条件"（例："未包含：司机未接单、超 3 天"）；
2. **口径同显**：命中行数 + 时间范围 + 状态集合一起给，让人能一眼判断范围对不对。

**以及一个更根本的判断**（审查提出，我认同）：这个端点**与"一个带自然语言解析的报表筛选器"没有本质区别**。既然如此，**更该做的是那个筛选器本身（扩参数/加聚合端点），而不是给它套一层聊天**。

### 4.3 那三处实测证据（保留，说明为什么"新建索引"不是答案）

**客户实体为什么没有单一主源——但这已经不重要了（三处实测证据，保留备查）：**

| 证据 | 实测结果 | 含义 |
|---|---|---|
| `customers` 表 | 本库**只有 2 行**（`(1,'registered',user_id=2,'Shipper')`、`(2,'tmp',None,...)`），写入点**只有一个**：`api/v1/customers.py:40 create_customer`（`Customer(...)` 建在 `:59`） | 审查建议"主源改 `customers`"——方向对（v1 用 `shipper_contacts` 确实错），**但落不了地**：AI 查它等于查一个空表 |
| `shipper_contacts` | 列 = `id, shipper_id, phone, display_name, created_at, updated_at`（**无 `name`**）；本库 owner 分布：46 行属货主、1 行属派单员（id=1 'ZhangM'） | 它是**货主自己的电话簿**，不是客户库 |
| `orders` | 174 单里 **`shipper_id` 只有 10 单为空**；10 单有 `temp_shipper_name`；**147 单有 `contact_boss_phone`** | **订单表才是客户信息的实际载体**（`shipper_id`→`users`；`temp_shipper_name`→无账号客户） |

> ⚠️ 我一度据此写道"'老王家'需要新建客户名索引，这是本项目从未有过的能力"——**这个结论在我读到 `q` 的实现后就作废了**（§4.1）。把它留在文档里，是为了记录"**读 schema 得出的结论，会被读实现推翻**"这个教训。

### 4.4 三条仍然适用的规则（若将来做实体解析）

1. **先查后确认**：先搜候选，再让人确认。
2. **命中多个 → 让人选**，不许模型自己挑；**不提供"就第一个吧"的默认项**。
3. **零命中 → 明说"查不到"**，404 原样回传，**禁止 AI 层"猜测性重试"**。

### 4.5 一条反直觉的推论：**让 AI 复述"我理解成了谁"，比让它闭嘴更安全**

派单员多是老年/低视力用户，"认知捷径"（automation bias）的真实风险是：**AI 把 A 客户的地址填给了 B 单，用户扫一眼就点了提交。**

对策不是"少显示信息"（那会让错误更隐蔽），而是**强制复述关键实体**：姓名 + 脱敏电话后 4 位 + 最近下单时间 → **三个冗余线索**，用户只要一个对不上就能立刻发现。

> 新增于 v2（v1 与第一轮审查都没提）：它的价值恰恰在于**对抗"表单填好了所以直接提交"**。

## 5. 第 2 步：表单预填 —— **v2 起草时我推荐它，随后被自己的发现推翻**

v2 初稿把它列为"第一个该给用户看的功能"，理由是"AI 只填表、不写库，绕开全部写操作风险"。**这个理由仍然成立，但它的前提被 §4.1 推翻了：**

| 假设 | 检验结果 |
|---|---|
| AI 能解析"老王家" | ❌ **不需要 AI**：`GET /orders?q=老王` 已经跨 7 个字段模糊匹配（`orders.py:193-203`） |
| 派单员录入慢、需要 AI 加速 | ❓ **未验证**：下单/记账本来就是结构化表单；"点选 + 填两个数字"是否真的慢，没有证据 |
| AI 填表能省时间 | ❌ **存疑**：用户仍要逐字段复核（§4.5 的 automation bias 对策要求他把姓名+电话+时间都看一遍）——**省的是打字，付的是复核**，对"两三个字段的表单"可能净亏 |

**结论：第 2 步暂时不做。** 它从"第一个该做的功能"降级为"**如果第 1 步的数据显示录入确实是瓶颈，再回来做**"。

> 这一段保留在文档里，因为它是本案最重要的自我修正：**同一个"表单预填"，在"AI 需要自己解析实体"的前提下是好设计，在"实体解析早就有现成实现"的前提下就是多余的一层。** 判断对错完全取决于一个可以 5 分钟读代码验证的事实。

### 5.1 如果将来真要回来做它，第二轮审查实测出 4 个坑（**先记下来，省得重踩**）

| # | 坑 | 证据 | 后果 |
|---|---|---|---|
| 1 | **坐标会丢**（最硬） | `OrderCreateViewModel.kt:29-30/171-172` 提交 `addressLat/addressLng`；人工路径必走 `applyPicked(:122)` / `applyAddress(AddressDto)`（带坐标） | AI 只填文本 → `address_lat/lng` 为 NULL（`models/order.py:33-34` 可空）→ **司机导航没有目标点，而表单不报错**。修法：预填只接受**带 id 的对象** |
| 2 | **一眼看不出的是"货主选错"，不是"地址填错"** | `OrderCreateViewModel.kt:160` 决定账本归属 | 地址错司机当场发现；**货主错要到对账才炸**。复述线索必须含**货主名 + 账户类型**并单独高亮 |
| 3 | **automation bias 是真的，且现有表单没有第二道闸** | `OrderCreateScreen.kt:110` 只有一颗 `PrimaryActionButton("提交订单 ¥…")`，**提交路径无确认弹窗**（`:368/:417` 是选图/选货主） | 预填后**一次点击即落库**——"AI 从不写"技术上成立，但"确认"被压缩成一次点击。修法：AI 填的字段标"未核对"并在逐项确认前禁用提交 |
| 4 | **价格档位** | `LineDraft.price` 是自由文本（`:18`）；批发商专属价在 `price_rules` | 填错档位**不报错，只是少收钱**（静默损失） |

## 6. 再往后的路（**都不是本轮计划，是"如果验证通过才长出来"的东西**）

**只有同时满足三条，才考虑给用户看聊天入口**：
1. 30 条真人问题里，"现有搜索/页面答不了"的占比 ≥25%（§3.3）；
2. 这些"答不了"的问题里，**大多数是聚合/多约束**（→ 那应该做**聚合端点**，仍然不需要聊天）；
3. 只有"**用户需要反复、自由地问不同组合**"时才需要自然语言入口。

**如果真走到那一步**，写入类仍然建议按下面这个顺序，而不是一上来做"AI 直接写"：

| 顺序 | 做法 | 为什么是这个顺序 |
|---|---|---|
| 1 | **扩 `GET /orders` 的查询参数**（支持"未接单超 N 天""运费未定价"这类缺失条件） | 一次改动，**零 AI 成本、零幻觉**，覆盖 §4.2 的多约束类问题 |
| 2 | **加一个聚合端点**（挂账×逾期×货主） | 同上，且数字由 SQL 算，**不会有算错风险** |
| 3 | 表单纯预填（AI 填、人点提交） | 若数据显示"录入"确实是瓶颈 |
| 4 | 才轮到"聊天式入口 + 写入自动化"（要确认卡/幂等/审计） | 前三条都覆盖不了时才做 |

## 7. 安全与机制（v2 已按审查意见大幅收窄）

### 7.1 幂等：**必须放服务端，客户端做不了**（v1 错误）

- 审查核实：后端全库**没有任何** idempotency/request_id 机制；**客户端本地方案也保证不了**——用户在另一台设备/另一个入口重试就绕过了。
- **正确做法**：写端点支持 `Idempotency-Key` 头，服务端按 `(operator_id, key)` 唯一索引去重。
- **对第 1/2 步无影响**（第 1 步只读、第 2 步走现有端点）；**第 3 步开始前必须先做**。
- ⚠️ v1 的验收标准"断网重试 3 次只产生 1 条记录"**在 v1 的设计下不可达**——已删。

### 7.2 审计：**服务端就够，且零迁移**（v1 高估）

| v1 的说法 | 事实（已核实） |
|---|---|
| "`operation_logs` 只有订单类动作" | ❌ `action` 是 **`String(64)`，没有 DB 级枚举**（`models/operation_log.py:20`）；`enums.py:54-59` **早就有** `LEDGER_CREATE/UPDATE/DELETE`、`PRODUCT_CREATE`、`PRICE_RULE_UPSERT`、`USER_CREATE` 等非订单动作 |
| "加动作值要改 `schema_bootstrap.py` 迁移（历史事故高发区）" | ❌ `schema_bootstrap.py` 里**根本没有 `operation_logs`** |
| "审计是最大隐藏工作量之一" | ❌ `write_log(action: OperationAction \| str)` 接受任意字符串（`services/operation_log_service.py:15,24`）→ **加 `AI_QUERY` / `AI_PREFILL` 零迁移** |
| 查询侧 | `GET /api/v1/operation-logs`（08A:179-180，权限 `OPERATION_LOG_READ`，派单员在 `rbac.py:68` 已有）→ **现成的审计查看入口** |

**v2 做法**：`write_log(action="AI_QUERY")`，并在 `change_payload` 里带 `{"source": "ai", "channel": "ai-query"}`。
**审查还指出一个 v1 完全没想到的点**：AI 通道在服务端**不可辨识**（同 token、同端点、同 operator）——`operation_logs` 分不清"人点的"和"AI 提议后点的"。**加 action 前缀 + payload 标记**才能让审计目标成立。

### 7.3 界面回执：v1 高估，真缺口只剩一个（已核实）

| v1 的说法 | 事实 |
|---|---|
| "手动记账没有任何推送" | ❌ **部分不成立**：`create_entry`（`ledger.py:185`）在 `:223` 有 `background_tasks.add_task(_bg_push_ledger_shipper, row.shipper_id)`；`push_events.py:58 push_ledger_updated` 存在；`message_center.py:385-387` 发 `{"type":"ledger.updated"}`；**Android 侧已经全链路接好了**（`core/RealtimeHub.kt:111` → `_refreshLedger`；`ui/dispatcher/DispatcherLedgerViewModel.kt:125` 已订阅） |
| 真缺口 | ✅ **事件发给 `shipper_id` 且仅当 `row.shipper_id is not None` 时触发** → **派单员自己记账时收不到** |
| "地址/联系人无推送" | ✅ 成立（`shipper.py` 内无任何 push 调用） |

**v2 做法**：① 记账推送补一个"也发给操作者自己"（复用 `emit_to_user`，`services/message_push.py:10`）；② 地址/联系人同理。**不需要新增 `client-refresh` 端点**——v1 提的那个端点**是绕一层**；Android 侧 `RealtimeHub.kt:125 notifyOrdersChanged()` 就是"本地操作后刷新列表"的现成范式。

### 7.4 权限模型：**两个比 v1 更严重的发现**（审查提出，我已核实）

| 发现 | 证据 | 对 AI 的含义 |
|---|---|---|
| **派单员对任何订单都无 scope 限制** | `_get_order_scoped`（`orders.py:318` 前）只对 SHIPPER/DRIVER 按 `current.id` 过滤，**派单员无任何过滤** | ⚠️ **v1 的验收标准"篡改参数访问他人订单→403"在当前权限模型下不可能通过**——因为派单员本来就能访问全部订单。**已改为**："验证货主/司机 token 不可越权" |
| **`cancel_order` 全局无 scope** | `orders.py:891-898`：派单员分支是 `pass`（无归属校验），只看状态 `:900` + 权限 `:907`（`rbac.py:112` 必过） | AI 工具**不提供 cancel**（高危且无边界），撤销走人工 |

> 08A:215 的授权列其实**已经写明**"体内权限:ORDER_CANCEL_SHIPPER + 体内权限:ORDER_CANCEL_DISPATCHER + 体内含角色判断（需读源码）"。**v1 写成"入口列说明不了准入范围"是不准确的**——准确说法是"**看得清，而且比想象的更危险**"。

### 7.5 提示词注入与字段白名单

- **数据一律当数据**：订单 `remark`/`internal_notes` 里可以写"忽略之前的指令…"，模型必须当文本处理。硬边界是**工具白名单**，不是 prompt。
- **禁止进 prompt**：商品成本价（`ProductOut` 含 `cost_price`，`schemas/product.py:71`——审查核实，有实据）、其他货主司机完整数据、完整手机号（脱敏后 4 位）、任何系统信息。
- **做法**：工具返回给模型的数据走 `toModelView(entity)` 投影，不是原样透传 API 响应。

### 7.6 日志（v1 风险描述偏高，已修正）

- 事实：`ApiClient.kt:36-38` 的 logging 级别是 `if (BuildConfig.DEBUG_LOG) BODY else NONE`。
- 含义：**release 构建不打印 body**，v1 说的"依赖里在就必须关"过头了。
- 仍要做：AI 请求单独走一个**不挂 logging 拦截器**的 OkHttp 实例（防 debug 构建泄露 key）。

### 7.7 key 存储的技术选型（**研究 agent 取证：v1 的默认答案已过期**）

| 事实 | 来源 |
|---|---|
| **Jetpack Security Crypto 全部 API 自 1.1.0-alpha07（2025-04-09）起弃用**，官方建议"改用平台 API、**直接使用 Android Keystore**" | [security 发布说明（官方）](https://developer.android.google.cn/jetpack/androidx/releases/security) |
| Keystore 官方文档 | [Android Keystore（官方）](https://developer.android.google.cn/privacy-and-security/keystore) |
| 官方 Android 侧 LLM SDK = **Firebase AI Logic**（`com.google.firebase:firebase-ai`，支持 `functionDeclarations`）；旧的 `com.google.ai.client.generativeai` 已弃用 | [Firebase AI Logic 上手](https://firebase.google.cn/docs/ai-logic/get-started)、[function calling](https://firebase.google.cn/docs/ai-logic/function-calling)、[迁移指南](https://firebase.google.cn/docs/ai-logic/migrate-from-google-ai-client-sdks) |
| SSE 用 `com.squareup.okhttp3:okhttp-sse`，但该项目 README **自述 experimental、"API is not considered stable"** | [okhttp-sse README](https://raw.githubusercontent.com/square/okhttp/master/okhttp-sse/README.md) |

**结论**：key 用**平台 Keystore API**（不是 EncryptedSharedPreferences）；流式解析要么接受 okhttp-sse 的 experimental 状态，要么自己按行解析 SSE。
