# R4 Canary 观察窗口（**预注册**）

> ⛔ 这份文档是在**观察之前**写的。它只有一个作用：让「看多少算够、什么算通过」
>   在**看到数据之前**定下来。
>
> ⛔ 数字的**唯一来源**是 `_tools/ops/_canary_status.py` 文件头那几个常量，
>   本文只写**口径与理由**，⛔ 不抄数字 —— 抄了就会有两份真相，其中一份迟早过期。

## 为什么必须预注册（用户 §8 的原话）

> 「我建议第一轮不要直接拿"全生产订单数量"当观察窗口，而是做一个**明确的最小观察窗口**……」
> 「达到预先定义的最小样本量 → 检查」

道理和判据一样：**事后挑阈值 = 没有阈值**。
「Canary 很稳定」这句话在事后是永远说得出来的 —— 只要把「多少算稳定」往后挪一点。

## 观察对象

**发布之后新产生的**运费决策：`orders.freight_rule_snapshot` 里 `pricing.kind` 有值的单，
且快照的 `pricing.at` ≥ 发布日（跑的时候给 `--since <发布日>`）。

⛔ **不给 `--since` 跑出来的数字是历史累计**（工具自己会写明这一点），那种数字不许当窗口结论。

## 分类（⭐ R4-36 起**优先读 `pricing.resolution`**，老快照才按 kind+reason 推断）

| 类 | 怎么认 | 含义 |
| --- | --- | --- |
| **contract** | `resolution = contract` | 契约真的算出来了 |
| **fell_back** | `resolution = fallback` | 被 canary 抽中了，但契约算不出来，**如实退回** |
| **not_in_bucket** | `resolution = not_in_canary` | 这一单没被抽中（或者这次调用根本没有金额） |
| **frozen** | `resolution = frozen` | 这一单**已经定过来源**，这一次是沿用（⛔ 不进分子也不进分母） |
| **stale** | `reason` 缺失 | R4-22 之前的旧式快照（⛔ 只许来自那次之前） |
| **inferred** | 没有 `resolution` 这一格 | ⛔ 不是桶：它标记"这些笔只能推断，而**推断分不出 frozen**" |
| ⛔ **unknown** | 取值**认不出**（大小写漂移 / 新增取值 / 空串） | ⛔ **不是任何一类**：落它的笔记**不**进样本量 |

⭐ 能这么分类，靠的是 R4-22 那条**原因码** + R4-36 拆出来的 `resolution`。
没有后者，「冻结沿用旧路」与「没抽中」写出来一模一样，冻结就永远验不了。

⛔ **`unknown` 不许并进任何一个已知桶**（R4-45）：并进去等于把"认不出"冒充成
"R4-36 之前的老快照、没被抽中"。形状矩阵实测过：`CONTRACT` / `Contract` / `unknown`
以前**全部**走到那一支 —— 而 `inferred` 这个标签的原意是"这些笔**没有**这一格"。

| 9 | ⛔ **没有认不出的取值**（形状换了就得当场看见） | 新增（R4-45） |

## ⭐ 窗口契约冲突的**裁决**（R4-46，2026-09-27）

### 一、冲突是什么

2026-09-27 **先有预注册**（本文件 + `_tools/ops/_canary_status.py` 文件头的常量），
随后在**对话里**又出现了一份门槛清单。两份的"样本量"那一条**数不一样**：

| 来源 | 写了什么 | 什么时候写的 |
| --- | --- | --- |
| **预注册**（本文件 + 常量） | 桶内 ≥ `WINDOW_MIN_IN_BUCKET` **且** 总数 ≥ `WINDOW_MIN_TOTAL` | **开窗之前** |
| 对话里的清单 | 「桶内 ≥ 20 / Total ≥ 20 / Contract ≥ 10」 | 开窗之后（复盘时凭记忆重述） |

⛔ 上表右边那一列里的数字是**被裁决的对象**，**不是本文主张的阈值** ——
本文主张的阈值只有一处来源（脚本常量），别处写的一律不作数。

### 二、⚠️ 先说清楚：这两条**不是矛盾**，是**严格度不同**

预注册那一条是 `总数 ≥ WINDOW_MIN_TOTAL`，它**蕴含**「总数 ≥ 20」。
⇒ 按预注册判过，就**自动**满足对话里那一条。

**所以真正的问题只有一个**：预注册那条**可以单独先红**，而对话里那条还绿。
这是一个「**要不要保留这条更严的门槛**」的问题，⛔ 不是「两句话打架」。

### 三、还有一层必须当场钉死：**"总数"到底指哪一堆**

窗口里其实有**三个**不同的量：

| 量 | 算式 | 它回答什么 |
| --- | --- | --- |
| **桶内** | contract + fell_back | 真的被 canary 抽中的有多少笔 |
| **总数**（本窗口采用） | 桶内 + not_in_canary | **参与过抽签**的有多少笔 |
| 字面"全部快照" | 上面 + frozen | 窗口里有多少份快照 |

⛔ 本窗口的"总数" = **中间那一个**（**不含 `frozen`**）。理由：`frozen` 那一次
**压根没有重新抽签**（它沿用已经定过的来源）—— 把它算进总数只会让门槛**变松**，
却**不会多出一笔 canary 证据**。这个定义写在常量的注释里，本裁决把它升级成**绑定口径**。

### 四、裁决

1. **以预注册的常量为准**：`WINDOW_MIN_IN_BUCKET` 与 `WINDOW_MIN_TOTAL` **一个都不改**。
   ⛔ 尤其不许把总数从注册值改成更小的数。
2. **"总数"按上表中间那一个算**（不含 `frozen`）。
3. **对话里那份清单不覆盖预注册** —— 它写在开窗**之后**，是对既有约定的一次**重述**；
   ⛔ 后写的重述不 override 先注册的契约。
4. **数字的唯一来源仍然只有一处**：`_tools/ops/_canary_status.py` 文件头。
   ⛔ 本文、台账、聊天记录里出现的任何数字**都不作数**。
5. 工具现在会**当场算出**"两条里真正卡着的是哪一条"。
   ⛔ 算法用的是**目标比例**（桶是 `order_id % 100 < p` 的均匀抽签，p 从 `.env` 读），
   **不是**拿当前窗口那几笔去估 —— 理由见下面的第六节之二。

### 五、为什么这么判（三条理由，都**不依赖**"现在数据长什么样"）

1. **预注册的全部意义就在于它先于数据**。看着数据把它改松，正是它要防的那件事 ——
   ⛔ 哪怕改完"看不出影响"也不行：**"能不能事后改"这件事本身就是被禁的。**
2. **它几乎没有代价，而且这个结论可以从代码推出来、不必等数据。**
   桶由 `order_id % 100 < p` 抽签，所以**参与抽签的决策**里
   「没被抽中 : 桶内」= `(100-p) : p` —— 只要 p 明显低于一半，
   桶内补到门槛那一刻，参与抽签的总数就已经远超总数门槛。
   **既然保留的成本接近零，就没有任何理由去付"事后改门槛"这个价。**

   ⚠️ **这一条我第一版写错过，如实记下来**：第一版拿**窗口里的观测比值**去外推
   （当时参与抽签的只有 3 笔，观测比值 0.50，而理论值是 2.33），于是算出
   "总数会不够"。**那是错的** —— n=3 上出现这个偏离是 ~19% 概率的正常波动，
   它推不出任何结论。工具因此改成**用代码定下来的比例**，并把观测值降级成**旁证**、
   样本不够时当场写「样本太少：既不足以推翻、也不足以支持」。
   ⇒ 这条错误的形状与本文件其他地方反复出现的是同一个：**把"没有结论"读成了"有结论"。**
3. **保留它同时满足对话里那一条**（更严蕴含更松）—— 所以保留**不违反任何一份文字**。

### 六、⛔ 反方意见也记下来（免得只有一边的声音）

支持改成更松那一条的理由是：**较严的那个数是实现方自己写的，不是需求方写的**。
预注册由实现方起草，需求方当时的清单里写的是更松的值。**这条理由成立，不是狡辩。**

所以裁决**留一扇有记录的门**（见下），但**默认状态不变**。

### 七、如果窗口结束时**只有总数那一条不过**，怎么办

⛔ **不许悄悄改常量**。走一次**记录在案的偏离决定**，四格必须写全：

| 格 | 写什么 |
| --- | --- |
| **事实** | 哪几条过、哪一条不过、那一项的实际数字 |
| **为什么它单独不过** | 是流量比例的问题，还是真的样本不足 |
| **影响面** | 少掉的这一段样本，会让**哪一条结论**说不清 |
| **谁批的 / 什么时候** | 需求方本人；⛔ 实现方**不许自己批** |

⛔ 在那之前：**窗口不算通过**，⛔ 不进 Shadow、⛔ 不碰 ⑧-b。

### 八、生效范围

本裁决**只对本次窗口有效**。下一次窗口（或比例再次调整后重开的窗口）
**必须重新预注册** —— ⛔ 不许直接沿用这一份：一个**已经看过数据**的裁决，
不能当成下一轮的"事先约定"。

### `pricing.resolution` 的「新缺口」怎么判（R4-45）

老快照缺这一格是**合法的**（R4-36 之前根本没有这一格）。判据不看写死的时间戳，而是
**让数据自己说话**：缺的那一批必须**全都早于**有值的那一批。

| 情形 | 判 |
| --- | --- |
| 一笔都不缺 | 过 |
| 有缺、有值、缺口全在值之前 | 过（那是 R4-36 的**存量**） |
| 有缺、**一笔值都没有** | ⛔ 不过（分不清是存量还是新漏） |
| 缺口出现在有值的**之后** | ⛔ 不过（说明有一条写入路径没带这一格） |

⛔ 为什么不比一个"代码批次上线时刻"：那等于给「发布是什么时候」立**第二个真相**，
发布一挪就得两边改。而且这一条**不会变成永远红**：切换干净过一次，它就永久绿。

## ⚠️ 一条必须知道的口径偏差（R4-26 撞出来的，不是 bug）

`price-freight`（**派单前**手动定价）会**提前把这一单的来源冻在 legacy** ——
那一刻**还没有司机**，契约看到的候选集是**全部价目**，多半算不出来。

⇒ **实际走契约的比例会低于配置的比例。**
看窗口时⛔ 不要拿「配了 30% 就该有 30% 走契约」当判据；
要按下面这个口径读：`contract / (contract + fell_back)` 才是"桶内真的走通了"的比例。

## 窗口通过之后：**Observation Review**（同样预注册，R4-45）

⛔ 九条判据全过 **≠** 可以 Cutover。用户 §十一 的原话：

> 「当窗口到 20+ / 10+ Contract 的时候，**不要立刻说"可以 Cutover"**…… 先做一次 Observation Review」
> 「因为：**机器门槛通过 ≠ 业务已经确认正确。**」

所以窗口满了之后、进 ⑧-b 之前，必须先做一次**逐条人工复核**。

### 摆什么（每一条 Contract 样本都要能摆出这几列）

    Order ／ Driver ／ Rule ／ Template ／ Route ／ Calculation Context
    契约算出来的费用 ／ 最终落库的费用 ／ Override ／ Contract 版本 ／ Provenance

### 找什么（六种异常 —— 全部**人判**，⛔ 机器不判）

| 要找的 | 长什么样 |
| --- | --- |
| 同一业务条件 → 不同结果 | 同一（司机规则、价目、路线）的两笔，费用不一样 |
| 相同模板 → 不同费用 | 同一个 `template_id`，算出来的数不同 |
| 同一路线 → 异常差异 | 路线相同而金额差得离谱（例如差一个数量级） |
| override 异常 | 改价幅度不合理 / 该 agree 的却 override / 反过来 |
| snapshot 缺字段 | 九条判据只保证「那几格**在**」，**语义对不对**要人看 |
| Contract identity 漂移 | 同一批样本里出现两个契约身份 |

### ⛔ 边界（与下面那条 Golden Case 边界是**同一条**）

机器在这一步只负责**把事实摆出来**（哪几列、值各是什么、哪几笔互相矛盾）。
「45 元业务上该不该是这么多」**只能由人判** —— ⛔ 不许让 Pricing 扩展给自己的输出盖章，
也**不许**把这条人工复核合并进那九条判据（合并了它就会退化成"跑绿就算数"）。

⚠️ **状态如实记着**：判据**已在这里预注册**，**抽样工具还没建** ——
窗口里现在只有 1 笔 Contract 样本，拿 1 条数据去建一个要在 10 条上用的工具，
只会得到一个"看起来能用"的东西。⛔ 这一条**不算完成**，窗口满时再建并在这里补用法。

## ⛔ 边界（在观察窗口期间**不许悄悄改掉**）

这三条是用户 2026-09-27 明确要求钉住的。要改，先改这一段文字 —— ⛔ 不许只在代码里改。

### ① Golden Case 证明的是**稳定性**，不是**业务正确性**

`_tools/qa/_golden/freight_pricing.json` 的期望值来自**扩展自己**，所以它只回答一件事：

    同样的输入 + 新代码 ⇒ 历史行为没有被偷偷改掉

它**不**回答「45 元业务上合不合理」。后者是**业务正确性验证**，只能由真实业务规则 /
人工业务判断 / 独立证据来证明。⛔ **不许让 Pricing 扩展给自己的输出盖章。**

（机器侧同一条边界：本窗口的 Correctness 维度**机器不判**，工具只回答「两个值在不在」。）

### ② 「撤回订单」≠「抹掉已经形成的定价事实」

`recall_dispatch`（撤回派单）会清掉状态 / 司机 / 人工改价，但**保留** `freight_fee` 与
`freight_rule_snapshot`。所以：

    窗口里看到「订单当前状态 = 待派」  ⇒ ⛔ 不许因此把它的 Pricing Decision 当成不存在

它**仍然是**本窗口的样本。这与 R4 的既有原则一致：**操作状态变化 ≠ 历史事实被删除。**

### ③ 本阶段**不动**的两样：Canary 比例与 App

- **比例保持不动**：现在的变量是"真实流量够不够"，⛔ 不是"比例高不高"。
  调比例会把「流量量不足」与「Canary 比例变化」两个变量搅在一起，
  而且会**同时**破坏本窗口的预注册前提（见本文件开头）。
- **不为了"证架构"去动 App**：生产 App 实际调用的那个 backend 入口
  （`POST /orders/{id}/assign`）**已经直接走过了**。App 侧再跑一次的价值是
  **UI / 产品交互验证**，而不是 R4 Pricing Architecture Proof ——
  那件事单独做，⛔ 不要在观察窗口期间多引入一个变量。

## ⛔ 施工禁区（**窗口达标之前**，用户 2026-09-27 定）

在「桶内 ≥ `WINDOW_MIN_IN_BUCKET` 且 Contract ≥ `WINDOW_MIN_CONTRACT`」达成之前，
下面这些**一律不做**：

| ❌ 不做 | 为什么 |
| --- | --- |
| 调 Canary 比例 | 会同时破坏预注册前提，并把「流量不足」与「比例变化」两个变量搅在一起 |
| 新增 / 修改生产价目 | 那是**改被测对象**：窗口里前后的样本就不再是同一套配置产生的 |
| 造单 ／ 补样本 ／ 手动补决策 | ⛔ **观察窗口只能由真实业务流量产生**；人造样本直接毁掉它的证据意义 |
| 强行触发 Contract | 那证明的是"我能让它跑"，不是"它在真实流量里跑得稳" |
| 进 Shadow ／ Release Rehearsal ／ ⑧-b | 窗口还没通过，后面每一步都没有依据 |
| 为了"看起来进度快"动观察门槛 | R4-46 已裁决：**预注册阈值不许事后改松** |

✅ **允许**：只读观察 ／ 修**明确发现的**证明缺陷 ／ 修测试基础设施的确定性问题 ／ 记录真实生产样本。

⭐ 为什么这条要写进**文档**而不是留在对话里（与 R4-46 是同一条道理：**对话里的约定不是制品**）：
违反这条禁区的后果**不可逆** —— 造出来的样本删不掉，窗口的证据意义一旦被污染就再也回不来。
