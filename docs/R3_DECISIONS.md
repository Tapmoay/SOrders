## 决策 1：上传资产是不是本机文件系统资产？（R3-03-A）

### 结论

**是。** 上传的图片与导出产物都是**本机文件系统资产**；多实例的模型是「**同机多进程 / 同一个挂载点**」，
不是对象存储。跨机器的共享盘与对象存储**留到第四轮**（指南 §二十七 也把对象存储排在那里）。

### 证据（都是当场查的，不是设想）

| 事实 | 出处 |
| --- | --- |
| 后端是 **systemd 服务**，`ExecStart` 是 `uvicorn … --workers 2` —— 两个 worker **在同一台机器、同一个磁盘**上 | 生产 `sorders-api.service` |
| MySQL 与 Redis 都跑在**同一台宿主机**上（不是外部托管） | 生产实测（R2 记录） |
| 上传目录是**相对路径**（改动前 7 个文件里散着 13 处 `Path("uploads")`），systemd 的 `WorkingDirectory=/opt/SOrders/backend` 决定它落在哪 | `backend/app/**` |
| 对象存储**一行代码都没接**（没有 oss2/boto3/minio 依赖，`_check_r3_constraints.py` 的 `no_premature_round4` 探针盯着这一条） | `backend/requirements.txt` |
| 导出产物已经被刻意挪出公开的 `uploads/`，走带鉴权的下载端点 | `services/ledger_export_paths.py` |

### 决策带来的三件事（都已落地）

1. **上传根目录变成一个配置项** `UPLOADS_DIR`（`backend/app/config.py` 的 `uploads_dir`，唯一入口 `uploads_root()`）；
   改动前是 7 个文件里 13 处字面量 —— 那种形状**没法保证**两个实例指向同一个目录。
2. **多实例的硬前提写进就绪度文档**：两个实例的 `UPLOADS_DIR` 必须指向同一个目录；
   同机多进程天然满足，跨机器要靠共享挂载点。
3. 判据 `_check_multi_instance_readiness.py` 核「业务代码里不再有写死的 `Path("uploads")`」。

### 什么时候重新审这个决策

- 要**跨机器**部署时（那时必须给一个共享挂载点，或者把对象存储提前）；
- 单机磁盘成为瓶颈时（图片按 3 年保留、1 年后压成 WebP，容量是可算的）；
- 用户改口径说「图片不再是我们自己的资产」时。

## 决策 2：多实例的**共享密钥**必须显式配置（R3-03 实验 1 顺带证出来的）

`JWT_SECRET_KEY` 留空时，每个进程会**各自生成一个本次进程专用的随机密钥**（见 `core/security`）。
单实例无所谓；**两个实例就变成「A 发的 token 到 B 上不合法」** —— 用户会看到「一会儿掉线一会儿不掉」。
所以多实例部署时 `JWT_SECRET_KEY` 必须配置，且两个实例用同一个值。

这不是新发现（第二轮就记过「.env 里是默认串」），但**是这次双实例实验第一次把它证成运行时事实**：
实验 1 里 A 登录拿到的 token 在 B 上读 `/users/me` 返回 200 —— 前提就是两个进程用了同一个 `JWT_SECRET_KEY`。
