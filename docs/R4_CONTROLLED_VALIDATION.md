## 〇、裁决要点（需求方 2026-09-27）

- 原 Observation Window「**不适合当前 Pre-Launch 阶段的 Gate**」；理由不是业务量少，
  而是「**当前还没有正式生产业务，所以不应该要求『自然业务统计样本』作为上线前的必要条件**」。
- 它不是没用，而是**换位置**：「从『上线前 Gate』移动成『上线后的运营验证 Gate』」。
- 阶段重命名：`架构整改 ✅` → `生产接线 ✅` → **`R4 Pre-Launch Controlled Validation`（当前）**
  → `R4 Post-Launch Natural Observation`（上线后）。
- **⛔ 不要再做架构整改** —— 「目前没有新的架构整改理由」。
- 受控验证的判据：`Scenario Coverage + Expected Result + Positive/Negative Control + Evidence`，
  ⛔ **不是 `Count >= 20`**。
- 所有测试数据必须有**明确的测试身份**（`Test Tenant / Test Shipments / Test Driver Accounts` 或 `test_run_id`）。

## 一、诊断（需求方版本，照录）

> 「原窗口问的是一个『不受我们控制的输入下会不会垮』的问题。」

这就是 **Natural Production Observation**，它只能在
「上线 → 真实用户出现 → 真实业务流量产生」之后做。把它当成上线前的绝对阻断条件，
就得到：

```
要上线 → 必须先有真实用户数据 → 但只有上线后才有真实用户数据 → 永远无法上线
```

⭐ **这才是当前逻辑真正的问题**：不是门槛高，是**这个 Gate 被放在了错误的生命周期阶段**。

## 二、⚠️ 事实更正：09-20/09-21 那 40 笔**不能**当作「真实试用流量」

本文件上一版（草稿）写过一句，**现在撤回**：

> ⛔ **撤回**：「09-20/09-21 两天 40 笔订单、30 个不同货主 —— 这不是『没人用』，是真实的试用流量。」

**撤回的理由**（比原稿给的理由更准）：`30 个不同 shipper_id` 只能证明
**存在 30 个不同的数据主体**，⛔ 不能单独证明它们是**外部真实用户产生的业务流量**；
而且那条推理**只查了 09-20 起的两天**，把中间那两天当成了「开始」—— 那是**查询窗口造成的假边**。

### 实测到的完整形状（这才是能站住的事实）

| 项 | 实测值 |
| --- | --- |
| 全库订单 | **2409 笔**，`2026-05-24` → `2026-09-27` |
| 日量级 | `05-24` 起**连续四个月约 20 笔/日**（09-18:18 ／ 09-19:17 ／ 09-20:17 ／ 09-21:23） |
| **断点** | `09-22` 起 **1 / 0 / 0 / 0**，之后只有演练单 |
| 账号 | 全库 **60 个用户**；其中 **55 个非模拟器号码** 的 `created_at` **全部是 `2026-09-21` 同一天** |
| 模拟器号段 | 只有 **5 个** `138000000%` |
| 09-20/09-21 的货主 | 25 个账号，**真实格式手机号**（如 `13744176324`），其中 2 个 `is_member=1` |

⇒ **两条都在，而且互相矛盾**：订单连续四个月、每天约 20 笔；
但**所有非模拟器账号都是同一天建的**。⇒ 这批数据**要么是导入/迁移进来的历史业务，
要么是灌进去的种子数据** —— ⛔ **从库里分不出来**。

### 因此，正式台账里这样记（⭐ 关键：记成「判定」，⛔ 不记成「测量」）

> **历史订单数据判定为测试/演练数据，不作为 Natural Production Observation 样本。**
> 判定人：需求方 ｜ 判定时间：2026-09-27 ｜ 依据：需求方对这批数据来源的领域知识。
> ⚠️ **这不是一次测量** —— 库里查不出「真客户 / 测试数据」这个区别（见上表）。
> 写成「谁判的」，是为了以后有人看到那 2409 笔时知道**该去问谁**，
> ⛔ 而不是以为系统里存着一条可复现的判据。

⚠️ **并且：这不代表「生产是空地」**。库里仍有 2409 笔带日期的订单、55 个账号、
以及建立在它们之上的账本/结算数据。⇒ 受控验证**可以**写生产，但
**理由不是「不会与真实数据冲突」**（那句站不住），而是
**「这批写入带可判定的身份，将来能整体识别与排除」**（见 §八）。

## 三、⭐ 受控窗口 ⛔ 不许沿用样本量门槛

| | 自然观察 | 受控验证 |
| --- | --- | --- |
| 测什么 | **不可控输入下的行为稳定性** | **我们明确知道要覆盖哪些状态，并逐条验证** |
| 门槛在对付什么 | **不可控方差** | 方差已被你控制住 |
| 所以它需要 | **样本量**把分支覆盖到 | **设计**把分支覆盖到 |
| 判据 | 桶内 ≥ 20 / 契约 ≥ 10 / 回退 ≤ 80% | **每条场景：Input + Expected kind/resolution/amount/provenance/invariant** |
| 第 20 笔的意义 | 第 20 次独立抽样 | ⛔ **没有意义**，第 2 笔之后只是重复 |

⭐ 一旦把 ≥ 20 搬过来，就会**为了凑数而造单**，然后绿灯亮起时没人说得清它证明了什么 ——
那正是 R4-45 形状审计的同一种病（**判据与数据形状不匹配，仍然 PASS**）。

⚠️ 也必须写清楚它**证明不了什么**：

> 受控验证证明的是**「链路真实」**与**「逻辑正确」**。
> ⛔ 它**证明不了**「上线后在真实负载下不会垮」—— 那是自然观察的事，且只能在发布之后做。

## 五、⛔ 串行，不并行（Canary 冲突，未变）

受控验证要**改 Canary 比例**（V3/V4/V7 都要），而自然窗口要求「前后样本出自同一套配置」。
⇒ **观察期内动过一次 Canary，那个观察窗口就作废**（不是打折）。所以只能：

```
阶段 1（现在）   只跑受控验证
      ↓ 通过
阶段 2（上线后） 重新预注册一份自然观察
```

⚠️ ⛔ 不能「把受控那几笔排除掉就接着算」—— 被扰动的是**配置**，不是样本。

### ⚠️ V8 的期望值要改（否则会把 R4-37 已裁决的事写反）

需求方矩阵里 V8 是「**拆单 → 子单成为新的 Pricing Fact**」。
⚠️ 这与 **R4-37 已裁决的冻结粒度**相反：

> R4-37：**新的订单 = 新的一次决策**；`split_order` **不给子单**写 `freight_fee` / 快照。

⇒ 正确的预注册期望是：**拆单后子单没有定价事实；子单要等它自己第一次被派单时才产生新决策。**
⛔ 若照原文写成「子单成为新 Pricing Fact」，这条用例会**以错误期望去测一个正确的实现**。

## 七、⛔ 覆盖**不能**靠「当前库里数一数」

上面那张表里 `not_in_canary` 一栏是本轮新发现的一条**设计约束**：

> R4-37 定了：**同一张单的再次写入 = 同一次事实的修订**（整份快照被替换）。
> ⇒ `#20851` 先写 `not_in_canary`、后写 `frozen`，**库里只剩 `frozen`**。

所以：**「当前快照的分布」不是分支覆盖的证据** —— 覆盖过的分支会被后来的修订覆盖掉。

⇒ 受控验证必须**当场留存证据**：每次写入都把工具的输出（含 `resolution` / 金额 / 快照原文）
落成一份**独立于业务表**的记录（`_tools/ops/r4_drill_records/` 已有的做法照搬）。
⛔ 否则跑完之后，只有「最后那一次」能被证明。

## ⛔ 边界（不许悄悄改掉）

1. **受控验证 ≠ 上线许可**：它证明链路与逻辑，⛔ 不证明负载稳定性。
2. **撤回 ≠ 抹掉定价事实**；**软删 ≠ 从没存在过**。
3. 本阶段 ⛔ 不动 Canary 的**最终目标值**（验证期间可临时切换，跑完必须切回 30 并记录时刻）。
4. ⛔ 不动 30% 的配置、不动 App 的定价展示口径。
5. **一切写入必须带 `test_run_id`**，⛔ 无标识的测试单一律不许进生产。
