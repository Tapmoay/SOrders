## 二、⚠️ 本轮 Final Review **抓到了一条**（⛔ 不是「没有问题」）

**事实**：`docs/R4_PROGRESS.md` 里有 54 条 `复现：` 命令（去重 28 条），
其中 **1 条**指向一个**根本不存在的脚本**：`python _tools/qa/_check_r4_constraints.py`。
而它要证的那句话是「指南原文归档为 ……（带来源 SHA256）」—— **既没有判据，那个 SHA 也重算不出来**：
把归档正文切出来按任何常规归一都得不到声明的 `26669 字节`（最接近的一档差 7 字节），
因为**原件 `ppkk.md` 不在仓库里**。

**为什么一直没被发现**：`python _tools/qa/_check_report_facts.py` 会逐条跑台账里的 ✅ 命令，
但它**只跑 `docs/R3_PROGRESS.md`** —— R4 那一侧没有任何东西在核。

**修法（两条，都已落地）**：

1. **补上真的判据** `_tools/qa/_check_r4_constraints.py`：核归档结构 / 附录标注齐全 /
   来源声明与常量一致 / 北极星可查，并在输出里**如实写明它没核「逐字节等于原件」**；
2. **把台账那句话改准确**：从「原文仍是逐字节那 26669 字节」改成
   「附录声明为 26669 字节 / SHA256 `E45A6CAF…`；⚠️ **该值从仓库里重算不出来**」——
   ⛔ 不许让读者以为 SQL/脚本能证明归档与原件逐字节相同。

⭐ **判定**：这**不是**「使 R4 目标无法成立」的缺陷（它不影响上面任何一条结论），
但它是**证据纪律**的缺陷 —— 按本仓库那条「文档语义不许超过代码事实」，当场修掉。

## 三、诊断端点的生命周期（R4-49 §四 要求明确归宿）

```
GET /api/v1/diagnostics/orders/{order_id}/pricing-decision
```

**裁决：保留。** 它的定位是 **Internal Diagnostic Surface**，⛔ **不是业务 API**：

| 约束 | 状态 |
| --- | --- |
| 只读（⛔ 不写库、⛔ 不落快照、⛔ 不留 decision） | ✅ 有零写入判据 |
| 走现有权限边界 `ORDER_DISPATCH`（⛔ 匿名不可达） | ✅ 无令牌实测 401 |
| ⛔ 不进 App、⛔ 不参与业务流程 | ✅ 机器守卫：`android/` 里零引用 |
| ⛔ 不许长成第二套 Pricing API | ✅ 机器守卫：只许 GET（出现写动词即报红） |

**为什么保留而不是删掉**：Shadow / Release Rehearsal / ⑫ Full Cutover **都会再要这个面** ——
「同一份输入在两个实例上给出什么 Decision」这件事，上线前后都要反复问。
删掉它，下一次还得再造一遍；留着它，代价是一条只读 GET。

⭐ 守卫写在 `_tools/qa/_check_r4_closeout.py` 第 3 组：**端点一旦长出写动词、
或者 App 里出现引用，当场报红**。这就是「不许慢慢长成第二套 API」这句话的机器形态。
