# 102 · 离线数据与图片归档方案设计（评审稿）

> 关联：101 报告、消息保留期机制（notifications days=30 惰性清理）
> 更新：2026-09-04 · 本方案为「客户端本地优先 + 服务器分级保留 + 图片回源」完整规格评审与落地设计

## 1. 策略规格（用户确认版）

### 文本类数据（订单 / 账本 / 地址联系人 / 消息 / 派单员工作数据）
| 区间 | 存放位置 | 说明 |
|---|---|---|
| 0 ~ 18 个月 | 服务器（主存）+ 手机本地全量 | 服务器权威源 |
| 18 ~ 24 个月 | 服务器**临时保存**（数据**从用户手机拉回**）+ 手机本地全量 | 暂存 6 个月 |
| 24 个月后 | 仅手机本地全量 | 服务器临时数据到点清除 |

### 图片类（送达照片 / 地址参考图 / 商品图）
| 区间 | 服务器 | 用户手机 |
|---|---|---|
| 0 ~ 3 个月 | **原始图** + 压缩图 | App 私有文件目录保存**原始图** |
| 3 个月后 | 仅**压缩图**（原图删除/转冷） | 原始图长期保留 |
| 高清查看 | 拉取**拥有者手机**原图（临时查看）；拉取失败 → 回退压缩图 | 在线时提供 |

压缩要求：体积尽量小，**不损失画质与具体信息**。

## 2. 容量复核（50 人 / 25 单每天）

### 文本（服务端，含索引）
| 口径 | 18 个月 | +6 个月临时 | 2 年后 |
|---|---|---|---|
| 订单+明细（2KB/单） | 27 MB | +9 MB | 手机本地 |
| 账本+消息 | 17 MB | +6 MB | 手机本地 |
| **合计** | **≈ 45 MB** | **≈ 60 MB** | — |

> 文本容量结论：**60MB 级，服务器全量保留 24 个月毫无压力**（10 年也才 300MB）。
> 回流机制唯一的实际价值是「新设备/换机在 18-24 月窗口内能补数据」；若接受该窗口，**建议服务器直接全量 24 个月**（省掉回流接口与失败链路），如需严格按规格实现也可（见 §4）。

### 图片
| 口径 | 计算 | 量级 |
|---|---|---|
| 服务器原图（3 个月窗口峰值） | 25 单/天 ×90 天 ×2 张 ×200KB | **≈ 0.9 GB** |
| 服务器压缩图（长期累计，120KB/张） | 18,250 张/年 | **≈ 2.2 GB/年** |
| 每用户手机原图（摊 180 单/年 ×2 张 ×200KB） | — | **≈ 72 MB/人/年** |

## 3. 三个硬点（必须先拍板）

### 硬点 1：高清图「回源用户手机」的可靠性是最大风险 ⚠️
- 技术现实：Android 之间**没有 P2P 直连**，「拉取别人手机」必须由服务器中转：请求方 → 服务器发起回源 → **推送任务给拥有者手机** → 拥有者 App 把原图传给服务器 → 请求方下载。
- 失败条件日常化：拥有者**离线 / App 被杀后台 / 未启动 / 换机 / 手动清理** → 高清图**永久只剩压缩图**。
- 国内 Android 后台保活差（厂商杀后台），推送可能延迟甚至丢失。
- **建议**：① 接受「高清=尽力而为」（压缩图兜底），或 ② 重要单据类原图服务器**低成本冷存**（OSS 归档 ~0.03 元/GB/月，全年原图才 0.9GB ≈ 每月 0.03 元，比回源可靠且便宜），3 个月后原图转冷存（不是删除），回源只作为**最后兜底**。**强烈建议 ②**。

### 硬点 2：原图放「App 私有目录」与「卸载不删」冲突
- App 私有目录（filesDir）**卸载即被系统删除**；Android/data 同样卸载删；唯一卸载后保留的路径是「导出到用户可见文件（Documents/Download）+ 应用导入」或 GMS 云备份（国内不可用）。
- 之前你要求「删 App 数据不跟着删」→ 原图如果要卸载不丢，必须**导出/导入机制**（加密 zip，用户手动/定时导出）。
- **建议**：原图默认 App 私有目录（满足「不影响相册」✅）；「卸载不丢」交给**导出备份**功能（文本+索引一起导出，原图可选）。

### 硬点 3：「不损失画质」vs「压缩到很小」的数学矛盾
| 方案 | 压缩率 | 画质 |
|---|---|---|
| 像素无损压缩（WebP Lossless / PNG） | 仅 25-40% | 100% 无损 |
| **感知无损（WebP Q80-85 / AVIF）** | 80-90% | 人眼基本不可辨（**推荐**） |
| 信息无损（单据可读/可 OCR，Q92） | 60-75% | 文字细节保真 |

- 照片类（场景/送达照）：**WebP Q82**（≈ 原图 1/8~1/10 体积，肉眼无感差异）
- 单据/金额/文字类：**WebP Q92**（或 JPEG-LS），保证金额、单号、地址等「具体信息」可读可识别
- 客户端**本地压缩后再上传**（同时减少流量与服务器存储）；原始图存手机，压缩图随包上传。

## 4. 落地接口设计（草案）

### 文本
- 服务器主存 18 个月：orders/ledgers/notifications 保留期策略由「无限制」改为 18 个月惰性清理（请求路径，**无后台任务**，同消息现有模式）；18-24 个月窗口：若按规格实现 → 客户端「归档回传」接口 `POST /archive/reclaim`（批量化 + 去重幂等，服务器冷表暂存 6 个月后清理）；若拍板 2 年全量 → 只改一个清理参数。
- 全量/增量：`since_id`/`updated_since` 游标（订单/账本/消息统一）。

### 图片
- 上传：客户端压缩（WebP 分级）→ 服务器存原图 + 压缩图 → 3 个月后原图转冷存/删（`expires_at` + 惰性清理）。
- 回源：`POST /images/{id}/reclaim-request` → Socket 推送拥有者 → 拥有者上传 → 回调请求方 `GET /images/{id}/reclaim-result`；超时/失败 → 前端自动回退压缩图 `GET /images/{id}/compressed`。

## 6. 最终定案（2026-09-04 已上线，覆盖此前全部方案）
- **所有业务数据服务器保存 3 年**：orders/ledgers/operation_logs/cash_flows/notifications；主数据(users/products/地址联系人)不清理
- **原始图片保存 1 年**：1 年后自动压缩为**感知无损 WebP（Q90 / 长边≤1920）**，原图删除（实测 2400×1600 JPG 60KB → 4.4KB）
- **软删除隔离 30 天**：用户删除订单→隔离区(用户不可见)→**派单员可查(GET /orders?deleted_only=true)并恢复(POST /orders/{id}/restore)**→30 天后物理清理
- 货主可软删自己 已送达/已撤销/异常 订单；派单员任意状态；进行中订单需走撤销/撤回
- 实现：app/services/data_retention.py + image_archive.py；lifespan 每日循环（启动即跑一次）
- 交付修复：bootstrap 加 fcntl 文件锁（uvicorn --workers 2 并发 DDL 1684）；nginx 加 /static/ 反代；静态图改应用层 handler
- 服务器全链路实测通过（软删/恢复/3年清理/图片压缩/静态访问）

## 7. 常驻数据 vs 临时数据（最终分类，2026-09-04）
| 分类 | 数据 | 保留规则 |
|---|---|---|
| 常驻（永久） | 商品信息、地址、联系人、常用线路、用户、挂账单位、价格规则（批发价）、车辆、运费模板 | 永不清理 |
| 临时（按规则） | 订单/明细、账本流水、消息、操作日志、费用流水 | 订单/账本/日志/费用流水 3 年；软删订单隔离 30 天后真删；消息 30 天 |
- 临时数据清理由 data_retention.py 每日循环执行（服务启动后即跑一次）
