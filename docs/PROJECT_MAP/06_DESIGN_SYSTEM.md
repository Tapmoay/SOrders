# 06 UI 设计与语义色体系

<!-- ref-prefix: android/app/src/main/java/com/tapmoay/sorders/ -->

> 标准：**苹果结构 × 日本配色**（japanese-street-color-system）：Apple HIG 结构/层级 + 日本街头广告式一色一功能高饱和语义色（面向老年/低视力用户，亮色高对比）。

## 1. 核心设计原则

- **一色一功能**：每个功能/模块有唯一语义色，跨端同功能同色（下单绿/账本橙/消息红/地址湖蓝）
- **背景分层**：页面底 `BackgroundLight=#F2F3F7`，卡片白底圆角（`MaterialTheme.shapes`），信息用 SectionCard
- **低调卡片**：白底 + 浅描边（#ECEFF5）或极浅阴影；不要重边框/大圆/浓渐变
- **文字层级**：关键是重要的数字/名称用色加粗，次要说明用灰色 `onSurfaceVariant` 小字
- **按钮风格**：默认 Material3 样式（用户否决过大圆圈/胶囊大按钮）；加减等主操作色可自定义淡蓝底
- **弹窗**：选择/确认类用 `AlertDialog`；表单类用 Drawer/ModalBottomSheet 由场景决定

### 4.1 商品卡上那两个数字（2026-09-19 用户要求"用对应的语义色和图标"）

> **2026-09-21 起：这一段说的零件已经收进 `ui/common/ProductCardKit.kt`**（商品管理改版第 1 期）。
> 卡片上那两个数字由 `productPriceFact(...)` / `productStockFact(...)` 造、
> 由 `ProductFacts(...)` 画，缩略图由 `ProductThumb(...)` 画，库存配色由 `productStockColor(...)` 判。
> **第二轮（同日）再往深做了一层**：连**行/卡的主体**（`ProductLine`）和
> **"显示哪两个数字、谁在前"**（`productFacts()`）也收进去了 ——
> **渲染商品的 5 个页面**（商品管理 / 批量操作 / 商品排序 / 选品 / 库存）全部同源，
> 改一处即可处处跟着变（详见 §4.2b 末尾那张表）。
> ⛔ **这五页谁也不许再各写一份** —— 判据
> `_tools/qa/_check_product_card_single_source.py`（53 项，反向验证 `_reverse_verify_product_card.py` 26/26）。
> 用户原话（这一轮为什么要收）：「他其实**复用了很多的组件**……我们参考他的样式和排版。」
> 收之前：商品名兜底色 `#1565C0` 全库 **5 份**（其中 4 份没 `try/catch`，库里一个脏颜色值就崩一页）。

用户原话：「那些信息是在商品管理中非常重要的，不一定非要等编辑才能看得到，
我们要用对应的语义色和图标在它的名字的下面进行显示，让人一眼就能看出来」。
实现是 `ui/common/ProductCardKit.kt`（**配色只有那一处**）：

| 信息 | 颜色 | 图标 | 为什么是这个色 |
|---|---|---|---|
| 售价 | 金橙 `MoneyOrange` | `Sell` | 系统里"钱"的语义色（与账本/报表/小计同色） |
| 库存 | 蓝青 `#00BCD4` | `Inventory2` | **库存管理模块的语义色**（跨端同功能同色：这个数字属于库存管理） |

⚠️ **卡片上只有这两个数字，而且一个一行**（用户 2026-09-19 的三条要求叠在一起）：
- **没有「分类」**：「既然已经在左边显示了分类，那右边的商品就不需要显示分类了」——
  分类由左边那根导航条（`CategoryRail`）表达。代价：「全部」那一档下卡片上看不出
  每件商品属于哪一类，想知道归属就点左边对应的分类。
- **没有「成本」**：「商品管理界面不要有成本价的显示，成本价是要在编辑里面才会有」——
  成本是内部数、不参与对客户报价，要看/要改都在「⋮ → 编辑」，进货时也能顺手改。
- **一个一行**：「那个库存在成本价的后面，这个不要有，他们全在成本价的下面」——
  原来用 `FlowRow` 流式排，`成本 ¥0.00` 短的时候 `库存` 被挤到同一行、长的时候又自己换行，
  **每张卡长得都不一样**。现在固定一行一个：布局可预测，数字还在竖直方向对齐成一列
  （扫一列价格比扫一片流式文本快）。

⚠️ **库存还会按状态变色**：`stock <= 0` → 红 #E53935（断货）、`<= lowStockAlert` → 黄 #FFB300。
这两个颜色不是装饰，是"这一行要你处理"的信号 —— 派单员扫列表时靠它决定先看哪几个。

### 4.0 卡片右侧那一列：`⋮` 在上，「改价」在下（**已废，2026-09-21**）

> ⛔ **这一条 2026-09-21 已经作废**：卡片右上角那个「⋮」**整个删掉了**，
> 右侧那一列也随之取消 —— 动作改到**卡片底部一排三个等宽大按钮**（见 §4.2）。
> 保留原文只是为了说明"当年的理由"，**不要照着它改回去**。

用户 2026-09-19：「商品右上角不是有 3 个点吗？那是我们的正常设置，我们在它的下面——
因为下面比较空嘛——在下面再加一个改价，这个改价就是改默认的售价，方便嘛、快捷」。

右侧固定一列（46dp）：顶上是 `⋮`（全部动作都在菜单里），**它下面那块本来是空白**，
现在放「¥ 改价」——一点就弹**只改默认售价**的小窗。三个理由：
1. **改售价是最高频的日常动作**（进价一变就要改），而走「⋮ → 编辑」要打开整个抽屉、
   滚到价格那一段、改完再保存；
2. 它**不占新地方**（那一列本来就空着），卡片不会因此变高；
3. 保存走 `PATCH /products/{id}` 的**部分更新**（只放 `default_unit_price`），
   不会顺手覆盖别人改过的名称/成本/库存。

⛔ **颜色必须用商品管理的模块色紫 `ProductPurple`，不能用钱的橙**（用户当天就指出来了：
「那个改价的按钮换个颜色，它与那个售价的颜色撞了一个色，换语义颜色」）——
同一张卡上「售价」那个数字已经是 `MoneyOrange`，再拿它染按钮就撞了；而这个按钮是
**商品管理里的一个操作**，用模块色正好（紫色本来被卡片上的分类 chip 占着，分类删掉后空出来了）。

⚠️ **弹窗预填的价要用 `trimMoneyZeros`，不能用 `formatMoney`**：库里的单价列是
`Numeric(14,4)`，直接显示是 `12.5000`；而 `formatMoney` 只留两位小数，会把 `12.3456`
显示成 `12.35` —— 在一个**可编辑**的价框里那等于骗人（用户不改直接保存，价就真的变了）。
显示用两位、编辑用去尾零，两者的区别就这一条（`util/Money.kt`）。

### 4.2c 卡片动作的**位置**：左＝反向/警示，右＝编辑（2026-09-22 定成规范）

用户对着订单卡片说的原话：

> 「假如像我们**派单员编辑**的话，一定是在**右边**的，而且他就是一个…**笔**啊，**这个不行**啊，
>  他**要一个图标**啊，**稍微圈一下**；然后呢**异常**的话，就放置在**左边**而且**是最左边**。
>  这样做的好区分，**包括以后的那个**只要涉及到**编辑**和其他的比如说**删除**等等，
>  **编辑一定在右边**（因为我们的**惯用手是右手**，我们好编辑），但是比如说**相反的操作，就在左边**」

**规范**（两条，都是"以后所有卡片"）：

1. **位置**：**右＝编辑类**（改这一条记录）；**左＝反向/警示类**（撤回、撤销、退货、异常…），
   其中**警示**（异常标记）放在**最左**。理由就是用户给的那条：惯用手是右手，正手够得着的位置留给"改"。
2. **形态**：卡片上的**图标**动作一律做成**圈底图标**
   （`ui/common/Components.kt::CardActionIcon`：12% 语义色圆底 + 同色图标，
   与卡片里那些说明性图标 `TintedIcon` **同一套语言** —— 一半描边一半实心会像两个人拼的）。
   ⛔ 裸 `IconButton` 里塞一个 18dp 图标**不算**：在信息很满的卡片上它太轻、手指也不好找，
   用户那句「**这个不行**」指的就是它。

**落地**：`OrderCard` 底部动作行有**两个槽** —— `leading`（左）与 `extra`（右）：
`leading()` 先画，`Spacer(Modifier.weight(1f))` 把 `extra()` 顶到右边。
⚠️ 只给 `extra` 时行为与以前**完全一样**（`leading` 默认空），所以司机端等老调用点一行都不用改。

| 页面 | 左（反向/警示） | 右（编辑） |
|---|---|---|
| 派单员「订单管理」 | 异常（**最左**）· 撤回 · 退货 | 编辑（圈底铅笔） |
| 货主「我的订单」 | 撤销订单 · 申请退货 / 撤回申请 | （空着 —— 这一页本来就没有"编辑"这种动作） |

**判据**：`_tools/qa/_check_order_list_ui.py` §6 + `_tools/qa/_reverse_verify_order_list_ui.py`
（其中一条注入就是把两个槽**对调**）。

⚠️ **这条规则其实先落在「账户管理」页**（同一天、另一个会话）：`ui/dispatcher/AccountManageScreen.kt`
的卡片底行早就是「左＝删除 / 停用启用 · 右＝编辑」，它也自带一个圈底动作控件
`private fun AccountAction(label, icon, tint, onClick)` —— 与 `CardActionIcon` 的差别只有
**它多一个文字标签**（理由写在那个函数的 KDoc 里：那一页的用户是派单员，只留图标会逼人靠猜）。

✅ **2026-09-22 已经收编**（用户点头：「对账户管理那个你也做了去吧」）：
`CardActionIcon` 多了一个可选参数 **`label`**（传了就是"圈底图标 + 文字"，不传就是卡片上那个
纯图标动作），`AccountAction` 缩成**一行委托**（`= CardActionIcon(…, label = label, size = 15.dp,
container = 30.dp)`）—— 真机核对过：那一页的观感与改前**完全一样**（尺寸/间距/配色逐项对齐）。
⛔ 以后任何页面想要"圈底动作"都走这一个控件，别再各写一份：
位置规范（左/右）与形态（圈底）都该只有一处实现，否则下一次改样式必然漏掉其中一页。
判据：`_check_order_list_ui.py` §6（「`AccountAction` 只是委托」+「`label` 是可选参数」）。

⛔ 卡片上**仍然只有两个数字**（售价 + 库存）、**一个数字一行**、**成本与分类都不在卡上**（§4.1 那三条不变）。

**⛔ 这两行的顺序、配色、文案**（"售价在前、库存在后"）**只定义在一个地方**：
`ui/common/ProductCardKit.kt::productFacts()`。用户 2026-09-21 第二轮的原话是
「像我们这样子的形式——比如说右边是分类、它是个条的，那个商品啊，它其实是**有点区别的**…
你也**全部做深**吧…**其他地方你也得改**，最好是采用（通）用的继承，**上次你改一个地方，它就其他跟着改了**」。

所以现在**渲染商品的 5 个页面**共用同一套零件（`ProductLine` + `productFacts` + `ProductThumb` + 两条判据）：

| 页面 | 形态 | 显示哪几条事实 |
|---|---|---|
| 商品管理 | `ProductLine` 大卡 | 售价 + 库存 |
| 批量操作 | `ProductLine` 紧凑行 + 左侧勾选框 | 售价 + 库存 |
| 商品排序 | `ProductLine` 紧凑行 + 右侧 ↑/拖动柄 | 售价 + 库存 |
| 选品页 | `ProductLine` 紧凑行 + 右侧 ＋ | **只有售价**（货主也看这一页，不露库存） |
| 库存管理 | 自己的外壳（那页的 DTO 没有图/名称色/售价） | 只有库存 + 占用 |

**"显示哪几条事实"是各页自己的业务口径**（上面第 4、5 行的差异是**有意的**，不是漏了改），
但"一条事实长什么样""怎么排""什么颜色"**只有一处**。
红线 `_tools/qa/_check_product_card_single_source.py`（53 项）逐条盯着，反向验证 26/26。

**库存的颜色判据也只有一处**（`productStockColor`）：断货红 `#E53935` / 到报警线黄 `#FFB300` / 正常蓝青 `#00BCD4`。
⚠️ 注意 `lowStockAlert = 0` 表示**不报警**（不是"阈值是 0"），所以"到报警线"那一档必须带 `lowStockAlert > 0` 前置条件。
库存页在第二轮之前自己判了一套**不一样**的（低库存红、缺货灰）→ 同一件商品在两页颜色不同，已归一。

### 4.3 一个页面有两个并列入口 → 底部一条栏（**三个入口时用"三格 + 中间圆钮"，2026-09-21 补**）

用户 2026-09-19：「给那个商品管理界面的下面加个导航栏，左边分组管理、右边商品新增，
那个 + 把它改成商品新增…**两个导航栏做得美观一点**」。

搬之前是**顶栏一个文字按钮 + 右下角一个 FAB**，两个毛病：
视线在屏幕上要跑两趟（一个在顶、一个在底）；FAB 还压着列表最后一张卡 ——
所以列表尾巴上被迫留了一句 `Spacer(72.dp)` 让位，而那句话在任何一页上都没有意义。

**两个入口时的写法**（原口径）：

| | 左（次） | 右（主） |
|---|---|---|
| 组件 | `OutlinedButton` | `PrimaryActionButton`（全项目主操作同一组件） |
| 外观 | 1.5dp 语义色描边 + 同色文字/图标 | 语义色实底 + 白图标 |
| 宽度 | `weight(1f)` | `weight(1.4f)` |
| 高度 | 56dp（与主按钮同高，视觉成对） | 56dp |

**三个入口时改用「三格」**（2026-09-21 用户：「**底部栅格组排直接照抄**，他怎么搞我们就怎么搞」）：
左右两格是**无边框的「图标 + 文字」**（不是描边按钮 —— 三个描边按钮会变成三个并排的框），
中间是**语义色圆钮 + 一行文字**（主操作居中，拇指够得着）。
商品管理页现在就是三格：**分类管理 / 商品新增（圆钮）/ 批量操作**。

四条纪律（两条口径都适用）：
1. 主次必须看得出来：两个入口时**一实一虚**；三个入口时靠**中间的圆钮**。
2. **染模块语义色**（这里是 `ProductPurple`），不是默认主题蓝 —— 一色一功能。
3. ⛔ **不许用别的功能的颜色**：同屏「售价」已经是钱的橙，再拿橙染按钮就是撞色
   （用户当天刚为这件事让改过一次，见 §4.1）。
4. 这一栏**不是** M3 `NavigationBar`、不会自己处理 insets → 自己加 `navigationBarsPadding()`
   （App 是 `enableEdgeToEdge()`，不加会被系统导航条压住半截）。
   搬完之后 Scaffold 的 padding 已经扣掉这条栏的高度，列表里那句让位用的
   `Spacer(72.dp)` **要一起删掉**，否则列表底下凭空多一块空白。
5. ⛔ **顶栏不许再挂同一批日常动作**：2026-09-21 顶栏只新增了一个「排序」——
   它与底栏那三个不冲突（那是"偶尔调一次次序"、而且有自己的一整页）。

### 4.4 搜索框：按人搜只有一份（`SearchField`），名册页走服务端

用户 2026-09-19：「还有其他的比如说，**司机管理**啊**账户管理**啊。这些也要添加搜索键。
然后这个搜索键可以根据他们的**名称**还有**电话号码**以及**电话号码的后 4 位**进行搜索」。

| 判据 | 规定 |
|---|---|
| 组件 | `ui/common/Components.kt::SearchField`（放大镜 + 入框即出 `✕` 一键清空 + 圆角 12 与 `SoTextField` 同族） |
| 提示文案 | 默认取 `core/UserSearch.HINT`（「搜姓名 / 手机号（后 4 位也行）」）—— **各页不许各写一句**：用户得先知道能按后 4 位搜才会去试 |
| 匹配规则 | `core/UserSearch.matches`（姓名 或 手机号，**子串**；后 4 位据此天然命中）／服务端 `app/core/user_search.py` |
| 取数位置 | **数据一次回全量的**（账本 `/ledger/accounts`、`/freight-settlement`）→ 本地过滤；**一页有上限的**（`/users` 最多 500）→ **必须**服务端 `?q=` |

为什么"名册页必须服务端"：一页 500 条，本地过滤时第 501 个人在客户端**根本不存在**，
而"列表里没有"会被读成"没有这个账号" → 再建一个 → 撞手机号唯一约束。
账本那两张接口本来就一次回全量，本地过滤反而更快（不必每敲一个字打一次后端）。

⚠️ **搜到 0 条时的说法要跟着变**：服务端搜过了就说"服务端按姓名/手机号搜过，确实没有"
（这是一句**结论**，可以照着去新建）；本地过滤只能承认"这一页里没有"。
⛔ 提示语里带**地址**的框（线路 / 地点 / 地址库）是**另一条规则**，不许套这个组件。

### 4.5 仪表盘：一屏看完各自的数，不要"先勾选再看"

用户 2026-09-19（**推翻**了他自己上一轮要的"搜索 + 多选"）：
「假如客户非常多司机非常多，那用户要是一个一个去选的话，那要有多麻烦啊。
**所有的账本你可以一个仪表盘的思维进行去构建**」。

落地写法（`DispatcherLedgerScreen.kt::KpiBlock` + `LedgerDashboardCard`）：

```
批发商账合计（当前时间范围）      ← 一行小字，说清"这是什么的合计"
¥12,345.00                        ← 钱：单独一行、最大最粗、橙（钱的语义色）
3 个账户 · 共 19 笔                ← 一行小字，解释上面那个数是怎么来的
[🔍 搜姓名 / 手机号（后 4 位也行） ✕]
```

三条纪律：
1. **钱单独一行**（沿用 §4.1 的"一个数字一行"）：三个数并排堆成一行小字，既不突出钱，
   也看不出哪个数在解释哪个。
2. **搜索之后合计跟着变**，并把「全部 N 个账户合计 ¥X」一起说出来 ——
   不说的话用户会拿筛出的那个数当总额去对账。
3. ⛔ **不要再加"勾选账户"这类控件**：一屏已经能看到每个账户各自的数了，
   再让人一个个勾，把力气花在重复劳动上；chip 上的"名字 + 金额"与列表里的是同一份信息，
   放两处必然出现"两边对不上"的困惑。红线 `_tools/qa/_check_user_search.py` 钉着它不许长回来。

### 4.6 两栏版式（"左边一个篮子、右边是它的内容"）

用户 2026-09-19 连着为三处点名了这个版式，原话都是"**像商品管理那样**"：

| 页面 | 左栏装什么 | 右栏装什么 |
|---|---|---|
| 商品管理 / 库存管理 | 商品分类 | 商品（卡片） |
| 下单页地址库抽屉 | 线路 / 我的地点 / 共享地点 + 自定义分组（**一格都不带"N 条"**，见下） | 对应的地点行 |

> ⚠️ **司机运费结算不在这张表里了**（2026-09-22 用户第二轮把它换成"账本那种形式"）：
> 原来它抄的正是这一页，用户看真机后原话是「**不要按照这样子的商品的管理**啊。这样子，**非常不好**」
> —— 现在它和账本页一样：**人走侧边抽屉**（`ui/common/PersonPicker.kt`）、时间走顶栏药丸，
> 见 §4.15 第 8 条。

**左边那一列只有一份实现**：`ui/common/Components.kt::MasterRail(items: List<RailItem>, selectedKey, onSelect, accent)`。

- `RailItem(key, label, subtitle)`：**key 与显示名刻意分开** —— 司机那一栏的 key 是 `d|12`、
  屏幕上是「王建国」；拿显示名当 key，两个同名司机就会互相点亮（本机 293 个司机，重名不是假想）。
- **行高自动**：有 `subtitle` → 60dp，没有 → 52dp。有副标题还压 52dp，两行字会挤在一起，
  而"挤"在老人用户那里等于看不清。副标题强制 `maxLines = 1` + 省略号：让它折行会把整列节奏顶乱。
- **选中态 = 白底 + 左侧一条语义色竖条**（外卖 App 的通用写法）。语义色由调用方给：
  商品/库存/地址用主题主色。
- ⛔ **两种排序不要混**：左栏的顺序就是右栏的顺序来源，**不许在右栏再排一次**
  （同一批数据两种顺序 = "我点的那个怎么跑到下面去了"）。
- ⚠️ **搜索框放在左栏上面、横跨整页**（与 §4.4 同一条理由）：左栏是"有哪几类"、
  搜索是"那个东西在哪"，两个维度；塞进左栏会被压成半宽，而且左栏为空时它跟着消失。
- ⚠️ **不是所有"东西多"的页面都该上两栏**：账本管理试过一版（左栏放 4 类账 + 4 个工具），
  用户看真机后否掉了，改成"工作台一格 → 账本管理**入口页**（报表中心那种形式）→ 账本页只看账"，见 §4.13。
- ⛔ **左栏要不要带"N 条"——按"这个数是不是一眼判断的依据"分，不是按"有没有地方放"**：

  | 左栏 | 副标题 | 为什么 |
  |---|---|---|
  | 下单页地址库（线路 / 我的地点 / 共享地点 / 自定义分组） | **一格都不带** | 用户 2026-09-19 看截图后点名：「那个分组下面不要显示有多少条啊，**这是多余信息**」。左栏回答"有哪几类"，条数回答"这一类里有多少个"——后者点进去一眼就数得完 |
  | 侧边抽屉里的司机名单（`PersonDrawer`） | `手机号 · ¥860 · 21 单` | 结算页挑人时"这位司机多少钱"**就是**在找的东西。（原来这条挂在 `MasterRail` 的左栏上；该页 2026-09-22 改成抽屉之后，同一个道理跟着搬到抽屉那一行） |

  ⚠️ 代价要说清：`MasterRail` 的**行高是整列统一的**（`twoLine = items.any { subtitle != null }`），
  只要有一格带副标题，整列六格全是 60dp、其余五格的第二行空着。真机截图里那五行
  「8 条 / 9 条 / 3 条 / 0 条 / 0 条」就是这么把一列撑高的。所以「管理分组」那格也不再挂
  「新建 / 排序」——它是**去的地方**不是**数据**，挂着只会让"整列里独独这一格是两行"。

`CategoryRail`（商品分类那一列）现在只是 `MasterRail` 的一层薄包装 ——
原来那段 Box/Text 是照抄的写法，抄到第三遍行高就会各自跑偏。

### 4.7 长地址从**尾部**省略（`TextOverflow.StartEllipsis`）

用户 2026-09-19 看下单页地址库截图后点名（原话）：

> 「它后面会有省略……省略是可以的，但是你要**从后面往前显示**。意思就是说，我们也首先肯定知道的是
> 这里面的那个地点嘛，**前面的前缀基本上不需要知道**，所以那个最明显的那个有颜色的标题
> 应该是**最后面**的那个地点」。

同一屏的地址**开头全是同一个前缀**（「北京市顺义区……」），真正区分彼此的只有**最后一段**
（村 / 小区 / 门牌 / 楼栋）。所以同一行里两段的省略方向**故意不同**：

| 位置 | 省略方向 | 理由 |
|---|---|---|
| 地点/线路的**标题**（湖蓝加粗那一行） | `TextOverflow.StartEllipsis`（省掉**开头**、留住尾部） | 标题常常**本身就是一串地址**（司机补录、共享地点进来的记录，`name` 就是详细地址）；按常规的尾部省略，真机上八行全是「北京市顺义...」，看八行等于没看 |
| 标题下面的**详细地址**（灰字那一行） | 仍然是尾部省略 | 它是"完整地址"，要从头念才知道在哪；而且它 `maxLines = 2`，两行基本够用 |

- ⚠️ 用系统自带的 `StartEllipsis`，**不要**自己写 `takeLast(n)`：按字符数截在中英混排上会截在半个词里
  （门牌号里常有 `A座 3 单元`、`Building 7`），而 Compose 的省略是**按排版结果**算的。
- ⚠️ 顺带修掉的一处**宽度对半分**：标题原来是 `Modifier.weight(1f, fill = false)`，
  后面还跟着一个 `Spacer(Modifier.weight(1f))` —— 两个 1 权重把可分配宽度**对半分**，
  标题只拿得到一半（这也是「北京市顺义...」明明右边还空着却被截断的直接原因）。
  标题改成 `weight(1f)` **独占**后同一行能多显示一倍的字；右侧的「有导航」不带权重，仍然贴边。
- ⛔ **别把 `Spacer(Modifier.weight(1f))` 加回来**——它看着"只是顶一下右边那两个字"，
  实际是在跟标题**抢宽度**。要让右端贴边，靠的是"标题独占剩余宽度"，不是再加一个权重。

### 4.8 错误的**落点**：表单的错画在表单里，页面级的错只管"这一页没加载出来"

用户 2026-09-19 报的缺陷（原话）：
> 「我新建了一个地点，但是我没有填任何地址。直接点击保存，然后再返回去的时候，
> 它那个地点库的**所有列表全消失了**，需要重新连接」。

**不是断线**，是那句话画错了地方：表单的校验错误写进了**页面级**的错误状态，
而页面级错误会把整页换成「一句话 + 重试」（`ErrorView`）。同一句话造出两个假象：

| 用户看到的 | 真相 |
|---|---|
| 点「保存」**没有任何反应** | 那句话画在抽屉**背后**，被抽屉盖住了 |
| 关掉抽屉后**三个列表全没了** | 那句话还挂着，整页被 `ErrorView` 顶掉；一条数据都没丢 |

所以一个页面上**必须有两个分开的错误状态**（`_check_ai_guardrails.py` 里那条
「加载错误与动作错误分开」钉的就是这件事）：

| 状态 | 谁写它 | 画在哪 |
|---|---|---|
| `loadError` | **只有** `load()` | 整页换成 `ErrorView` + 「重试」 |
| `formError` | 抽屉/弹窗里的校验与保存失败（`ui/common/Components.kt::FormErrorLine`） | **在那张抽屉/弹窗内部**、提交按钮上方 |
| `notice` | 行上的「删除 / 设为默认」这类**没有表单可挂**的动作 | Snackbar（`OneShotSnackbar`，用完置回 null） |

- ⛔ **打开表单时清掉 `formError`**：不复用上一张表单的报错（不然一打开就顶着一行红字）。
- ⚠️ 另一条同源的脆弱：一个页面要拉的**几个列表必须各自独立**地加载 ——
  原来那三个列表串在**一个** `try` 里，任何一个失败整页就变错误页，
  另外两条明明拿得到的数据也一起看不见了。现在全挂才算"这页没加载出来"，
  只挂一部分就照常显示 + Snackbar 说一句。

### 4.9 数字的口径词必须跟着**实际窗口**走（2026-09-20）

一个页面上的数字只要依赖某个时间窗口，写它口径的那几个字就必须来自那个窗口本身。
运费结算页原来把「本月」写死在**四处**（标题 / 仪表盘 / 统计块 / 空列表文案），
加上"自己选一段时间"之后，这四处的数字可能根本不是本月的 —— 而**用户看不出这一点**
（数字不会自证是哪一段的，页面说"本月"他就当成本月）。

实现：`FreightSettlementViewModel` 只暴露两个**由窗口算出来**的词 ——
`periodLabel`（标题与药丸上的短标签：`本月`/`上月`/`上上月`/`09-01~09-20`）与
`periodWord`（句子里的口径词：`本月`/`所选区间`）；页面上**不许再出现写死的"本月"**。

- ⚠️ 自定义区间时**把那段日期显示出来**（药丸上就写 `09-01~09-20`，不是"自定义"三个字）：
  一页上至少要有一个地方写着"这些数字是哪一段的"，否则「共 3 位司机 · 应得 ¥860」没有范围可对。
- ⚠️ 自定义起止按**当地整天**取（`00:00:00` ~ `23:59:59`）：不补时间的话"选到今天"会把今天
  送达的单整批漏掉，而界面上看不出少了一天。后端在窗口两侧都换算成 UTC（`to_utc_naive`）。
- ⚠️ 换了时间窗口要**清掉左栏的选中**：那个 key 在新窗口里可能不存在，界面会"回落到第一位"，
  留着旧 key 会让左栏高亮和右栏内容对不上。

### 4.10 文案：常驻"几个字"，解释走「最多出现三次」（2026-09-20）

用户原话：
> 有些功能不需要说太多，只需要一个简单的字、简单的一句话，大概字数最多是 7 到 8 个字就可以了…
> 比如说共享库，本来就写了一大堆话在下面，没必要，直接删掉就可以了。
> 或者你可以这样子：第一次和第二次的时候它是出现在那里，下次再点击的时候它就不会有了…
> 第四次就不会有了。

于是界面上的文字分成两类，各归各的：

| 类型 | 例子 | 规矩 |
|---|---|---|
| **常驻的数 / 标签 / 按钮 / 行内说明** | 「地点名」「我到了，补导航」「已在共享库里」 | **≤ 8 字**。它是给**已经会的人**看的，不是每次都重新教一遍 |
| **解释"按下去会发生什么 / 这个数是哪来的"** | 「存三处：这单 / 货主库 / 共享库」的补充句 | 走 `ui/common/Components.kt::HintOnce`：**前 3 次出现，第 4 次起消失** |

- 实现：`core/HintPrefs.kt`（SharedPreferences 计数，**同步可读**——合成时就要决定画不画，
  用 DataStore 会"先画一帧再消失"，比不显示更难受；与 `AlertPrefs` 同一个理由）
  ＋ `ui/common/Components.kt::HintOnce(prefs, key, text)`。
- ⚠️ `key` 是**永久身份**（`"order.nav_block"`），不是屏幕上那句话：改文案不该让用户重看三遍，
  也不该蹭别人的额度。
- ⚠️ 计数在**进入这一次**就 +1：用户在几个页面之间来回切，那就是几次"看到"。
- ✅ **「我的 → 提示」**（默认**关**）＝打开后不走这个机制、一直显示。
  给"想不起来当初那句话怎么说的"的人，也是这条规则真机验收的入口。
  （标题只留两个字：用户 2026-09-20 看真机截图说「你只要把那个标题改成提示就可以了」——
  原来写「提示一直显示」，和副标题的"一直显示"重复了一遍。）
- ⛔ **不放宽的那部分**：错误/校验信息（"一句能照着做的中文"）、数字的口径说明
  （毛利只按有成本快照的行算…）**照旧要写清**——它们不是"教学"，是"这次到底发生了什么"。
  这一条只收**教学/引导**类的常驻长句。

### 4.12 图表：三种图可切换，但**数目只许一个来源**（2026-09-20）

用户 2026-09-20 对派单员账本的要求：「最上面是有日期还有预设的日期…下面就是个圆形扇形统计图
和一个条形统计图…**3 个图可以进行切换**，折线条形扇形」。落到规则上是四条：

1. **三种图共用一件事**：`ui/common/Charts.kt`（`LineChart` / `BarChart` / `PieChart`）。
   ⛔ **别处不许自己 `Canvas(` 画图**（红线 `_tools/qa/_check_ledger_dashboard.py` 会红；
   白名单只有 `util/Watermark.kt`＝导出图片的水印）。
2. **图上的数必须与屏幕上那个合计同源**：取数一律走各页的**纯函数**（账本是
   `ui/dispatcher/LedgerCharts.kt`），页面自己再 `sumOf` 一遍就是第二份口径 ——
   表现是「上面写 ¥3,200、扇形加起来 ¥2,800」，两个数都不报错。这条判据真的拦过一次注入。
3. **数据支持不了就不给那一档**：货主账/批发商账的接口只回账户汇总、没有按天的数，
   所以那两档只有「排行 + 构成」两种图（`chartTypesFor`，有单测）。
   硬凑一条按天曲线，会在明细被截断时画出**比合计小**的线 —— 同一屏两个数，比"少一种图"糟得多。
4. **扇形的两条硬规矩**：环心那个数 = **切片之和**（不是从别处塞一个合计进来）；
   切片跟着搜索走、超过 6 块合并成「其他」但**绝不丢**（丢了占比就加不到 100%）。
   配色取 `ChartPalette`，判据是**两两 RGB 距离 ≥60** —— 两块颜色接近就只能靠图例反查，图等于白画。

**日期档位**（同一轮的要求）：档位与区间在 `ui/common/DatePresets.kt`（纯函数、有单测）。
形态分两种、**都在 `ui/common/Components.kt`**：通用筛选条用横滑胶囊行 `DatePresetRow`，
**账本类页面（派单员账本 / 货主账本 / 司机账本）用顶栏药丸** `DatePresetPill` + `DatePresetDialog`
（见 §4.15）；两边的档位与区间共用 `DatePresets` 那一份。
⚠️ 口径写死为：**本月 = 本月 1 日 ~ 今天**（未来的日子没有账）、**上周 = 上周一 ~ 上周日**
（不是"最近 7 天"，那是另一档）。第一格是**「全部」＝不带日期条件**。

### 4.13 工作台与「入口页」：东西多就先开一个入口页，不要往工作台上堆（2026-09-20 三轮定稿）

用户 2026-09-20 为「账本管理」改了**三轮**，最后一句把前两轮都推翻了：

> 派单员的那个工作台全部改一下，**改回原来的样式**……首先，我们将**司机的账和司机结算**这 2 个东西

> 然后车辆台账属于车辆管理，车辆管理直接放在桌面上就行了。

（被推翻的两轮，记下来免得再试：① 账本页做左栏两栏；② 工作台做**第二张卡片**装那 8 件事。）

所以现在的形状是：

| 层 | 是什么 | 从哪儿来 |
|---|---|---|
| 工作台 | **一张卡片**（全部业务模块，一屏图标） | `Modules.dispatcherEntries` |
| 「账本管理」入口页 | 点网格上那一格进来，**报表中心那种形式**（两列入口卡） | `Modules.ledgerHomeEntries`（**唯一一份清单**，6 格） |

- ⛔ **工作台只有一张卡片**。加过第二张（8 件事），用户当天否掉 —— 同一批东西分两块，
  用户要在两块区域之间来回找；网格装得下就装网格。

- ⛔ **「司机结算」不单独占一格**（用户点名"合并成一个"），而且**账本页里也不再挂入口**

- ⛔ **「车辆管理」在工作台上**（用户：「车辆管理直接放在桌面上就行了」）；

### 4.14 账本页的排版：时间 → 谁 → 数据（2026-09-20 第三/四/五轮，控件形态见 §4.15）

用户 2026-09-20 看真机时把账本页的排版一次说清（第三轮删掉了页内那条 4 页签导航，
第五轮又把「搜索框 / 人员一排 chip / 三张图」换掉了）：

> 整个排版是**先是搜索**，然后再是**时间**，最后在下面再就是**选择司机**；先选择司机，
> 下面的数据才会出来，**不过默认是全部**……**包括其他的货主以及批发商都是一样的**。

四条可直接照做的规矩（账本页是第一个这么做的页面，别的"按人看账"的页面照抄）：

1. **顺序固定**：时间（顶栏）→ **人** → 数据。选人那一步的前置动作是"找得到人"，
   所以**搜索长在选人那个控件里**（第五轮：抽屉里的搜索框），不再单独占一整行。
2. **选人默认「全部」**：不选人＝看所有人（合计 + 每人一行），选了人＝只看他这一段。
   两层的分界是**一个状态**（`personKey`），所以"抽屉里点一下"与"点某一行"走同一条路
   （`openPerson` / `selectPersonKey`）——两条路＝迟早出现"点了没反应"。
3. **筛选控件别改合计**：抽屉里的搜索只筛**名单**，页面上的合计永远是"所有人"的 ——
   边打字边改合计，关掉抽屉就会剩一个对不上的总数（`dashboard()` 刻意不接 `visibleAccountRows()`）。
4. **批量动作只能落在"一个收款人/一个对象"这一层**（用户：「如果是**全部**的话，那个合计
   **不能**批量核销，只能下到每个司机/货主才能批量核销」）：账本页里"核销全部"只出现在
   **某个人的合计**下面，一次收款单带他这一段的全部 `order_ids`；⛔「全部人」那一层不给 ——
   收款单绑的是某个客户的档案，在那一层收钱就等于把钱记到某个随机的人头上。

### 4.16 卡片上"突出什么"可以是**数据**决定的（开销卡片，2026-09-20）

用户看开销管理时说了一句可以直接当规矩用的话：

> 这个关联跟**对应的分类**是有关系的 —— 比如说燃油或者说维修这些主要是车辆，所以关联的是车辆，
> **首要突出的是车辆**；如果是其他的成本，可能关联的就是其他的……要**具体问题具体判断，不能一刀切**。
> 关联订单号放在**点详情**的时候看。

三条落地方式：

1. **"突出哪一项"是名册里的一列**（`expense_categories.link_kind` ∈ vehicle/driver/order/none），
   不是客户端 `when(分类名)`。用户新加一个"违章罚款"并在分类管理里选「车辆」就能用——
   ⛔ 硬编码的后果不是"少一个功能"，而是"新分类的卡片形态没人管"。
2. **兜底顺序必须有**：分类说"车辆"、这一笔却没填车 → 退到司机 → 再退到订单；
   三项都没有就不显示那一行（**不临时挑一个**——那是替用户编事实）。
   纯函数 `core/ExpenseLink.kt`（有单测）+ 红线钉着。
3. **次要信息降级、不删除**：突出项之外还填了的关联，用小字列在下面一行；
   **金额只有一个、日期只有一处**（重复出现必然"两处对不上"）；
   完整来源（哪一单、哪个司机/车辆）在「详情」里看。

⚠️ 这条规矩不限于开销：任何"一类东西的卡片上最该看什么"的问题，先问"这件事能不能变成数据"
（名册里的一列 / 一个开关），再考虑写进代码。

### 4.18 价目卡的"重要信息"：路线与价格最大，其余降级（运费模板 / 计费规则，2026-09-21）

用户这一轮两句原话：

> 「这个运费模板，我们也可以按商品做一个相应的分类，也可以**创建分类进行管理**……**他那个运费模板
>  是有自己的一套分类的**，只是我们复用他那个代码和方法」；
> 「运费模板的卡片也做得**美观一点**，**信息主要的也重要信息主要做得明确一点**，包括计费规则的
>  卡片信息也要做得明确一点」。

七条可直接照做的规矩：

1. **分类栏 + 右侧列表**（与商品管理/库存/开销同一套观感）：左边是分类名册（可维护、可排序），
   右边是该分类下的价目。⛔ 分类栏的格子**由名册算出来**，不是手写枚举。
2. **"一类东西在哪几类下出现"要和"属于某一类"分开写**：一条价目可以挂**多个**分类
   （用户：「一个模板可以有多个分类」），所以分组规则是"在哪几类下都出现"，
   **一处实现**（`underFreightTab`，有单测）—— 各页各写一遍必然出现"同一条价目在这里有、在那里没有"。
3. **卡片上只留两件大字：这条路线（起点 → 终点）与价格**。分类用色块、车型/司机/备注降级成小字。
   理由与 §4.16 同源：**一屏里最重要的那个数必须一眼看到**，而"分类标签 + 路线 + 价格 + 车型 +
   司机 + 备注"揉成一行小字时，用户每次都要重新读一遍才知道哪个是钱。
   计费规则卡同理：**那句话（后端 `PayRule.describe()`）**在前，按分类的金额表逐行跟在后面。
4. **一级主数据不做"多条件匹配"**：价目只管"这条路线上这一类货多少钱"；**谁用它**（车型/司机）
   由「计费规则」勾选决定 —— 用户原话：「运费模板不会去匹配车型也不会匹配司机……这一目录就归这个
   计费规则，而这个规则在匹配对应的司机」。界面上也要照这个层级写：价目卡写"被哪几份规则用着"，
   规则里写"用哪些价目"。⛔ 别把两件事揉进一张卡的两个字段里 —— 那样"它到底按什么匹配"谁也说不清。
   勾选价目的那个界面**照选品页**（左分类栏 + 全选本分类 + 单独勾），因为用户对"挑东西"的心智模型
   就是那一套。

5. **配置里的歧义要在配置时看得见**：匹配有多条同样优先的价目时，系统**不猜**（报歧义让派单员挑）——
   所以价目卡上必须写明"算哪几类货、谁能用"，否则用户根本无从判断歧义在哪。
6. **长列表收敛成一行，缺配置必须显式说出来**（2026-09-21 第三轮，真机截图抓到）：
   规则卡原来把勾中的价目**全名全列**（勾了 8 条 → 占 4 行，卡片被撑高一倍，而且**一个价格都看不到**），
   勾 20 条就更没边。现在是一行：`价目 8 条：惠州江北 → 东莞樟木头 ¥62.00、惠州仲恺 → 深圳龙岗 ¥88.00 等`
   （**条数 + 前两条 + 价格**，`maxLines = 2`）。价格由后端 `template_briefs` 随出参一起给
   —— 它本来就在查那批价目行，**零额外查询**，别让客户端为了显示价格再打一轮。
   ⛔ 另一半更要紧：**没勾价目时原来什么都不显示**，用户看不出"这条规则还没配好、派单会全部进待定价"。
   现在是一行红字。判据：一张卡上"没配 / 没启用 / 没绑定"这类**空状态必须有人说话**——
   沉默等于让用户以为自己已经配好了。
7. **操作按钮贴最右、和最后一行信息同排**（2026-09-21 第四轮 —— 用户两句话拼起来才是完整口径）：
   他先说过「删除和编辑的按钮不要放在右边放在左边」，我照做成了**单独占一行、靠左**；
   他看完真机纠正：「编辑和删除移到**最右边**去……卡片**高度变窄**一点」。
   两句合起来的意思其实是 **别让按钮单独占一行**：
   `Row { 信息 Modifier.weight(1f); 按钮们 }` —— 信息吃掉剩余宽度、按钮被挤到最右，
   **卡片因此少一行**（真机 1080 宽：一屏从 3 张变 4 张）。
   ⚠️ 判据必须双向：红线里既断言"同排写法在"，也断言老的 `Arrangement.Start` **不在** ——
   只断言一边的话，把行改成单独一行靠左它照样绿。

⚠️ 这条规矩不限于价目：**任何"一张卡上放了很多字段"的列表**，先问"用户在这一屏上真正要做的决定是什么"，
把服务于那个决定的两三项放大，其余降级 —— 而不是把所有字段排成一列等宽小字。

### 4.17 手动记账：**能从库里选的就别让人手打**（账本「记一笔账」，2026-09-20 第七轮）

用户看着那个 `记一笔账` 弹窗说：

> 这个商品是**可以在现有的商品库进行选择的**。这一般情况下，假如**订单没有走**、但是有一笔账
> 是这样存在的；**未注册的话也可以直接填**，它会显示到列表上、**会自动帮他注册一个临时账户**，
> 也就相当于一个普通账户吧。然后**时间备注也是可以填的**；**他只要填数量、对应的价格是会有的**，
> 但是可能单价是不一样的 —— **单价是可以进行改的**，也就是预售价他可以进行单独调整。

三个字段各自的出处（这是"输入口径"这一类问题的通用解法）：

| 字段 | 从哪来 | 为什么不能是别的 |
|---|---|---|
| **商品** | **只能从商品库选**（复用同一份选品 UI，单选） | 手打会打出「红富士苹果 / 红富士 / 苹果」三个名字，库存与报表按名字分组时就变成三件货；单价、单位本来就挂在商品上 |
| **货主** | 选已注册的，**或直接填未注册的名字** | 没建过档的客户是真实业务（"来收一趟货"）。填了的名字就是**临时货主**（与「代理下单」同一套口径），下次在**同一个选择器的「用过的临时货主」段**里能再选到 —— 这就是他说的"显示到列表上、相当于一个普通账户" |
| **单价** | 选商品时**自动带出**（有专属价用专属价），**可以改** | 用户要的是"预售价可以单独调整"。⛔ 但他**手改过之后不许被拽走** —— 换货主时按"当前价是否还等于上一次自动带出的价"判断，否则等于悄悄改了他刚报的价 |

⚠️ "换货主"包括**换成未注册的名字 / 清空**：临时货主没有专属价，不重算的话价会**停在上一家的专属价**上
（真机实测：顺鑫蔬菜批发 荷兰豆 13.2 → 改成临时货主后仍显示 13.2，而正确价是默认 14.8）。
三个入口都必须调**同一处**重算（`repriceIfAuto`），否则"换个入口就少算一次"。

四条落地时最容易踩的坑：

1. **客户端不许自己算钱传上去**：`total` 交给后端用 Decimal 算（`unit_price × quantity`）。
   客户端 Double 乘一遍会出现 `36.900000000000006` 这种尾数进库 —— 这是"同一个数两处算法"那一课
   （见 `_tools/qa/_check_single_source.py`）。
2. **名册搜索走服务端**：名册一页有上限，本地过滤手里这一页的话，第 N+1 个人在客户端根本不存在 →
   用户会去"填一个新货主" → **同一个人两本账**。截断位与"没搜到"必须分开说。
3. **一笔账只记一件商品**：单选模式（再挑一件是**换掉**，不是累加）；多件＝多行账，
   而"一次点确认发多个请求"必然出现部分成功（本项目的规矩：批量动作要有数量上限与逐条汇报）。
4. **表单带选择器时用单独一页**，不要塞进 `AlertDialog`：全屏选品层套在弹窗里就是两层 modal 窗口叠着，
   而且字段一多弹窗会顶到屏幕边（与「新增开销」同一个结论）。

⚠️ 这条规矩不限于记账：**"这个字段的取值能不能从已有数据里选出来"**是每次做表单前该问的第一个问题。
手打的名字/编号在库里就是新的一行，而**两边都不报错**。

### 4.15 同一页上两个筛选控件**不许长一个样**：时间＝顶栏药丸、人＝侧边抽屉（2026-09-20 第五轮）

用户看完第四轮的真机，把三样东西一起否掉了：

> 那个折线图条形图还有扇形图，我们**直接去掉**就行了啊，其他的都也去掉……到时候
> **在报表中心看**就可以了。那个时间也太复杂了，这样的不好，换一种**崭新形式**，
> **但是时间和选择人物不要选择一样的展现形式**；选择人物，我们使用那种**侧边栏抽屉**，
> 可以在那里寻找人物，点击人物就可以了。（选择司机那一行）**假如司机多的话，
> 那我要选该怎么去选呢？**

四条可直接照做的规矩：

1. **同一页上两个筛选控件不许是同一个形态**：时间＝顶栏一个药丸（点开是一列档位清单），
   人＝页面上一行入口（点开侧边抽屉）。两个都做成"一排 chip"或两个都做成下拉，
   用户每次都得先分辨"这一排到底是什么"。
2. **名单长的那个用抽屉**（能搜、能滚、选中即关）；**档位少的那个用药丸＋清单**
   （9 档一屏放得下，不用横向滑）。
3. **抽屉里的搜索只筛名单，不改页面上的合计**（见 §4.14 第 3 条）。
4. **账本页不画图**：图归报表中心（那里有营业额/商品/司机三套现成的）。账本页只给数 ——
   要看图的动作是"去报表中心"，不是"在账本页切图表类型"。
   ⛔ 别为了"以后可能要用"把取数函数与配色表留着：没人调的图＝下一个人以为这一页还能切图
   （第五轮已把 `LedgerCharts.kt` / `ChartPalette` / `PieChart` 整块删除，
   `_tools/qa/_check_ledger_dashboard.py` 钉着"账本页一张图都不画"）。

5. **默认窗口要落在"有数"的那一天**（用户 2026-09-20 尾：「这些时间默认是**今天**的，
   如果今天**没有任何订单**的话，然后再是**昨天**，以此类推」）：
   打开页面先按**今天**拉一次（绝大多数时候就是它，屏幕立刻有东西），
   这一段没账才异步退档 **今天 → 昨天 → 前天 → 近 7 天 → 全部**；
   **点开某个人时也一样**（他这一段没单就退到他最近有单的那一天），否则点谁都是空屏。
   ⛔ 两条边界：**用户自己挑过档位（含手输区间）之后永不再自动改**（"默认"只在他还没表态时生效）；
   退档的判据必须与页面自己的取数**同源**（订单账看流水、司机账看结算分组、客户账看账户汇总——
   换个接口猜"有没有单"，会出现"退到的那一天页面还是空的"）。

6. **药丸是"页面级"的：切视图不许把它藏起来，页面里也不许再冒出一条胶囊行**
   （2026-09-20 22:5x，用户第三次点名）。原话：
   > 你这个**账目流水**为什么也不做对应的那个**右上角的时间图标**？他还是那个**滑动型**的。

   背景：货主账本顶栏那颗药丸外面套了一道 `if (!vm.showFlow)`——切进「账目流水」那个二级视图，
   药丸就消失，而流水页里又铺着一条 `DatePresetRow`，于是"同一个页面，一个视图有药丸、
   另一个视图是横滑的胶囊"。三条规矩：
   - 药丸**常驻顶栏**，任何视图（含二级视图）都看得见它；
   - 一个页面**只有一个**时间窗口：切视图**不换窗口**，换档时**两个视图一起重取**
     （只刷新一个的话，切到另一个会看到上一个窗口的数——药丸上却写着新窗口，两个数都不报错）；
   - 账户流水的 `entry_date` 与订单的"送达日"本来就同源（`services/ledger_sync.py`），
     共用窗口**不会让任何一边少算**；反过来"两个视图各看一段时间"才是假的。
   ⚠️ 判据可 grep：账本类页面里**不该出现** `DatePresetRow`（它只属于筛选条）。

7. **2026-09-22：两个订单列表也照这条改了**（派单员「订单管理」/ 货主「我的订单」）。
   用户原话：「他如果点**已送达**的话，他会有一个…那个**时间**，我们就**复用我们那些代码和形式**
   在**右上角**，那个有**预选也可以自定义时间**」「**货主的那个时间也移到那上面去**」。落地面：
   - 时间窗口从**列表第一行的横滑胶囊**（`DateRangeFilter`）换成**顶栏药丸**
     （`DatePresetPill` + `DateFilterDialogs`），页面里那条胶囊行整条删掉；
   - 药丸只挂在**带日期窗口的档位**上，判据是**档位自己**的标记
     （`ui/common/OrderTabs.kt::OrderTab.dated`）—— ⛔ 不许写 `tab == 3 || tab == 4`：
     档位顺序一动，窗口就会**静默挂到别的档上**（本轮货主那列就挪过一格）；
   - **默认档 = 今天**（用户：「时间默认的是今天」）→ 空态文案**必须指到那颗药丸**。
   - **「全部」也要有时间筛选**（用户 2026-09-22 第二轮：「那个只针对…像是**全部、已完成**的
     （才）要选择时间。对，**全部我们也要有时间的筛选**」）—— 它是"找某一单"最常用的入口；
     **「派单中」「已接单」不给**（「他属于**正在进行**啊，所以他是**不会有选择时间**」：
     进行中的单本来就该全都在眼前，套一层窗口就是"积压的老单不见了"，而界面上一个字都不说）。
   - **自动挡（自动退档）要做**（用户：「他们是有那个**找订单的规则**，也就是**自动挡**，他需要做」）：
     进带窗口的档位时先只**探测**哪一档有单（今天→昨天→前天→这周→上周→近 7 天→本月→上月，
     都没有就不带日期条件），定下来之后**只取一次数**（不是"先按今天拉一次"——那是"闪两下"）；
     用户**手动挑过就永不自动改**。
     ⚠️ **每次进带窗口的档位都要重新找**，不是"整个页面只挑一次" —— 真机上当场抓到过：
     先点「全部」（挑到「今天」）再点「已送达」就不再挑了，「已送达 + 今天没单」**停在空列表上**，
     正是用户要避免的那个画面。阶梯是共享的 `DatePresets.ORDER_PRESET_LADDER`

   - **两个订单列表的这套状态机是同一份**：`ui/common/OrderWindowViewModel.kt`

### 4.11 AI 圆钮坐在凹口里，凹口两侧必须是**曲线过渡**（2026-09-20）

用户看真机截图：
> 它那个圆圈图标它是被 2 个矩形像是框在一起的…就是它那个角是尖尖，把它做一个曲线过渡。

- 形态：导航条上沿在圆钮位置**凹进去**（`ui/nav/NotchedNavBar.kt::NotchedBarShape`），
  圆钮不是"贴在平沿上"。圆心在栏**内侧**（半径−凸出）。
- 两侧的角**必须**是同时与上沿、大圆**相切**的圆角，而且半径只有唯一一个正确取值：
  **圆心深度**（= 钮半径 − 凸出，真机 17dp）。两个相切条件把"圆角半径"和"切点落在大圆哪儿"
  锁成一一对应（`sin γ = (圆心深度 − f) / (半径 + 缝 + f)`）：
  - 取大了取不了（切点会掉到大圆下半圈，缺口被啃掉一块）；
  - **取小了就会留下一小块"喙"**：切点退回大圆上半圈，旧形状那道方角只被削掉一半
    （试过 6dp，真机上喙宽 1.2dp），而且旁边多一条缝。所以这个半径**不写成常量**，
    由相切条件解出来——写成常量等于给"切点落在哪儿"开了一个能改错的旋钮。
- 必然的后果：上沿开口被撑宽（34dp → **55dp**）；那几 dp 正是原来尖角所在的位置，
  所以看着是"角被抹圆了"，而不是"缺口变大了"。开口 55dp < 左右两个 Tab 图标内沿 60dp ✓。
- ⚠️ 这块**画错了不报错、不崩、肉眼还分不清**（第一版把圆心算到栏外，坑全被圆钮盖住）。
  所以判据不落在"像不像"，而落在**相切关系 + 像素**上：单测 `NotchedBarTest`、
  红线 `_tools/ai/_check_nav_guardrails.py`、像素量尺 `_tools/notify/_measure_notch.py`
  （量"缺口边缘从 0 爬起来要走多远"——圆滑是 ≈5dp，尖角是 0dp），
  外加一张**已知答案的对照图** `_tools/notify/_notch_render.py --check`
  （同一套公式画"带过渡/尖角"两张，要求量尺前者过、后者挂）。

### 4.19 「一行放不下怎么办」：**换行 或 整条滑动**（⛔ 不缩字号、不截断）—— 2026-09-22 定成全局规范

用户原话（先说要做"等比缩放"，看到坏屏后自己把口径改掉）：
> 「所有卡片样式要根据手机的不同的大小来做一个适配……比如说就是正常的一种缩放吧，svg 啊的一种形式」→
> 「**我们的小屏整体的样式是不能有改变的**……甚至那个小屏啊，我发现，我们这些**字体都已经看不清了**……
> 我们要去**权衡一下大屏小屏**……你要看**其他人的方案**是怎么做的，尤其是**大厂**……
> **他不可能每度做一遍**吧」。

**结论（先按官方文档把"等比缩放"这条路否掉，再动手）**
1. ⛔ **不做"按屏宽等比缩放字号/间距"**（把 dp/sp 乘 `屏宽/设计稿宽`，社区叫 AutoSize）。
   [窗口大小类别](https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes)
   把 **宽度 < 600dp 的手机竖屏全部算同一档（紧凑）**，断点只有 600/840/1200/1600 ——
   也就是说**手机之间本来就不该做两套版式**，"每个机型适配一遍"从规范上就是错的。
2. ⛔ **不缩小字号**。[网格和单位](https://developer.android.com/design/ui/mobile/guides/layout-and-content/grids-and-units)
   写明 dp 管"跨屏幕物理一致"、**sp 管"跟随用户字体设置"**；
   [Android 14 起](https://developer.android.com/about/versions/14/features)支持字体放大到 **200%**，
   非线性曲线的唯一目的就是"别让大字被截断"。把老人特意调大的字压回去，与这条正好相反。
   ⚠️ 顺带一个**量具教训**：验收小屏要**只改 `wm size`、绝不改 `wm density`**（工具 `_tools/qa/_screensize.py`）。
   改 density 会把字渲染成**只有 57% 物理大小**，看起来"字体全变小了"——那是量具造成的假象，
   真实 320dp 小屏的字号与大屏**物理大小一模一样**（320dp ＝ 2 英寸）。
3. ⛔ **不截断**，尤其状态/档位这种"少一个字就是另一个意思"的词。

→ 于是"放不下"只剩两条路：**换到下一行**、或**整条横向滑动**。两种做法都要先知道"到底放不放得下"，
所以全 App 只有一把尺：`ui/common/Adaptive.kt::rememberTextWidth()`（用 `TextMeasurer` **实测**，
不按字数猜 —— 中文字宽≈1 个字身、数字/字母只有 0.55 左右，估出来的迟早算错某一档）。

**两条形态的落地（放得下时与以前逐像素相同，这是硬要求）**

| 位置 | 放得下 | 放不下 |
|---|---|---|
| `SegmentedStatusTabs`（档位条） | 等宽平铺（原样） | **整条横向滑动**，每格按内容宽度 |
| `OrderCard` 的单号 + 状态徽章 | 单号吃剩余宽度、徽章贴右（原样） | **单号独占一行 + 徽章右对齐到下一行** |

真机实测（判据 `_tools/qa/_check_adaptive_layout.py` 43 项 + 反向验证 11 种注入）：
- 320dp + 系统字号 1.3 时，档位条原来把「已接单」切成「**已接**」、「已送达」切成「**已送**」——
  **少一个字就是另一个意思**，用户根本分不出这两档，而界面上没有任何提示说"这里被吃掉了两个字"。
  现在标签完整、放不下的那一格半露在屏幕边缘（这就是"可以滑"的提示）。
- 单号是 21 位，320dp 下和徽章挤不进一行时会被折成「…31271」+「78」；现在是单号独占一行。

**⚠️ 这一节我自己踩过的两个坑（都写成了判据，别重复）**
- **量宽度别把内边距算进去**：等宽那一支的文字**不加左右内边距**，如果量的时候算上、画的时候也加，
  等于把每格的内容盒子挤窄 28dp → **411dp 上六个档位全被切掉最后一个字**，而"放得下"的判定还认为自己对，
  **两边都不报错**。判据：`pad = if (fits) 0.dp else TAB_H_PADDING` + 量的必须是纯文字宽。
- **可伸缩的文本必须显式 `weight(1f)`**：不给 weight 时它会去吃宽度、把**后面的兄弟**挤瘪。
  真机证据（**411dp 下就能看见**）：开销卡的「关联订单 SO2026…」把右边的日期挤成一条缝，
  一个 `2026-09-19` 被折成 `202`/`6-0`/`9-1`/`9` **四行**。
  存量处数记在 `_tools/qa/_adaptive_squeeze_baseline.txt`（18 个文件 / 36 处）——**只许往下减，涨一处就红**。

**大屏（≥600dp）怎么办**：只做一件已经落地的事 —— 入口网格列数按宽度算
（`ui/common/EntryGrid.kt`，`maxOf(2, 屏宽/160)`）：**手机恒 2 列（外观零变化）**，平板才 3 列以上。
⛔ 不用 `GridCells.Adaptive(minSize)`：它在 320dp 会掉到 **1 列**，那就是"小屏样式变了"。

## 5. 用户明确偏好（改 UI 前必看）

### 5.0 ⛔ **分组一律白卡，不许用描边框当分组**（2026-09-22 用户定成全局规范）

用户对着一屏"新增线路"（那一屏每个字段都是一个描边输入框、浮在偏灰蓝的底上）说：

> 「…只是用**线框**框起来的话太不美观了，而且也不够**醒目对比**，所以把他们改进这种
>  **白色的卡片样式**…**这就是个设计规范，包括以后也是这样子啊，所有都要这样子去改**」

**规范**（三个都要满足，缺一个就还是"框套框"）：
1. **分组容器 = `SectionCard`**（白卡：圆角 16、极轻阴影、**无边框**，靠灰底分层）——
   不许用 `BorderStroke` / 描边 `Surface` / 一堆 `Outlined*` 拼出一个"分组"；
2. **组标题在卡外**（一行小字，可带一个语义色小图标）；放进卡里就又多一条"框里的标题行"；
3. **卡里只放共用行**（`ui/common/FormRows.kt`：`FormInputRow` / `FormTextAreaRow` /
   `FormPickRow` / `FormActionRow` / `FormSwitchRow`），**一个描边输入框都不许有** ——
   值本身就是占位符（"请输入商品名"写在右边灰字里），不需要再画一个矩形。
4. 分组之间的间距 **14dp**、组标题与卡 **6dp**（写死在用法里，别一页一个样）。

**为什么这条值得立成规范而不是"这次改好看点"**：同一个人在同一批截图里已经为它说过两次 ——
第一次是对「新增商品」（"不是很好看，也太乱了"，根因就是**三层框叠加**：
描边输入框 → 外面套描边卡片 → 每个字段再跟一句灰字），第二次是这一屏。
两次的修法是同一个（白卡 + 无边框行 + "值即占位符"）。

### 6.1 外观模式（白天 / 夜间 / 随日落自动）

「我的」页两行（三端共用同一个页面，所以三端都有）：

| 行 | 行为 |
| --- | --- |
| **随日落自动切换**（默认**关**） | 打开后按当天日出日落自动切：天黑（太阳高度角 −6°，民用暮光）切夜间、天亮切回白天。右侧写清"下一次什么时候切" |
| **夜间模式 / 白天模式** | 手动开关。**自动打开时这一行置灰**并写明「已交给自动切换」——否则会出现"点了一下又自己弹回来" |

- 判定在 `core/SunClock.kt`（纯函数）：界线 = 民用暮光（太阳高度角 −6°）；**有手机定位就用真实经纬度**（`core/SunLocation.kt`，拿不到就退回"时区中央经线 + 35°N"估算）；定时器 `ui/theme/AutoSunTheme.kt` 挂根节点；状态在 `ui/theme/Theme.kt` 的 `ThemeMode`（明暗与自动开关都落盘）。
- 那一行右侧会**如实写明依据**：「按定位」还是「时区估算，开定位更准」——两个精度差很多（新疆约 2 小时），含糊过去等于骗人。
- ⚠️ 定位失败时高德会回调 `(0,0)`（不是 null）：不校验就会算出错 8 小时的日落**且不报错**，所以坐标必须过 `SunLocation.isPlausible`。
- 自动开关是**设备级**的（跟账号无关，换账号不变），和系统"深色模式"的直觉一致。
- ⛔ 暗色下必须还能分层：`SurfaceDark` 必须亮于 `BackgroundDark`，卡片补淡描边（阴影在暗色下看不见）。
- 详见 `AI_ASSISTANT_PLAN_V3.md` §51 与红线 §21。
