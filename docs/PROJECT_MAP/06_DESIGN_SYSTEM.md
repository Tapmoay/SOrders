# 06 UI 设计与语义色体系

<!-- ref-prefix: android/app/src/main/java/com/tapmoay/sorders/ -->

> 标准：**苹果结构 × 日本配色**（japanese-street-color-system）：Apple HIG 结构/层级 + 日本街头广告式一色一功能高饱和语义色（面向老年/低视力用户，亮色高对比）。

## 1. 核心设计原则

- **一色一功能**：每个功能/模块有唯一语义色，跨端同功能同色（下单绿/账本橙/消息红/地址湖蓝）
- **背景分层**：页面底 `BackgroundLight=#F2F3F7`，卡片白底圆角（`MaterialTheme.shapes`），信息用 SectionCard
- **低调卡片**：白底 + 浅描边（#ECEFF5）或极浅阴影；不要重边框/大圆/浓渐变
- **文字层级**：关键是重要的数字/名称用色加粗，次要说明用灰色 `onSurfaceVariant` 小字
- **按钮风格**：默认 Material3 样式（用户否决过大圆圈/胶囊大按钮）；加减等主操作色可自定义淡蓝底
- **弹窗**：选择/确认类用 `AlertDialog`；表单类用 Drawer/ModalBottomSheet 由场景决定

## 4. 具体业务用色约定（报表/订单页）

- 金额（钱）：橙 #FF9500；小计/合计 同理
- 数量：蓝 #1E6FFF（如 "· 数量 5"）
- 商品名：紫 #8455E6（SemiBold）
- 货损/异常：红 #FF4D4F/#E53935
- 毛利/成功：绿 #00B578
- 加减按钮淡蓝：底 #E8F2FF / 图标 #1E6FFF（**用户明确要求保留，勿改回青绿**）
- 工资制司机：灰 #8A8A8E 标注「工资制」；计件司机待结运费：橙红 #FF6B2C

### 4.1 商品卡上那四个数字（2026-09-19 用户要求"用对应的语义色和图标"）

用户原话：「那些信息是在商品管理中非常重要的，不一定非要等编辑才能看得到，
我们要用对应的语义色和图标在它的名字的下面进行显示，让人一眼就能看出来」。
实现是 `ui/dispatcher/ProductsScreen.kt::ProductFacts`，**配色只有那一处**：

| 信息 | 颜色 | 图标 | 为什么是这个色 |
|---|---|---|---|
| 售价 | 金橙 `MoneyOrange` | `Sell` | 系统里"钱"的语义色（与账本/报表/小计同色） |
| 库存 | 蓝青 `#00BCD4` | `Inventory2` | **库存管理模块的语义色**（跨端同功能同色：这个数字属于库存管理） |

⚠️ **卡片上只有这两个数字，而且一个一行**（用户 2026-09-19 的三条要求叠在一起）：
- **没有「分类」**：「既然已经在左边显示了分类，那右边的商品就不需要显示分类了」——
  分类由左边那根导航条（`CategoryRail`）表达。代价：「全部」那一档下卡片上看不出
  每件商品属于哪一类，想知道归属就点左边对应的分类。
- **没有「成本」**：「商品管理界面不要有成本价的显示，成本价是要在编辑里面才会有」——
  成本是内部数、不参与对客户报价，要看/要改都在「⋮ → 编辑」，进货时也能顺手改。
- **一个一行**：「那个库存在成本价的后面，这个不要有，他们全在成本价的下面」——
  原来用 `FlowRow` 流式排，`成本 ¥0.00` 短的时候 `库存` 被挤到同一行、长的时候又自己换行，
  **每张卡长得都不一样**。现在固定一行一个：布局可预测，数字还在竖直方向对齐成一列
  （扫一列价格比扫一片流式文本快）。

⚠️ **库存还会按状态变色**：`stock <= 0` → 红 #E53935（断货）、`<= lowStockAlert` → 黄 #FFB300。
这两个颜色不是装饰，是"这一行要你处理"的信号 —— 派单员扫列表时靠它决定先看哪几个。

### 4.0 卡片右侧那一列：`⋮` 在上，「改价」在下（**紫色**）

用户 2026-09-19：「商品右上角不是有 3 个点吗？那是我们的正常设置，我们在它的下面——
因为下面比较空嘛——在下面再加一个改价，这个改价就是改默认的售价，方便嘛、快捷」。

右侧固定一列（46dp）：顶上是 `⋮`（全部动作都在菜单里），**它下面那块本来是空白**，
现在放「¥ 改价」——一点就弹**只改默认售价**的小窗。三个理由：
1. **改售价是最高频的日常动作**（进价一变就要改），而走「⋮ → 编辑」要打开整个抽屉、
   滚到价格那一段、改完再保存；
2. 它**不占新地方**（那一列本来就空着），卡片不会因此变高；
3. 保存走 `PATCH /products/{id}` 的**部分更新**（只放 `default_unit_price`），
   不会顺手覆盖别人改过的名称/成本/库存。

⛔ **颜色必须用商品管理的模块色紫 `ProductPurple`，不能用钱的橙**（用户当天就指出来了：
「那个改价的按钮换个颜色，它与那个售价的颜色撞了一个色，换语义颜色」）——
同一张卡上「售价」那个数字已经是 `MoneyOrange`，再拿它染按钮就撞了；而这个按钮是
**商品管理里的一个操作**，用模块色正好（紫色本来被卡片上的分类 chip 占着，分类删掉后空出来了）。

⚠️ **弹窗预填的价要用 `trimMoneyZeros`，不能用 `formatMoney`**：库里的单价列是
`Numeric(14,4)`，直接显示是 `12.5000`；而 `formatMoney` 只留两位小数，会把 `12.3456`
显示成 `12.35` —— 在一个**可编辑**的价框里那等于骗人（用户不改直接保存，价就真的变了）。
显示用两位、编辑用去尾零，两者的区别就这一条（`util/Money.kt`）。

### 4.2 卡片上的动作：三个以上就收进「⋮」

用户 2026-09-19：「右边 3 个按钮太占位置了，把在保证按钮性的同时，又让他不占位子」。
商品卡与分类行都改成 **右上角一个 `MoreVert` + `DropdownMenu`**（动作一个不少，
可发现性靠标准「⋮」），腾出来的整条右边还给信息。
**判断依据**：横排的 `IconButton` 每个约 48dp，三个就是 144dp —— 那正好是商品名+数字被挤成
两行灰字的宽度。反过来说，**只有一个主操作时仍用显式按钮**（不要为了统一把所有东西塞进菜单）。

### 4.3 一个页面有两个并列入口 → 底部一条栏，不要两个角各一个

用户 2026-09-19：「给那个商品管理界面的下面加个导航栏，左边分组管理、右边商品新增，
那个 + 把它改成商品新增…**两个导航栏做得美观一点**」。

搬之前是**顶栏一个文字按钮 + 右下角一个 FAB**，两个毛病：
视线在屏幕上要跑两趟（一个在顶、一个在底）；FAB 还压着列表最后一张卡 ——
所以列表尾巴上被迫留了一句 `Spacer(72.dp)` 让位，而那句话在任何一页上都没有意义。

落地写法（`ProductsScreen.kt::ProductsBottomBar`，直接照抄）：

| | 左（次） | 右（主） |
|---|---|---|
| 组件 | `OutlinedButton` | `PrimaryActionButton`（全项目主操作同一组件） |
| 外观 | 1.5dp 语义色描边 + 同色文字/图标 | 语义色实底 + 白图标 |
| 宽度 | `weight(1f)` | `weight(1.4f)` |
| 高度 | 56dp（与主按钮同高，视觉成对） | 56dp |

四条纪律：
1. **一实一虚**才叫"美观"—— 两个等宽同色的按钮看不出哪个是主操作；
   判据是"哪个是日常动作"：新增商品天天点，分类管理偶尔动一次。
2. **染模块语义色**（这里是 `ProductPurple`），不是默认主题蓝 —— 一色一功能。
3. ⛔ **不许用别的功能的颜色**：同屏「售价」已经是钱的橙，再拿橙染按钮就是撞色
   （用户当天刚为这件事让改过一次，见 §4.1）。
4. 这一栏**不是** M3 `NavigationBar`、不会自己处理 insets → 自己加 `navigationBarsPadding()`
   （App 是 `enableEdgeToEdge()`，不加会被系统导航条压住半截）。
   搬完之后 Scaffold 的 padding 已经扣掉这条栏的高度，列表里那句让位用的
   `Spacer(72.dp)` **要一起删掉**，否则列表底下凭空多一块空白。

### 4.4 搜索框：按人搜只有一份（`SearchField`），名册页走服务端

用户 2026-09-19：「还有其他的比如说，**司机管理**啊**账户管理**啊。这些也要添加搜索键。
然后这个搜索键可以根据他们的**名称**还有**电话号码**以及**电话号码的后 4 位**进行搜索」。

| 判据 | 规定 |
|---|---|
| 组件 | `ui/common/Components.kt::SearchField`（放大镜 + 入框即出 `✕` 一键清空 + 圆角 12 与 `SoTextField` 同族） |
| 提示文案 | 默认取 `core/UserSearch.HINT`（「搜姓名 / 手机号（后 4 位也行）」）—— **各页不许各写一句**：用户得先知道能按后 4 位搜才会去试 |
| 匹配规则 | `core/UserSearch.matches`（姓名 或 手机号，**子串**；后 4 位据此天然命中）／服务端 `app/core/user_search.py` |
| 取数位置 | **数据一次回全量的**（账本 `/ledger/accounts`、`/freight-settlement`）→ 本地过滤；**一页有上限的**（`/users` 最多 500）→ **必须**服务端 `?q=` |

为什么"名册页必须服务端"：一页 500 条，本地过滤时第 501 个人在客户端**根本不存在**，
而"列表里没有"会被读成"没有这个账号" → 再建一个 → 撞手机号唯一约束。
账本那两张接口本来就一次回全量，本地过滤反而更快（不必每敲一个字打一次后端）。

⚠️ **搜到 0 条时的说法要跟着变**：服务端搜过了就说"服务端按姓名/手机号搜过，确实没有"
（这是一句**结论**，可以照着去新建）；本地过滤只能承认"这一页里没有"。
⛔ 提示语里带**地址**的框（线路 / 地点 / 地址库）是**另一条规则**，不许套这个组件。

### 4.5 仪表盘：一屏看完各自的数，不要"先勾选再看"

用户 2026-09-19（**推翻**了他自己上一轮要的"搜索 + 多选"）：
「假如客户非常多司机非常多，那用户要是一个一个去选的话，那要有多麻烦啊。
**所有的账本你可以一个仪表盘的思维进行去构建**」。

落地写法（`DispatcherLedgerScreen.kt::KpiBlock` + `LedgerDashboardCard`）：

```
批发商账合计（当前时间范围）      ← 一行小字，说清"这是什么的合计"
¥12,345.00                        ← 钱：单独一行、最大最粗、橙（钱的语义色）
3 个账户 · 共 19 笔                ← 一行小字，解释上面那个数是怎么来的
[🔍 搜姓名 / 手机号（后 4 位也行） ✕]
```

三条纪律：
1. **钱单独一行**（沿用 §4.1 的"一个数字一行"）：三个数并排堆成一行小字，既不突出钱，
   也看不出哪个数在解释哪个。
2. **搜索之后合计跟着变**，并把「全部 N 个账户合计 ¥X」一起说出来 ——
   不说的话用户会拿筛出的那个数当总额去对账。
3. ⛔ **不要再加"勾选账户"这类控件**：一屏已经能看到每个账户各自的数了，
   再让人一个个勾，把力气花在重复劳动上；chip 上的"名字 + 金额"与列表里的是同一份信息，
   放两处必然出现"两边对不上"的困惑。红线 `_tools/qa/_check_user_search.py` 钉着它不许长回来。

### 4.6 两栏版式（"左边一个篮子、右边是它的内容"）

用户 2026-09-19 连着为三处点名了这个版式，原话都是"**像商品管理那样**"：

| 页面 | 左栏装什么 | 右栏装什么 |
|---|---|---|
| 商品管理 / 库存管理 | 商品分类 | 商品（卡片） |
| 司机运费结算 | 司机（名字 + 「¥860 · 21 单」） | 那位司机的**统计**（上）+ **价格明细**（下） |
| 下单页地址库抽屉 | 线路 / 我的地点 / 共享地点 + 自定义分组（**一格都不带"N 条"**，见下） | 对应的地点行 |

**左边那一列只有一份实现**：`ui/common/Components.kt::MasterRail(items: List<RailItem>, selectedKey, onSelect, accent)`。

- `RailItem(key, label, subtitle)`：**key 与显示名刻意分开** —— 司机那一栏的 key 是 `d|12`、
  屏幕上是「王建国」；拿显示名当 key，两个同名司机就会互相点亮（本机 293 个司机，重名不是假想）。
- **行高自动**：有 `subtitle` → 60dp，没有 → 52dp。有副标题还压 52dp，两行字会挤在一起，
  而"挤"在老人用户那里等于看不清。副标题强制 `maxLines = 1` + 省略号：让它折行会把整列节奏顶乱。
- **选中态 = 白底 + 左侧一条语义色竖条**（外卖 App 的通用写法）。语义色由调用方给：
  商品/库存/地址用主题主色，运费结算用本页的珊瑚橙 `#FF8A65`。
- ⛔ **两种排序不要混**：左栏的顺序就是右栏的顺序来源，**不许在右栏再排一次**
  （同一批数据两种顺序 = "我点的那个怎么跑到下面去了"）。
- ⚠️ **搜索框放在左栏上面、横跨整页**（与 §4.4 同一条理由）：左栏是"有哪几类"、
  搜索是"那个东西在哪"，两个维度；塞进左栏会被压成半宽，而且左栏为空时它跟着消失。
- ⚠️ **不是所有"东西多"的页面都该上两栏**：账本管理试过一版（左栏放 4 类账 + 4 个工具），
  用户看真机后否掉了，改成"工作台一格 → 账本管理**入口页**（报表中心那种形式）→ 账本页只看账"，见 §4.13。
- ⛔ **左栏要不要带"N 条"——按"这个数是不是一眼判断的依据"分，不是按"有没有地方放"**：

  | 左栏 | 副标题 | 为什么 |
  |---|---|---|
  | 下单页地址库（线路 / 我的地点 / 共享地点 / 自定义分组） | **一格都不带** | 用户 2026-09-19 看截图后点名：「那个分组下面不要显示有多少条啊，**这是多余信息**」。左栏回答"有哪几类"，条数回答"这一类里有多少个"——后者点进去一眼就数得完 |
  | 司机运费结算 | `¥860 · 21 单` | 这一页是结算，"这位司机多少钱"**就是**扫这一列时在找的东西，不是点进去才知道的细节 |

  ⚠️ 代价要说清：`MasterRail` 的**行高是整列统一的**（`twoLine = items.any { subtitle != null }`），
  只要有一格带副标题，整列六格全是 60dp、其余五格的第二行空着。真机截图里那五行
  「8 条 / 9 条 / 3 条 / 0 条 / 0 条」就是这么把一列撑高的。所以「管理分组」那格也不再挂
  「新建 / 排序」——它是**去的地方**不是**数据**，挂着只会让"整列里独独这一格是两行"。

`CategoryRail`（商品分类那一列）现在只是 `MasterRail` 的一层薄包装 ——
原来那段 Box/Text 是照抄的写法，抄到第三遍行高就会各自跑偏。

### 4.7 长地址从**尾部**省略（`TextOverflow.StartEllipsis`）

用户 2026-09-19 看下单页地址库截图后点名（原话）：

> 「它后面会有省略……省略是可以的，但是你要**从后面往前显示**。意思就是说，我们也首先肯定知道的是
> 这里面的那个地点嘛，**前面的前缀基本上不需要知道**，所以那个最明显的那个有颜色的标题
> 应该是**最后面**的那个地点」。

同一屏的地址**开头全是同一个前缀**（「北京市顺义区……」），真正区分彼此的只有**最后一段**
（村 / 小区 / 门牌 / 楼栋）。所以同一行里两段的省略方向**故意不同**：

| 位置 | 省略方向 | 理由 |
|---|---|---|
| 地点/线路的**标题**（湖蓝加粗那一行） | `TextOverflow.StartEllipsis`（省掉**开头**、留住尾部） | 标题常常**本身就是一串地址**（司机补录、共享地点进来的记录，`name` 就是详细地址）；按常规的尾部省略，真机上八行全是「北京市顺义...」，看八行等于没看 |
| 标题下面的**详细地址**（灰字那一行） | 仍然是尾部省略 | 它是"完整地址"，要从头念才知道在哪；而且它 `maxLines = 2`，两行基本够用 |

- ⚠️ 用系统自带的 `StartEllipsis`，**不要**自己写 `takeLast(n)`：按字符数截在中英混排上会截在半个词里
  （门牌号里常有 `A座 3 单元`、`Building 7`），而 Compose 的省略是**按排版结果**算的。
- ⚠️ 顺带修掉的一处**宽度对半分**：标题原来是 `Modifier.weight(1f, fill = false)`，
  后面还跟着一个 `Spacer(Modifier.weight(1f))` —— 两个 1 权重把可分配宽度**对半分**，
  标题只拿得到一半（这也是「北京市顺义...」明明右边还空着却被截断的直接原因）。
  标题改成 `weight(1f)` **独占**后同一行能多显示一倍的字；右侧的「有导航」不带权重，仍然贴边。
- ⛔ **别把 `Spacer(Modifier.weight(1f))` 加回来**——它看着"只是顶一下右边那两个字"，
  实际是在跟标题**抢宽度**。要让右端贴边，靠的是"标题独占剩余宽度"，不是再加一个权重。

### 4.8 错误的**落点**：表单的错画在表单里，页面级的错只管"这一页没加载出来"

用户 2026-09-19 报的缺陷（原话）：
> 「我新建了一个地点，但是我没有填任何地址。直接点击保存，然后再返回去的时候，
> 它那个地点库的**所有列表全消失了**，需要重新连接」。

**不是断线**，是那句话画错了地方：表单的校验错误写进了**页面级**的错误状态，
而页面级错误会把整页换成「一句话 + 重试」（`ErrorView`）。同一句话造出两个假象：

| 用户看到的 | 真相 |
|---|---|
| 点「保存」**没有任何反应** | 那句话画在抽屉**背后**，被抽屉盖住了 |
| 关掉抽屉后**三个列表全没了** | 那句话还挂着，整页被 `ErrorView` 顶掉；一条数据都没丢 |

所以一个页面上**必须有两个分开的错误状态**（`_check_ai_guardrails.py` 里那条
「加载错误与动作错误分开」钉的就是这件事）：

| 状态 | 谁写它 | 画在哪 |
|---|---|---|
| `loadError` | **只有** `load()` | 整页换成 `ErrorView` + 「重试」 |
| `formError` | 抽屉/弹窗里的校验与保存失败（`ui/common/Components.kt::FormErrorLine`） | **在那张抽屉/弹窗内部**、提交按钮上方 |
| `notice` | 行上的「删除 / 设为默认」这类**没有表单可挂**的动作 | Snackbar（`OneShotSnackbar`，用完置回 null） |

- ⛔ **打开表单时清掉 `formError`**：不复用上一张表单的报错（不然一打开就顶着一行红字）。
- ⚠️ 另一条同源的脆弱：一个页面要拉的**几个列表必须各自独立**地加载 ——
  原来那三个列表串在**一个** `try` 里，任何一个失败整页就变错误页，
  另外两条明明拿得到的数据也一起看不见了。现在全挂才算"这页没加载出来"，
  只挂一部分就照常显示 + Snackbar 说一句。

### 4.9 数字的口径词必须跟着**实际窗口**走（2026-09-20）

一个页面上的数字只要依赖某个时间窗口，写它口径的那几个字就必须来自那个窗口本身。
运费结算页原来把「本月」写死在**四处**（标题 / 仪表盘 / 统计块 / 空列表文案），
加上"自己选一段时间"之后，这四处的数字可能根本不是本月的 —— 而**用户看不出这一点**
（数字不会自证是哪一段的，页面说"本月"他就当成本月）。

实现：`FreightSettlementViewModel` 只暴露两个**由窗口算出来**的词 ——
`periodLabel`（标题与药丸上的短标签：`本月`/`上月`/`上上月`/`09-01~09-20`）与
`periodWord`（句子里的口径词：`本月`/`所选区间`）；页面上**不许再出现写死的"本月"**。

- ⚠️ 自定义区间时**把那段日期显示出来**（药丸上就写 `09-01~09-20`，不是"自定义"三个字）：
  一页上至少要有一个地方写着"这些数字是哪一段的"，否则「共 3 位司机 · 应得 ¥860」没有范围可对。
- ⚠️ 自定义起止按**当地整天**取（`00:00:00` ~ `23:59:59`）：不补时间的话"选到今天"会把今天
  送达的单整批漏掉，而界面上看不出少了一天。后端在窗口两侧都换算成 UTC（`to_utc_naive`）。
- ⚠️ 换了时间窗口要**清掉左栏的选中**：那个 key 在新窗口里可能不存在，界面会"回落到第一位"，
  留着旧 key 会让左栏高亮和右栏内容对不上。

### 4.10 文案：常驻"几个字"，解释走「最多出现三次」（2026-09-20）

用户原话：
> 有些功能不需要说太多，只需要一个简单的字、简单的一句话，大概字数最多是 7 到 8 个字就可以了…
> 比如说共享库，本来就写了一大堆话在下面，没必要，直接删掉就可以了。
> 或者你可以这样子：第一次和第二次的时候它是出现在那里，下次再点击的时候它就不会有了…
> 第四次就不会有了。

于是界面上的文字分成两类，各归各的：

| 类型 | 例子 | 规矩 |
|---|---|---|
| **常驻的数 / 标签 / 按钮 / 行内说明** | 「地点名」「我到了，补导航」「已在共享库里」 | **≤ 8 字**。它是给**已经会的人**看的，不是每次都重新教一遍 |
| **解释"按下去会发生什么 / 这个数是哪来的"** | 「存三处：这单 / 货主库 / 共享库」的补充句 | 走 `ui/common/Components.kt::HintOnce`：**前 3 次出现，第 4 次起消失** |

- 实现：`core/HintPrefs.kt`（SharedPreferences 计数，**同步可读**——合成时就要决定画不画，
  用 DataStore 会"先画一帧再消失"，比不显示更难受；与 `AlertPrefs` 同一个理由）
  ＋ `ui/common/Components.kt::HintOnce(prefs, key, text)`。
- ⚠️ `key` 是**永久身份**（`"order.nav_block"`），不是屏幕上那句话：改文案不该让用户重看三遍，
  也不该蹭别人的额度。
- ⚠️ 计数在**进入这一次**就 +1：用户在几个页面之间来回切，那就是几次"看到"。
- ✅ **「我的 → 提示」**（默认**关**）＝打开后不走这个机制、一直显示。
  给"想不起来当初那句话怎么说的"的人，也是这条规则真机验收的入口。
  （标题只留两个字：用户 2026-09-20 看真机截图说「你只要把那个标题改成提示就可以了」——
  原来写「提示一直显示」，和副标题的"一直显示"重复了一遍。）
- ⛔ **不放宽的那部分**：错误/校验信息（"一句能照着做的中文"）、数字的口径说明
  （毛利只按有成本快照的行算…）**照旧要写清**——它们不是"教学"，是"这次到底发生了什么"。
  这一条只收**教学/引导**类的常驻长句。

### 4.12 图表：三种图可切换，但**数目只许一个来源**（2026-09-20）

用户 2026-09-20 对派单员账本的要求：「最上面是有日期还有预设的日期…下面就是个圆形扇形统计图
和一个条形统计图…**3 个图可以进行切换**，折线条形扇形」。落到规则上是四条：

1. **三种图共用一件事**：`ui/common/Charts.kt`（`LineChart` / `BarChart` / `PieChart`）。
   ⛔ **别处不许自己 `Canvas(` 画图**（红线 `_tools/qa/_check_ledger_dashboard.py` 会红；
   白名单只有 `util/Watermark.kt`＝导出图片的水印）。
2. **图上的数必须与屏幕上那个合计同源**：取数一律走各页的**纯函数**（账本是
   `ui/dispatcher/LedgerCharts.kt`），页面自己再 `sumOf` 一遍就是第二份口径 ——
   表现是「上面写 ¥3,200、扇形加起来 ¥2,800」，两个数都不报错。这条判据真的拦过一次注入。
3. **数据支持不了就不给那一档**：货主账/批发商账的接口只回账户汇总、没有按天的数，
   所以那两档只有「排行 + 构成」两种图（`chartTypesFor`，有单测）。
   硬凑一条按天曲线，会在明细被截断时画出**比合计小**的线 —— 同一屏两个数，比"少一种图"糟得多。
4. **扇形的两条硬规矩**：环心那个数 = **切片之和**（不是从别处塞一个合计进来）；
   切片跟着搜索走、超过 6 块合并成「其他」但**绝不丢**（丢了占比就加不到 100%）。
   配色取 `ChartPalette`，判据是**两两 RGB 距离 ≥60** —— 两块颜色接近就只能靠图例反查，图等于白画。

**日期档位**（同一轮的要求）：档位与区间在 `ui/common/DatePresets.kt`（纯函数、有单测），
胶囊那一行在 `ui/common/Components.kt::DatePresetRow`；通用筛选条与账本页**共用**这两份。
⚠️ 口径写死为：**本月 = 本月 1 日 ~ 今天**（未来的日子没有账）、**上周 = 上周一 ~ 上周日**
（不是"最近 7 天"，那是另一档）。第一格是**「全部」＝不带日期条件**。

### 4.11 AI 圆钮坐在凹口里，凹口两侧必须是**曲线过渡**（2026-09-20）

用户看真机截图：
> 它那个圆圈图标它是被 2 个矩形像是框在一起的…就是它那个角是尖尖，把它做一个曲线过渡。

- 形态：导航条上沿在圆钮位置**凹进去**（`ui/nav/NotchedNavBar.kt::NotchedBarShape`），
  圆钮不是"贴在平沿上"。圆心在栏**内侧**（半径−凸出）。
- 两侧的角**必须**是同时与上沿、大圆**相切**的圆角，而且半径只有唯一一个正确取值：
  **圆心深度**（= 钮半径 − 凸出，真机 17dp）。两个相切条件把"圆角半径"和"切点落在大圆哪儿"
  锁成一一对应（`sin γ = (圆心深度 − f) / (半径 + 缝 + f)`）：
  - 取大了取不了（切点会掉到大圆下半圈，缺口被啃掉一块）；
  - **取小了就会留下一小块"喙"**：切点退回大圆上半圈，旧形状那道方角只被削掉一半
    （试过 6dp，真机上喙宽 1.2dp），而且旁边多一条缝。所以这个半径**不写成常量**，
    由相切条件解出来——写成常量等于给"切点落在哪儿"开了一个能改错的旋钮。
- 必然的后果：上沿开口被撑宽（34dp → **55dp**）；那几 dp 正是原来尖角所在的位置，
  所以看着是"角被抹圆了"，而不是"缺口变大了"。开口 55dp < 左右两个 Tab 图标内沿 60dp ✓。
- ⚠️ 这块**画错了不报错、不崩、肉眼还分不清**（第一版把圆心算到栏外，坑全被圆钮盖住）。
  所以判据不落在"像不像"，而落在**相切关系 + 像素**上：单测 `NotchedBarTest`、
  红线 `_tools/ai/_check_nav_guardrails.py`、像素量尺 `_tools/notify/_measure_notch.py`
  （量"缺口边缘从 0 爬起来要走多远"——圆滑是 ≈5dp，尖角是 0dp），
  外加一张**已知答案的对照图** `_tools/notify/_notch_render.py --check`
  （同一套公式画"带过渡/尖角"两张，要求量尺前者过、后者挂）。

### 6.1 外观模式（白天 / 夜间 / 随日落自动）

「我的」页两行（三端共用同一个页面，所以三端都有）：

| 行 | 行为 |
| --- | --- |
| **随日落自动切换**（默认**关**） | 打开后按当天日出日落自动切：天黑（太阳高度角 −6°，民用暮光）切夜间、天亮切回白天。右侧写清"下一次什么时候切" |
| **夜间模式 / 白天模式** | 手动开关。**自动打开时这一行置灰**并写明「已交给自动切换」——否则会出现"点了一下又自己弹回来" |

- 判定在 `core/SunClock.kt`（纯函数）：界线 = 民用暮光（太阳高度角 −6°）；**有手机定位就用真实经纬度**（`core/SunLocation.kt`，拿不到就退回"时区中央经线 + 35°N"估算）；定时器 `ui/theme/AutoSunTheme.kt` 挂根节点；状态在 `ui/theme/Theme.kt` 的 `ThemeMode`（明暗与自动开关都落盘）。
- 那一行右侧会**如实写明依据**：「按定位」还是「时区估算，开定位更准」——两个精度差很多（新疆约 2 小时），含糊过去等于骗人。
- ⚠️ 定位失败时高德会回调 `(0,0)`（不是 null）：不校验就会算出错 8 小时的日落**且不报错**，所以坐标必须过 `SunLocation.isPlausible`。
- 自动开关是**设备级**的（跟账号无关，换账号不变），和系统"深色模式"的直觉一致。
- ⛔ 暗色下必须还能分层：`SurfaceDark` 必须亮于 `BackgroundDark`，卡片补淡描边（阴影在暗色下看不见）。
- 详见 `AI_ASSISTANT_PLAN_V3.md` §51 与红线 §21。
