① 一句话：**同一行有两个答案。** 账本行的「合计」与「数量 × 单价」可以永久不一致 —— 手工记账建行时
两者一致（`3 × 20.00 = 60.0000`），但只要一次 `PATCH` 只带 `total`，合计就换成另一个数（`288.00`）
而数量/单价原样不动。**钱的那一侧按 `total` 走**（账本账户、欠款、导出都读 `total`），**人看的那一侧
按数量×单价理解**（行内三个数并排显示），于是「这一行到底是多少钱」取决于谁在看、看的是哪一格。

② 现在这条路是：派单员对 AI 说「把这笔的合计金额改成 288」（或任何走到 `update_ledger_entry` 的话）→
`android/app/src/main/java/com/tapmoay/sorders/ai/AiWriteLedgerHandlers.kt:119-174` 的
`UpdateLedgerEntryHandler` 把 `new_amount` 落成 `Change("合计金额", …, "total", 288.00)`（`:130-134`，
**不带** `quantity` / `unit_price`）→ `AiWriteDataSource.kt:612-639` 组 `LedgerUpdateRequest` →
`PATCH /api/v1/ledger/entries/{id}` → `backend/app/api/v1/ledger.py` 的 `update_entry`，HEAD 上
`:464-467` 那四行「显式给了 `total` 就用 `total`，否则才 `unit_price × quantity`」照收 → 200 落库。
人工界面**不提供**改账本行的入口（`repo.updateLedger` 全仓唯一调用点是 `AiWriteDataSource.kt:628`），
所以这条路实际上只有 AI 走得到 —— 而 AI 卡片本来就支持同时给数量与单价（`new_quantity` `:142-144`、
`new_unit_price` `:145-147`），只是用户说「改合计」时它不会自己去动那两个数。

③ 三件事变了：① `backend/app/api/v1/ledger.py` 多出**唯一一处**金额算法 `resolve_line_total`
（`:141-182`）与它的一句文案助手 `_money`（`:136-139`）；② `create_entry`（`:382-383`）与
`update_entry`（`:519-521`）都改成调那一处 —— 显式给的 `total` 与 `数量 × 单价` 不一致就 400，
文案把**两个数**都报出来并给出可行改法；③ `backend/app/schemas/ledger.py:24-28` 那句「不动 total 与
`unit_price × quantity` 是否必须相等…要改得先拍板」的过期注释改成新口径。可观察结果：
`PATCH {"total":"288.00"}` 打一行 3 × 20.00 ⇒ **400**「账本行的「合计」必须等于 数量 × 单价：这一行
是 数量 3 × 单价 20.00 = 60.00，与你给的 合计 288.00 不一致。要改合计，请同时把数量或单价改成乘积
等于它的值（例如 数量 1、单价 288.00 —— 记一整笔金额就这么写）。」；改成
`PATCH {"total":"288.00","quantity":1,"unit_price":"288.00"}` ⇒ 200 且三数自洽。

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

- **结论**：**CORE 的一处收口（账本行的金额算法）＋ INFRASTRUCTURE（判据 / 反验 / 单测）＋
  PRESENTATION：零 ＋ EXTENSION：零**
- **五问依据**（规范 §三）：
  - ① 是否定义核心事实？**是** —— 「这一行账是多少钱」就是账本行的核心事实；合计与数量×单价打架时，
    这条事实就没有唯一答案。
  - ② 是否改变核心不变量？**是（收紧）** —— 新不变量：手工记账行的 `total ≡ unit_price × quantity`；
    旧不变量：`total` 以请求里给的为准（且允许与乘积不符）。**没有放松任何一条**。
  - ③ 是否必须永久存在？**是** —— 账本行的金额口径是账目可解释性的前提，不是某个客户端的偏好。
  - ④ 是否可能出现多个实现？**否** —— 本单把两份实现（create 一份、update 一份）收成一处；
    判据里有一条结构锚就钉着「`return` 只有两个出口」。
  - ⑤ 删除后 Core 是否仍然成立？**不成立** —— 删掉它，「合计」就又可以与数量×单价不一致，
    同一行重新长出两个答案。

### R4-BOUNDARY-JUSTIFICATION：为什么边界解决不了这件事

这件事**不能**靠外围解决，三条理由都是硬的：

1. **写入口不止一个。** 只在 HTTP 层加校验等于只堵住一条路：账本行的金额在 `create_entry`（建行）与
   `update_entry`（改行）里**各长了一份算法**，两份就会漂移（HEAD 上已经是两份）。要一次收口，
   只能把它们合并成 Core 里的一处 —— 现在两个入口都调 `resolve_line_total`，判据里那条
   「合计不许从请求里直接搬」的结构锚就是钉这个的。
2. **数据库层堵不住。** 给 `ledgers` 加一条 `CHECK (total = unit_price * quantity)` 看起来最省事，
   但老库里**已经有**三数不一致的行（测试会话在 8020 副本库留下的 id=976；本单自己那个副本库里也有
   一条被删掉的探针行），加约束的迁移在老库上会直接失败；而 SQLite 改约束要重建表，
   那会把「历史行当时就是那么写的」这件事一起抹掉。所以本单只**拦新写入**。
3. **客户端提示不算事实。** 在 AI 卡片上加一句「只改合计，数量×单价 不会跟着变」，用户仍然会得到
   一行两个答案 —— 提示不是不变量。而且客户端自报的东西本来就不可信（同批的 TB-11 就是
   「`X-SOrders-Origin` 谁都能带」），一致性只能在服务端判。

## ④ Behavior Contract

```text
Input          PATCH /api/v1/ledger/entries/{id}（LedgerUpdate 的任意子集：total / unit_price / quantity /
               entry_date / product_name / product_id / shipper_id / temp_shipper_name / note …）；
               POST /api/v1/ledger/entries（LedgerCreate，同上加 source）
Output         200 + 整行 LedgerOut（创建是 201）；失败 400 + 一句能照着改的中文文案
Success        手工行：落库后 total == unit_price * quantity（请求里给了 total 就必须与乘积一致）；
               订单行（source=ORDER）：total 仍以订单行的金额为准（显式给的 total 优先，没给按乘积）
Failure        一致性与已送达闸任一不满足就是 400，**且什么都不发生**：不写 ledgers 行、不写 outbox、
               不写 operation_logs、不动账户（失败时**不**产生半成品事实）
Boundary Cases ① 只给 total 且与乘积不符 → 400（文案报出两个数）；② 只给 total 且相符 → 200；
               ③ 同时给 total 与数量/单价且一致 → 200；④ 只给数量或单价（不给 total）→ 合计按乘积重算；
               ⑤ total 给 0 或缺省 → 视为「没给」，按乘积算（老语义）；⑥ 只给备注/摘要 → 一个数都不动；
               ⑦ source=ORDER 且订单已送达/已撤销/已退货 → 仍是那句既有的 400（闸在金额校验之前）；
               ⑧ 建行时带不一致的 total → 400（同一处算法）
Side Effects   LedgerOut 里 total 的变化会自然反映到账本账户/欠款/导出（它们本来就按 total 取数）
Authorization  沿用既有权限点（账本行写权限与 update_entry 现在完全一致），⛔ 不新建权限体系
Compatibility  **Compatible**（对既有合法调用）：只给了 total 且与乘积一致的老请求照旧 200；
               单元价与数量一起给的老请求照旧按乘积算；source=ORDER 的语义一个字没变。
               Breaking 的只有一种调用：**显式把 total 写成与 数量×单价 不符的值** —— 那正是本单要
               拒绝的形状（HEAD 上它会 200 落库）
```

## ⑤ Data Contract

- **新增/改动哪些字段**：**零**。`ledgers` 表不加列，`LedgerCreate` / `LedgerUpdate` 不加字段 ——
  本单只改「给的数怎么被接受」，不改「有什么数」。
- **Owner 是谁**：账本行金额的唯一 Owner 是 `backend/app/api/v1/ledger.py`（Core 写入路径）；
  归属表见 `docs/R4_CORE_EXTENSION_MAP.md`。
- **什么时候写 / 什么时候不写**：写 —— 建行、以及改行时请求里出现 `total` / `unit_price` / `quantity`
  三者之一；不写（一个数都不动）—— 改行时这三者一个都没出现（只改备注、摘要、日期、货主、商品名）。
- **是否允许 NULL**：`total` 一直是 NOT NULL（模型里就是非空金额列），本单不改这条；
  「请求里没给 total」与「total 写 NULL」是两件事 —— 前者按乘积算数，后者根本进不去。
- **历史数据怎么办**：⛔ **一行都不回填、一行都不改**。老库里三数不一致的行（如果还有）保持原样 ——
  它们当时就是那么写进去的，那是历史事实；本单只保证**新写入的**不再长成那样。判据里也没有任何
  「扫描历史行并要求它们一致」的项。
- **迁移怎么做 / Rollback 怎么办**：**不写迁移**（没有 schema 变化）。Rollback = 把 `create_entry` /
  `update_entry` 的调用换回 `git checkout HEAD -- backend/app/api/v1/ledger.py`（`:464-467` 那段），
  历史数据不受影响。
- **删除本功能后历史数据还能不能解释**：能 —— 历史行仍带着它自己的 `quantity` / `unit_price` / `total`
  三个数，读出来照样能算、能对账；不一致的行照样看得出不一致（本单不改它们的数）。

## ⑥ CHG 专章

### Before

改之前：用户（实际是 AI 的「改合计金额」）对一行 `quantity=3 / unit_price=20.00` 的账本行发
`PATCH {"total":"288.00"}` ⇒ **200**，库里三数并存（3 / 20 / 288），账本账户从 200.0000 变成 488.0000
（按 288 计）。两个写入口各有一份算法，病灶逐字：

`update_entry`（HEAD `backend/app/api/v1/ledger.py:464-467`）：

```python
        if "total" in raw and raw["total"] is not None:
            row.total = raw["total"]
        elif "unit_price" in raw or "quantity" in raw:
            row.total = row.unit_price * row.quantity
```

`create_entry`（HEAD `backend/app/api/v1/ledger.py:312-314`）：

```python
    total = body.total
    if total is None or total == Decimal("0"):
        total = body.unit_price * body.quantity
```

两句的口气都是「显式给了 `total` 就照收」——**不看它与 `数量 × 单价` 的关系**。

### After

改之后：同一个请求 ⇒ **400**，一个字都没落库，账户一动不动；文案把两个数都报出来并给出可行改法：

```text
账本行的「合计」必须等于 数量 × 单价：这一行是 数量 3 × 单价 20.00 = 60.00，与你给的 合计 288.00
不一致。要改合计，请同时把数量或单价改成乘积等于它的值（例如 数量 1、单价 288.00 —— 记一整笔金额
就这么写）。
```

改法就三步（都在 `backend/app/api/v1/ledger.py`）：

1. 新增 `_money`（`:136-139`）与**唯一**的 `resolve_line_total`（`:141-182`）：订单行照旧
   （`if source == LedgerSource.ORDER: return given_total if given_total is not None else computed`，`:170-171`），
   手工行要求 `given_total is None or given_total == computed`（`:172-173`），否则 400（`:174-182`）。
2. `create_entry` 删掉老的三行，换成 `:382-383`（`given_total` 取值 ＋ 一次调用），放在
   `source != MANUAL` 那道 400 之后 ⇒ 来源报错优先。
3. `update_entry` 把 `:464-467` 换成 `:514-521`（`given_total` 取值 ＋ `if given_total is not None or
   `"unit_price" in raw or "quantity" in raw:` 一次重算）⇒ 只改备注/摘要时一次都不进这里。

### 为什么选「严格一致」而不是「允许显式声明不一致」

台账 TB-10 的「建议改法」给了两条路（① 只给 total 时同步 `unit_price = total / quantity`；
② 加 `total_override` 标记并在列表/导出显示）。本单选了**第三条、也是更保守的那条**：

1. **不接受任何「同一行两个答案」的形状。** 方案① 会**凭空造出用户没说过的单价**（用户说「合计改成
   288」，代码却把单价改成 96 或 288），折扣/抹零场景下更错；方案② 把不一致变成合法状态，
   之后每一处（界面、导出、对账、司机账单）都要解释它，而 TB-11 已经证明客户端自报的标记不可信。
2. **不一致的请求只有一种来路，而它本来就有更好的说法。** 用户能走到这条路的只有 AI，AI 卡片本来就
   支持同时给数量与单价（`new_quantity` / `new_unit_price`），400 文案直接把「要改合计就同时改数量
   或单价」写清楚（含「数量 1、单价 X」的记整笔写法）⇒ 用户自己就能改对，不需要服务端猜。
3. **财务宁保守**（用户 2026-10-04 的口径）。让数据层不可能出现两个答案，比给这个状态加一个到处都要
   解释的标记省事、也安全。
4. **老语义一个字没破。** 「没给 total（或给 0）＝按乘积算」、订单行按订单行的金额 —— 这两条都原样保留；
   被拒的只有「显式写一个与乘积不符的值」。

### Must Preserve

```text
- 历史账本行 / 历史金额 / 已冻结的金额事实（一行都不回填、一行都不改）
- 历史 Provenance / Audit / operation_logs（before/after 三个数照旧记账）
- source=ORDER 的取数口径与订单同步（ledger_sync.py）
- 「已送达 / 已撤销 / 已退货」闸（_reject_if_order_closed）与它的两个调用点
- 权限点与鉴权（不新建体系）
- API compatibility（既有合法调用的响应形状不变）
- 本事项特有的：账本账户 / 欠款 / 导出的取数口径（它们本来就按 total 计）
```

### Blast Radius（L0～L3）

**L3**（Core Fact / Money / Ledger —— 规范 §二十六：命中钱与账本 ⇒ 不能走普通流程直接合并，
最低要求是正式变更审查）。级别不是自选的：改的是**账本行的钱**，而且**收紧了一个 PATCH 契约**。
本单按 §二十七 的三条件交账：① 有证据（红证 2 failed ＋ 8031/8032 两跑）；② 只治那个病
（同一行两个答案 —— 不动表、不动别的口径、不顺手治历史行）；③ 写下来（本单 §⑥ 逐字记着病灶与取舍）。
