## ④ Behavior Contract

```text
Input：OrderDto（orderProducts[].lineTotal / unitPrice / returnedQuantity、returnedAmount）—— 全是既有字段。
Output：商品明细的行金额 = "¥" + lineReceivableCents 换算出来的字符串；合计 = "¥" + orderReceivableCents；
        真退过时合计行右边多一颗 error 色小字「已退 ¥<returnedAmount>」。
Success：一行里的件数与钱说同一件事（都是退货后的净数）；退了货的单，用户在详情页就能看到钱退了多少。
Failure：没有运行时失败面 —— 算式写错只会「数字看着不对」，不会崩、不会报错（这正是必须有判据的原因）。
Boundary Cases：
  - 没退过货的单（returnedQuantity = 0 且 returnedAmount = 0）：净额 == 原额，一个像素都不变；
    判定用 returnedAmount > 0.0，因此老单不显示那颗「已退 ¥X」。
  - 整行退光（returnedQuantity == quantity）：行金额画 ¥0.00 —— 是期望行为（件数那一列画「×0 已退 N」）。
  - 历史折扣行（unitPrice × quantity ≠ lineTotal）：走 line_receivable 的减法，不乘数量，因此不会失真。
  - 司机看不到金额那一列：与本次无关，保持不变。
Side Effects：无（同一个数的另一种算法，且比原来更接近账目）。
Authorization：未触碰。
Compatibility：Compatible —— 纯展示层换算，接口与数据库不动；回滚即回到毛额显示。
```

## ⑥ CHG 专章

### Before

用户在真机上看到的：一张退过货的单，商品明细里写着「火腿 ×2 已退 3」（CHG-0054 之后的净件数），
右边的金额还是退货前的原价；合计也是原价 —— 退了 3 件，钱一分没动。用户的原话是
「为什么钱还是整个的整数」。

### After

同一个动作：件数仍是净数，右边的钱也跟着退 —— 行金额 = 行金额 − 单价 × 已退数量，合计 = 各行净额之和
（与账本页、与后端 order_money.py 同一条口径）；真退过的单，合计那行右边多一颗红字「已退 ¥X」，
把「退掉的那部分」显式说出来。没退过的单一个像素都不变。把本刀回滚，用户看到的就是 Before 那一段。

### Must Preserve

```text
- 历史订单 / 历史金额 / 已冻结的 Pricing Fact（一行不改）
- 账本与账本红冲（Ledger / LedgerPersonStats.kt 一处不动，本刀只复用）
- 权限与角色裁剪（司机仍看不到金额列）
- 件数那一列的净数口径与「已退 N」小字（CHG-0054 立的口径）
- 现场支付确认弹层与订单卡片的金额口径（本刀明确不碰）
```

### Blast Radius（L0～L3）

**L1** —— 一个页面里的两个私有换算函数与三处调用点 ＋ 一节设计基线的文字。不碰数据、不碰权限、
不碰状态机、不碰后端；坏掉的方式「全都不报错」（编译通过、用例全绿，界面上却一眼看出钱不对），
所以本刀必须自带判据与反验。
