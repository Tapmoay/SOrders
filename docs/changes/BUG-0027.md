### R4-BOUNDARY-JUSTIFICATION：为什么边界解决不了这件事

用户看到的两个症状（「列表静默少一张」与「点开只说订单不存在」）都**不能靠边界修**：

- 司机端**无从知道**这单被删了：后端不发信号，客户端只能轮询 —— 而本项目的列表只在实时信号或手动刷新时重拉，「实时」会退化成「最多晚 N 秒」，且**仍然没有一句话**。
- 「让详情页自己分辨」也不行：它拿到的是同一句 404「订单不存在」，与「单号打错」「这单不是你的」**逐字相同**，客户端没有任何可判别的信息（这正是 TA-06 的机制）。
- 反过来让后端**改状态码**（403 / 410）来区分同样不行：`orders_common.py` 的 docstring 写明理由 —— 状态码差异会让司机反推出「有一张我看不见的已删除单」。所以本单只改 **detail 文案**，状态码仍 404。
- 因此最小改动落在**投递侧**：两个写事务里各入队一个事件（复用 `orders.assigned` / `orders.delivered` 同一条 outbox → 派发表 → message_center 链），司机端按已有 `when (e.type)` 加两支。⛔ 明确**没有**走「给 `orders` 加 `deleted_by` 列」或「司机端加轮询」那两条路：前者要迁移 + 模型 + 核心区口径同改，后者把实时变成延迟且解决不了「没有一句话」。

## ④ Behavior Contract

```text
B1 派单员删掉一张在途单（DELETE /orders/{id} → 204）时，同一个写事务里入队 orders.deleted，载荷 {"order_id": <id>, "user_ids": [司机, 货主]}（空值不进名单）。
B2 派单员恢复一张单（POST /orders/{id}/restore → 200）时，同形入队 orders.restored。
B3 两个事件都在 _outbox_deliver 里登记：orders.deleted → push_order_deleted(user_ids, order_id)；orders.restored → push_order_restored(...)；没登记仍抛 RuntimeError（老规矩不变）。
B4 两个事件都在 AGGREGATE_KEY 里解成 order_id —— 发件箱按聚合根串行重试，不会与同一张单的其它事件乱序。
B5 每个收件人各收一条站内信（type=order.deleted / order.restored，幂等键 order.deleted:<id> / order.restored:<id>，按收件人再拼 #<uid>）＋ 系统通知 ＋ 实时信号（载荷带 order_id / order_no）。
B6 司机端 PushTrust 认这两个类型；order.deleted 在 RealtimeHub 里重拉列表**并且播报一句**、同时让 NewOrderAlert 闭嘴（shouldStop）；order.restored 只重拉列表、不播报。
B7 被删的单与撤回/取消共用去重键 revoked:<id>：同一单先撤回后被删只喊一次（60 秒去重窗口）。
B8 司机点开一张已被软删的在途单：后端仍回 404，但 detail 是「订单已被派单员删除，如需找回请联系派单员从回收站恢复。」；非在途的软删单是「订单已被删除，如需找回请联系派单员从回收站恢复。」。
B9 不是这张单当事人的用户（别的司机 / 别的货主）拿到的仍是「订单不存在」——状态码与文案与改前逐字相同，不许从文案反推出「有一张你看不见的单被删了」。
B10 司机端详情页逐字认这两句并渲染「已被派单员删除」面板 + 「返回」按钮；其它任何错误（网络失败 / 500）仍走原来的「重试」，不许被误判成「订单被删了」。
```

## ⑤ Data Contract

- **新增两个发件箱事件类型**（不是表）：`outbox_events.event_type` 增 `orders.deleted` / `orders.restored`；`AGGREGATE_KEY` 两者都映射到 `order_id`。
- **新增两条站内信 / 实时类型**：`messages.type` 增 `order.deleted` / `order.restored`（实时信号同名字段 `type`）——安卓的事件白名单与播报判定认的就是这两个名字。
- **载荷**：发件箱 `{"order_id": int, "user_ids": [int, ...]}`；实时 `{"type": "order.deleted" | "order.restored", "order_id": int, "order_no": str}`。
- **幂等键**：`order.deleted:<order_id>` / `order.restored:<order_id>`（`message_center.create_message` 会再拼 `#<recipient_id>`，多收件人互不吞）。
- `orders_common.DELETED_ORDER_NOTICES` / `PLAIN_NOT_FOUND_NOTICE`：**HTTP detail 的取值**（不是库字段）；对当事人分岔、对非当事人不变。
- 表结构 / 迁移：**无**。没有新列 / 新表 / 新索引；`orders.deleted_at` 与 `orders.status` 的语义一字未改。
- **老数据（legacy）**：本单之前被删掉的单不会补发事件（历史无所谓 —— 那些卡在列表里早已是删除后的状态）；30 天隔离与物理清理路径一字未动。

### 这次怎么做的

1. **软删/恢复在写事务里入队事件**：`delete_cancelled_order` 与 `restore_order` 各加一行 `outbox.enqueue(db, "orders.deleted" | "orders.restored", {"order_id": order.id, "user_ids": [x for x in (order.driver_id, order.shipper_id) if x]})` —— 放在状态写入与 `write_log` 之间，与业务同一事务（回滚时事件一并消失）；同时删掉一个不用的 `shipper` 依赖（签名清理）。
2. **登记聚合根**：`AGGREGATE_KEY` 增两行（都映射 `order_id`），发件箱按聚合根串行重试 —— 同一张单的 delete/restore 不会乱序；`NO_AGGREGATE` 不动（没有新理由）。
3. **派发表登记两支**：`main.py` 的 `_outbox_deliver` 把两个事件各转成一个薄包装调用，载荷里的 `user_ids` / `order_id` 显式转 `int`（发件箱载荷是 JSON，空载荷不许炸）。
4. **发布器三腿齐全**：`message_center` 新增 `publish_order_deleted` / `publish_order_restored` —— 站内信（带标题与「回收站」出口）＋ `emit_notification` ＋ `emit_realtime`（载荷带 `order_id` / `order_no`，安卓那边认得出是哪张单）；幂等键 `order.deleted:<id>`。删除那条 `speech_important=True`（该打断司机），恢复那条 `False`（不该打断他）。
5. **404 文案对当事人分岔（状态码不变）**：新增 `_deleted_order_notice(order, role, current)` —— 非当事人回 `PLAIN_NOT_FOUND_NOTICE`（「订单不存在」，与改前逐字相同），当事人在途回「订单已被派单员删除……」，非在途回「订单已被删除……」，两句都给出「从回收站恢复」这条出路。⛔ 不改成 403/410：那会让司机反推出「有一张我看不见的已删除单」。
6. **司机端认得出、不静默、给出口**：`PushTrust.ORDER_TYPES` 加两个类型；`NewOrderAlert` 把 `order.deleted` 并进撤回/取消那一支（同一句语音、同一个去重键、并且让「来订单了」立刻闭嘴）；`RealtimeHub` 的 `order.deleted` 支重拉列表 **＋ 播报一句**，`order.restored` 支只重拉；新增 `ui/order/OrderDeleted.kt`（两句文案与后端逐字对齐 ＋「返回」按钮），详情页在 **`ErrorView` 之前**插一支渲染它 —— 顺序错了就等于没写（`ErrorView` 会把「订单不存在」和「重试」抢走）。

```text
Known Limitations
```
- **恢复不播报**（只重拉列表）：恢复不是「该司机动手」的事，做成了与删除不对称 —— 若日后产品要求「恢复也响一声」，改 `RealtimeHub` 的 `order.restored` 支即可（判据里有一条专门钉着「恢复不许播报」，改的时候要一并改）。
