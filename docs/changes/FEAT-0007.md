## ① 六问

① **我要解决什么问题？**
   联系人多了以后是一条**没有结构的平铺长列表**：同一个收货人可能在「永盛食品仓库」「永盛食品门店」两处以不同称呼存着，
   用户只能靠搜索找。地点早就有分类（`place_categories` 名册 + 左栏），联系人没有。

② **当前用户 / 业务流程是什么？**
   货主 / 批发商 / 派单员进「地址与联系人 → 联系人」，看到的是按常用度排序的一张长列表；新增/编辑联系人只有
   「称呼 + 电话」两格。地点一侧已经是「左分类 + 右列表」，并能进第二层管理名册。

③ **哪个现有事实或能力会发生变化？**
   `shipper_contacts` 多一格 `category`（自由文本，空串=未分类）；联系人页多一个左栏与一个分类下拉；
   多一组按人分区的名册端点 `/api/v1/contact-categories`；`ContactOut` / `ContactDto` 多一格 `category`。

④ **哪些东西明确不能变化？**
   - ⛔ `place_categories` 表本身（不加 `kind` 列、不动它的唯一约束）—— 两张名册的级联目标不同，合表就要每次判 `kind`；
   - ⛔ `shipper_contacts.phone` 的唯一约束与 CHG-0010 那套「空号存 NULL」口径；
   - ⛔ 下单 / 派单的业务口径（补号写回档案那一步）；
   - ⛔ `vehicles.vehicle_type` 那种既有的计费词汇表；
   - ⛔ 历史联系人不回填分类（不许替用户猜）。

⑤ **这个变化属于 Core、Extension 还是 Infrastructure？**
   **EXTENSION IMPL + PRESENTATION**，不是 Core（见 ③）。

⑥ **什么证据能够证明它完成？**
   `python _tools/qa/_check_contact_categories.py`（**100 项**）+ 反向验证 **31 条注入全报红** +
   `backend/tests/test_contact_categories.py` **13 个用例** + 三台模拟器实测（见 ⑧）。

## ④ Behavior Contract

```text
Input          POST/PATCH/DELETE /api/v1/contact-categories…、POST/PATCH /api/v1/shipper/contacts（带 category）
Output         ContactCategoryOut(id, name, sort_order, contact_count) / ContactOut(..., category)
Success        新建分类 → 进名册末尾；改名 → 名册与**挂着的联系人**一起改（含回收站里那条）；
               整份重排 → 顺序就是左栏顺序；删除 → 204
Failure        重名 → 409「分类「X」已经存在了」；超 200 个 → 400；还有联系人挂着就删 → 400
               「还有 N 位联系人挂在这个分类下，先把他们改成别的分类（或改个名）再删」；
               名字纯空格 → 422；拿别人的分类编号来改 → 404（⛔ 不是 403：名册不区分"不存在"与"不是你的"）
               **失败时什么都不发生**：不改名、不删除、不把联系人挪到未分类
Boundary Cases 32 字上限（schema max_length=32 → 422，不是悄悄截断）；200 个上限；
               空串 = 明确移出分类（PATCH）；None = 不动（PATCH）；
               回收站（软删）里的联系人也跟着改名，但**不**算进「还有 N 位」
Side Effects   写一条审计（CONTACT_CATEGORY_UPSERT / _DELETE / _REORDER）
Authorization  既有权限点 `address:manage`（gate = backend/app/api/v1/shipper.py:31，角色 = 货主 + 派单员）
               ⛔ 不新建权限体系；司机 403
Compatibility  Compatible（只加字段与端点，既有字段语义不变）
```

## ⑤ Data Contract

- **新增/改动哪些字段**：
  - `shipper_contacts.category`：`String(32) NOT NULL DEFAULT ''`，`index=True`（索引名 `ix_shipper_contacts_category`）
  - 新表 `contact_categories`：`id / shipper_id(FK users.id) / name String(32) / sort_order / 时间戳`，唯一键 `uq_contact_category_owner_name(shipper_id, name)`
  - `ContactCreate.category`（默认空串）/ `ContactUpdate.category`（str | None：None=不改、空串=清空）/ `ContactOut.category`（`str` 默认空串，⛔ 不是可空）
- **Owner 是谁**：**货主 / 派单员自己**（按 `shipper_id` 分区；批发商在本仓库就是货主，没有独立角色）
- **什么时候写 / 什么时候不写**：只在用户明确选/敲了分类时写；POST 是 upsert —— **已经存在的那条联系人在这次没带分类时不许被抹掉**
- **是否允许 NULL**：`category` **不许** NULL（空串 = 未分类）；名册 `name` 也不许 NULL
- **历史数据怎么办**：**不回填**。42 位既有联系人全部停在 `''`（未分类）——
  ⛔ 这一位到底是「老客户」「供货商」还是「司机」没有任何人能证明，⛔ 不许按现在的规则猜过去
- **迁移怎么做 / Rollback 怎么办**：`012_contact_categories``（加列 + 建索引，分开判分开跑，可重跑）；
  Rollback = 删索引与列（数据是空串，丢了不影响任何计算）；`contact_categories` 表由 `create_all(checkfirst=True)` 建
- **删除本功能后历史数据还能不能解释**：**能**。分类只是一格字符串标签，删掉功能后档案、订单、账本全部照旧可解释
