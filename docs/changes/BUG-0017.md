① 商品**沽清**（`is_active = false`）之后，下单页那张卡**还亮着**、圆形加号**还能点**、还能加进购物车、点「确定下单」**还真的下得出去** —— 沽清等于只贴了一张「已沽清」的角标，没拦住任何人。用户 m01347 的原话是：「灰掉了之后**就不能点**……就是**整卡变灰**嘛……就是**拦住不让下**，不可能是提示后他仍然可以下呀。」
② 派单员在商品页把一件商品沽清（`products.is_active` 置 false）→ 货主 / 派单员进下单页点「地址库」上面那颗选品按钮，弹层走 `container.repo.products()`（默认 `includeInactive = true`）→ 列表里**仍然有它**，卡上贴「已沽清」，但加号没有 `enabled`、整行 `onAdd` 照常 → 加进购物车 → 提交时客户端只检查"有没有价格"，服务端 `build_order_products` 只拒"商品不在库"与"商品已删除" → 单子带着沽清商品落库，司机照送。
③ 「沽清」这件事的含义变了：从**只贴角标**变成**真的不能卖** —— ① 卡整体变灰（图/名/价一起暗）；② 加号灰掉、点它没有反应、**不弹数量小窗、不加行**；③ 点「确定下单」时**拦住**，并指认是哪一行；④ 服务端同一条闸门也拦（客户端只挡界面，AI 下单与老包能绕过）。
④ 见 §② Must Not Change：另外两处选品（订单详情"改行"、派单池改单）本来就走 `includeInactive = false`（**已成立、不动**）；`ProductCheckList`（可见范围 / 授权页）用的**同一个角标**，那一页下架商品**必须仍可勾**；角标文案**只有「已沽清」**；历史订单 / 金额 / 核销 / 账本一字不动。
⑤ **Presentation ＋ Core 的既有不变量**：界面上"点不动"是 Presentation；"下单闸门多一条拒绝"落在 `backend/app/services/order_flow.py` 的 `build_order_products` —— 那是**下单这件事的核心不变量**（什么样的行允许变成订单行）。
⑥ ① 新判据 `_tools/qa/_check_sold_out_block.py`（≥40 项，含"空转即停"）；② 配套反向验证 `_tools/qa/_reverse_verify_sold_out_block.py`（每条注入都让判据变红并点名对应那一条）；③ 单测（`ProductPickerTest` / 服务端 `order_flow` 那条拒绝）；④ 编译与既有红线全绿；⑤ 真机：派单员沽清一件 → 货主下单页里那张卡是灰的、点加号没反应 → 先在购物车放一件再沽清再提交，被拦住。

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

- **结论**：**CORE**（`backend/app/services/order_flow.py :: build_order_products` 是"什么样的行能变成订单行"这一条核心不变量的所在地）＋ **PRESENTATION**（`ui/common/ProductPicker.kt` 与提交前的提示）。
- **五问依据**（规范 §三）：
  - ① 是否定义核心事实？**是** —— "订单行只能来自还在售卖的商品"是订单这件事的核心事实之一；今天它只覆盖"不在库 / 已删除"，漏了"已沽清"。
  - ② 是否改变核心不变量？**是（补齐，不是改写）** —— 不变量本身（下单闸门）不动，是把沽清这条事实补进闸门的判定里。
  - ③ 是否必须永久存在？**是** —— 只要商品还能被沽清，下单就必须一直拦住它。
  - ④ 是否可能出现多个实现？**否** —— 下单只有一条路（`build_order_products`）；界面只是它的提前告知。
  - ⑤ 删除后 Core 是否仍然成立？**否** —— 删掉这条闸门，沽清商品立刻又能变成订单行（这正是本次报的 bug）。
- **要改 Core 时的三问**（规范 §F1）：
  - 为什么现有 Extension 边界无法解决？下单行的构造只有 `build_order_products` 一处；界面拦不住 AI 下单与老包，Extension 里没有第二个能封住"沽清商品变成订单行"的地方。
  - 为什么修改 Core 是必要的？因为"沽清 = 不能卖"必须在下单这条唯一的路上成立，否则它永远只是界面上的装饰。
  - 修改后 Core 的不变量是什么？**订单行引用的商品，必须是"存在的 ∧ 未删除的 ∧ 在售的"**（前两条已有，本次补第三条；手输自定义商品继续豁免）。
- **核心改动声明行**（改核心区文件时**必须**，写在 `AI_WORK_CLAIM.md`「进行中」）：
  `核心改动：backend/app/services/order_flow.py —— 为什么必须动核心：下单只有 build_order_products 这一条路，沽清要真的"不能卖"就必须在这条路上成立；界面拦不住 AI 下单与老包。`

## ④ Behavior Contract

```text
Input          选品弹层里的一件商品（ProductDto）／提交时购物车里的每一行（product_id + 数量 + 单价）
Output         界面上：沽清那张卡变灰、加号点不动、不加行；提交时：error 文案指认第一件沽清的行
Success        沽清商品永远进不了购物车；购物车里混进沽清行时提交被拦住并说清是哪一行
Failure        失败时不发生什么：不产生半成品订单（服务端整单回滚，一条订单行都不落库）；界面不弹数量小窗、不加行
Boundary Cases · 下架商品在下单页仍要看得见（列表仍含它，只是点不动）
               · 先在购物车放一件 → 派单员再沽清 → 提交：客户端拦住（这是"看得见的旧状态"那条路）
               · 客户端被绕过（AI 下单 / 老包）→ 服务端拦住（同一句话）
               · 手输的自定义商品（没有 product_id）不受影响
               · 商品已删除（is_deleted）仍然走原来那句"已经删除了"
               · 商品不在库（编号对不上）仍然走原来那句"已经不在商品库里"
Side Effects   无：不写库、不发通知、不动库存（沽清本身不扣库存，本事项也不引入扣库存）
Authorization  沿用既有权限点（货主自己下单 / 派单员代客下单），⛔ 不新建体系
Compatibility  Compatible —— 接口与字段都没变；客户端老版本仍可能把沽清商品加进购物车，但服务端会拦住并给出同一句人话
```

## ⑤ Data Contract

- **新增/改动哪些字段**：**无**。只**读** `products.is_active`（这一列早就存在，沽清就是把它置 false）。
- **Owner 是谁**：`products` —— 商品主数据，Owner 是商品库（派单员侧的商品页）。
- **什么时候写 / 什么时候不写**：本事项**一个字都不写**（只读）。沽清动作本身仍然由商品页写 `is_active`，不在本事项范围内。
- **是否允许 NULL**：不涉及（`is_active` 是 NOT NULL 的布尔位）。
- **历史数据怎么办**：**不动**。已经下出去的、含沽清商品的历史订单照旧能看、能改数量、能转单、能拆单 —— 它们不经过 `build_order_products`。
- **迁移怎么做 / Rollback 怎么办**：无迁移。回滚 = 还原三处代码（`ProductPicker.kt` / `OrderCreateViewModel.kt` / `order_flow.py`），无需改数据。
- **删除本功能后历史数据还能不能解释**：**能** —— 本事项不产生任何新字段、新状态、新记录。

## ⑥ CHG 专章（FEAT / GOV 不适用时写「不适用：<理由>」）

### Before

1. 派单员把「红富士苹果」沽清。

### After

1. 派单员把「红富士苹果」沽清（这一步流程不变）。
2. 货主进下单页 → 选品弹层：**整张卡变灰**（图 / 名 / 价一起暗）＋ 角标仍是「已沽清」→ 加号是**灰的**，点它**没有反应**：不弹数量小窗、不加行、整行也点不动。
3. 如果购物车里**在沽清之前**已经放了一件：点「确定下单」→ **被拦住**，提示指认「第 N 行的「红富士苹果」已经沽清」，购物车里的那一行留在原地等他删掉或换一件。
4. 就算绕过界面（AI 下单 / 老包）直接打接口：服务端 `build_order_products` **同样拦住**，整单不落库，返回的是同一句人话。
