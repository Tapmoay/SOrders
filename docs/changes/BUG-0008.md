① **司机（以及后端确实存在的批发商）每次登录 / 恢复会话，App 都向前端读不到的资源发一次请求，后端每次都回 403。**
   它不打断任何操作（失败是静默的），所以唯一的表现是**后端日志一直在响**；用户点名要它消失。

② **换算表是全库共用的一份**（"一车 = 8 方"，2026-09-24 加的功能），App 用 `UnitConv` 这一个持有者缓存它，
   `RealtimeHub` 在**会话建立时**拉一次 —— 理由是订单卡片 / 订单详情 / 下单页 / 商品页四处都要它，
   而它们没有共同的"载入完成"点。谁能读这张表是用户 2026-09-24 点名的两个角色：**货主与派单员**
   （后端 `api/v1/unit_conversions.py:44` 的 `UnitOwner`，与 `ShipperOrDispatcher` 同一个集合 —— 下单与录单位都是这批人干的）。

③ **变化的是"预取的前置条件"。** 以前唯一条件是"有一个会话"；现在第一条件是"这个会话的角色读得到"。
   这条判定被放在 `UnitConv.ensure` 的**第一行**，并且 `roleKey` 是**必填参数** —— 于是"哪一页能拉"
   在**编译期**就必须被回答一次，不会再有人顺手写出一个不带角色的调用。

④ **不能变的四件事**：
   - 换算的**显示**（订单卡片 `ui/common/OrderCard.kt`、订单速览 `ui/common/OrderPeek.kt`、
     订单详情 `ui/order/OrderDetailScreen.kt`、下单页清单行 —— 一处都不许因为这次改动变空）；
   - **失败仍然静默**（`refresh` 里的 `runCatching { … }.onSuccess { … }` 不许改成抛异常：
     换算只是"多显示一个数"，一次网络抖动不该让订单列表变成错误页）；

## ② Must Change / Must Not Change

**Must Change**

1. `UnitConv.ensure` 必须收**角色 key**，且**第一行就是门**（`if (!canRead(roleKey)) return`）—— 排在 `if (loaded) return` 之前。
2. 角色清单 `READ_ROLE_KEYS` 必须与后端 `UnitOwner` **逐字一致**（`shipper` / `dispatcher`），
   并且**必须按后端角色 key 判**，不许用 App 的 `Role` 枚举（`Role.fromKey` 把不认识的 key 折成 SHIPPER，
   后端的 `wholesaler` 会因此漏过门）；
3. 三个调用点各传自己的角色：会话层传**会话里的** `s.role`，下单页与新增商品页传同步的 `cachedRole()`；
4. 新增 Android 单测，钉住这份清单（含 `wholesaler` / `null` / 空串三格反向）；
5. 新增机器判据与反验脚本（本事项的主要交付物）。

**Must Not Change**

1. **后端 `UnitOwner` 不许加角色**（司机就是读不到这张表 —— 他不下单、也不录单位）；
2. `backend/tests/test_unit_conversions.py` 里两条既有用例不许删、不许改松；
3. `UnitConv.refresh` 的**静默失败**语义不许改；
4. 换算的四个显示落点不许改（这次只在"预取"这一侧动）；
5. 不加新依赖、不加新页面、不改任何接口的请求体。

## ④ Behavior Contract

- **Input**：`roleKey: String?` —— **后端角色的 key**（`shipper` / `dispatcher` / `driver` / `wholesaler` / `null`）。
- **Output**：无返回值；副作用是"换算缓存被填上一次"（只有在门放行时）。
- **Success**：`roleKey ∈ {shipper, dispatcher}` 且没拉过 → 发一次 `GET /api/v1/unit-conversions`，成功则整表替换缓存（`accept`）。
- **Failure**：
  - 角色不在白名单（`driver` / `wholesaler` / `null` / 空串）→ **直接 return，一个请求都不发**；
  - 网络 / 后端失败 → **静默**（`runCatching` 吞掉，保留上一次的表，不清空、不抛、不提示）。
- **Boundary Cases**：
  - 已经拉过（`loaded == true`）→ 不再拉（幂等），**但角色门仍然先判**（顺序不许反）；
  - 同一会话里角色变了（换账号）→ 退出登录时 `clear()` 会把缓存与 `loaded` 一起清掉，下一个会话重新判角色；
  - 批发商账号：App 的 `Role` 枚举认不出它（折成 SHIPPER），所以**必须**用 session 里的 key 判 —— 这是本事项最容易写错的一格。
- **Side Effects**：只有一个网络请求（或者一个都不发）；不改任何服务端状态（GET，无副作用）。
- **Authorization**：**不改**。后端仍是 `require_roles(UserRole.SHIPPER, UserRole.DISPATCHER)`，司机 GET → 403（契约在用例里钉着）。
- **Compatibility**：`ensure` 的签名变了（多一个**必填**参数）—— 这是**故意的**：旧签名在编译期就找不到，
  于是"没有传角色"的调用不可能被漏掉（判据 §三 另有一条"没有旧签名残留"）。

## ⑤ Data Contract

**本事项不动数据。** 没有新表、没有新列、没有迁移、没有回填、没有 NULL 语义变化。

- **字段 / Owner**：不适用（换算表本身 `unit_conversions` 是既有的，本次一行也不改）。
- **何时写**：不适用（客户端只读）。
- **NULL**：不适用（唯一相关的"空"是 `roleKey == null`，语义是"读不到角色 → 不发请求"，已在 §④ 写死）。
- **历史数据**：不适用（旧版本 App 留下的行为痕迹只有日志，日志不是数据资产）。
- **迁移 / 回滚**：不适用 —— 回滚就是 `git revert` 这一个提交，没有任何数据侧动作。
- **删功能后还能不能解释**：能 —— 换算表与它的显示都在后端/前端各自的既有位置上；
  这次只多了一条"谁能预取"的判定，删掉它之后的历史（日志里曾有 403）也仍然是自解释的：
  "那时客户端不分角色地预取"。

**After**

```kotlin
val READ_ROLE_KEYS: Set<String> = setOf("shipper", "dispatcher")

fun canRead(roleKey: String?): Boolean = roleKey != null && roleKey in READ_ROLE_KEYS

suspend fun ensure(repo: AppRepository, roleKey: String?) {
    if (!canRead(roleKey)) return   // ← 门在最前面
    if (loaded) return
    refresh(repo)
}
```

会话建立时传**会话里的角色 key**：

```kotlin
scope.launch { runCatching { UnitConv.ensure(container.repo, s.role) } }
```

`ui/dispatcher/ProductFormScreen.kt`。

**Blast Radius**：App 一个文件加两个字符串常量 ＋ 三个调用点的实参；**后端与数据库零改动**。

- 判据只能证明"App 里没有不带角色的调用"，**不能**证明"线上每个版本都不发" —— 旧版本 App 在用户手机上仍然会发（它已经装出去了）；
  这条噪声的彻底消失依赖发版，本事项只能保证**新版本不再发**（真机取证用的就是新装的包）。
- 门是按**会话里的角色 key**判的，如果后端将来新增一个"也能读换算"的角色，必须**同时**改 `READ_ROLE_KEYS`、
  后端 `UnitOwner` 与判据 §一 —— 只改一边会被 §一 当场判红（这正是它存在的理由）。

**Rollback**：`git revert` 两个提交即可；无需数据侧动作（本事项不动数据）。

**Historical Data Impact**：无 —— 没有新增/修改任何持久化数据；唯一的历史痕迹是日志里那些旧 403，
它们仍然可解释："那时的客户端不分角色地预取。"

**最后一个问题：如果把这个功能整个删掉，历史还能不能解释清楚？**

能。换算表（`unit_conversions`）与它的四个显示点都在各自的既有位置上，"预取"只是缓存填充时机；
删掉它之后，页面会晚一步显示"≈ 80 方"（或者要等下一次进管理页），历史数据不会有任何解释不出来的部分。
