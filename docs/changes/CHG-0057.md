## ③ Boundary

- **结论**：**CORE（补联系信息这一扇门）＋ INFRASTRUCTURE（新增权限点与能力表登记）**，Blast Radius **L1**
- 逐问依据：
  · 数据 Owner 变了吗？—— **没有**。四个联系字段的 Owner 仍是订单（`models/order.py:56-65`：这一单联系信息的快照）；没有新表、没有新列、没有迁移。
  · 有没有新的写入？—— **有，但只有一条**：货主对**自己名下**那一单的四个联系字段（走 `update_order(contact_only=True)`，与派单员同一条实现）。
  · 算法动了吗？—— **没有**。只新增一个**只读**导出值 `contact_risk`，唯一实现是 `services/order_contact.py::contact_risk_of`；它不写库、不改任何既有判定。
  · 权限动了吗？—— **加了**一个权限点（`order:edit_contact`，scope=own，只给货主）；**既有权限点一个都没改**（尤其没有把 `ORDER_EDIT` 给货主）。
  · 状态机动了吗？—— **没有**。补联系信息不推进、不重置任何状态；终态（已完成 / 已取消 / 已退回）仍拒绝编辑。
- **核心改动声明**：把「补这一单送给谁、打给谁」从派单员的编辑权里**切出来**，交给货主自己，并让「账上认不出人」这件事第一次**看得见**（`contact_risk`）。

## ④ Behavior Contract

- **Input**：`PATCH /orders/{order_id}/contact`，体是 `OrderContactUpdate`（继承 `OrderUpdate`，实际只该带四个联系字段；PATCH 语义：`None` = 不改这一项）。
- **Output**：`OrderOut`（与 `PATCH /orders/{order_id}` 同一个出参模型，含新字段 `contact_risk`）。
- **Success**：四个字段里至少给了一个、且都不是越界字段、且单据不是终态 ⇒ 落库 ＋ 写 `ORDER_UPDATE` 操作日志（`before`/`after` 恰好那四个字段）⇒ 200。
- **Failure**：
  · 什么都没有 ⇒ 400 `没有要补的联系信息`；
  · 给了联系字段以外的内容（送货地址 / 地址坐标 / 配送说明 / 订单备注 / 内部备注）⇒ 403 `联系信息以外的内容要派单员才能改（<字段名>）`；
  · 单据已是终态 ⇒ 400 `订单已结束，不可再编辑`；
  · 不是自己名下的单（货主）⇒ 403 `无权访问`（`_get_order_scoped`）；
  · 电话格式不合法 ⇒ 客户端先挡一道（`InputRules.phoneError(..., required = false)`），后端仍按既有校验兜。
- **Boundary Cases**：
  · 四个字段全是空串（`""`）：算「给了一个值」（`None` 才是不改）⇒ 允许，效果是把名字清空 —— 判据不拦这个，它是 PATCH 语义的一部分。
  · 两个电话都空、只补姓名：**允许**（要不到电话正是这一条的由来）。
  · 单据没有司机（`driver_id is None`）：不发 `orders.edited`。
  · 单据终态但只补联系信息：落库成功、**不推**站内信。
  · 同一单连续补两次：两次都留下 `ORDER_UPDATE` 日志（`before`/`after` 各记一次）。
- **Side Effects**：单未结束且有司机时，异步发一条 `orders.edited`（司机收到 `orders_edit_driver` 站内信 ＋ 实时 `order.updated`，客户端只重拉列表）。
- **Authorization**：`order:edit_contact`（货主，scope=own）；派单员经 `BYPASS_ROLES` 也可进，但在这扇门里能动的比 `PATCH /{order_id}` **更少**。
- **Compatibility**：老客户端不认识 `contact_risk`（多一个字段，忽略即可）；不认识新端点也不会去调它。历史空单不需要迁移，读的时候现算。

## ⑤ Data Contract

- **改动哪些字段**：**不加字段、不加表**。这一刀只**写**既有的四个联系字段：`contact_dongjia_name` / `contact_dongjia_phone` / `contact_boss_name` / `contact_boss_phone`；只**读**地多出一个出参 `OrderOut.contact_risk: bool`。
- **字段 Owner**：订单（`backend/app/models/order.py:56-65`）。这四个列是「这一单联系信息的快照」，`dongjia` = 收货人（到现场接货的人）、`boss` = 下单人。
- **什么时候写**：只在 `PATCH /orders/{order_id}/contact`（或派单员那条老路）成功时写；写的是用户当场填的值，不派生、不补全。
- **格式**：姓名是字符串（后端 `max_length=64`）；电话走 `OptionalContactPhone`（既有校验），空串 = 没填。
- **是否允许 NULL**：允许（`contact_risk` 的判据正是「两个姓名都空」，见下）。
- **历史数据**：不动。存量里四个联系字段全空的单**照旧可读**，只是现在 `contact_risk=true` 会在详情页与货主订单卡上被指出来（m01199 的兜底：**查询期判据、零落库**）。
- **迁移与 Rollback**：无迁移。回滚 = 撤掉这一刀的两个提交：权限点、端点、面板、红标一起消失；用户已经补过的四个字段**留在原列里**（本刀没动数据形态，也没有影子表）。
- **删除后能否解释**：能——每次补联系信息都写一条 `OperationAction.ORDER_UPDATE` 日志，`change_payload` 里 `before`/`after` 恰好那四个字段（补的人、补前补后都在里面）。
