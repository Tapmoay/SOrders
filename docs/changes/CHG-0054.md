# CHG-0054 · 退货在订单详情里看得见：件数画**净数** ＋ 小字「已退 3」，卡里就地画出这一单的退货申请（只读、不跳转、没退过就不画）

> 出处：用户 2026-10-06 交来的只读排查台账 `_tmp/USER_BUG_LEDGER_20261006.md` 的 **L-21**。
> 正文那一版（ref **m00481**）是：「申请了退货，派单员也通过了，为什么再点击订单详情那个商品的页面并没有发生改变……要有一个显示，已退货多少……总数从 5 个，退了 3 个，总数会变成 2 个，然后再下面会有一个红色的 −3」—— 台账当时的建议是把件数改成「5 → 2」再叠画一颗红色的 `−3`。
> 台账**附录 G** 是更晚的一次裁定（ref **m00542**）：「只显示最后的数字，然后后面一个小字『已退 3』」＋「在查看的时候也可以查到这个单子的退货单，退货单也可以查到这个单子」。台账汇总表那行逐字写着「用户已定（**m00542**：只显示净数 ＋ 小字『已退 N』）」，附录 H 逐字「**L-21**：口径见附录 G，无变化」。
> 两条口径冲突，**以晚的为准** ⇒ 本 CHG 走 m00542 的 (b) 案：件数只画**净数**，后面跟一颗小字；⛔ **不**做「总数 5 → 2 ＋ 红色 −3」的旧账叠画（`quantity` 与 `returnedQuantity` 都还在数据里，谁要旧账仍然读得到）。
> 台账是只读排查的产物（HEAD `9fb541d`），本文件是它的立项与收口。

- **结论**：**PRESENTATION（展示层）**
- 逐问依据：
  · **数据 Owner 变了吗**？没有。`returnedQuantity`、退货申请本体、驳回原因、办理人都是后端写的，客户端只读。
  · **有没有新的写入**？没有。那一块一次都不写：判据组 3 逐条钉住无 `.saveEdit`、无 `.submit`、无 `container.repo.`、无 `vm.`。
  · **算法动了吗**？没有。`core/ReturnRules.kt` 一个字没动；`netQty` 是**展示**口径，与后端 `max_returnable` 同源同义（可退上限仍是后端说了算）。
  · **权限动了吗**？没有。取数按登录缓存里的角色**原文**分派，两个角色各走各自的接口，司机不拉。
  · **状态机动了吗**？没有。申请的状态流转仍在退货申请页，详情页只是把结果画出来。
- **核心改动声明**：这一刀只改「画什么、画在哪」，不改「谁能写、写什么」。

## ④ Behavior Contract

- **Input**：`OrderDetailViewModel.returnRequests: List<ReturnRequestDto>`（打开详情时拉一次，与订单本体同一次刷新）；`OrderProductDto.quantity` / `returnedQuantity`。
- **Output**：件数列显示净数（`quantity - returnedQuantity`，下限 0）；净数后按需显示「已退 N」；卡片尾部按需显示这一单的退货申请清单。
- **Success**：有申请 → 逐个胶囊 ＋ 要退什么（`linesSummary`，最多两行，超出省略号）＋ 申请时间（`formatDateTime`）；被驳回的补一行「驳回原因：…」；已办结的补「已由 X 办理 · 时间」。
- **Failure**：取数失败（网络 / 403 / 后端 5xx）→ 列表保持空 → 这一块**整块不画**（不写 error、不画空标题、不影响订单本体）。角色认不出 → 同样不拉、不画。
- **Boundary Cases**：
  · 没退过货（`returnedQuantity == 0`）→ 不画小字（不给没退过的行加噪音）；
  · 没申请 → 不画那一块（一条都没有还画空标题，比不画更像「没加载出来」）；
  · 退到超过原件数（历史脏数据）→ 净数下限 0，绝不会画出负数；
  · `linesSummary` 很长 → 最多两行 ＋ 省略号（`_check_text_truncation.py` 的红线仍在）；
  · 驳回但派单员没填原因 → 「（派单员没有填原因）」兜底；办结但办理人名字为空 → 「派单员」兜底；
  · 司机打开详情 → 列表恒空、整块不画（司机本来也看不到退货申请页）。
- **Side Effects**：一次额外的 GET（与订单本体同一次刷新里发出）；没有写请求、没有本地持久化、没有广播。
- **Authorization**：货主 `GET /return-requests/mine`（`ShipperOnly`）、派单员 `GET /return-requests`；司机两个都 403，因此客户端先按角色原文分派、认不出的一律不拉（真门仍在后端）。
- **Compatibility**：接口与返回体沿用既有（`order_id` 过滤已存在）；老数据 `returnedQuantity` 缺省 0 → 与改动前逐像素一致（既不画小字也不画申请）。

## ⑤ Data Contract

- **改动哪些字段**：无。没有新增字段、没有改字段含义、没有改接口。
- **字段 Owner**：后端（退货流程写 `returned_quantity`；退货申请本体与状态由退货申请接口给）。
- **什么时候写**：退货通过 / 办理时由后端写；客户端只在打开详情时**读**。
- **是否允许 NULL**：`returnedQuantity` 是数值（缺省 0）；`rejectReason` / `handledByName` / `handledAt` 允许空 → 都有兜底文案。
- **历史数据**：老订单 `returnedQuantity = 0` → 不画小字、不画申请块，页面与改动前一致。
- **迁移与 Rollback**：无迁移（后端零改动）。回滚 = 撤掉这一提交，界面回到「件数＝原数量」的老样子，**数据不受影响**（净数只是展示口径，没有写回任何地方）。
- **删除后能否解释**：能。申请书与退货单都在后端，详情页只是它们的一个只读视图。
