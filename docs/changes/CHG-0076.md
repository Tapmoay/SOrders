### 用户原话与口径（本条的唯一权威 = 台账 L-39 一节）

- **用户原话**（ref **m01547**，台账 `_tmp/USER_BUG_LEDGER_20261006.md:1966` 逐字）：「就是他在那个**我的**里面加一个**按钮**……因为有些批发商他可能**不想让我们去管他的账**，所以我们就给一个功能，**开启**这个按钮：他那个我的账本就会显示**别人欠他的钱**、还有对应的**商品的定价**、以及对应的对**某些人显示多少价格**；如果**关闭**了的话，他就**没有这些功能**，他这个账本**只显示他欠我们的钱**……只记录欠派单员（总分销商）的钱，其他都不搞，**他也不需要去管那个商品**。」
- **落法定为改法 A**（ref **m01685**，台账 `:1992-1996` 逐字）：「呃对对对那个关于我的那个开关啊，嗯**后端也跟着改**。」⇒ 开关**存后端**（⛔ 不是只存本地、⛔ 不是让派单员替他关 `is_member`），与 `is_member` **两列并存**。
- **四问全答**（ref **m13365**，台账 `:2008-2013`）：① 关掉 ⇒ 两个读端点**返回空（0 / 空列表）＋ 一个标记**，⛔ **不是 403**（免得旧 App 弹报错）；② **默认开**（＝现状，老库回填 true）；③ 关掉**连异常订单 / 核销一起收**；④ **派单员不给看、不代设**（这是批发商自己的选择）。台账 `:2011` 已写「四问全答 ⇒ 本条口径已全部落定 ⇒ 等立项动工」。
- ⛔ 硬约束（`backend/app/schemas/shipper_settlement.py:87-89`）：**两本账绝不互写**；关开关**不许改动任何金额**，只是不显示 / 不提供。

① **要解决什么问题**：今天的账本页由 `users.is_member` **一处分档**（`ui/shipper/ShipperLedgerScreen.kt:81`/`:205`/`:224`/`:249`/`:656`/`:678`/`:73`/`:308-346`/`:466`/`:476`/`:482`/`:331`/`:522`；普通货主只剩订单列表 `:577`）—— 也就是说**只要你是批发商，就必须管下游的账**（别人欠他多少钱、给谁什么价）。现实里有些批发商只想记「他欠派单员的钱」，不要商品定价、不要给某些人单独定价这些功能。本条给他在「我的」页一个开关自己决定；关掉后这本账只显示「他欠派单员（总分销商）的钱」，服务端两个读端点照同一口径收窄。

② **当前用户 / 业务流程**：批发商（`UserRole.SHIPPER` ＋ `is_member=True`，这个列**只有派单员能改** —— `backend/app/api/v1/users.py:347-348`）打开「我的账本」→ 汇总 `GET /shipper-ledger/summary`（`backend/app/api/v1/shipper_ledger.py:284-291` 按 `is_member` 决定要不要算收入侧）＋ 结算单列表 `GET /shipper-ledger/settlements`（`:327-369`）→ 核销写入走 POST / DELETE / restore（`:391`/`:521`/`:574` 三处都过 `_require_member`）。普通货主看到的只有「他欠派单员的钱」那几档。

③ **哪个现有事实或能力会发生变化**：新增一个**用户偏好列** `users.downstream_ledger_enabled`（默认 true）＋ 一个新写端点 `PATCH /users/me/downstream-ledger`；`/users/me` 出参加这个值；汇总出参加一个**标记** `downstream_ledger_enabled`；上面那两个读端点与三个写端点在关掉时按 ④ 收窄。`is_member` 的**身份含义一个字不改**（工作台「批发商」徽章 `_tools/qa/_check_workbench_member_badge.py:183` 的 `repo.me().isMember` 依赖它）。

④ **哪些东西明确不能变化**：今天所有**金额事实**（关开关不产生、不修改、不隐藏任何历史核销 / 账单记录 —— 只是不显示、不提供入口）；`is_member` 的含义与它的写路径（派单员专属）；账本页 `ui/shipper/ShipperLedgerScreen.kt:394` 的支出段只在「全部」档画（台账 L-17 / ref **m00354**）与 `:487` 那句常显口径句（E2E P25）；两本账互不写入；普通货主 / 司机 / 派单员的任何现有行为。

⑤ **Core / Extension / Infrastructure**：结论 **EXTENSION IMPL**（依据见 ③ Boundary 的五问）。

⑥ **什么证据能够证明它完成**：新判据 `_tools/qa/_check_downstream_ledger_switch.py` ＋ 新反验 `_tools/qa/_reverse_verify_downstream_ledger_switch.py`（注入式，逐条改坏必须判红）；后端 pytest 里关掉那几条（返空 ＋ 标记、三个写端点 403、非货主调新端点 403）；迁移 026 可重跑且老库回填 true；客户端闸门是 `canManageDownstream`；真机截图（开关行两态 ＋ 关掉后的账本页）；`python _tools/qa/_check_all.py` 全绿（EXIT=0）。

  ③ 是否必须永久存在？**否** —— 删掉开关与那一列，账本回到「批发商一律管下游账」，Core 仍成立（这一列是偏好，不解释任何历史事实）。

  ⑤ 删除后 Core 是否仍然成立？**是**（同 ③）。
- **要改 Core 时的三问**：不适用（结论不含 CORE，不动 `backend/app/core/` 里任何核心区文件）；因此也不需要「核心改动声明行」。

## ④ Behavior Contract

```text
Input:
  - PATCH /users/me/downstream-ledger  {"enabled": true|false}（只有货主能调自己）
  - 既有两个读端点 GET /shipper-ledger/summary、GET /shipper-ledger/settlements
Output:
  - 新端点回 UserOut（含 downstream_ledger_enabled）
  - 汇总多一个标记字段 downstream_ledger_enabled: bool
Success:
  - 开着（默认）⇒ 今天的一切一模一样（金额、档位、核销入口都在）
  - 关掉 ⇒ 汇总收入侧全 0 / 结算单列表为空数组 ＋ 标记 false；写核销 403；
    账本页退回「只看他欠派单员的钱」那一档
Failure（失败时不发生什么）:
  - enabled 不是布尔 ⇒ 422（Pydantic），一列都不写
  - 非货主调这个端点 ⇒ 403（require_roles(UserRole.SHIPPER)），一列都不写
  - 派单员 / 管理员调 ⇒ 403（⛔ 不代设）
  - 关掉时想核销 ⇒ 403，且**不产生任何核销记录**（钱一分不动）
  - 失败一律不落半改状态（改开关就是单列 UPDATE）
Boundary Cases:
  - 老库 / 老客户端：列回填 true ⇒ 行为＝现状；旧 App 不认识新字段也不会坏（读端点仍 200）
  - 关掉后两个读端点仍 200（⛔ 不是 403）：summary 全 0、settlements 空数组
  - 关掉再打开：立刻恢复（一条记录都没删，数与记录原样回来）
  - is_member=false 的普通货主：开关行不显示（他本来就没有下游账）
Side Effects:
  - 一次 users 单列 UPDATE（审计沿用既有路数）
  - 关掉后客户端不再请求收入侧（VM 分档），不留缓存数字
Authorization:
  - 读：既有 ShipperOnly（backend/app/api/v1/shipper_ledger.py:67 require_roles(UserRole.SHIPPER)）
  - 写开关：同一个角色依赖，⛔ 不新建权限点
  - 核销写端点：既有 _require_member ＋ 新增 _require_downstream
Compatibility: Compatible（只加字段与端点；关掉时读端点仍 200 返空）
```

## ⑤ Data Contract

- **新增字段**：`users.downstream_ledger_enabled` `BOOLEAN NOT NULL DEFAULT 1`（`backend/app/models/user.py` 加 `Mapped[bool] = mapped_column(Boolean, default=True)`）。
- **Owner**：`users` 表上的**用户自身偏好**（与 `is_member` 同一张表、**两个意思**；归属见 `docs/R4_CORE_EXTENSION_MAP.md` §3/§4）。写权限**只给本人**（新端点只写 `current.id`）。
- **什么时候写 / 不写**：只在用户点开关时写；关掉**不写任何账本 / 核销 / 订单行**。
- **是否允许 NULL**：不允许（NOT NULL DEFAULT 1）。
- **历史数据怎么办**：老库该列一律 backfill **true** ＝ 现状 ⇒ 历史数值的解释一字不变（⛔ 不按现在的规则猜过去）。

- **删除本功能后历史数据还能不能解释**：能 —— 它是偏好、不是事实来源；删掉后历史金额与核销记录仍然自洽。

## ⑥ CHG 专章（FEAT / GOV 不适用时写「不适用：<理由>」）

### Before

- 「我的」页第一层 6 行，没有开关（`_tools/qa/_check_profile_page.py:57 N_ROWS = 6`）；批发商的账本取景由 `is_member` **一处**决定，想「不管下游的账」没有办法 —— 除非派单员把他的 `is_member` 关掉，那就连批发商身份一起丢了。
- 服务端两个读端点与三个写端点只认 `is_member`；`/users/me` 出参里 `is_member` 是唯一相关的布尔（`backend/app/schemas/user.py:32`）。

### After

- 第一层 7 行：第 7 行「管下游的账」**仅批发商可见**（`vm.user?.isMember == true`），trailing ＝ 常显状态回执 Text（「已开启」/「已关闭」）＋ `Switch`，subtitle ＝ 一条 `Hint`（纯教法句）。
- `users.downstream_ledger_enabled` ＋ 迁移 026 ＋ 模型 ＋ `UserOut` ＋ 新 `PATCH /users/me/downstream-ledger`。
- 汇总出参新增标记；关掉 ⇒ 收入侧全 0 且**不查核销**；`settlements` 返空数组；三个写端点 403 ＋ 专用文案。
- 客户端 `canManageDownstream = isMember && downstreamEnabled` **一处**闸门（账本页 / VM；原 `s?.isMember == true` 那处改成它）。

- 历史 Provenance / Audit / Ledger：核销记录、账单、审计行一条不删不改
