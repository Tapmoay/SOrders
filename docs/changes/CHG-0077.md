① 批发商（`users.is_member`）今天**不能给自己的商品定价**，也**不能给不同的下游客户不同的价** —— 他与下游那本账（`GET /shipper-ledger/summary` 的收入侧）算的是**公司给他的订单行单价**（`order_products.unit_price`），而用户要的是「**别人欠他的就按照他自己定的价来**」。
② 今天：派单员在 `price_rules` 里给批发商设专属价（第二层价）→ 批发商下单，订单行 `unit_price` 记公司给他的价 → 他把货卖给下游（收货人写在订单的 `contact_dongjia_name/phone`）→ 他自己的账本按 `姓名|电话` 给下游记账、核销（`shipper_contacts` 是他的下游客户名册）。**系统里没有第三层价**（派单员 → 批发商 → 下游客户）——`price_rules.shipper_id` 的语义是「**被给价的那个批发商**」，⛔ 不是「定价的人」。
③ 新增一层事实：**批发商自己的一层价**（新表 `shipper_prices`）＋ **下单当时的快照**（新列 `order_products.shipper_unit_price`）；下游应收从此按「下游单价 × 净件数」算（新钱数 `line_downstream_receivable`），而不是订单行金额。
④ 不能变：订单行金额（`unit_price` / `line_total`）与**公司那本账**（`ledger` / `cash_flow` / 应付）**一个字节不动**；`price_rules` 的语义与授权（派单员专属写）不动；`shipper_contacts` 仍是唯一的下游客户名册（⛔ 不把账本里的 `姓名|电话` 变成实体）；`is_member` 与 L-39 那个开关的收窄（关掉 ⇒ 定价入口与下游账一起收）；**历史订单不追改**；AI 不参与定价。
⑤ **CORE**（依据见 ③ Boundary 五问）：它定义了一个新的核心钱数（下游应收），而钱只能有一个算法出口。
⑥ 判据 `_tools/qa/_check_shipper_pricing.py` ＋ 反验 `_tools/qa/_reverse_verify_shipper_pricing.py` ＋ 单测（下单快照 / 两本账互不写 / 老单不追改 / 越权）＋ 老库迁移实测 ＋ 真机两态（有价 / 无价）＋ 全量静检 `_check_all.py`。

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

- **结论**：CORE
- **五问依据**（规范 §三）：
  - ① 是否定义核心事实？**是** —— 「下游客户欠他多少钱」是账本的核心事实；它的**单价**从此多一层「他自己定的价」，必须与订单行金额一样只有一个来源。
  - ② 是否改变核心不变量？**是（受控）** —— 下游应收的来源从「订单行 `unit_price`」变成「订单行上的快照 `shipper_unit_price`（没有快照就回落 `unit_price`）」。不变量本身不变：任一行的应收 ＝ 单价 × 净件数（`quantity − returned_quantity`），四舍五入到分（`q2`），减去已核销；钱只有一套算法（`services/money_contract.py` 钉住）。
  - ③ 是否必须永久存在？**是** —— 订单行上的快照一旦写下就是历史事实（「当时他定的价」的唯一凭据），删功能也不能删它。
  - ④ 是否可能出现多个实现？**否** —— ⛔ 只允许一个出口（`services/order_money.py::line_downstream_receivable`），`_tools/qa/_check_money_contract.py` 的 forbid 正则钉住「别处又算了一遍」。
  - ⑤ 删除后 Core 是否仍然成立？**是** —— 快照列置空即回落订单行单价，公司那本账与支出侧本来就不看它。
- **要改 Core 时的三问**（规范 §F1）：
  - 为什么现有 Extension 边界无法解决？下游应收今天**没有**「他自己定的价」这一层事实；把第三层硬塞进 `price_rules` 会与 `uq_price_rule_shipper_product` 撞唯一键，并让**派单员给批发商的价**被批发商自己的价覆盖 —— 那是数据事故，不是边界问题。
  - 为什么修改 Core 是必要的？钱的算法只有一个出口（`services/order_money.py` ＋ `services/money_contract.py`）。下游应收若在 Extension 里另算一份，账本与报表就会各写一份金额 —— 2026-09 那次「客户端自己求和少算 62%」的事故就是同一个病根。
  - 修改后 Core 的不变量是什么？**任一行的下游应收 ＝ 下游单价（快照优先，回落订单行单价）× 净件数（`quantity − returned_quantity`），`q2` 到分；已核销从同一个出口扣；公司那本账与支出侧看不到这个数。**
- **核心改动声明行**（改核心区文件时**必须**，写在 `AI_WORK_CLAIM.md`「进行中」）：

  `核心改动：backend/app/services/order_money.py —— 为什么必须动核心：下游应收的单价多了一层「批发商自己定的价」，而钱只能有一个算法出口（新钱数 line_downstream_receivable 登记进 services/money_contract.py）。`

  `核心改动：backend/app/models/order.py —— 为什么必须动核心：下单当时的价必须以订单行的快照定格（order_products.shipper_unit_price），否则改一次价会把历史账单一起改掉。`

## ⑥ CHG 专章（FEAT / GOV 不适用时写「不适用：<理由>」）

### Before

批发商在账本里只看到**公司给他的价**算出来的下游应收：同一条订单行，公司按 `unit_price` 记账，他自己的下游账也按同一个数记账 —— 他给老客户让的那点利、给新客户加的那点价，系统里**无处可放**。他要给某个下游客户单独定一个价，唯一的办法是让派单员去改 `price_rules`（那是**公司给他的价**，改了会一起改掉他自己的成本口径与公司那本账）。

### After

批发商在「下游定价」页给自己名下（他下过单的 ∪ 派单员给他设过专属价的）商品定一个**默认下游价**，还能对**指定联系人**单独定一个价（覆盖默认价）。此后：他下单时（收货人匹配到某个联系人）系统把**当时的价**快照进订单行（`shipper_unit_price`）；他自己的账本收入侧、核销上限、异常订单全部按这个快照算 —— 「**别人欠他的按他自己定的价来**」。**公司那本账一个字节不动**（订单行金额、应付、流水全按公司给他的价），差额归他。改价**只影响之后的单**（老单按快照，永不追改）。

### Must Preserve

`text
- 历史订单 / 历史金额 / 已冻结的 Pricing Fact
- 历史 Provenance / Audit / Ledger
- 权限
- API compatibility
- 本事项特有的：两本账互不写（下游应收与公司账互不影响）；price_rules 的语义（shipper_id = 被给价的批发商）；shipper_contacts 是唯一的下游客户名册；L-39 开关关掉时定价入口与下游账一起收；AI 不参与定价（⑤ 口径）。
`

### Blast Radius（L0～L3）

**L2** —— 新表 ＋ 新列 ＋ 新权限点 ＋ 新端点 ＋ 客户端新页面，且下游应收这一核心钱数多了一层来源；但两本账互不写、老单数字逐格不变、公司侧金额一个字节不动（判据与单测各钉一条）。
