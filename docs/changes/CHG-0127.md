# CHG-0127 · 固定工资司机也有「我的账本」：工资那一半账 ＋ 派单员按月核销工资

> 变更单（CHG）：给**固定工资的司机**补上「我的账本」里**工资那一半**（按月列工资单、已核销 / 未核销分开、
> 任职期间工资改过就有变更时间线），并在**派单端**加一页「司机工资（按月）」：生成 / 重算未核销的月薪单、
> 一键核销（建结算单 + 立刻 confirm）、作废 / 标记已付款。
> 由来：用户 2026-10-15 口述（m43131）——「我们的大车司机也就是固定工资的司机不是没有我的账本吗，
> 我们加一个我的账本啊，这个我的账本就是**统计他的工资**的……如果在任职期间他的固定工资发生了改变，
> 我们也同样也是有记录的，也会有个统计；当然，如果……已经核销了……表示已核销，就是**重新计算那个没有
> 核销的工资**……同时，我们那个派单员可以在司机账本这里啊，对他的工资进行核销」。
> 硬约束（同一次口述）：「其实很多代码是给复用的能复用就复用啊」⇒ **不新造单据类型**：核销直接复用现成的

① 固定工资的司机点进「我的账本」**看不到自己的工资**：那一页只有运费（派单结算）那一半。他要知道「这个月该拿多少、哪些已经核销、我来之后工资改过几次」只能去问派单员。派单员那头同样没有入口：工资只能线下算、线下给，App 里连一张单据都没有。
② 现在的流程：司机端「我的账本」＝ `ui/driver/DriverFreightScreen.kt`，取数走 `DriverFreightViewModel` 的 `freightSettlementRange(...)`（`GET /freight-settlement`）；派单端「运费结算」＝ `ui/dispatcher/FreightSettlementScreen.kt`，核销走 `POST /driver-settlements` ＋ `/{id}/action`。后端 `driver_bills.py` 早就有 `billType = "salary"` 这一支（`services/driver_pay.monthly_salary_of` 算月薪），但**刷新未核销那一半**与**入口**都没做。

## ④ Behavior Contract

```text
Input          司机端：打开「我的账本」（ProfileScreen 入口 → vm.user 三个字段之一为 true）
               派单端：运费结算页 →「司机工资（按月）」→ 选司机 →「生成 / 重算」或「核销这个月的工资」
Output         司机端：工资那一半页 —— 汇总卡（已核销 / 未核销两个数）+ 当月明细 + 变更时间线；
               派单端：该司机逐月的工资单列表（金额 / 规则名 / 说明 / 状态）+ 三个动作按钮
Success        生成 / 重算 ⇒ 该月**未核销**的月薪单按当前工资重算（金额 / 规则 / 说明一起更新），
               返回里带上新建的 + 真动过的那些；界面上「未核销的跟着新工资走」写在脚注里；
               核销 ⇒ 建一张 settleType = "salary" 的结算单并**立刻 confirm**，那一张从此变成「已核销」；
               作废 / 付款 ⇒ 走现成的结算单动作，钱与状态仍由结算单说了算。
Failure        司机端：工资取数失败 ⇒ 只有工资那半页显示错误（salaryError ＋ error 色），运费那半页照常显示；
               派单端：生成失败 ⇒ 页面上的错误提示（不产生半成品事实：后端整批在一个事务里）。
Boundary Cases 这个司机没有被挂过月薪规则 ⇒ has_salary = false，入口按老口径（按单两个字段）决定，账本仍是原样；
               某月一条单都没有 ⇒ 生成时新建；该月单已存在但金额没变 ⇒ 一个字节都不写（不进 refreshed）；
               该月单已被草稿结算单锁住（settled_doc_id 非空但状态仍是 open）⇒ **不重算**，界面显示「已核销」；
               月薪为 0 / 规则被删 ⇒ 仍按 monthly_salary_of 的口径算；月份字段脏（长度 < 7）⇒ 原样显示（宁可丑，不可无）。

Authorization  沿用既有：司机只能读自己的（GET /driver-bills 与 /users/me 都按当前用户）；
               生成 / 核销仍要求派单员权限（本单不加权限点、不改可见性判断）。
Compatibility  Compatible —— 请求不传 refresh_unsettled 时行为一字不变（缺省 False）；
               `/users/me` 只多一个只读字段；两份既有判据钉着的文案与函数名一字未动。
```

## ⑤ Data Contract

- **新增/改动哪些字段**：① `DriverBillGenerateBody.refresh_unsettled: bool = False`（只增，缺省即老行为）；② `/users/me` 出参 `has_salary: bool | None = None`；③ `DriverBillDto` 的 App 侧补全 `rule_name` / `note`（后端**本来就在返回**，App 之前没接）。⛔ 数据库一行结构都没动：`driver_bills` 的 `settled_doc_id` / `status` / `amount` / `rule_id` / `rule_name` / `note` 都是既有列。
- **Owner 是谁**：字段归属没变 —— 工资单归 `driver_bills`（司机账本），月薪口径归 `backend/app/services/driver_pay.py`，结算单归既有的 `settlement_docs`。
- **什么时候写 / 什么时候不写**：写＝生成 / 重算时、且该月单存在、且 `_is_open_unlocked` 为真、且金额真的变了（`exists.amount != sal`）；不写＝没开开关 / 已核销 / 被结算单锁住 / 金额没变 / 这个司机没挂月薪规则（`has_salary = false` 时入口都不出现）。
- **是否允许 NULL**：允许且语义明确 —— `has_salary` 为 `None`（老后端）时入口按老口径判；`settled_doc_id` 为 `None` 就是「没被任何结算单锁住」，这正是判据的一半。
- **历史数据怎么办**：一条都不回填、不迁移。历史月薪单原样留在库里：已核销的照旧显示「已核销」，未核销的等到派单员点「生成 / 重算」时才按当前工资重算，且每次重算都留痕（旧数记在 `refreshed_total` 里，日志查得到「改之前是多少」）。
- **迁移怎么做 / Rollback 怎么办**：不适用（无迁移）。回滚＝把上面那批文件还原成改动前的版本：后端不传开关即回到老行为、App 侧多出来的一页与半页直接删掉；数据侧无需任何动作（本次没写过新结构，重算过的月薪单金额可人工按日志恢复）。
- **删除本功能后历史数据还能不能解释**：能 —— 月薪单、结算单、审计日志都是既有事实，与这次多出来的入口 / 版式无关；删掉出口行与那一页，运费的账仍能逐条对上。

## ⑥ CHG 专章

### Before

- 司机端「我的账本」只有运费那一半；固定工资司机进去看到的是空的或只有零星运费。
- `/users/me` 只有 `pays_per_order` / `has_per_order_earnings`；`ProfileScreen` 的入口按这两个字段判，固定工资司机**看不到**这个入口（2026-09-20 的旧裁决）。
- `driver_bills` 的 SALARY 分支只会**新建**该月的单；已经存在但未核销的单，工资改了也不会跟着变（要么手工改库，要么先作废）。
- 派单端没有任何按月核销工资的入口；核销只能靠线下或直接写结算单。

### After

- 司机端「我的账本」＝ 运费 ＋ 工资两半页：`showFreight` 与 `showSalary` 各判各的（没工资的司机看不到工资那半页，有工资没运费的司机也不会看到一片空白）；工资那半页有汇总（已核销 / 未核销两个数）、当月明细（每条带规则名与说明）、变更时间线（相邻两张不一样才算一次）。
- 入口闸门三个字段并列：`vm.user?.paysPerOrder == true || vm.user?.hasPerOrderEarnings == true || vm.user?.hasSalary == true`；尾注按「他进去能看到什么」念三档：运费 / 工资明细、工资明细、按单计费明细。
- 生成 / 重算带 `refresh_unsettled = true`：该月**未核销且金额真的变了**的月薪单按新工资重算（四个字段一起改），先记旧数再改，返回新建的 + 刷新的，并写审计日志。
- 派单端多一页「司机工资（按月）」：选司机（现成 `PersonDrawer`）→ 该司机逐月工资单（金额 / 规则名 / 说明 / 状态）→ 「生成 / 重算」＋「核销这个月的工资」（建单 + `confirm` 一步走完）＋ 作废 / 付款（现成动作）；空态指向下一步。
- 运费结算页多一个出口行「司机工资（按月）」，排在结算单那行之后、不写金额。

### Must Preserve

- 已核销的月薪单：金额、规则、说明一个字不动（两个条件取或的补集才是可重算的）。
- 运费那半页：取数、文案、`_check_driver_money.py` 逐字钉着的两行、以及「`ui/driver` 下只有运费那一页画钱」。
- 入口那三个字段的写法（并列、不抽函数）与老那半边的一字一句。
- 结算单状态机与权限：`confirm` / `pay` / `cancel` 仍是既有动作，本单只调用不修改。
- 别人判据钉着的锚点：`_is_open_unlocked`、`SalarySheetsRow` 的位置与形状、`PersonTriggerRow(` 唯一一处、旧测试函数名。

### Blast Radius（L0～L3）

- **L1** —— 改动面横跨后端（1 个端点 + 2 个 schema + 1 个出参）、App（9 份文件，其中 3 份新建）、判据 / 反验 / 单测 / 文书。
- 之所以不是 L0：它决定了「哪个数算进哪本账」与「谁还能改这张单」——改错了**不会编译失败、也不会让别的判据变红**（后端只有真跑钱的集成测试兜着，App 这半只有本判据）。
- 之所以不是 L2 / L3：没有数据库迁移、没有新表、没有权限模型变化；不传开关时行为与改动前逐字相同。
