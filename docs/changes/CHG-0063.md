```text

   a) `ui/theme/Color.kt` 亮色四个 token 的值（页面底 → 周围那几层，越往下越深一档）：
      BackgroundLight     #F2F3F7 → #F8F7F4
      SurfaceVariantLight #ECEFF5 → #F1EEE9
      SurfaceContainer    #E6E9F0 → #E9E6DF
      SurfaceContainerHigh#DDE1EA → #E1DDD5
      口径：一套「暖白家族」（每一层 R 比 B 高），层与层之间仍严格递减。
   b) 接线**没改**（Theme.kt:89/:93/:100/:101 四处原样）—— 这一刀是「换值不换线」。
   c) `docs/PROJECT_MAP/06_DESIGN_SYSTEM.md:10` 那一行（设计基线写着旧色值，改色必须同步）。
   d) 两处**讲历史**的注释跟着现状：`ui/theme/Color.kt:226`（拿「白卡 + 灰底」当例子讲暗色分层）、
      `ui/common/Components.kt:493-497`（讲 M3 弹层默认容器当年是 #DDE1EA）。
   e) 一条既有判据的口径：`_tools/qa/_check_ledger_dialog_style.py` 第 5 组第一条从「必须是 #DDE1EA」
      松成「不是纯白、也不亮过 #F0F0F0」——**原意（弹层不许被刷成纯白冒充卡片）一个字没变**。

② 为什么要改
   用户看真机后的原话：「我们的整体背景基调，颜色太过于灰蓝了不好看。我更偏向于稍微偏白一点啊，整体的基调。」
   旧值四个都是 B 通道高于 R（#F2F3F7 / #ECEFF5 / #E6E9F0 / #DDE1EA），这正是「灰蓝」的来源。

③ 谁受影响
   亮色下的整机观感：50 处 `Scaffold` 的页面底、顶栏（`Components.kt:208-211` 的 topAppBarColors 读同一个 token）、
   周围那几层容器、以及全库几十处继承 `surfaceContainerHigh` 的弹层。暗色、底部抽屉、侧面抽屉不受影响。

④ 不改会怎样
   观感问题继续（用户已经说「不好看」）；更麻烦的是**它会一直在每一页重复出现** —— 页面底是全 App 共用的那一层。

⑤ 有没有更小的改法（逐条否掉）
   - 逐页改底色：台账 `:774` 明确否（「这一个 token 全 App 一起变……不要逐页改」），逐页改还会漏、会漂移。
   - 只改页面底、顶栏不动：顶栏读的就是 `colorScheme.background` 同一个 token，改了这一层顶栏自然跟着变，
     不需要、也不允许再给顶栏单独塞一个颜色（那会多出第二份真相）。
   - 用中性灰（如 `#FAFAFB`）：用户拍板要「暖」，中性灰 R == B 达不到这个口径。
   - 把底部抽屉/侧面抽屉一起往白走：用户 m09782 点名不许 —— 抽屉那一层是 `SheetSurface #F0F0F0`，
     底部抽屉与侧面抽屉共读它，动了就是「搞反了」。
   - 顺手把暗色也提亮：用户没提，且暗色那一套是另一条线（暗色下分层靠「亮一点的灰 + 更黑的黑」）；
     没有理由夹带，风险也大。
   - 连白卡（`SurfaceLight`）一起改：白卡本来就是纯白，动了只会把分层弄塌。

⑥ 怎么验证
   新判据 `_tools/qa/_check_warm_surface_palette.py`（四个精确值 ＋ 每层 R > B ＋ 分层严格递减 ＋
   旧值 0 命中 ＋ 抽屉那一层与它的接线没动 ＋ 暗色与描边没动 ＋ 设计基线同步）；
   新反验 `_tools/qa/_reverse_verify_warm_surface_palette.py`（12 种真实会发生的破坏方式，逐条要求判据报红）；
   既有两条回归（`_check_sheet_form_pages.py` 钉抽屉那一层、`_check_ledger_dialog_style.py` 钉弹层护栏）；
   真机（emulator-5554）改前/改后截图各一张。
```
