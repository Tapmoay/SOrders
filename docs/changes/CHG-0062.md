## ② Must Change / Must Not Change

**Must Change**

- 分类授权必须**现查商品库**（`Product.category.in_(allow_categories), Product.is_deleted.is_(False)`）—— 以后新增到这一类的商品自动可见（m00688 的硬要求）。
- **排除优先**：结果 = 选中 − 关掉（`picked - hidden`；`_split_rows` 让 deny 压 allow）；`scope="all"` 时排除行照样生效。
- 四维都要能落库、能读回：单品授权 / 单品排除 / 分类授权 / 分类排除；唯一索引**必须带 `mode`**（否则同名分类的 allow 与 deny 互相顶掉）。
- 写入前**两道闸门**：勾了商品但全不在库 → 400；配完一个都看不到 → 400（商品库为空时不拦）。
- 分类改名必须级联可见范围的行，**授权与排除两个方向**；撞车时先删重复再改名，最后删掉同名上那条授权行（拒绝优先）。
- 「谁不受限」用 `None` 表示，**不许用空集合**（空集合 = 真的什么都看不到）。
- 界面上那一套勾选清单**只有一份**：`ui/common/ProductCheckList.kt`；商品批量操作页与商品可见范围都调它。
- AI 卡片必须写清改的是谁 / 现在什么模式 / 改成什么模式 / 关掉了什么（商品名与分类名逐个列出），配完一个都看不到在**弹卡之前**就拒绝。

**Must Not Change**

- ⛔ `scope="all"` 且一条排除行都没有 ⇒ `visible_product_ids()` 返回 `None`（不受限）—— 不许退化成空集合（那会让所有老货主上线即空目录）。
- ⛔ **派单员不受限**（`visibility_applies_to()` 只对 SHIPPER 生效）；改错了没人能改回来。
- ⛔ 列表过滤 / 详情按 404 回 / 下单拦截**三处都要拦**，一处都不许撤。
- ⛔ 迁移不许把老行回填成 `custom`，也不许把列默认值改成 `deny`。
- ⛔ 接口形状向后兼容：新增字段都是可选、默认空；老客户端不改也能跑。
- ⛔ 商品行 / 售价 / 下架角标的事实与外观仍走 `ui/common/ProductCardKit.kt`（零件只组装，不自己画）。

## ③ Boundary

- **结论**：**DOMAIN ＋ PERSISTENCE ＋ API ＋ PRESENTATION ＋ AI**（一次口径扩展，跨后端与客户端），Blast Radius **L2**。
- **不改**：拦截语义（列表 / 详情 404 / 下单拒）、派单员不受限、`product_scope` 开关本身的含义、商品实体与其它端点。
- **不做**：① 不做"按分类快照"（用户明确否掉）；② 不给可见范围做时间窗 / 生效期；③ 不做整类"全部关掉"之外的批量导入；④ 不把可见范围搬成独立路由（仍是编辑抽屉里的第二层）；⑤ 不改 AI 那三条既有能力的口径。
- **为什么这条边界解决不了**：可见范围是**授权**，只能靠后端解析那一刻算准 —— 客户端那份草稿勾选（分类 × 商品）只是人的意图；任何"抄一份编号存起来"的做法都会在下次新增商品时失真（这正是 m00688 不允许的）。

## ④ Behavior Contract

- 给某货主配「只给勾选的」＋ 勾上分类「水果」⇒ 他的选品页能看到水果类**现在与以后**的所有在架商品（`is_deleted` 的不算）。
- 同一类里单独关掉一件 ⇒ 那一件看不到（详情 404、下单被拦），这一类其它商品照常。
- `scope="all"` ＋ 关掉一件 ⇒ 除了那一件，其余全部可见。
- 分类改名（`PUT /product-categories/...`）⇒ 该分类上**授权行与排除行一起改名**；撞车时合并 / 丢弃，响应与审计里带 `visibility_renamed`。
- 勾了商品但全都不在库 ⇒ 400「勾选的商品都不在商品库里了（可能已被删除），请重新勾选」。
- 配完一个都看不到（且商品库里有在架商品）⇒ 400（`custom` 与 `all` 两句不同文案）。
- 非货主 / 批发商调可见范围写入 ⇒ 400（「商品可见范围只对货主/批发商有意义（派单员不受限，否则改错了没人能改回来）」）；读别人的按既定权限口径 403 / 404。
- 界面：抽屉里那一格点进去 = 整屏第二层；改的是草稿，回到上一层按「保存」才写进去（那句说明常驻在第二层底部）。
- 批量操作页的勾选清单与商品可见范围**长得一样、行为一样**（同一份零件）。

## ⑤ Data Contract

- 表 `user_product_visibility`（不新增表）：新列 `category_name VARCHAR(32) NULL`、`mode VARCHAR(8) NOT NULL DEFAULT 'allow'`；唯一索引 `uq_upv_category ON (user_id, category_name, mode)`；行种类 = 两列取值组合（`product_id` 非空 = 单品行，按 `mode` 分授权 / 排除；`category_name` 非空 = 分类行）；`CheckConstraint("(product_id IS NULL) <> (category_name IS NULL)", name="ck_upv_one_target")` **只对新库生效**。⚠️ 老库上 `product_id` 原本 NOT NULL ⇒ 024 会**重建整表**把它变成可空（重建后 CHECK 也落到老库上）。
- 接口 `/users/{id}/product-visibility`：读回 `ProductVisibilityOut(scope, product_ids, category_names, hidden_product_ids, hidden_category_names)`；写入 `ProductVisibilityIn`（`scope ∈ {all, custom}`；四个列表各带 `max_length`：`MAX_VISIBLE = 2000` / `MAX_CATEGORIES = 200`），每个分类名走 `CategoryName = Annotated[str, StringConstraints(max_length=32)]`（去空格、去重、**空串要留着** = 未分类）。
- 上游联动：`products.category`（改名时同一事务里一起 UPDATE）＋ 新建 / 改商品时自动补分类名册（口径未变）。
- 审计：`OperationAction.PRODUCT_VISIBILITY_SET` 的 payload 九键（`user_id / user_name / scope / product_ids / category_names / hidden_product_ids / hidden_category_names / product_count / category_count / hidden_count`）；分类改名那条 payload 多一格 `visibility_renamed`（`rows_renamed` / `rows_merged` / `allow_rows_dropped`）。
- 迁移 `024_product_visibility_targets.py`：`VERSION = 24`、`NAME = "product_visibility_targets"` —— 全新库直接 return（模型建表自带两列、索引与可空 `product_id`）；老库先 ALTER 补列 ＋ 建索引，若 `product_id` 仍不可空再**重建整表**（sqlite）或 `MODIFY COLUMN product_id INT NULL`（其它方言）。
