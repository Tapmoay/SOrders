## ③ Boundary（Core / Extension / Infrastructure / Presentation）

- **结论**：**CORE 文件中的幂等 Extension 段**（`core/schema_bootstrap.py`）+ EXTENSION IMPL（分类名册）+ PRESENTATION（左栏）。
- **五问依据**（规范 §三）：
  - ① 是否定义核心事实？**否** —— 它不改任何业务事实（钱、订单、账本一个字不碰），只摆名册行。
  - ② 是否改变核心不变量？**否** —— `users.category` 的匹配口径、迁移入口、自愈顺序都没变。
  - ③ 是否必须永久存在？**是（那一列与那条迁移）** —— `parent_id` 是名册的结构事实；播种段的**作用**长期需要，
    位置可以搬。
  - ④ 是否可能出现多个实现？**是** —— 默认分类的来源可以搬到别处；但「名册为空才播种」这条语义只能有一处。
  - ⑤ 删除后 Core 是否仍然成立？**是** —— 删掉播种段，名册回到需要人手工加的状态，系统照常跑。
- **要改 Core 时的三问**（规范 §F1）：
  - 为什么现有 Extension 边界无法解决？默认分类必须**在服务启动时**自己长出来（新装 / 清库都要），
    而启动期唯一被保证执行的代码就是 `schema_bootstrap`；写成一次性迁移的话，清库那一次它早就跑完了，
    名册从此空着且**不可恢复**（这正是本次要修的病）。
  - 为什么修改 Core 是必要的？`schema_bootstrap` 里已经有**三段同形先例**（商品分类 / 预订单分类 / 开销分类的名册回填），
    本事项只是第四段，语义与它们逐条相同（名册为空才播种、绝不复活单个删除）。
  - 修改后 Core 的不变量是什么？① 自愈仍在迁移之前；② 每次启动幂等（只为空名册插行，`COUNT(*) = 0` 之外一行不写）；
    ③ 不读写任何业务数据（只查 `users.category` 的文本，不改它）。
- **核心改动声明行**（写在 `docs/AI_WORK_CLAIM.md`「进行中」）：
  `核心改动：backend/app/core/schema_bootstrap.py —— 为什么必须动核心：默认分类要在**启动期**自己长出来（清库/新装都要），而启动期唯一被保证执行的代码就是这段自愈；写成一次性迁移的话清库之后不可恢复。`

## ④ Behavior Contract

```text
Input          建分类 POST /user-categories {name, sort_order?, parent_id?}（parent_id 不传 = 建大类）
Output         出参多一格 parent_id（None = 大类）；GET 仍是按 sort_order, id 平铺的一列
Success        子类挂在大类下面；左栏出现「大类 + 缩进的子类」；点大类筛出它下面所有子类的账号
Failure        父不存在 → 400「上层分类不存在（可能刚被删掉了），换一个再试」；
               父自己是子类 → 400「只能做两级：「X」自己就是子分类，不能再往它下面挂」；
               删大类而它还有子类 → 400 并点名那几个子类；
               **失败时不发生什么**：不建半行、不改任何账号的分类、不把父悄悄换成大类。
Boundary Cases 名册为空（→ 播种六类）；parent_id 指向已删的行（界面**降级成大类照样画**，账号不会点不到）；
               库里手工塞了第三层（同上，降级成大类）；用户删掉一个分类（重启不许复活）；
               回收站账号的分类名（不算在用，不进名册）
Side Effects   启动日志里一行 warning（播种了几个）；名册写动作各写一条 operation_log（USER_CATEGORY_UPSERT/DELETE，payload 含 parent_id）
Authorization  写：require_permission(Permission.USER_MANAGE)（只有派单员）；读：登录即可（司机端也要显示分组名）
Compatibility  Compatible —— 出参**只加字段**；老客户端忽略 parent_id（左栏退化成单级，与改动前一样）；
               `users.category` 与改名级联的语义一个字节没变
```

## ⑤ Data Contract

- **新增/改动哪些字段**：`user_categories.parent_id`（INTEGER NULL，自引用外键 + 索引）。
- **Owner 是谁**：分类名册（`api/v1/user_categories.py`，与 `product_categories` 同一套：全店一份、派单员维护）。
- **什么时候写 / 什么时候不写**：只在建分类时写（且父必须是大类）；改名/排序不动它。
- **是否允许 NULL**：允许，`NULL` = 大类本身（不是 0、不是空串 —— 没有父就是没有父）。
- **历史数据怎么办**：⛔ **不回填**。老库一行都没有父子信息，谁是谁的子类**没人能证明** ——
  一律落进 `NULL`＝大类。名册为空的库会被播种六个默认分类（那六个是用户点名的，不是从老数据猜的）。
- **迁移怎么做 / Rollback 怎么办**：`030_user_category_parent`（加列 + 建索引，与 `014` 逐条同形，可重跑）；
  回滚 = `DROP INDEX ix_user_categories_parent_id` + `DROP COLUMN parent_id`（两级的关系随之消失，
  `users.category` 一个字节都不受影响）。
- **删除本功能后历史数据还能不能解释**：能。`users.category` 从来只存**叶子名**，
  删掉 `parent_id` 只是「这一格属于哪个大类」消失，账号的分类照旧解释得通。

## ⑥ CHG 专章

### Before

① 名册是空的（清零生产时被清掉），左栏只剩「全部」；补分类的唯一办法是派单员在界面里一个个手打 ——
   换一个库就再来一遍。② 名册是平表：六个大类与任意多的小类**平铺在一列**里，
   「货主」下面挂不出「食堂」；用户原话是「假如他没有多少分类吗？一堆的话到时候查起来非常麻烦」。

### After

① 名册**整个为空**时，服务启动自己摆上六个分类（派单员 / 货主 / 批发商 / 小车司机 / 大车司机 / 挂车司机），
   顺序就是用户点名的顺序；已经在用的分类名排在它们后面一起收进来。用户**删掉一个**分类不会被重启复活。
② 「管理分类」面板的「新建」多一格**上层分类**：选一个大类 = 建它下面的子类，选「顶层分类」= 建大类本身。
   账户管理左栏画成两级（子类缩进一级、没有展开箭头）；**点大类筛出它下面所有子类的账号**，点子类只筛那一类；
   卡片上画的仍然是账号自己那一格名字（叶子名）。

### Must Preserve

```text
- 历史账号的 users.category 字符串（一个都不改写）
- 改名级联（改分类名 → 同事务把所有挂着的账号一起改，含回收站里的）
- 还有账号挂着不许删；删除不提供「顺手改成未分类」
- 权限点（写 = USER_MANAGE，读 = 登录）
- API 兼容（只加字段）、四个名册页共用的那一份名册
- 三个筛选的顺序；抽屉里不显示条数
```

### Blast Radius（L0～L3）

**L2**：动了一张表的**一列**（迁移 + 三处接口 + 一个页面 + 一份名册面板），但**没有**动钱的算法、
订单流转、账本口径、权限体系，也没有动 `users.category` 的存储与匹配口径。

## ⑩ 追加（2026-10-11 01:0x，落地记录）

- **方案选择**：选 **方案 B（`parent_id`）**，不选方案 A（名字里带分隔，如 `货主 / 食堂`）。理由：
  ① 用户点名的大类**本来就是名册里的一行**（六个默认名各占一行，「有哪些大类、什么顺序」要有出处）；
  方案 A 得靠前缀**造**一个父格，那个出处就没了；
  ② 方案 A 改大类名要重写所有子类名 + 所有账号的 `category`（前缀级联），
  而现在的改名级联是**整名相等**（`User.category == old_name`）—— 正好打在本事项明令不许破坏的那段语义上；
  ③ 分隔符会跟用户自己起的名字打架。代价（一列 + 一条迁移 + 三处接口 + 三条校验）本单付得起，结构是正的。
- **构建与单测（本地）**：`gradle -p android :app:testEmuDebugUnitTest --tests "*AccountCategoryTreeTest*"`

  等它们改好之后复跑即绿）。
