# BUG-0005 · 退货办完了，司机不知道：他送的那一单被退了，账单可能被改，而他没有任何信号

> 走查自 2026-10-03 三端真机 E2E 报告（`_tmp/E2E测试报告.md`）P27。
> 这不是「少发一条通知」：退货这件事有三个当事人 —— 货主（钱退给他）、派单员（他办理）、司机（这一趟是他跑的），
> 而消息只发给了前两个。司机端更彻底：订单详情的时间线上没有「退货」那一行，
> 整单退货的单还会从他自己的「已完成」列表里**凭空消失** —— 他会以为自己看错了。

① E2E 报告 P27 逐字：**货主端与派单员端都收到了「退货已办理」消息；司机端一条都没有。**三个症状是同一件事的三个面：
   **P27-a（消息）** 司机收件箱里没有一条关于退货的消息（`_tmp/w558_msg.png` 里只有「新派单」「送达已确认」两类）。
   **P27-b（时间线）** 订单详情页的「流转记录」里没有退货/红冲一行 —— 即使订单头已经挂着「已退货」徽章（`_tmp/w558_done.png`）。
   **P27-c（列表）** 整单退完的单（`status = RETURNED`）从司机自己的「已完成」页签里**消失了** —— 他的活儿白干了吗？没人告诉他。
   影响（报告原话）：**他的运费可能被扣、这一单可能不再结算，而他没有任何信号。**

② 现在的样子：退货有两条链路（直连 `POST /api/v1/orders/{id}/return`、申请链路 `return_order_request.py` 的 fulfill），
   但**只有唯一一个执行入口** `return_order(db, order, items, *, note="", operator_id) -> ReturnResult`
   （`backend/app/services/order_return.py:210-383`）—— 钱的口径、账本红冲、库存回补、订单状态迁移都在它里面。
   退货相关的既有消息都在 `backend/app/services/message_center.py`：`order.return_request`（`publish_return_request_to_dispatchers:577` → 派单员）、
   `order.return_request.rejected:616`、`order.return_request.closed:510`、`order.return_request.done:645`（→ 货主 `req.shipper_id`）——
   **收件人只有货主与派单员两方，司机从来不在名单里**；发件箱里退货域的事件（`returns.requested` / `returns.rejected` / `returns.request_closed` / `returns.done`）
   也全是「给货主 / 给派单员」的事实，**没有一条事实是「司机也要知道」的**。
   客户端这边：`ui/order/OrderDetailScreen.kt` 的流转记录只画 下单 / 派单 / 司机确认 / 送达 / 撤销，`returnedAt` 有值也不画；
   `ui/driver/DriverOrdersViewModel.kt` 的「已完成」只认一个状态字面量 `"DELIVERED"`（`:200`），
   而整单退完后 `order.status` 是 `RETURNED` ⇒ 那张单从此不进任何页签（进行中用 `OrderStatusModel.DRIVER_OPEN`，已完成只认 DELIVERED）。

③ 变化：三处，一个方向 —— **让「这一单被退了」成为一条司机也收得到的既成事实**，并把客户端两处「看不见」补上：
   (a) 在唯一入口发一条新事实：`return_order()` 里新增一行 `outbox.enqueue(db, "returns.order_returned", {...})`
   （`backend/app/services/order_return.py:371`，与红冲/回补/状态写**同一个事务**）；负载只带既成事实：
   `order_id` / `returned_amount` / `refund_amount` / `fully_returned` / `items`。
   (b) 发件箱认它的聚合根是**那张订单**（`backend/app/core/outbox.py:100` 新增 `"returns.order_returned": "order_id",`），
   `backend/app/main.py:177` 新增派发分支 → `push_events.push_order_returned_to_driver`（`backend/app/services/push_events.py:195`）
   → `message_center.publish_order_returned_to_driver`（`backend/app/services/message_center.py:699`）：
   给 `order.driver_id` 写一条 `type="order.returned"` / 标题「订单被退货了」的消息，幂等键 `f"order.returned:{order_id}:{event_id}"`。
   (c) 客户端：流转记录补一行「退货」（`ui/order/OrderDetailScreen.kt:970`，夹在「送达」与「撤销」之间）；
   司机的「已完成」改成认 `FINISHED_STATUSES = listOf("DELIVERED", "RETURNED")`
   （`ui/driver/DriverOrdersViewModel.kt:25`，取数 `:199-201` 与空态探测 `:168-170` **同源**）。

④ 不能变：① **退货不改司机应付** —— `backend/app/services/order_return.py:26-36` 模块 docstring 里「三条刻意不做的」第一条逐字：
   `**不复原司机账单**：司机把货送到了、这一趟跑完了，退货是客户与公司之间的事。`
   ② 「整单退货的单，司机跑了这一趟的那笔应付还算不算」是**产品决策**，不是本事项能替它下结论的
   （`backend/app/api/v1/driver_bills.py:50-68` 那张表写死了三个数：账单驱动 9 笔 ¥198 / 结算单能结的 6 笔 ¥132 / 运费结算页 4 单 **¥88** 且只认 `status=DELIVERED`，
   `:59` 明写「整单退货的单是 RETURNED，被排掉」，`:66-67` 把它挂在声明页「待拍板」）
   ⇒ **消息里一个字都不许替这个决策下结论**（⛔ 不许写「这一单的运费照结」，也不许写「会被扣」）；
   ③ 钱与状态的口径：退货金额、账本红冲、库存回补、`status` 迁移一个字不动（新代码只在末尾追加一行事件）；
   ④ 货主与派单员既有的四条退货消息（`order.return_request*`）语义、收件人、文案一字不改；
   ⑤ 部分退货的单仍然留在「已送达」（`fully_returned=false` 时 `status` 不变）；整单退货仍然 `status=RETURNED`；
   ⑥ 收件人只能是这张单的司机本人（`order.driver_id`），⛔ 不许群发、不许发给别的角色；
   ⑦ 发件箱「与业务写同一事务」与 `attempts` 的成败语义不变（本次没有新增推送出口，仍然只有 5 处）。

⑤ 结论：**Infrastructure（发件箱多一种事件 + 一个派发分支与推送出口）＋ Presentation（两处客户端读数）**，
   并且**动了核心区文件一行**：`backend/app/services/order_return.py` 在 `_tools/qa/_core_files.txt:49` 里（守「退货金额与账本红冲」）。
   ⇒ Blast Radius **L2**（新增一条跨模块事件契约与一种新的通知类型，客户端行为随之改变，两份治理文档要登记）。

   之所以不是 L3：没有 Schema 迁移、没有新表新列、没有钱的口径变化、没有权限模型变化、没有接口出参变化。

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

- **结论**：INFRASTRUCTURE（可靠投递侧多一种事件与一个派发分支）＋ PRESENTATION（客户端两处读数），其中**核心区文件动了一行**
- **五问依据**（规范 §三）：
  - ① 是否定义核心事实？**是，但只是转述一条既有事实** —— 「这张单被退了、退了多少、是不是整单退完」在 `return_order()` 里已经写定；
    本事项不定义新事实，只是把它**发出去**（发件箱里多一条事实通知）。
  - ② 是否改变核心不变量？否 —— 「同一笔钱不许出现两个数」（`_core_files.txt:49` 给 order_return.py 写的守卫）一条不改：
    金额仍然是 `return_order` 的回参，消息中心**不重算**（与 `publish_return_request_done:655-658` 同一条纪律）。
  - ③ 是否必须永久存在？**是** —— 「退货办完了」这件事必须留下一条可被消费者取走的记录，否则「谁该知道什么」永远靠人喊。
  - ④ 是否可能出现多个实现？**是，而且本事项的重点就是不许** —— 所以事件发在**唯一入口**而不是两条链路的调用方；
    判据第 2 节钉住「`returns.order_returned` 的 enqueue 只有一处」「两个端点文件里不许各写一遍」。
  - ⑤ 删除后 Core 是否仍然成立？**成立** —— 摘掉这一行事件与这个派发分支，退货本身的钱、库存、状态一字不少（见 ⑨ Rollback）。
- **要改 Core 时的三问**（规范 §F1）：
  - **为什么现有 Extension 边界无法解决？** 司机的可见性有三条腿：事件（事实出得来）、派发（事实送得到）、客户端（画得出）。
    第二、三条确实在 Extension / Presentation 层，但**第一条出不来**：退货执行只有 `return_order()` 一个入口，
    而它在核心区（钱与红冲的守卫文件）—— 事件若不发在这里，就只能让每个调用方自己发，那正是「同一件事有两个说法」的开始。
  - **为什么修改 Core 是必要的？** 因为「退货办完了」这条事实的**唯一产生点**就在核心函数里面；
    在入口之外补一张表或加一个回调钩子，等于把「事件与业务同事务」这条保证拆掉（回调失败就丢事实）。
  - **修改后 Core 的不变量是什么？** ① 金额仍然只算一次（消息中心不重算，直接透传 `return_order` 的回参）；
    ② 事件与红冲 / 回补 / 状态写在同一事务里，事务回滚则事件不存在（不会出现「消息说退了、账本没退」）；
    ③ 一行 `outbox.enqueue(...)` 是本次在核心文件里的**全部**改动，`order.status` 的 CAS、账本红冲、库存回补一行未动。
- **核心改动声明行**：`核心改动：backend/app/services/order_return.py —— 为什么必须动核心：退货执行只有 return_order 一个入口，「办完了要告诉司机」这条事实的唯一起点就在这里；本轮只在末尾追加一行 outbox.enqueue（金额 / 红冲 / 回补 / 状态 CAS 一行未动）。`
  （同一条已写进 `docs/AI_WORK_CLAIM.md` 的声明块，`_check_core_freeze.py` 第 3/4 条认这一行。）

Authorization  收件人 = order.driver_id（这张单的司机本人）；消息类型 order.returned 只由发件箱消费者产生；
               ⛔ 不新建权限体系，后端接口自身的 RBAC 一字不改

## ⑤ Data Contract

- **新增/改动哪些字段**：**无新字段、无新列、无迁移**。落下来的是两张既有表里的记录：
  `outbox_events`（`event_type=returns.order_returned`，payload 五个键）与 `notifications`（`type=order.returned`，payload 五个键）。
- **Owner 是谁**：事件 `returns.order_returned` 的 Owner 是**退货域**（`order.return`）—— 由 `return_order()` 在业务事务里写；
  消息的 Owner 是 `message_center`（`publish_order_returned_to_driver`）；
  收件人由**订单**决定（`order.driver_id`），不由消息发布者决定。
- **什么时候写 / 什么时候不写**：只有 `return_order()` 真的执行完（红冲与状态写在同一事务里）才写事件；
  消费者侧三种情况不写消息：订单不存在 / `driver_id` 为 NULL / 司机账号不存在。
- **是否允许 NULL**：`driver_id` 允许 NULL（自提单），语义 =「这张单没有司机，没有人需要被通知」；
  消息正文的 `items` 允许空串（写成「（明细见订单详情）」）；`refund_amount` 为 0 时不出现退款那句。
- **历史数据怎么办**：**什么都不做** —— ⛔ 不回溯补发本事项之前那些退货单的消息；
  但 P27-c 那一半对历史数据**立刻生效**：库里已有的整单退货单，司机一打开「已完成」就能看到（客户端读的是既有状态，不是新字段）。
- **迁移怎么做 / Rollback 怎么办**：**无迁移**。Rollback = 删掉 enqueue 那一行 + 派发分支 + 两个推送 / 发布函数 + 客户端两处改动；
  已产生的历史通知记录可以留着（它们记录的是真发生过的事），也可以按 `type="order.returned"` 清掉。
- **删除本功能后历史数据还能不能解释**：能 —— 退货记录、红冲、账本、库存、订单状态全不受影响；
  只是退回「司机不知道这一单被退了」的旧样子。

## ⑥ CHG 专章（FEAT / GOV 不适用时写「不适用：<理由>」）

本事项是 **BUG**（修复三个已声明的行为缺陷），不是能力变更；按规范仍写清 Before / After 对照。

### Before

三个缺口，一个现场：**「这一单被退了」这条事实没有第三个人收得到。**
货主与派单员都收到了「退货已办理」（`order.return_request.done`）；司机端一条都没有（`_tmp/w558_msg.png` 里只有「新派单」「送达已确认」两类）。
司机点开订单详情：订单头挂着「已退货」徽章，流转记录却只到「送达」为止 —— 退货那一行不存在（`_tmp/w558_done.png`）。
再切到底栏「已完成」：那张单**不在**列表里（整单退完 `status=RETURNED`，而客户端只认 `"DELIVERED"`）—— 他跑过的那一趟在自己的账面上凭空消失了。

### After

退货办完的那一刻（无论走直连还是走申请办理），退货域发出一条 `returns.order_returned`；发件箱消费者把它变成司机收件箱里的那条消息：
**「订单被退货了 —— 订单 SO202610034194369285 退货了：清远土鸡×1，退货金额 ¥10。这一单已经整单退完。这一趟你已经跑完，账单不会被退货改动（有疑问看「我的账单」里这一笔）。」**
同一时刻实时通道推 `order.returned`，司机在「消息」页签上能立刻看到（`_tmp/b5_b5_driver_msg.png`）。
订单详情的流转记录多一行「退货 10-03 11:29」，排在「送达」之后、「撤销」之前（`_tmp/b5_driver_timeline.png`）；
司机「已完成」里那张单还在，带「已退货」徽章（`_tmp/b5_driver_finished2.png`）。
同一张单退两次就是两条消息（各自带自己的 event_id），⛔ 不会因为「同一张单」被吞掉第二条。

### Must Preserve

```text
- 退货不改司机应付：不复原、也不扣（order_return.py:26-36 三条刻意不做的第 1 条）
- ⛔ 消息里不替产品决策下结论：不写「运费照结」，也不写「运费会被扣」（driver_bills.py:50-68 说这是待拍板的决策）
- 退货金额 / 账本红冲 / 库存回补 / order.status 迁移：一个字不动
- 货主 / 派单员既有的四条退货消息：收件人、类型、文案一字不改
- 部分退货的单仍然留在「已送达」；整单退货仍然 status=RETURNED
- 收件人只能是 order.driver_id 本人；司机端看不到别人的单
- 发件箱与业务同事务、attempts 至少一次语义、推送出口仍只有 5 处
- 历史 Provenance / Audit / Ledger：本事项只**追加**记录，不改写任何既有记录
```

### Blast Radius（L0～L3）

**L2** —— 新增一条跨模块事件契约（`returns.order_returned`）与一种新的通知类型（`order.returned`），
客户端两处读数随之改变，两份治理文档需要登记；不动数据、不动钱、不动权限、不动路由、不动接口出参。
之所以不是 L1：这不是一页里的局部行为，而是**模块之间的一条新契约**（谁该知道什么），且动了核心区文件一行。
之所以不是 L3：没有 Schema 迁移、没有新表新列、没有钱的口径与权限模型变化，接口出参与表结构零改动。
