**① 要解决什么**：货主 / 批发商 / 派单员下单时，**没有地方说"这单哪天送到"**。
用户 2026-10-21 原话：「他们下单的时候……**可以选择送到的日期**，UI 我们也做好；然后我们还要加一个警示，
**在那个日期选择前面加一个红色的警示**……告诉他们**订单必须提前一天下达，当天下的单不一定能准时送达**」。

**② 当前流程是什么**：下单页只有「为谁下单 / 商品明细 / 收货地址 / 联系信息」四张卡；
订单表上只有 `order_date`（**哪天下的单**）与 `delivered_at`（送达那一刻才写），
"约的哪天送"**在送达之前根本不存在** —— 派单员和司机只能靠电话问。

**③ 哪个现有事实会变**：`orders` 多一列 `delivery_date`（期望送达日，可空）；
`POST /orders` 多收一个可空字段、`OrderOut` 多回一个可空字段；下单页多一张卡。
**没有任何既有字段的语义被改写**（`order_date` 仍是下单日、`expected_deliver_before` 仍是 SLO 截止时刻）。

**④ 明确不能变**：
- ⛔ `order_date` 的语义（报表按它分桶、账本兜底归属日用它）；
- ⛔ `expected_deliver_before` 的语义（准时率分母 + 自动异常的触发点：**不许**拿"选了个日期"去写它，
  否则到点这单会自己变成异常单）；
- ⛔ 钱 / 状态机 / 权限 / 账本 / 库存一个字不动；`OrderUpdate` 本轮**不加**这一格（改单改日期另起一单）；
- ⛔ 存量单**不回填**（他们当时没有这个约定，猜一个日子 = 伪造历史事实）；
- ⛔ 不新建权限点、不新建端点（下单仍是 `POST /api/v1/orders`）。

**⑤ Core / Extension**：**PRESENTATION + 既有表上的一个可空附加属性**。
它是订单的一个属性，不改核心不变量（钱/状态/权限/历史）。唯一碰到的核心区文件是
`services/order_flow.py`（**拆分单继承送达日**），已按规矩在 `AI_WORK_CLAIM.md` 写「核心改动」一行。

**⑥ 证据**：判据 31 项 + 反验 13 条注入（全被抓）+ 后端用例 3 条 + Android 单测 7 条 +
真机（模拟器 5554，派单员）四张截图（红条 / 抽屉 / 日历 / 选完回填）。见 ⑦ ⑧。

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

- **结论**：**PRESENTATION + 既有表上的可空附加属性**（不新增核心事实，也不新增扩展点）
- **五问依据**（规范 §三）：
  - ① 是否定义核心事实？**否** —— 它是订单的一个可选描述（"约的哪天送"），
    钱、状态、权限、历史事实都不由它定义；删掉这一列，Core 一条规则都不用改。
  - ② 是否改变核心不变量？**否** —— 恒等式（`goods_amount − returned_amount == …`）、
    状态机、`entry_date` 全部不经过它。
  - ③ 是否必须永久存在？**否** —— 下一版可以整列删掉，历史单只是少一个"当时约的哪天"。
  - ④ 是否可能出现多个实现？**是**（"这单约的哪天"将来可能还有"按线路约定""按客户约定"），
    所以本轮**刻意不做抽象**：先用这一列跑起来，等第二个实现出现再判（规范 §7「模糊时先不要抽象」）。
  - ⑤ 删除后 Core 是否仍然成立？**是** —— 删掉卡片与列，下单/派单/送达/账本全链路照旧。
- **核心改动声明行**（`AI_WORK_CLAIM.md`「进行中」已写）：
  `核心改动：backend/app/services/order_flow.py —— 为什么必须动核心：拆分单是这张单的派生行，送达日不继承就会在新单上凭空消失（同一趟货两个日子），改动只有一行赋值、不动状态机。`

## ④ Behavior Contract

```text
Input          下单页「送达日期」那一格选的日期（YYYY-MM-DD）；默认＝明天（设备当地日 +1）
Output         orders.delivery_date；OrderOut.delivery_date（原样回读）
Success        下单成功，库里与出参都是选的那天
Failure        选了一个**早于今天**的日子 ⇒ 400「送达日期不能早于今天」，**不创建订单**
Boundary Cases · 今天可选（界面标「不保证准时」）；· 昨天及更早：日历里点不动 + 服务端 400；
               · 设备时区跨日（页面开着过夜）：提交前按当天再判一次；
               · 不传（AI / 老客户端）：照收，NULL；· 坏串：客户端当"未选择"、服务端 422
Side Effects   无（不写账本、不扣库存；订单创建本身的既有副作用不变）
Authorization  复用 `order:create`（谁能下单谁就能选那天，⛔ 不新建权限点）
Compatibility  **Compatible**：入参与出参都是**可空新增**字段；老客户端不传 = NULL，
               老后端不认识这个字段 = 忽略（客户端 DTO 有默认值 null）
```

## ⑤ Data Contract

- **新增/改动哪些字段**：`orders.delivery_date`（`DATE NULL`）；`OrderCreate.delivery_date`、
  `OrderOut.delivery_date`、Android `OrderCreateRequest.deliveryDate` / `OrderDto.deliveryDate`。
- **Owner 是谁**：订单表自己（`app/models/order.py`）。写入口只有 `commands/order.py::create_order`
  （外加派生单的两处继承：拆分 `services/order_flow.py`、转货 `commands/order.py`）。
- **什么时候写 / 什么时候不写**：下单时**带了就写**；没带就 **NULL**（⛔ 不给默认值 —— 那等于替用户
  认下一个他没选过的日子，与 `freight_rule_snapshot`「千万不要猜着补」同一条口径）。
- **是否允许 NULL**：允许，且 NULL 有明确含义：**这一单没选过**（存量 / 老客户端 / AI）。
- **历史数据怎么办**：**不回填**。老单当时没有这个约定；按今天的习惯替它写一个日子就是伪造历史。
- **迁移怎么做 / Rollback 怎么办**：`036_order_delivery_date`（先判列存在再 ALTER，可重跑）。
  Rollback = 停用界面 + `ALTER TABLE orders DROP COLUMN delivery_date`（没有别的表引用它，
  删列不会让任何既有查询失效）。
- **删除本功能后历史数据还能不能解释**：能 —— 其它事实（下单日、送达时刻、账本）都不经过它。
