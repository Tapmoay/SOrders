# CHG-0050 · 送达一律要照片：挂车 / 整车不再按计费规则免拍照，所有司机走同一条「拍照送达」

> 出处：用户 2026-10-06 交办的排查台账 `_tmp/USER_BUG_LEDGER_20261006.md` 的 **L-15**。
> 用户原话（台账记的 ref 是 **m00354**）：「**挂车**……**他也要拍照，同样的流程。**」
>
> 台账把这条定性为**一句口径推翻一条机制**：客户端与后端各有一处"按计费方式免拍照"的分支 ——
> `ui/order/OrderDetailScreen.kt` 的 `if (order.freightVisible) { … 完成订单 / 收取现金 / 挂账 … }`
> （点一下直接完成，走 `POST /orders/{id}/complete`，**不带照片**），以及
> `backend/app/services/order_flow.py` 那道 `if not delivery_photo_urls and not has_per_order_pay(order): raise …`
> （"这张单不按单拿钱"的工资制单可以不带照片完成）。**挂车默认按单计费** ⇒ 挂车那一档正好同时命中
> 客户端那条支路与后端那道豁免：账照入、库存照扣、司机账单照生成，**只是没有任何送达凭证**。
>
> 用户要的是「同样的流程」：**所有司机一律先拍照**，收款方式在拍完照之后的完成块里选（与其它司机逐字相同）。
> 台账另外写明两条纪律，本事项逐条照办：
> ① 撤的是**照片豁免**，⛔ 不是计费口径 —— `has_per_order_pay` / `order_mode` 仍是"钱那一侧"的判据
>   （按单账单、运费提醒在用），一个字不改；
> ② 老端点 `POST /orders/{id}/complete` 与 `vm.completeDirect` ⛔ **不许删**（老版本 APK / 外部调用方还要走），
>   收紧要收在**服务端那道门**上（空照片列表一律 400）。
> 台账是只读排查的产物（HEAD `9fb541d`），本文件是它的**立项与收口**。

**① 我要解决什么问题？** 挂车（整车同理）司机送达时**可以不拍照**：界面上那个分支点一下「完成订单 / 收取现金 / 挂账」
就把单完成了，后端那道照片门也因为"这张单不按单拿钱"而放行 —— 于是这一单在系统里**没有任何送达凭证**，
事后谁也说不清货是不是真送到了。用户要的是「他也要拍照，同样的流程」。

**② 当前用户 / 业务流程是什么？** 送达 = 司机在「已接单」的订单里拍照 → 写送达备注（可选）→ 选收款方式（现金 / 挂账）
→ 点完成（`completeDelivery` → 上传端点 `complete-with-upload`）。而**按单计费**的司机（挂车 / 整车默认就是）
在界面上看到的是另一条：动作卡上直接给「完成订单」（未勾收现）或「收取现金 / 挂账」两颗，
点下去走 `completeDirect` → `POST /orders/{id}/complete`，**body 里的 `delivery_photo_urls` 是空列表** ——
后端那道 `if not delivery_photo_urls and not has_per_order_pay(order)` 正好为假，放行。

**③ 哪个现有事实或能力会发生变化？** 客户端：① 司机动作卡**只剩一颗**「拍照送达 / 继续拍照」；
② 「送达凭证」那一块（拍照 + 缩略图 + 送达备注）从"对按单计费的单整块不画"改成**对所有可完成的司机都画**；
③ 完成块（收现金 / 挂账 + 完成键）的闸门里去掉 `!order.freightVisible` 那半句。
服务端：`order_flow.complete_delivery` 那道门对**空照片列表一律** `raise`（不再看 `has_per_order_pay`）。
文档：`DOMAIN_MODEL.md` 的 `DELIVERED` 那一格照实写明「所有司机一律」。

**④ 哪些东西明确不能变化？** `has_per_order_pay` / `order_mode` / `rule_of_user` 四条计费判据的定义与用途
（按单账单 `driver_bills.py:240`、运费提醒 `message_center.py:190` 仍在用）；`freight_visible` 这个出参与客户端 DTO 字段
（`Dtos.kt:187` —— 老包要读，⛔ 删它要另开 CHG）；`POST /orders/{id}/complete` 这条端点与
`vm.completeDirect` / `repo.completeDirect`（老版本 APK 与外部调用方要用）；收款方式（现金 / 挂账）的选择照样有；
L-14 那道"凭证必须是本系统上传的产物"的形状门；软删门；状态机与账本算法。

**⑤ 有没有更小的改法？** 有，而且是**只做一半**的改法，被台账否掉：只收紧后端那道门、界面照旧 ——
那样挂车司机点「完成订单」会拿到一个 400 红字，而页面上**没有拍照的地方**（凭证块对他整块不画），
等于把人堵死。本事项按"界面与门同时改"办：三个界面点（动作卡 / 凭证块 / 完成块闸门）与后端那道门一起动。

**⑥ 如果什么都不做，会发生什么？** 挂车那一档继续产生**没有送达凭证的已送达订单**（而且是**静默**的：
界面上点一下就成了，没有任何提示说"这一单没拍照"）；台账里的 L-22「补拍水印」也就无从谈起 ——
凭证本身不存在的单，没有可补拍的对象。

- **改 Core 三问**（`docs/DEVELOPMENT_SPEC.md:402`）：
  - **① 为什么现有 Extension 边界解决不了这件事？** 这道门长在 `complete_delivery()` **函数体内**、在一切扩展点之前，
    它判的是「这次状态迁移准不准发生」——Extension 层（端点 / 依赖 / 事件 / 发件箱）没有「拦下这次迁移」的位置：
    端点 `orders_delivery.py:326-328` 只负责把 `ValueError` 翻成 `HTTPException(400)`，判定在哪产生它并不关心。
    若把收紧做在客户端（Presentation），它只能挡**本版本的 App**：老版本 APK 与外部调用方直连
    `POST /orders/{id}/complete`（客户端 `AppRepository.kt:938` 那条路送的就是空照片列表）照样能无凭证送达，
    而且客户端判定不构成任何可核验的事实门（判据也钉不住别人的手机）。
  - **② 为什么修改 Core 是必要的？** 因为 Core 自己此前**放弃**了这条不变量的一部分：`if not delivery_photo_urls:`
    下面原本挂着 `if not has_per_order_pay(order):` —— 条件是「司机不按单结账」，而 `has_per_order_pay` 属**计费**维度
    （`driver_pay.py:448`，定义在 :284 的 `rule_of_user` / :426 的 `order_mode` 同一族）。凭证要求与计费方式在 Core 里
    被耦合在一起：挂车 / 整车默认按单计费 ⇒ 顺带被免掉凭证。只要这层耦合留在 Core，Core 之外的任何补救都只能「绕过」
    它而无法「收口」——照片门是送达这条迁移的一部分，不是它的旁观者。
  - **③ 修改后 Core 的不变量是什么？** **`OrderStatus.DELIVERED` 的准入 = 提交的 `delivery_photo_urls` 非空
    ∧ 每张都以 `/static/uploads/delivery/` 开头 ∧ 订单未软删（`:407`）∧ 当前状态恰为 `ACCEPTED`（`:409`）
    ∧ 调用者恰为本单司机（`:411`）∧ 端点的 `Permission.ORDER_COMPLETE_DRIVER` 门通过 —— 与计费方式、
    与司机的工资 / 按单口径**无关**。** 缩口方式是「删条件」而不是「加分支」：`has_per_order_pay` 这一层被删掉，
    Core 为这件事不再引用它（`rule_of_user` 仍用在 `:148` 的模式快照上，那是另一件事，原样不动）。

- **什么时候写 / 什么时候不写**：客户端——每拍一张写一次 `capturedPhotos`（既有）；服务端——送达事务里**读**
  `delivery_photo_urls` 做准入（本事项把"可以为空"改成"必须非空"）。⛔ 这条收紧**不写任何新数据**。
- **是否允许 NULL**：`delivery_photo_urls` 是 `list[str]`，服务端现在的口径是**必须非空**（此前对工资制司机可为空）；
  客户端 `capturedPhotos` 为空是允许的**界面态**（含义是"还没拍"，不是错误数据）。
- **历史数据怎么办**：一个字节都不动。库里已经存在的 `DELIVERED` 订单（含那些当时合法的"无照片送达"）保持原样；
  历史事实的解释方式不变 —— "当时的口径允许"就是当时的事实。
- **迁移怎么做 / Rollback 怎么办**：没有迁移。Rollback = `git revert` 实现提交（2 个 .kt + 1 个后端 .py + 1 份文档
  + 1 处既有用例随动 + 两份新 QA 脚本 + 三份文档）；回滚后挂车 / 整车 / 工资制司机重新可以无照片完成（走后端那道豁免与
  客户端的直结入口）。
- **删除本功能后历史数据还能不能解释**：能。本事项**没有新增任何记录字段**，所以回滚既不会让已送达的单失去解释，
  也不会让"哪一单有没有照片"这件事变得查不出来（照片落在既有的上传路径上，订单与它的关系未变）。
