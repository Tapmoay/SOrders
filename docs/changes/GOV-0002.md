## ① 六问

① **解决什么问题？** `docs/DEVELOPMENT_SPEC.md` §一 把日常开发的编号从 `R4-xx`
改成四种事项 ID（`FEAT/CHG/BUG/GOV-xxxx`）。但 R3 时代写下的
`R3-D02 [commit_milestone_tag]` **只认 `R<3-9>-<两位数字>`** ——
于是**按新规范写的提交全部被判红**。这是新旧规范直接冲突，不是"某条判据坏了"。

② **当前用户 / 业务流程是什么？** 提交时按规范 §一 把 ID 写在首行；判据检查"每条提交能否回溯"。

③ **哪个现有事实或能力会发生变化？** "可回溯"的**合法形状**从一种变成两种。

④ **哪些明确不能变化？** 见 ② 节。

⑤ **属于 Core / Extension / Infrastructure？** 都不是，是 **GOV**（治理规则本身）。

⑥ **什么证据能够证明它完成？** `_check_r3_constraints.py` 8 组全绿 +
`_check_all.py` 全绿 + 底下 ⑦ 的四件事。

## ② Must Change / Must Not Change

```text
Must Change:
- _tools/qa/_milestone_tag.py 增加 ITEM_TAG = (FEAT|CHG|BUG|GOV)-四位数字；milestone_tag_of 两种都认
- 重号规矩**只对里程碑编号生效**（事项 ID 不判重）
- 没有 ID 的提交：只有"它根本不是开发事项"这一种合法情形，且**必须正文写明「无 ID：<理由>」**

Must Not Change:
- ⛔ **不许把"每个提交都能回溯"这条治理削弱掉**（用户 v2 的原话：「扩展编号容量不能削弱
  『每个提交必须有明确位置』的治理」）—— 现在仍然是"要么有编号，要么有书面理由"，没有第三种
- ⛔ 里程碑编号的旧形状 R<3-9>-<两位数字> 与它的重号规矩原样保留（不翻旧账、不改历史提交）
- ⛔ 不重写任何已有提交（`83d57ff` 那条"环境准备"正文里**本来就写着**「无 ID：…」）
```

所以本事项做了三件事，不只是改正则：① 改语法；② **重号规矩重新界定适用范围**（并写明理由）；
③ 留下这份变更记录 + 反向可核的证据。

## ④ Behavior Contract

```text
Input          git log（基线提交..HEAD）的标题与正文
Output         每条提交能不能回溯到一个编号（或一条书面理由）
Success        标题带 R<3-9>-<nn> 或 FEAT/CHG/BUG/GOV-四位数字 → 过
Failure        两者都没有、正文也没有「无 ID：<理由>」→ 红（不产生"默默通过"）
Boundary Cases 标题里两个编号（取第一个） / R4-100 这种多打一位（不算命中）
               同一事项 ID 出现多条提交（**合法**） / 同一里程碑编号出现多条（红）
Side Effects   无（纯读 git）
Authorization  不适用
Compatibility  兼容：旧形状照收
```
