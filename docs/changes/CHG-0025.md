# CHG-0025 · 沽清 / 上架**必须先问一句**，而且那句话只有一份（2026-10-03 E2E 走查 P29）

> 走查原话（`_tmp/E2E测试报告.md:109`，逐字）：
> **P29 沽清（下架）/上架 没有二次确认（单卡与批量都一样）**
> 操作：商品管理 → 选中商品 → 沽清（下架）；或单卡上的「沽清」
> 实际：**立即执行**，只有一句 toast「沽清：成功 1 / 1」，没有确认弹层。只有「删除」有确认（且说明是软删、进回收站）。
> 影响：误触一下商品就静默下架（本次测试中确有一次误触把赣南脐橙下架，事后才发现）。
> 证据：`_tmp/rp_batch.png` `_tmp/rp_up.png`
>
> 结论：单卡与批量两个入口**都要先问一句**，而且问的那句话**全库只有一份** —— 两处各写一份的话，
> 下次改口径必然漏一页（这个仓库里已经吃过一次这种亏：同一条后果写在两个页面里，改一处、另一处留旧话）。
>
> ⛔ 两件明确不做：**不给它套红色危险件**（`DangerConfirmDialog` —— 沽清是可逆的，把「删数据」与
> 「改在售开关」画成同一件事会让人不敢点）；**不给「本次运行不再弹」那种记忆** —— P29 的病就是
> 「一次误触即生效」，用记忆免弹等于把误触原样放回去。

① **我要解决什么问题？** 商品「在售 / 沽清」这条写路径上**没有确认这一步**：卡片上那颗按钮、批量页那两个
胶囊都是「一点即改」。走查时**一次误触就把「赣南脐橙」静默下架**，事后翻列表才发现；而同一张卡上的
「删除」反倒有确认（还说明是软删、可去回收站恢复）—— 同一排按钮里，破坏力更小的那个反而更谨慎。

② **当前用户 / 业务流程是什么？** 派单员在「工作台 → 商品管理」里管几十件商品：临时缺货点一下「沽清」
让客户端立刻看不到它，补货回来点「上架」。批量页用来一次处理一整类（走查当时那一类是 **37 件**）。
这两个动作的共同点：**它改的是「客户端能不能看见、能不能下单」**，而按钮与「改价」「编辑」并排站在一起。

③ **哪个现有事实或能力会发生变化？** 只有**改在售状态那一步的时机**：从「点一下 → 直接发请求」变成
「点一下 → 开确认弹层 → 确认后才发请求」。接口（`updateProduct`）、请求体
（`ProductUpdateRequest(isActive = …)`）、权限、库存 / 订单 / 账本联动**一样没变**。
附带两处必要改动（否则「确认完什么都没发生」）：`ProductsViewModel.toggleActive` 补 `acting` 与
一句成功汇报（原来两样都没有）；批量页补上 `vm.error` 的渲染（原来写进去没人画 ——
闸门那句「先勾选商品」会静默消失）。

④ **哪些东西明确不能变化？** 软删那套语义与它的红色危险件；两处「沽清＝红 / 上架＝绿」的颜色语义；
按钮与胶囊的文案（「沽清（下架）」「上架」）与位置；批量页逐条执行 + 「沽清：成功 2 / 2」那套汇报口径；
`run()` 里那道「先勾选商品」判据（界面上的 `canAct()` 是**补充**，不是替换 —— 动作本身也得自证）。

⑤ **这个变化属于 Core、Extension 还是 Infrastructure？** **Presentation** —— 界面上多一道确认，
调用链、数据、权限一个字没改（见 ③）。

⑥ **什么证据能够证明它完成？** 判据 `_tools/qa/_check_product_active_confirm.py` **31 项**（含「全库只有一份
后果文案」「入口不许绕开弹层」「批量先过 `canAct()`」这类查全库的断言）；反向验证

## ② Must Change / Must Not Change

```text
Must Change:
  - 单卡那颗「沽清 / 上架」：只负责**打开确认弹层**，不再直接改在售状态。
  - 批量页那两个胶囊（「沽清（下架）」「上架」）：同样只打开确认弹层。
  - 两个入口共用**同一个弹层、同一份后果文案**（ui/common/ProductCardKit.kt::ProductActiveConfirmDialog）。

  - 「删除」的软删语义与它的红色危险件（DangerConfirmDialog）—— 本次一个字不动。

  - 接口、请求体、权限、审计、库存联动、账本、订单 —— 一行不改。
  - 批量页逐条执行与「沽清：成功 2 / 2」式汇报口径；run() 里原有的「先勾选商品」判据。
  - 不给这个动作加「本次运行不再弹」之类的记忆开关。
```

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

**结论：Presentation。** 这一批改的是「点下去之后先问一句、问完才发请求」，以及那句问话放在哪一份文件里；
业务规则、数据结构、权限判定一处没碰。

**五问依据**

- **输入**：仍是用户在商品卡 / 批量页上的点击 —— 没有新增参数、没有新增端点。
- **状态**：新增的三个界面状态（`toggleFor`、`confirmingActive`、`canAct()` 里的错误话术）都只在页面
  生命周期内活着，不进 VM 的业务字段、不进数据库。
- **边界**：批量页的「勾了吗」由 `canAct()` 在**开弹层之前**判；`run()` 里原有的判据保留（双保险）。
- **失败**：请求失败仍走原有的 `error` → 页面级 snackbar 路径；本批给批量页补上了那个渲染，失败从此看得见。
- **依赖**：只依赖既有的 `AlertDialog` 与主题色（`Success` / `colorScheme.error`），没有新依赖。

**核心改动声明**：无核心业务改动，故不设 Core / Extension / Infrastructure 三个边界行。

## ④ Behavior Contract

```text
Input:       用户在单卡上点「沽清」/「上架」，或在批量页勾选若干商品后点「沽清（下架）」/「上架」。
Output:      先出现确认弹层（标题点名对象与方向、正文写清后果、确认钮文案跟着方向走）；
             确认后才发 updateProduct(isActive = …)，成功后列表刷新并给一句 snackbar。
Success:     状态确实被改：卡片出现/消失「已沽清」徽章、按钮文案翻转；
             单卡 snackbar「<商品名> 已沽清 / 已上架」，批量 snackbar「沽清：成功 N / M」「上架：成功 N / M」。
Failure:     接口失败 → error 走页面级 snackbar（单卡与批量两页现在都渲染它），列表状态不变。
             批量页一个都没勾 → 不弹层，snackbar「先勾选商品」。
Boundary Cases:
             · 商品名很长：标题按 maxLines 截断，不换行撑破弹层。
             · 批量勾了 1 件 / 全选一整类（37 件）：同一句话，subject 写「选中的 N 个商品」。
             · 弹层打开时按返回 / 点外部：等同于「取消」，不发任何请求（onDismiss 只清状态）。
             · 连点确认：vm.acting 期间按钮转忙，不会重复提交两次。
Side Effects: 仅一条：确认后的一次 updateProduct（与改动前**同一个**请求）。
Authorization: 不变 —— 仍是商品管理 / 批量操作那套既有权限，本批不碰 RBAC。
Compatibility: 不涉及接口兼容性（请求体与响应体一个字没改）。
```
