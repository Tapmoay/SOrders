## ① 六问

### 问 1：用户看到的是什么？期望是什么？

「地址与联系人」页三张卡（**常用线路 / 地点 / 联系人**）右边原本各有**两颗**圈底图标：
红底垃圾桶（删除）＋ 蓝底铅笔（编辑）。用户的原话是「**删除键卡片删除键移到编辑界面当中**」——
也就是把垃圾桶从卡上拿掉，放进**点铅笔之后弹出来的那张编辑抽屉**里；
而且点它**不能直接删**：「**删除都要做二次确认**……**不要点一下就直接删掉了，防止误触**」。

现在这一页的删除是**一点即删**：手指扫过卡片右上角，一条常用线路 / 一个联系人 / 一个常用地点
当场就没了（虽然顶上会留一行「已删除 X ＋ 撤销」，但那是**事后**的兜底，不是**事前**的拦阻）。

### 问 2：为什么现在不对？

一个原因是**形态**：删除和编辑挤在同一张卡的同一行，两者只差**颜色和图标**，
而这一页的卡片又长得几乎一样（列表里一屏五张），误触概率本来就高。
更深的原因是**没有闸**：这一页的删除是「点一下 → 直接落库」，
而共用件 `DangerConfirmDialog`（商品卡的沽清 / 上下架就是走它）**早就有了**，
这一页却一直没用 —— 「哪些页面该问一句」在代码里**没有任何机制**，只靠写的人记得。

### 问 3：最小的改动是什么？

四处，都在这一页内部：

1. **举手与执行分开**（`AddressViewModel.kt`）：新增 `askDelete(kind)` —— 只把"要删的是哪一档、叫什么名字"
   记进 `pendingDelete`，**一个落库调用都不发**；新增 `confirmDelete()` —— **全 VM 唯一**的落库点，
   顺手把抽屉关掉；新增 `cancelDelete()` —— 只清状态。三个 `delete*` 本体一行未动。
2. **两句话是纯函数**：`deleteConfirmTitle(what, name)`（标题点出删的是哪一条，名字空着就退成「删除这条 X？」）
   ＋ `deleteConfirmMessage(what)`（正文说清"软删 ＋ 列表顶上留一行「已删除 X」＋ 撤销可以恢复 ＋ 离开这一页就找不回来"）。
   纯函数 ⇒ 单测能直接钉住这两句话（弹层上说什么不再靠肉眼）。
3. **卡片与抽屉**（`AddressScreen.kt`）：三张卡去掉删除那一颗（只剩右边编辑）、
   三个编辑抽屉各加一行红字「删 除」（只在**编辑已有**的时候出现），点它只调 `vm.askDelete(...)`；
   页尾（页面最外层，不在抽屉里）画一份共用的 `DangerConfirmDialog`，确认才走 `vm.confirmDelete()`。
4. **单测 ＋ 判据**：`AddressDeleteConfirmTest.kt` 钉住那两句话；
   `_check_delete_confirm.py` 钉住"举手不落库 / 确认是唯一落库点 / 三处入口 / 两句话 / 接线"。

### 问 4：不改会怎样？

误触那一下**没有任何东西拦得住**：一条常用线路（收发货地址 ＋ 联系人）就这么没了，
用户得自己发现顶上那行「撤销」、并且在它还在的时候点下去。真机上这一页的卡片密度不低，
删除和编辑还长在同一行的同一侧。

### 问 5：怎么知道改好了？

四件事：**新判据** `_check_delete_confirm.py`（六层，含反空转与"唯一落库点"）；
**反向验证** `_reverse_verify_delete_confirm.py`（17 条注入：把举手改回直接删、把确认钮改成空、
把两句话删掉、把单测改成壳……每条都必须让判据报红）；
**既有红线** `_check_address_cards.py`（按新布局重写，卡上不许再有删除）＋ `_check_delete_undo.py`（撤回那条链路照旧绿）；
**真机**：模拟器上点一遍 —— 卡片上没有垃圾桶、抽屉里有、点了先弹确认、点「取消」什么都不发生、
点「删除」才消失并且顶上能撤销。

### 问 6：动了谁？

见头部 Blast Radius。一句话：**这一页 ＋ 它的判据**，后端与仓库层一行未动。

## ④ Behavior Contract

1. 卡片上**没有**删除入口：三张卡各只剩一颗编辑（圈底铅笔，`contentDescription = "编辑"`）。
2. 删除入口在各自的**编辑抽屉**里：只在**编辑已有**那条时出现（新增时没有"这一条"可删）。
3. 点抽屉里那一行**什么都不发生**（不落库）：只有页尾弹层上点「删除」才真的删。
4. 弹层标题**点名删的是哪一条**（带名字）；名字空着时退成「删除这条 X？」，**不留一对空引号**。
5. 弹层正文必须说清四件事：软删、列表顶上留一行「已删除 X」、点「撤销」可以恢复、离开这一页就找不回来。
6. 点「取消」或点空白处 = **什么都不发生**（只是把弹层关掉）。
7. 确认之后：抽屉关掉、那条从列表消失、顶上出现「已删除 X ＋ 撤销」（**这一条是既有行为，没动**）。

4. **Known Limitations**：抽屉里那一行删除**够不着**"跨页删除"这类批量动作（本批没有批量删除）；
   `pendingDelete` 只在内存里 —— 退到后台再回来它还在（VM 没重建），彻底离开这一页才清。
5. **Rollback**：把三张卡的删除图标与 `onDelete` 形参加回去、删掉三个抽屉里的那三行与页尾弹层即可（判据会当场报红，正是要它红）。
6. **Historical Data Impact**：无（这一批不动任何数据与接口）。

> **最后一个问题**：这次改的其实是"**危险动作与手指之间要不要隔一道闸**"。
> 上一版把删除放在卡片右上角、和编辑在同一个位置，靠**颜色**区分；
> 这次把它挪进"要点两下才到"的地方，并且**让它在落库之前必须遇到一次确认**。
> 判据这一侧也换了个思路：不再只数"卡片上有几颗、谁左谁右"，而是钉住
> 「**全 VM 只有一个落库点**」—— 这一条不随布局变，布局再怎么改，只要还有一条绕过确认的路，它就红。
