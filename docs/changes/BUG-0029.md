# BUG-0029 · 客户收款登记之后没有任何撤销/红冲入口

> 来源：测试台账 **TB-09**（财务方向测试 2026-10-10 03:03 CST 在 8020 副本库上复现；严重度 **可疑**）。现象：派单员在账本里登记一笔客户收款（`POST /api/v1/ledger/receipts`）会一次写**四个落点** —— `shipper_receipts` 一行、它写下的 `cash_flows`(`RECEIPT_*`) 若干行、被翻成 `paid=true` 的那几张订单、以及由前两者算出来的 `turnover` 的 collected/arrears 与 `customer-balances`；而**撤销入口一个都没有**（`DELETE|PATCH /api/v1/ledger/receipts/{id}`、`POST /{id}/restore`、`/{id}/cancel`、`DELETE /api/v1/cash-flows/{id}`、`POST /api/v1/cash-flows/{id}/restore` 全部 **404**），App 侧只有 `listReceipts` / `createReceipt`。系统自己知道：`backend/app/api/v1/orders_payment.py:199` 的报错原文写着「系统目前**没有撤销收款的入口**……如果这笔收款记错了，请联系管理员在账上冲正」—— 而管理员同样没有任何入口。一笔记错的收款永久留在「已收」里，只能靠把货退掉（`REFUND_CUSTOMER` 退现）或直接改库来纠正。
> 用户 2026-09-20 定的硬规矩是「**所有删除一律软删（伪装删除）＋ 必须有恢复路径**」，落地要点第④条原文是「**界面要有一个手边的撤销入口**（不要只把恢复藏在 AI 撤回卡里）」—— TB-09 踩的正是这一条：系统自己都在说"撤不回来、去找管理员"，而管理员手上也没有那扇门。
> 修复：DSH 修复会话 `625da590-1164-4807-ab86-106e24c84559`，2026-10-10 05:1x–06:0x CST（证据见 §⑧）。

① **我要解决什么问题？** 一笔记错的客户收款**没有任何回头路**，三个层级都没有：

### R4-BOUNDARY-JUSTIFICATION：为什么边界解决不了这件事

TB-09 的症状（"登记错了撤不回来"）**不是越界造成的**，而是**一条写入路径没有反向路径**：

- `cash_flows` 早就有 `is_deleted` / `deleted_at`（供应商付款那一期加的），同一张表在客户收款这条路上却没有任何回头路 —— 这是能力缺口，不是分层错误；
- 撤销必须**四个落点一起**回滚。把这四件事拆到四个扩展点上（收款单一个、流水一个、订单一个、报表一个）只会造出"改了一半"的中间态：`order_money` 的口径是「有流水按流水算、没流水才按 `paid` 算」，任何一半单独执行都会留下一个**两边都不报错、但数对不上**的状态；
- 也不能靠"再写一笔反向的钱"绕过：那会在账上留一对谁也不敢删的行，而且"这笔到底算不算"要靠人去读备注（供应商付款那一期的 docstring 已经把这条路否掉了）—— 本单沿用它的结论：**撤销 = 把那一行藏起来**。

所以最小改动落在**接口层 ＋ 一次幂等 DDL**：两个端点把四个落点一起翻、一次翻完；⛔ 明确**没有**走「给 `cash_flows` 加一种反向 `biz_type`」或「在 `accounting_service` 里加一个 `reverse_receipt`」那两条路：前者要动 `cash_flows` 的语义与所有按 biz 取数的口径，后者会动到钱的核心实现。

## ④ Behavior Contract

```text
B1  撤销：DELETE /api/v1/ledger/receipts/{receipt_id} → 204（仅派单员；其它角色 403「仅派单员可操作」）。
B2  撤销同时把四个落点一起回滚：① 收款单 is_deleted=1、deleted_at=<now>；② 这笔收款写下的每一行 cash_flows（doc_id=收款单 id 且 party_type=customer 且 biz_type ∈ {RECEIPT_CASH, RECEIPT_TRANSFER, RECEIPT_ARREARS}）is_deleted=1、deleted_at=<now>；③ 这笔核销过、且此刻仍是 paid=true 的订单 → paid=false、payment_method="arrears"；④ turnover.collected / arrears_total 与 customer-balances 由 ①②③ 自动跟着回到收款前（那两处不重算、只搬 order_money）。
B3  撤销**不是物理删除**：三处的行都还在库里（收款单、资金流水、订单），只有标记位变；再次撤销 → 400「这笔收款（#id）已经撤销过了，不用再撤一次」，且账上的数一个都不动。
B4  撤销**找不到流水时拒绝**（400）：只把收款单藏起来、钱还留在账上会让两边对不上 —— 宁可不动。
B5  撤销/恢复都在**同一个事务**里写一条 operation_logs（RECEIPT_CANCEL / RECEIPT_RESTORE，payload 带 receipt_id / customer_id / amount / method / order_ids / flow_ids），并往发件箱入一条 ledger.updated（收件人 = 客户账号 ＋ 这一批单的司机 ＋ 派单员）。
B6  恢复：POST /api/v1/ledger/receipts/{receipt_id}/restore → 200，返回收款单（含 is_deleted=false / deleted_at=null）；没被撤销的 → 400「没有被撤销，不需要恢复」（幂等，第二次不许把数改回来第二遍）。
B7  恢复把四个落点原样放回：收款单与流水 is_deleted=0、deleted_at=null；订单 paid=true、payment_method 按收款单的 method 写回（cash/transfer/wechat → "cash"，否则 "arrears"）。
B8  恢复的四道门（都在**改数之前**判完，任一不成立 → 400 并点名）：订单不存在 / 订单在回收站 / 订单已撤销或已退货 / 订单现在已经是「已收款」（可能又收过一次）—— 最后一道是不让同一笔钱被算两遍。
B9  收款记录默认看不见已撤销的：GET /api/v1/ledger/receipts 不带参数时过滤 is_deleted=false；include_deleted=true 时连已撤销的一起返回（回收站档，界面「恢复」的落点），行里带 is_deleted / deleted_at。
B10 App：「客户收款」页收款记录每一行有「撤销」（点开二次确认，文案写明"会从已收里退回来，不是删掉，随时能恢复"）；撤销成功那条 snackbar 自带「撤回」；标题行右侧「显示已撤销」切到回收站档，那里的行给「恢复」。
B11 审计页：撤销/恢复各显示中文名「撤销收款」/「恢复收款」（不是原始码）。
B12 钱的金额一律不变：收款单 amount、流水 amount、订单行金额、结算与司机账单，一个字节都不动。
```

## ⑤ Data Contract

- **表结构（新增两列 ＋ 一个索引，幂等 DDL）**：`shipper_receipts.is_deleted BOOLEAN NOT NULL DEFAULT 0`、`shipper_receipts.deleted_at DATETIME`、`CREATE INDEX ix_shipper_receipts_is_deleted`；历史行回填 `is_deleted = 0`（⛔ 不留 NULL）。
- **接口（新增两个写端点）**：`DELETE /api/v1/ledger/receipts/{receipt_id}`（204，无出参；403 非派单员 / 404 不存在 / 400 已撤销过或找不到流水）；`POST /api/v1/ledger/receipts/{receipt_id}/restore`（200，`ShipperReceiptOut`；403 / 404 / 400 没被撤销或四道门任一不成立）。
- **接口（既有出参扩两个字段）**：`ShipperReceiptOut.is_deleted: bool = False`、`ShipperReceiptOut.deleted_at: datetime | None = None` —— 老客户端不认识这两个字段不会报错（多余字段被忽略），新客户端在老后端上回落 `false` / `null`。
- **接口（既有查询参数）**：`GET /api/v1/ledger/receipts?include_deleted=true`（缺省 false = 老行为：只返回"活着"的收款）。
- **审计动作码**：`OperationAction.RECEIPT_CANCEL = "RECEIPT_CANCEL"`、`OperationAction.RECEIPT_RESTORE = "RECEIPT_RESTORE"`（`operation_logs.action` 存枚举名）。
- **老数据（legacy）**：本单之前登记的收款**全部视为"活着"**（回填 0），行为与改前逐字相同；已撤销的收款不进任何金额计算，`cash_flows` 那两列的既有纪律（凡取数带 `is_deleted.is_(False)`）一个字没变。
- **两处刻意不过滤的读取**（是判断，不是漏）：`backend/app/api/v1/arrears.py:243`（删挂账单位前的占用计数 —— 已撤销的收款单那一行**还在库里、还指着这个单位**，算进去才保守）与 `backend/app/api/v1/customers.py:154`（客户合并搬迁 —— 连已撤销的也要搬，否则回收站里那张单指向一个不存在的客户）。

## ⑥ CHG 专章

### 病灶：一条写入路径，四个落点，一条反向路径都没有

```python
# backend/app/services/accounting_service.py:521-536 与 :489 / :515（改前 → 改后**逐字未动**）
    receipt = ShipperReceipt(customer_id=..., amount=..., method=..., received_at=...,
                             order_ids=order_ids or None, settle_mode=..., ...)
    db.add(receipt)
    db.flush()
#   ↑ 落点①：收款单一行
#   ↓ 落点②：这笔钱写下的资金流水（逐单核销逐行 / 滚动一笔，doc_id=收款单 id）
    for oid, part in per_order.items():
        db.add(CashFlow(order_id=oid, amount=part, ..., doc_id=receipt.id, **common))
#   ↓ 落点③：被核销的订单翻成已收
    update(Order).where(Order.id.in_(settling), Order.paid.is_(False)).values(
        paid=True, payment_method="cash" if ... else "arrears")
#   ↓ 落点④：turnover 的 collected/arrears 与 customer-balances 由上两处算出来（不另存）
```

四个落点全在，**反向的一个都没有**：`shipper_receipts` 当初没有软删两列、没有删除端点；`cash_flows` 有 `is_deleted` 但客户收款这条路上没有撤销端点（同一张表的供应商付款那条路有）；订单的 `paid` 翻上去之后再没有任何一条路翻回来。于是那句报错文案成了唯一的"出口"：「系统目前没有撤销收款的入口……请联系管理员在账上冲正」—— 而管理员也没有入口。

### 改法（三条，都在 §② 的 Must Change 里）

1. **收款单学会"伪装删除"**：挂 `SoftDeleteMixin` ＋ `schema_bootstrap` 幂等 DDL 两列 ＋ 索引 ＋ 回填（照 `cash_flows` / `products` 那一期的体例）；
2. **两个端点把四个落点一起翻**：撤销 = 流水逐行软删 ＋ 订单收回未收款 ＋ 收款单软删；恢复 = 原样放回（四道门在改数之前判完）。**判据「这笔收款写了哪些流水」只有一处**（`doc_id == receipt_id` 且 `party_type == customer` 且 `biz_type ∈ RECEIPT_FLOW_BIZ`）—— ⛔ 只认 `RECEIPT_CASH` 的话，转账 / 微信 / 挂账结清的收款撤不干净；
3. **给人一扇手边的门**：收款记录行上的「撤销」＋ 回收站档的「恢复」＋ 撤销后 snackbar 上的「撤回」；审计页两个中文名。

### 为什么不是"再写一笔反向的钱"

那会留下**一对谁也不敢删的行**，而"这笔到底算不算"要靠人去读备注 —— 供应商付款那一期已经把这条路否掉了（`backend/app/models/cash_flow.py` 的模块 docstring 逐字写着理由），本单沿用：**撤销 = 把那一行藏起来，恢复 = 原样放回来**。

### 为什么这一单没顺手把 AI 侧也开出来

两个新端点在 `_tools/ai/_write_coverage.py` 的 `EXCLUDED` 里各有一条**排期**理由（不是永久排除）：用户 2026-09-20 那条硬规矩的第④条原文要的正是"**界面**要有一个手边的撤销入口"，所以本轮先把那扇门给人开出来；AI 侧的成对动作（`ledger.cancel_receipt` ↔ `ledger.restore_receipt` ＋ 撤回卡）单独立项 —— 理由写在那个脚本里（撤销要四个落点一起回滚、恢复的四道门读的是**提交那一刻**的库，而确认卡是**预览那一刻**写好的）。同时把 `ai/AiRevert.kt` 里那句「收款一旦入账，撤回来等于把账抹掉」换成**指向真实入口**（那句话在本单之后是假话）。
