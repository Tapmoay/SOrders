## ① 六问

**① 要解决什么**：用户 2026-10-22：「更新日志……就是每次办完更新了什么可以查看的，就在我们那个
**更新那个入口**里有个更新日志，可以查看每个版本更新了什么」。

**② 当前流程是什么**：只有一条 `GET /api/v1/system/app-version`，读服务器上的 `version.json` ——
**每次发布都被覆盖**，只留得住最新一版和它的 note。「检查更新」弹窗里能看到那一句，但**历史没有**。

**③ 哪个事实会变**：多一份**历史**（`docs/releases.json` → 服务器 `uploads/app/releases.json`）、
多一条只读接口 `GET /api/v1/system/app-releases`、多一个入口「更新日志」。既有接口与 version.json 一字不动。

**④ 明确不能变**：
- ⛔ `version.json` 的契约（检查更新仍然只认它；老客户端照旧）；
- ⛔ 不改「检查更新」的判定逻辑（versionCode 优先）；
- ⛔ 不加权限：这条接口和 app-version 一样是**公开只读**（谁都能看"这软件改了什么"，那不是秘密）；
- ⛔ 历史**只追加**，不回改（⛔ 不许把一条旧记录改成"今天的口径"）。

**⑤ Core / Extension**：**Infrastructure + Presentation**。它是一条只读的版本说明，不碰业务事实。

**⑥ 证据**：判据 18 项、dev 后端 curl 回两条、模拟器截图（入口 + 弹层）。见 ⑦ ⑧。

## ④ Behavior Contract

```text
Input          GET /api/v1/system/app-releases（无参数、无鉴权）
Output         {"items": [{"version": "0.2.20", "version_code": 2026101502, "date": "2026-10-15", "note": "…"}, …]}
Success        按 version_code 降序，最多 50 条
Failure        文件缺失/坏 JSON ⇒ 退回 version.json 那一条（仍是 200，界面上有内容）；
               ⛔ 绝不返回空列表（空列表在界面上读起来是"这软件从没更新过"）
Boundary Cases · 同一 versionCode 重发：publish_apk.py 覆盖那一条而不是追加第二条
               · versionCode 缺失（老数据）：按文件顺序，不参与排序
Side Effects   只读（不写库、不发通知）
Authorization  公开只读（与 app-version 同一条口径）
Compatibility  **Compatible**：新增接口，老客户端不受影响
```

## ⑤ Data Contract

- **新增哪些字段**：`docs/releases.json` 的 `items[]`：
  `version` / `version_code` / `date` / `note`（+ 文件级 `_note` 说明）。
- **Owner**：发布脚本 `_tools/deploy/publish_apk.py`（**唯一写入口**；⛔ 界面与后端都不写）。
- **什么时候写**：每次发布（上传 APK 之后、写 version.json 之后）；⛔ 平时不写。
- **是否允许 NULL**：`date` / `note` 允许为空（界面就不印）；`version` 必填。
- **历史数据怎么办**：手工补了 0.2.19 / 0.2.20 两条（这是**真实发过的**两版，note 取自当时的发布说明）；
  ⛔ 再往前的版本**不补**（当时的 note 已被覆盖，编一个就是伪造历史）。
- **迁移怎么做 / Rollback**：没有数据库迁移；回滚 = 撤掉接口与那一行入口，`docs/releases.json` 留着无害。
- **删除本功能后历史数据还能不能解释**：能（那份 json 就是记录本身）。
