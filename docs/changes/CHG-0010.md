① 派单员（以及货主 / 批发商）手上常常只有**一个名字、没有电话**的联系人（工地上的人、只报名的收货人）。
现行「新建联系人必须填手机号」把这种人挡在门外，用户只能随手编一个号——编出来的号是**假事实**，
既污染档案，又会顶掉唯一约束。需求方原话：「新建联系人的时候不需要必填手机号」。
需求方还追加了一条**闭环**要求：「在下单的时候用户或者说是货主批发商以及派单员是可以不这个手机号的，
**一旦补上去了，他就自动的做一份保存**」——补上的号不该只在这一次订单里生效。

② 现在的流程：任何入口新建联系人都要过 `InputRules.phoneError(required = true)`，
后端 `ContactCreate.phone` 必填、库里那一列 NOT NULL（写空串进库）；派单时从联系人里选收货人，
姓名与电话带进订单表单，但**改完不会回写档案**，下次下单还得再填一遍。

③ 三件事变：
  · **写入门槛**：手机号从必填变选填，但**姓名与手机号至少有一个**（不能建一个完全空的联系人）；
  · **存储事实**：没填就是 `NULL`（不是空串），空号之间不互相顶唯一约束；
  · **取值闭环**：提交订单时，若收货人是从档案里选的、档案里没号、这次填了号 → 写回档案。

④ 不能变：
  · `uq_shipper_contact_phone`（同一货主下手机号唯一）与「同号即同人」的判重语义；
  · 代理下单「选货主 → 下单人姓名必带 + 有电话才填电话」——本来就是对的；
  · 软删除的 `_del{id}` 后缀机制与 restore 的匹配规则；
  · 历史联系人的号码一个字都不动（**不回填空串**）；
  · 订单本身的事实（金额 / 状态 / 归属 / 司机快照）。

⑤ **Infrastructure + Presentation**：库列与出参归一属于数据契约的**放宽**（不是新事实），
UI 校验与写回触发属于展示层与调用编排；没有引入新的核心概念。

⑥ 证据：判据 `_tools/qa/_check_contact_binding.py`（**77 项**，原 43 项）+ 反向验证
`_tools/qa/_reverse_verify_contact_binding.py`（**33 条**注入）+ 回归用例
`backend/tests/test_contact_phone_optional.py`（7 个用例）三处同时证明；再用三台模拟器实机验一遍新建 / 下单 / 写回。

## ② Must Change / Must Not Change

```text
Must Change:
- 新建联系人的手机号由必填改选填，但姓名与手机号不许同时为空（前后端同一条文案）
```

## ④ Behavior Contract

```text
Input          ContactCreate{name, phone?} / ContactUpdate{phone?}；下单时收货人姓名 + 收货人手机号（可空）
Output         ContactOut.phone（库里 NULL → 出参一律 ""）
Success        ① 只填姓名 → 201，phone 为 NULL（出参 ""）
               ② 姓名+号码都填 → 与现在完全一致
               ③ 提交订单且 收货人来自档案 + 档案无号 + 本次填了号 → 订单照常创建，随后 PATCH 回写档案
Failure        姓名与手机号都为空 → 400「联系人的姓名和手机号至少填一个」（Create/Update 都拦）；
               号码格式非法 → 422（既有 ContactPhone 规则，未放宽）；
               回写失败 → 只记日志，**不回滚订单、不弹错**（订单已经成立，补号是附带动作）
Boundary Cases 两条都没号的联系人可以共存（NULL 不参与唯一约束）；
               给原本没号的人补号 = 正常 PATCH；
               PATCH 同时清空姓名与号码 → 400；
               补的号撞上别人已有的号 → 409 该电话已存在已有联系人；
               删除没号的联系人 → 不许编出 _del{id}，库里仍为 NULL；restore 仍能按后缀找回
Side Effects   提交订单时可能多发一次 PATCH /contacts/{id}（仅三条件同时成立时）
Authorization  沿用既有联系人写权限，⛔ 不新建权限点
Compatibility  Compatible（放宽）：老客户端继续必填，行为不变；新客户端可不填；
               出参 NULL→"" 让所有老读端无需改动
```

## ⑤ Data Contract

- **新增/改动哪些字段**：`shipper_contacts.phone` —— `VARCHAR(32)` **NULL 化**（类型与索引不变）。
  没有新增列、没有新增表。**含义变了的那一格是**：`NULL` = 「这个人没留号码（未知）」，
  空串 = 不合法值（前后端都不再写空串进库）。
- **Owner 是谁**：联系人档案归属 `shipper_contacts`（货主域），见 `docs/R4_CORE_EXTENSION_MAP.md`。
- **什么时候写 / 什么时候不写**：只在 Create / Update；**下单成功后的回写**只写「档案里原本为空」的那一格，
  档案里有号就一个字都不动（`if (archived.phone.isNotBlank()) return`）。
- **是否允许 NULL**：允许（本次改动的全部内容）。姓名仍不可为空。
- **历史数据怎么办**：**原样不动**。迁移 011 只改列定义、不 UPDATE、不回填空串 ——
  历史上「编出来的号」仍留在库里，由人来改；系统不替它判断真假。
- **迁移怎么做 / Rollback 怎么办**：`backend/app/migrations/011_contact_phone_optional.py`
  （`VERSION = 11` / `NAME = "contact_phone_optional"`）：先 inspect 列是否已经可空，可空即直接 return（幂等）；
  SQLite 走 `_sqlite_rebuild(engine)`（中转表 `shipper_contacts_chg0010_stage` → DROP → 按模型重建 → 搬回），
  其它方言 `ALTER TABLE shipper_contacts MODIFY COLUMN phone VARCHAR(32) NULL`。
  Rollback = 写一个 012：先把没有号的行**人工**补上号码，再改回 NOT NULL（⛔ 不许编造号码）。
  这是本事项唯一「回不去」的地方，必须人来做。
- **删除本功能后历史数据还能不能解释**：能。NULL 就是「当时没留号码」，不需要别的表来翻译。

## ⑥ CHG 专章

### Before

- 新建联系人：号码一栏写着「手机号（必填）」，留空 → 红字「请填写手机号」，保存键点不动。
- 后端：`ContactCreate.phone` 必填；库里那一列 NOT NULL（空值写空串进库）。
- 派单时选了联系人 → 姓名与号码带进订单表单；**改完号码只属于这一张订单**，档案还是旧的。

### After

- 新建联系人：占位文案「手机号（选填）」；只填姓名就能存；姓名与号码都空才算错，红字「姓名和手机号至少填一个」。
- 后端：没填 → 库里 `NULL`；两个都没号的联系人**可以共存**；出参把 NULL 归一成空串。
- 派单时先从联系人里选收货人：之后**手动改「收货人名称」** → 视为换人，不再回写（`pickedContactId = null`）；
  **手动改「收货人电话」不算换人** —— 给没号码的联系人补号码，正是要写回**同一条**档案。
  ⚠️ 这两栏口径不同是刻意的，别"顺手对齐"：第一版把电话那一栏也解绑了，
  模拟器 E2E 实测「那条联系人到下单结束还是没号码」（订单 549 建成了，档案 42 的 phone 仍是 NULL）。
  填了号、档案里原本没号 → **提交订单成功后**自动 PATCH 回写档案，档案列表同步刷新。
- 只对「选出来的那个人」回写；手打一个从没进过档案的收货人，**不会**凭空建档案。

### Must Preserve

```text
- 历史订单 / 历史金额 / 已冻结的 Pricing Fact
- 历史 Provenance / Audit / Ledger
- 权限
- API compatibility
- 同一货主下手机号唯一（uq_shipper_contact_phone）与「同号即同人」判重
- 代理下单「选货主 → 下单人姓名 + 有电话才填电话」（本来就是对的，一个字没动）
- 软删除 _del{id} 后缀与 restore 匹配规则
- 历史联系人的号码内容（不回填、不猜测）
```

### Blast Radius（L0～L3）

**L3**。理由：本事项含**数据库迁移 011**（改 `shipper_contacts.phone` 的可空性），
按规范 §二十六 命中 L3 触发项「数据库迁移」；L3 要求 = 证据表 + 反向验证 + 回滚预案 + 关闭六格，
本文件 ⑦⑧⑨ 逐条对应（与 FEAT-0001 / 迁移 010 同口径）。
副作用半径本身很小（只碰联系人档案一列 + 两个调用点的编排），但**列定义变更属于不可回退类改动**，
所以按最严的一档走。
