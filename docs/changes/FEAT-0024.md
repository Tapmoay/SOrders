## ① 六问

① **要解决什么问题？** 用户能在 AI 聊天里贴图（`ai/AiAttachment*`、`AiVision.kt` 早就能收图、也能看懂图），但**贴了图之后没有任何写动作能把它用起来** —— 想让 AI「把这图设成商品图」，AI 只能说"我做不到"。用户原话（2026-10-11）：「我们的那个 AI 要**支持上传商品图片**的 —— 我给它一个图片，他能帮我上传商品图片，包括什么**地点图片**啊、什么……图片，他都能帮我上传。」

② **当前用户/业务流程？** 人工路径早就存在：商品编辑页有「选图 → 上传 → 写进 `image_url`」；地点/线路抽屉有 `ImageStrip`（拍/选多张 → 逐张上传 → 随对象 PATCH 进 `image_urls`）。缺的是**模型这一侧**：它拿不到文件。

③ **哪个现有事实会变化？** AI 写动作清单多三条：`products.image` / `location.image` / `address.image`；`_tools/ai/_write_coverage.py` 的 `EXCLUDED` 里两条「上传类：模型给不出文件」被**移出**（那两条现在有 AI 动作了）。

④ **哪些东西明确不能变？** ① **多图字段的三档语义**（缺省 = 不改 / `[]` = 清空 / 非空 = 整体替换 —— 2026-09-03 定的）；② **撤回锚**（payload 里带着那个键的旧值，旧 URL 一直在服务器上，撤回只是一次普通的字段写回，**不重新上传**）；③ 上传仍走**既有的两条端点**（`POST /products/{id}/image` 与 `POST /shipper/locations/image`），不新增上传端点；④ `prepare` 阶段**绝对不写后端**（上传发生在 `commit`，即用户点确认之后）。

⑤ **属于 Core、Extension 还是 Infrastructure？** EXTENSION IMPL（`ai/AiWriteImage.kt`、`ai/AiWriteImageHandlers.kt`、`ai/AiImageInbox.kt`）＋ 既有端点的复用。

⑥ **什么证据能够证明它完成？** `_tools/qa/_check_ai_image_actions.py` 33 条断言全过；反验 `_reverse_verify_ai_image_actions.py` 8/8 条注入全部变红且逐字节还原；单测 `AiWriteImageTest` 13 例；`_write_coverage.py --check` 不再把这两条算成缺口。

## ② Must Change / Must Not Change

```text
Must Change:
- 三条写动作：products.image（商品只有一张图）/ location.image（地点，多图）/ address.image（线路，多图），
  一律 risk = MEDIUM（要确认）、group = 商品 / 地址；
- 链路：图片字节**在预览那一刻**就由 App 钉进确认卡的 payload（KEY_IMAGE_DATA），
  用户点确认时用的就是那一张（不会因为中间他又贴了别的图而串）；
- 卡片写清「给谁 / 用聊天里第几张 / 替换还是追加 / 原来是几张」；
- 防呆：这次聊天里**没有图就拒绝**（⛔ 不发一张没有图的空卡）；贴了多张而没点名 → 把这几张列成候选；
  点了一个不存在的序号 → 如实说现在有几张；
- 商品只有一张图，不提供「追加」；地点/线路必须把「追加 / 整套替换」问清，问不清就拒绝；
- _write_coverage.py 的 EXCLUDED 里两条上传端点的理由与「v3.7 永久排除」那句话一起删掉（⛔ 不留化石）。

Must Not Change:
- 多图字段的三档语义（None=不改 / []=清空 / 非空=整体替换）；
- 撤回锚与撤回路径（旧 URL 不重新上传，只写回旧值）；
- 上传端点（复用既有的两条，不新增）；
- prepare 不许写后端；
- 后端权限与鉴权；订单/账本/库存的任何字段。
```

## ④ Behavior Contract

```text
Input          模型的一次 preview_write：products.image / location.image / address.image
               ＋ 一个名字参数（product / location / address，走 AiWriteArgs.strict 解析成编号）
               ＋ 可选 image_index（「第几张」，1 开始）
               ＋ 多图那两条必填 mode（APPEND / REPLACE）
               —— 图片字节**不由模型给**，它只说「用第几张」。
Output         一张确认卡：摘要「把商品「红富士苹果」的展示图换成这一张」/「给地点「老王家仓库」的图片
               再加一张（原来 已有 2 张）」；明细写清用哪张、替换还是追加、原来是哪几张；payload 里
               带着图片字节（KEY_IMAGE_DATA）、目标编号、最终图片列表的锚（image_url / image_urls）。
Success        点确认 → 先上传（拿 URL）→ 再写对象（商品 PATCH image_url；地点/线路 PATCH image_urls）
               → operation_logs 与人工操作同形。
Failure        这次聊天没图 → 拒绝并告诉用户「请先在聊天框里贴一张图」（不发电空卡）；
               多张没点名 → 拒绝并把候选列出来；序号越界 → 拒绝并说清有几张；
               缺 mode（多图那两条）→ 拒绝并问清「加到后面」还是「整套换掉」；
               上传失败 → 该条不写、如实报错。失败时**不**发生：不产生半成品事实（先传后写两步里
               第一步成功、第二步失败时对象上的旧图仍在，不会变成空）。
Boundary Cases 一张图不点名（就用那一张）；多张不点名（拒绝 + 候选）；序号越界（说清有几张）；
               商品（单图）传 mode（忽略）；多图传 APPEND（原来为空 → 就是这一张）；
               多图传 REPLACE（旧的全摘掉）；非图片 / 超过 4MB 的 data URL（当场拒绝，不上传）。
Side Effects   ① 往服务器上传一个文件（复用既有端点）；② 改对象的图片字段；③ 写一条 operation_logs。
Authorization  沿用既有权限点（商品 product:manage、地点/线路 shipper 侧各自的写权限）。
Compatibility  Compatible —— 新增动作，不改既有动作的参数与语义；多图字段的出参把 image_url 兼容合并。
```

## ⑥ CHG 专章

**不适用：本事项是 FEAT（新增能力），没有"改之前的行为"要对比。** 与它相关的既有行为（多图三档语义、撤回锚、上传端点）**一个字都没改**，见 §② Must Not Change。

### 为什么选「先把文件落成 URL、再走既有 image_url 字段更新」，而不是「新增带文件的写动作」

两条路都走得通，选前者有三个具体理由：

1. **可撤回路径清楚**：图片字节与旧值一起钉在 payload 里，撤回就是「把这个键写回旧值」；旧 URL 一直在服务器上、不重新上传。若新增一条"带文件的写动作"，撤回时那份文件得再过一遍上传，撤不干净。
2. **与人工路径一模一样**：`ui/shipper/AddressViewModel.kt:577-579` 就是「先 uploadLocationImage 拿 URL、再随对象 PATCH 进 image_urls」。AI 走同一条路 ⇒ 两条路的产物形态完全一致（否则会出现"AI 传的图和人工传的图在库里长得不一样"）。
3. **变更面最小**：不新增后端端点、不新增权限点（新增上传端点会立刻触发 `_write_coverage.py` 的新缺口，而那正是本轮要清理的东西）。

### Blast Radius（L0～L3）

**L2** —— 新增三条写动作与一条"预览时钉字节"的链路，改到 `AiPendingWrite` 的载荷与 `AiWriteService` 的处理器注册；不涉及领域模型、数据库结构、权限、对外契约。回滚 = 摘三行注册。
