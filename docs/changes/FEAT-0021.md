# FEAT-0021 · 九类新消息的生产者（后端：让消息自己出现）

- **ID**：`FEAT-0021`
- **类型**：FEAT
- **状态**：进行中（**后端已完成**；⛔ 未部署、未构建 APK、未发布 —— 按用户口径与另一个会话的改动一起一键部署）
- **Owner**：后端会话（DSH `bc25d535-ddd7-43d1-87e3-82dd7428f701`，父 `session-bd8fe093-bbe1-4814-af6d-586e0980ff81`）
- **开工日期**：2026-10-11 ｜ **关闭日期**：待与另一会话的改动合并部署后关闭
- **Blast Radius**：L2 —— **行为与数据**：`notifications` 表会多出七类新行（用的是现成列，**无 DDL / 无迁移**）；五条既有写路径（新设备绑定、两个解冻端点、手工出入库、送达实扣、发票开具）多了"写一条消息"这个**与业务同事务的副作用**；`backend/app/main.py` 多一条每日循环。⛔ 无新增列、无新端点、无新权限点、⛔ App 一个文件没改。

## ① 六问

1. **用户要什么**（2026-10-11 任务书逐字）："给九类新消息补『生产者』——它们现在只会显示、不会自己出现"；"账号在一台**新设备**上登录成功时，给**账号本人**发一条 danger 消息"；"商品库存**低于报警阈值** `products.low_stock_alert` 时发 danger、低于建议水位发 warn"；"供应商应付款到期前 N 天（自定，写进变更单）发 warn、已逾期发 danger；每日扫一次"；"能顺手做就做；做不了就在变更单里列成『下一单』，⛔ 不要留半成品"；"同一件事不许反复刷屏……**判据要钉住这一点**（连续跑两次扫描，通知条数不增加）"。
2. **现在是什么样**：FEAT-0019 已交付**渲染**（`notifications.severity` 列 ＋ `payload["emphasis"]` ＋ App 卡片），九类 `type` 也在 `SEVERITY_BY_TYPE` / `EMPHASIS_BY_TYPE` 里登记了档位与新闻词 —— 但**全库没有任何一处代码会创建这九类行**。它们只出现在 `message_center.py` 的表里与 Android 的 `MessageGrading.kt` 里。
3. **为什么现在不行**：消息中心是个"只读陈列柜"——样式做好了、客户端认这些类型、档位也定了名，但**永远不会有一条**。用户点开消息 Tab 永远看不到库存告急、账款逾期、新设备登录。
4. **改成什么样**：新增 `backend/app/services/message_producers.py` —— **"发什么"（文案 / 点名 / 深链）只有这一个文件**；"怎么发"（`severity_for` 档位判定、`emphasis_for` 四道闸、幂等键拼法）仍只有 `message_center` 一处，生产者里 ⛔ 不出现 `Notification(` 与 `severity=`。触发两条路：① 业务写路径上的钩子（新设备绑定 / 设备解冻 / 库存变动 / 发票开具），与业务**同一个事务**；② `main.py` 里一条**每日兜底扫描**（库存低 / 应付临期 / 应付逾期 / 应收超限）—— 扫描**幂等**，跑 N 次结果相同。
5. **怎么证明改对了**：判据 `_tools/qa/_check_message_producers.py`（八组 190 项）＋ 反向验证 `_tools/qa/_reverse_verify_message_producers.py`（8 条注入全部被抓、末尾逐字节还原）＋ 单测 `backend/tests/test_message_producers.py`（14 条，含"连续跑两次扫描、通知条数不增加"）。
6. **怎么回退**：`git revert` 两笔代码提交（＋ 文书一笔）即可；数据面见 ⑨ Rollback —— 已经发出去的那七类消息是**真实事件记录**，回退代码不会让它们消失（只是不再新增）。

## ④ Behavior Contract

- **Input**（生产者 API，全部只在本文件被调用）：
  - `notify_stock_low(db, *, product_id, stock=None, day=None) -> int`
  - `scan_stock_low(db, *, day) -> int`
  - `payable_due_date(payable) -> date` / `payable_kind(payable, *, day) -> str | None`
  - `notify_payable(db, *, payable, kind, day) -> int` / `scan_payables(db, *, day) -> tuple[int, int]`
  - `scan_arrears_over_limit(db, *, day) -> int`
  - `notify_invoice_issued(db, *, invoice, operator_id=None) -> int`
  - `notify_new_device_login(db, *, user, binding, source) -> int`
  - `notify_device_unfrozen(db, *, user_id, count, anchor) -> int`
  - `run_daily_scan(db, *, day=None) -> dict[str, int]`（返回 `stock_low` / `payable_due_soon` / `payable_overdue` / `arrears_over_limit` 四项计数，末尾 `db.commit()`）
- **Output**：向 `notifications` 追加行，`category="reminder"`，`type` 为上述七个之一，`severity` 由 `severity_for(type)` 现算，`payload["emphasis"]` 由 `emphasis_for` 过滤后写入；返回值 = **本次新写的条数**（`0` 表示"要么不成立、要么今天已经发过"）。
- **Success**：库存到线 / 应付临期或逾期 / 欠款超限 / 发票开具 / 新设备登录 / 设备解冻各自产生对应的那一类消息，收件人正确（库存 / 应付 / 超限 / 发票 → **在用派单员**；新设备登录 / 设备解冻 → **账号本人**）。
- **Failure**：`type` 不在表里不会被本模块产生（模块里每个 `type_` 都是字面量）；商品 / 应付单 / 供应商不存在或已删 → 返回 0 **不抛错**（这不是故障，是这件事没意义了）；派单员一个都没有 → 返回 0 **不报错**。
- **Boundary Cases**：库存 `>` 阈值不发、`==` 阈值**发**（≤）；`low_stock_alert = 0` 是"不报警"而不是"阈值是 0"⇒ 不发；`stock` 传不传都行（不传只读列值 —— 送达实扣走 SQL 表达式自减，ORM 实例上那个数可能是**扣减前**的）；应付剩 7 天 → 临期、**第 8 天不发**、到期当天 → 临期、逾期 1 天起 → 逾期；**付清的应付单不发**（`unpaid <= 0`）；`account.new_device_login` 只在 `source == SOURCE_LOGIN` 时发（注册绑第一台设备不是"新设备登录"）；`count <= 0` 的解冻不发；同一锚点重放不发第二条。
- **Side Effects**：写 `notifications` 行 ＋ 写 `outbox_events` 行（同一个事务）；不额外 commit（去重撞键时吞掉唯一键冲突并跳过，见 `_send`）。
- **Authorization**：**无变化** —— 本单没有动任何权限点、端点门或 RBAC；生产者是在既有端点已经过完权限校验之后才被调用的。
- **Compatibility**：新增的七类 `type` FEAT-0019 时就已在 App 的 `MessageFamily` 里认过；HTTP 契约一个字没改。

## ⑤ Data Contract

- **写哪些字段 / 行的形状**：`notifications` 的 `recipient_id / category("reminder") / type / title / content / payload / severity / idem_key`（`severity` 与 `payload.emphasis` 由工厂现算，本模块不填）；
  - `stock.low`：`payload = {product_id, product_name, stock, low_stock_alert, stock_date}`，`idem_key = "stock.low:{product_id}:{YYYY-MM-DD}"`；
  - `payable.due_soon` / `payable.overdue`：`payload = {payable_id, supplier_id, supplier_name, amount_unpaid, doc_date, due_date}`，`idem_key = "{kind}:{payable_id}:{due_date}"`；
  - `arrears.over_limit`：`payload = {unit_id, unit_name, credit_limit, credit_used}`，`idem_key = "arrears.over_limit:{unit_id}:{YYYY-MM}"`（**自然月**：额度是持续状态，不是事件）；
  - `invoice.issued`：`payload = {invoice_id, invoice_no, direction, amount}`，`idem_key = "invoice.issued:{invoice_id}:{invoice_date}"`；
  - `account.new_device_login`：`payload = {user_id, device_tail, binding_id}`（`device_tail` **只给末 4 位**，⛔ 不给整串设备指纹），`idem_key = "account.new_device_login:{binding_id}:{bound_at}"`；
  - `account.device_unfrozen`：`payload = {user_id, device_count}`，`idem_key = "account.device_unfrozen:{user_id}:{anchor}"`。
- **Owner 是谁**：`backend/app/services/message_producers.py`（"发什么"）；档位与点名规则的 Owner 仍是 `backend/app/services/message_center.py`。
- **什么时候写 / 什么时候不写**：只在上面那五个业务动作发生时、以及每日扫描那一跑里写；⛔ 不在读路径写、⛔ 不在登录鉴权失败时写、⛔ 付清 / 已删 / 阈值 0 / 注册绑定时不写。
- **是否允许 NULL**：`payload` 允许为 NULL，但本模块这七类**都带 payload**；`idem_key` 这七类**必填**（去重的前提）；`severity` 非空。
- **应付账期与临期天数（推定规则，必须写在这里）**：库里**没有账期 / 到期日字段**（`grep 账期|due_date` 只命中 `message_center.py` 的表），所以 `payable_due_date(payable) = payable.doc_date + PAYABLE_TERM_DAYS`，其中 `PAYABLE_TERM_DAYS = 30`（**月结 30 天**是这一行的推定口径，⛔ 不是数据库事实）；临期窗口 `PAYABLE_DUE_SOON_DAYS = 7`，即**到期前 7 天（含到期当天）发 warn、逾期发 danger**。将来真加了账期字段，**只改 `payable_due_date` 这一处**（注释里已写明）。
- **历史数据怎么办**：⛔ 不回填、不改写任何存量行 —— 这七类消息**从本单上线那一刻起**才有；存量消息的 `severity` / `emphasis` 语义不变。
- **迁移怎么做 / Rollback 怎么办**：⛔ **本单没有迁移**（`idem_key` 列与唯一索引是 FEAT-0019 之前的既有结构）。回滚 = `git revert` 代码；已经写进去的通知行**不需要清理**（它们是真实发生过的提醒，删掉反而丢证据）。
- **删除本功能后历史数据还能不能解释**：能 —— 每一条新消息都是自足的一句话＋一组结构化键（商品 / 单据 / 单位 / 发票 / 用户），删掉生产者不影响它们的可读性与可解释性。
