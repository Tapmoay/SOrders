## ④ Behavior Contract

**动作 1：`purchase_orders.create`（把这张进货单录进来）**
- 参数：`rows`（必填，表格原文：每行「商品 / 数量 / 单价」）、`supplier`（供应商名，必填）、`doc_date`（单据日期，可空＝今天）、`remark`（备注，可空）。
- `prepare`：解析 `rows` → 逐行解析商品名（对着 `ds.products()` 名册，找不到就如实报"名册里没有这个商品，先建商品"）→ 每一行都要有数量（正整数，≤ `MAX_QUANTITY = 100_000`）与单价（正数，≤ `MAX_AMOUNT = 1000000`）→ 同一商品只允许一行（后端也是这个规矩）→ 供应商对着 `ds.suppliers()` 找（找不到就如实说，并提示可以先用「新增供应商」）→ 产出 `NeedConfirm` 卡片。
- 卡片（HIGH 风险）：写清供应商、单据日期、**每一行**（商品 × 数量 × 单价）、合计、以及"**保存之后**：库存 +N、这个商品的成本价按这一单重算、供应商欠款 +合计"。
- `commit`：调 `ds.createPurchaseOrder(...)` **一次**，让后端在同一个事务里把三处一起落；逐条如实汇报，部分失败就说清哪一行没进去（`pendingNote`）。
- 撤回：**没有**"一键撤回"（新建出来的那一条在写之前没有编号 —— `ai/AiRevert.kt:68-74` 的既有口径）。这张卡完成后给一句**专门**的话，点名出路：说一句「撤掉采购单 #N」→ 走「撤采购单」，冲库存 ＋ 撤应付 ＋ 重算成本价。

**动作 2：`purchase_orders.update`（改这张单的单头）**
- 参数：`supplier`（改成哪个，可空）、`doc_date`（可空）、`remark`（可空）、`order_id` 由卡片/名册带出。
- **只改单头三样**（供应商 / 单据日期 / 备注）。**改行不在这里** —— 要改数量或单价请「撤单重开」。理由写进 Known Limitations：后端 `_apply_items`（`purchase_service.py:527`）是**整份替换**语义，把多行替换塞进撤回快照会让"撤回每一行旧值"变成最危险的形状（与 `ai/AiRevert.kt:72-74` 拒绝给批量调价做撤回是同一个理由）。
- 撤回：把三个旧值写回去（快照 `readKeys = supplier_id / doc_date / remark`）。

**动作 3：`purchase_orders.delete`（撤掉这张单）**
- 「撤单」＝ `DELETE /purchase-orders/{id}`：同时冲库存 ＋ 撤应付 ＋ 重算成本价（后端既有语义）。卡片把这三件事写出来。
- ⛔ 卡片**不写单价与合计**（撤单是库存与欠款的事；成本开关关着的人不该从卡片上看到钱）。
- 撤回：`paired` 成对 —— `purchase_orders.restore` 把它放回来（走 `POST /purchase-orders/{id}/restore`）。

**动作 4：`purchase_orders.restore`（从回收站放回来）**
- 撤回路径专用（`undoOnly = true`，模型看不到它）：参数 `target_id`（编号，由撤回入口带过来），`params = emptyList()`。
- 恢复要做一遍与建单同形的事，后端也会如实报"库存不够"；卡片如实转述。

**成本闸（口径 m13365 ③ 不破例）**：`create` 与 `update` 的"钱"藏在 `rows` 文本里，现有那道 `costFieldIn(params)` 只看**顶层**键（`AiWriteService.kt:773` / `:777 COST_PARAMS = listOf("cost_price", "unit_cost")`）⇒ 对采购单形同虚设。新增一个"整条动作都建立在成本上"的集合，把这两个动作也拒掉，复用同一条话术（"打开它之后我才能…"＋位置＋临时办法）。`delete` / `restore` **不过成本闸**（撤单是库存与欠款的事）。

## ⑥ CHG 专章

### 为什么是"确认卡"而不是"直接建"
口径 m13365 ② 定的是 **HIGH 档 ＋ 必须先给确认卡** —— 用户原话里的"也可以不新建"就落在这里：AI 读出的是它**以为**单子上写的东西，看错一行就是一笔错账，所以钱的事一律先摆出来给人看一眼。卡片上必须能看出"这几行、这个供应商、这个日期、一共多少钱、保存之后哪三处会怎么变"。

### 为什么 update 只改单头
三种改法摆在一起比过：**(a)** 单头三样（供应商 / 日期 / 备注）—— 撤回只需三个键，风险最低，选它；**(b)** 连行一起改 —— 撤回要把"每一行的旧值"写回去，而后端 `_apply_items` 是整份替换语义，快照与撤回会变成全仓库最危险的一处，⛔ 不选；**(c)** 干脆不给改 —— 用户就会"撤单重开"，那反而更容易把一张已经入库的单撤错，⛔ 也不选。要改行时的正式路径是**撤单重开**，卡片与文档都写着这句话。

### 撤回为什么不是"一键撤回"
`ai/AiRevert.kt:68-74` 写着既有口径：新建类动作的撤回还没做（"编号在写之前不存在"），`:104-105` 又明确拒绝"有时能撤、有时不能"的承诺。所以这一单**不新造** post-commit 撤回钩子，而是给 `purchase_orders.create` 写一条**专门的** `UNDO_NONE` 理由 —— 通用兜底那句写着"可以停用/下架"，对采购单是错的；专门那条点名出路：说一句「撤掉采购单 #N」→ 走「撤采购单」。删 / 恢复则**真的能撤**（`paired` 成对）。

### 判据与反验（本单自带的两个脚本）
`_tools/qa/_check_ai_purchase_orders.py`：四个动作的 id / 组 / 角色 / 风险档逐字对；行参数必须叫 `rows`；表格解析器的行号与报错；成本闸覆盖 create 与 update；四张卡片文案里没有 `**加粗**`、撤单卡片里没有单价与合计；`_write_coverage.py` 四条 EXCLUDED 确实删掉了、`_app_feature_coverage.py` 的写能力确实认领了「采购单」；`AiResources` 的资源条目与 `AiRevert` 的专门理由都在；⛔ 后端六个端点与三个 schema 的字节没动。
`_tools/qa/_reverse_verify_ai_purchase_orders.py`：逐条注入（把动作改成货主可用 / 把 `rows` 改名成 `items` / 拿掉成本闸 / 给撤单卡片加上合计 / 把 EXCLUDED 加回去 / 把 `_write_coverage` 的注释与条目改坏 / 让 `update` 去改行 / 拆掉 `paired` 的恢复动作 / 让 AI 直写 `inventory_movements` …），每注入一条都必须让对应判据变红；完事按字节还原。

### 真机验收（台账附录 S `:2610`，⛔ 真图不是造的 JSON）
拍照（或从相册选一张进货单照片）→ AI 读出供应商与每一行 → 确认卡 → 确认 → 建单成功 → 三处都对（库存 +N / 成本价按这单 / 供应商欠款 +金额）→ 再问 AI 查得到 → 撤单 → 三处同时回退 → 撤回卡把它放回来。
