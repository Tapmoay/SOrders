① 用户勾选的「每次 AI 动作都落一行，管理端可查」在真机上只兑现了**一半**：AI 改过什么看得见，**AI 查过什么看不见**。走查现场的证据：`ai_operation_logs` 当时 102 行、其中 82 行是 GET，但那 82 行**全是写动作 prep 里顺带的那几次读**；纯读动作（「我能定价的商品有哪些？」这类）**一行都不落**。⇒ 管理端那本账回答不了「他是不是悄悄查过这个」——而 CHG-0082 要的正是这个。

② 当前流程：AI 的动作分两条路 —— **写**走 `ai/AiWriteService.kt`（用户在确认卡上点过之后才真调端点，`:1285 ClientOrigin.asAi(p.actionId) { handler.commit(...) }` 是唯一一处带头）；**读**走两条路：`ai/AiReadService.kt`（读目录里的 70 条读动作）与 `ai/AiTools.kt`（那 8 个老工具：找货主 / 库存报警 / 司机跑货 / 货主表现 / 两个导出 / 读数据 / 记住 / 改数据）。两条读路都**没有**挂头，而 `core/ApiClient.kt` 只在 `ClientOrigin.current()` 非空时才加 `X-SOrders-Origin`。

③ 会变化的事实：`ai_operation_logs` 的内容 —— 读动作第一次进这本账（动作名用**读目录里的规范名**，如 `invoices.list_invoices`；工具驱动的读用**工具 id**，如 `inventory_alerts`）。

④ 明确不能变的：后端 `core/ai_operation.py` 一个字节不动（它本来就记任何带头请求）；写路径的规矩（**只有确认执行那一步带头、预览不带头**）；`HEADER` / `ACTION_HEADER` 两个头的语义（`X-SOrders-Ai-Action` 只是给流水看得懂用，⛔ 不是授权依据）；本机能力那条分支（一个请求都不发）；附件解析与遥测那两处**故意不带**（理由见 ⑥）。

⑤ 这是 **Extension**：扩的是「哪些请求算 AI 干的」这条判定面，不动 Core（后端中间件 / 端点 / 权限点 / 表结构）。

⑥ 证据：判据 `_tools/qa/_check_ai_operation_log.py`（**106 项**）＋ 反验 `_tools/qa/_reverse_verify_ai_operation_log.py`（**25 条注入**，✅ **26/26 全部成立**，收尾「还原后判据重新全绿」）＋ 单测 **1361 / 0 failed / 2 skipped** ＋ 真机（`emulator-5554`）：问一句「有哪些商品库存到红线了？」之后 `ai_operation_logs` 里出现 `inventory_alerts` 的 GET 行（截图 `shots/63_ai_log_read_rows.png` ＋ `python _tmp/api.py ops` 的真行）。

## ③ Boundary（边界：为什么这件事不该在代码边界以外解决）

结论：**这条线的落点只能是"发出端挂头"**，不能靠「管理端自己猜」（看不出来）或「后端按 User-Agent 猜」，更不能靠「各页面自己记得带」。

五问依据：

1. **用户侧**：他要的是「这本账完整」——查过和改过都是 AI 替他干的事；少一半，这本账就不能拿来判断"AI 有没有动过"。
2. **代码侧**：判定面本来就是一个请求头（`core/ClientOrigin.kt`），而 Android 侧只有 `ApiClient` 一处加头 —— 所以缺的是"发请求的人有没有说自己是 AI"，不是"后端记不记"。
3. **重复侧**：写路径已经这么做了一年多（`AiWriteService` 一处），读路径照同一个形状接上，不另造机制。
4. **风险侧**：读动作带头只会多审计行，**不会**多给任何权限（后端权限点照旧；`ACTION_HEADER` 明说不是授权依据）。
5. **能力侧**：动作名必须让管理端看得懂 —— 所以读目录用规范名、工具用工具 id；`READ_DATA` 那条分支里内层 `AiReadService` 会**覆盖**外层动作名（流水跟着规范名走，不是那个笼统的 `read_data`）。

**核心改动声明**：**无**。（`_tools/qa/_core_files.txt` 里 AI 只有 `ai/AiWriteService.kt` 一行，本单没碰它；改的是 `ai/AiReadService.kt`、`ai/AiTools.kt` 两个非核心文件 ＋ 两份判据脚本。）

## ④ Behavior Contract

```text
Input:
  - 读动作：模型调 read_data（{"action": "<读目录里的动作>"}）或调那 8 个老工具之一。
Output:
  - 后端 ai_operation_logs 多一行：user_id / action（规范名或工具 id）/ method / path / status_code /
    ok / request_id / duration_ms / created_at。
Success:
  - 读成功 ⇒ 一行 200；读失败（如 403）⇒ 一行带状态码与失败原因（这本账要的正是"试过但被挡住"）。
Failure:
  - 后端写流水失败 ⇒ 只 logger.warning，绝不影响这次读（中间件那条纪律没动）。
Boundary Cases:
  - READ_DATA 分支：外层工具 id（read_data）被内层规范名覆盖 ⇒ 记的是 invoices.list_invoices；
  - 本机能力（定位这类）：一个请求都不发 ⇒ 不带头、不记行（⛔ 不许凭空多一行）；
  - 预览（preview_write）：只读不写 ⇒ 读的部分带头记行，写的那部分**不带头**（真正的写只在确认之后）；
  - 找货主 / 库存报警这类工具内部还会再打若干端点 ⇒ 每一跳都带头（同一个上下文里）。
Side Effects:
  - ai_operation_logs 多出读行（量级：用户问一次常见问题 1~3 行）；
  - 管理端「AI 操作流水」页从此能看到纯读动作。
Authorization:
  - 不改任何权限：action 头只用于展示，后端一步都不拿它做判断。
Compatibility:
  - 判据 101 → 106 项（新增：工具分发只套一层 / 套在 when 外面 / 动作名用工具 id / 取消照样穿透 /
    ai/ 里带头的一共三个文件）；反验 23 → 25 条注入；
  - 既有写路径的行为与那两条"预览不带头"的判据一字未改。
```

## ⑥ CHG 专章

### Before

- `ai/AiReadService.kt`：`val id = runCatching { resolveId(need) }.getOrNull()`（`:353`）、`val root = repo.rawGet(path, plan.query)`（`:371`）—— 两处都发 HTTP，都不带头；文件里连 `ClientOrigin` 的 import 都没有。
- `ai/AiTools.kt`：`override suspend fun execute(name: String, argumentsJson: String): String` 里直接 `return try { when (name) { … } } catch (…)` —— 8 个工具各自的 `repo.*` 调用（`:380 repo.searchUsers`、`:418 repo.inventoryBelowAlert()`、`:443 repo.driverPerformance`、`:480 repo.shipperPerformance`、`:569 repo.ledgerAccounts`、两个导出走 `AiExportService`）都不带头。
- 症状（真机）：问「有哪些商品库存到红线了？」助手答得出三条，`ai_operation_logs` 一行没多。

### After

- `ai/AiReadService.kt`：新增 `import com.tapmoay.sorders.core.ClientOrigin`（`:3`）；网络段总说明（`:334-345`，写清"每一处网络调用都套 `ClientOrigin.asAi`"、动作名用规范名、本机分支不套）；`:353 val id = runCatching { ClientOrigin.asAi(action.action) { resolveId(need) } }.getOrNull()`；`:371 val root = ClientOrigin.asAi(action.action) { repo.rawGet(path, plan.query) }`。
- `ai/AiTools.kt`：新增 import；`ClientOrigin.asAi(name) { when (name) { … } }`（`:340-353`，包在 `try` 里、`when` 外层 —— 取消/异常处理照旧在外层）。
- 判据 `_tools/qa/_check_ai_operation_log.py`：**101 → 106 项** —— 写侧那句「`ClientOrigin.asAi(` 只有 1 处」原样保留（它只管 `AiWriteService.kt`），新增工具分发小节（处数 1 ／ 套在 `when` 外面 ／ 动作名用工具 id ／ 取消照样穿透 ／ `ai/` 里带头的一共三个文件）＋ 把读侧注释里的由头补全。
- 反验 `_tools/qa/_reverse_verify_ai_operation_log.py`：**23 → 25 条注入** —— 新增 ㉔「工具分发点不带头」（回到真机那个缺口）与 ㉕「只给一支工具带头」（处数判据仍是 1，专测"套在 `when` 外面"这条结构判据）。

### 取证途中撞上并随动修掉的地方

- **本单的缺口是"真机抓出来的"**：先按"读目录那两条路"改完（CHG-0089 第一版），在 5554 上验读动作 —— `invoices.list_invoices` 两条 GET 落账（流水 103 / 105）✅；紧接着问「有哪些商品库存到红线了？」却**一行不落** ⇒ 才发现工具分发那条路（`AiTools` 的 8 个老工具）根本没经过 `AiReadService`。补上 `execute` 那层包装后重验（见 ⑧）。
- **判据的"处数"改成"三处"**：原来只钉 `AiWriteService` 一处，现在写 1 ＋ 读 2 ＋ 工具 1；另外加了一条"文件集合"判据（`ai/` 里带头的一共 `AiReadService.kt` / `AiTools.kt` / `AiWriteService.kt` 三个），防止将来新加一条网络路又悄悄绕过。
- **反验脚本自身出过一次错**：加 ㉔/㉕ 时手抖把 ㉓ 的第 5 个元素吞了，`--dry` 立刻报 `ValueError: not enough values to unpack (expected 5, got 4)` ⇒ 修好后才继续（记在这里，免得下次以为是判据问题）。

### Must Preserve

- 预览不带头（`AiWriteService` 那条"只有确认执行那一步"的判据与反验 ㉑原样）；
- 后端中间件三条硬纪律（独立会话 / 线程池 / 异常吞掉 / 取消原样抛）；
- `ACTION_HEADER` 不是授权依据；本机能力分支不套；附件解析与遥测不套（见 ⑤ 与 ①）。

### Blast Radius

**L2 —— Contract / Data**：写进 `ai_operation_logs` 的行变多（读动作进账）。回滚 = 去掉两处 `asAi` 包装（历史行**不回改**：已经落账的读行是事实，留着）。
