① 第 4 轮测试（方向 A · 软删与恢复入口一致性普查）实测：一条**被设为默认**的常用地址，删掉再恢复之后**默认标记没了**（同一个用户的其它八类实体恢复后 diff 全是 `{}`，只有这一类是 `{"is_default": [1, 0]}`）⇒ 用户每次误删默认地址，恢复回来还得手动再设一次；而下单页取默认地址是「少一次操作」的关键路径。
② 用户动作：地址与联系人 → 常用线路 → 某条「设为默认」→ 误删 → 回收站/恢复入口把它放回来。
③ 只有**恢复端点写回的一个字段**：恢复后这条地址的 `is_default` 从「永久 false」变成「这段期间没人当默认就 true」。
④ 不变量：① 删除那一刻**仍然**把 `is_default` 清成 false（`services/soft_delete.py:88-94` 记着 R11-F4 的理由：默认标记不能留在一条列表里看不见的行上，否则下单页会取到一条已删的地址）；② 恢复**不许抢**别人在删除期间被设上的默认；③ 恢复不能改地址的任何其它字段；④ 不新增列、不改表结构、不改接口出参。
⑤ Extension（一个既有恢复端点的行为修正），不碰 Core。
⑥ 判据 `_tools/qa/_check_address_default_restore.py` 16 项全过、且在**改前源码**上跑 6 条不成立；反向验证 `_tools/qa/_reverse_verify_address_default_restore.py` 6/6 全红且逐字节还原；单测 `backend/tests/test_address_default_restore.py` 三个用例：改后 3 passed、去掉修复那两行 1 failed、还原后 3 passed。

## ④ Behavior Contract

```text
Input           POST /api/v1/shipper/addresses/{id}/restore（这条地址在回收站里）
Output          200 + AddressOut；is_default 的取值按下面两条规则
Success        ① 这期间**没有**任何活着的默认地址 → 恢复的这一条 is_default = True（把用户原来的偏好还回来）
               ② 这期间**别人**被设成了默认 → 恢复的这一条 is_default = False（不抢）
Failure        地址不存在 / 不属于当前用户 → 404「未找到对应记录」；地址没被删 → 400「这条地址没有被删除，不需要恢复」
Boundary Cases 这条地址本来就是普通地址（删之前 is_default=false）→ 恢复后仍是 false（不凭空变成默认）；
               用户在删除期间把**另一条**设成默认再取消默认 → 恢复时按「此刻有没有默认」判，仍然还回来
Side Effects   只改这一行的 is_default（外加 is_deleted/deleted_at），其它地址一个字段不动
Authorization  不变（ShipperOrDispatcher + 归属校验）
Compatibility  Compatible —— 出参字段没增没减、没改类型；老客户端只会看到「恢复后默认标记回来了」
```

## ⑥ CHG 专章

### Before

```text
① 建一条地址 → 设为默认（is_default=true）
② DELETE /shipper/addresses/{id} → 204：is_deleted=true、deleted_at=now、**is_default=false**
③ POST /shipper/addresses/{id}/restore → 200：is_deleted=false、deleted_at=NULL
   ⇒ is_default 仍是 false —— 用户恢复回来的不是原来那条「默认线路」，得手动再设一次
```

实测（第 4 轮 A 普查）：diff = `{"is_default": [1, 0]}`，同批八类实体 diff 全是 `{}`。

### After

```text
③ POST /shipper/addresses/{id}/restore → 200：is_deleted=false、deleted_at=NULL，
   并且**如果此刻这个用户名下没有别的活着的默认地址** → is_default=true
   （有人在被删期间当上了默认 → 保持 false，绝不抢）
```
