## ① 六问

① **解决什么问题？** 2026-10-03 全量反向验证（`python _tools/ai/_reverse_verify_all.py --changed`，77 分钟）
有 3 份不达标，其中 `_tools/qa/_reverse_verify_r4_all.py` 是**整份被打断**：它的锚点
`    money: Money` 在 `backend/app/core/contracts/pricing.py` 里出现了 2 次（`:96` 的
`class PricingResult`、`:160` 的 `class PricingLine`），`Sandbox.replace` 的唯一性断言直接抛错，
**后面的用例一条都没跑**，报告里只留一句「非零退出」。

更深的问题不是那一行锚点，而是**元检查看不见它**：审计锚点的
`_tools/qa/_check_reverse_verify_anchors.py` 只从「注入元组」里抽（说明, 路径, 原文, 替换成, 期望），
而 r4_all 那类脚本把注入写成 `sb.replace(路径, "原文", "替换成")` —— 一条元组都没有，
所以它在报告里是「**0 条**」。而 0 条看起来是正常的（那些驱动别人的 harness 本来就是 0 条），
**锚点腐烂永远不会被看见**。这是本项目栽过 5 次的形状：元检查安静地少查。

② **当前用户 / 业务流程是什么？** 开发者在提交前跑全量反向验证；那条元检查是它的前置审计
（`python _tools/qa/_check_reverse_verify_anchors.py`），负责在「注入已经烂掉、反向验证变成恒 SKIP」时先喊出来。

③ **哪个现有事实或能力会发生变化？** 「注入表长什么样」从**一种**（元组）变成**两种**（元组 + 注入助手调用）；
并且新增一条下限：「注入表认得出的脚本数」。

④ **哪些明确不能变化？** 见 ② 节 Must Not Change：判据口径、`sub()` 的「全换」语义、
「注入残留 vs 锚点腐烂」的修法相反这条分工。

⑤ **属于 Core / Extension / Infrastructure？** 都不是，是 **GOV**（判据 / 工具链本身）。

⑥ **什么证据能够证明它完成？** `python _tools/qa/_check_reverse_verify_anchors.py` 绿
（1426 条锚点 / 128 份脚本注入表认得出）+ `python _tools/qa/_reverse_verify_anchor_audit.py` **11/11 全红**
且逐字节还原 + `_check_all.py` 全绿 + 底下 ⑦ 的四件事。

## ② Must Change / Must Not Change

```text
Must Change:
- _tools/qa/_check_reverse_verify_anchors.py：加第二支抽取（ast.Call + HELPER_NAMES + 实参 >= 2 +
  首个实参解析成**已存在的文件**）；成因判断抽成 judge_missing() 供两支共用
- 新增下限 MIN_SCRIPTS_WITH_TABLE：**注入表认得出的脚本数**（抽不出来 = 安静地少查）
- 唯一性只在「自己断言了唯一」的助手上要求（strict_helper_names：函数体里有 count(...) 与 1 比较，
  含 n = text.count(...) 之后 if n != 1 的间接写法）
- _tools/qa/_reverse_verify_r4_all.py：Sandbox.replace 的裸 assert 改成 SystemExit（说清在哪几行 +
  指向静态审计命令）；那条锚点带上紧邻的上下文行让它唯一

Must Not Change:
- 判据口径一个字不动：它仍然只回答「注入的原文还找得到吗」
- 不把 sub() 当严格助手：它是故意的「全换」语义，按整份脚本判严格会给 5 条注入报假红
- 下限只加不减；已有的红线一条都不放宽
- 不碰任何业务代码 / 数据 / 端点 / 权限
```

### 为什么不能只改那一行锚点（老毛病：只擦这一次）

只把 `    money: Money` 改成两行就完事，等于**只擦了这一次**：同一类写法（函数式注入表）下一次
照样腐烂，而且照样**看起来是 0 条**。所以本事项做三件事：① 让元检查**看得见**第二张注入表；
② 给「看得见多少」加下限，抽不出来就喊；③ 把「唯一性」这条新红配上它自己的注入用例
（见 ⑦ 反向），否则新红本身就是死代码 —— 实测确实如此，见 ⑧ 最后一行。

## ④ Behavior Contract

```text
Input          _tools/*/_reverse_verify_*.py 全部脚本，以及它们声明的每一条注入（原文 -> 替换成）
Output         每条注入：还在 / 锚点腐烂（原文找不到且替换串不在）/ 注入残留（替换串在文件里）/
               报表搬家（源码按报表生成，不算腐烂）；外加「这份脚本的注入表认得出几条」
Success        全部锚点还在 -> 退出 0，打印「N 条注入原文全部还在（M/153 份脚本的注入表都认得出）」
Failure        ① 有腐烂 -> 点名脚本与标签（退出 1）② 注入残留 -> 报「注入残留」且**不许**再说「去更新锚点」
               ③ 脚本数 / 锚点数 / 有替换串的锚点数 / 注入表认得出的脚本数 任一低于下限 -> 先喊「抽取失效」
Boundary Cases 同一段原文出现多次：严格助手（自己断言唯一）-> 红「要求它唯一」并给行号；
               非严格助手（sub / 全换语义）-> 不算错
               首个实参不是文件（Path("D:/") 这种目录、text.replace("a","b") 这种字符串方法）-> 跳过
               正则锚点（re: 前缀）-> 按正则再看一眼，不误判成腐烂
Side Effects   只读（--restore 才会写，且按字节还原并逐字节核对）
Authorization  不适用
Compatibility  元组那一支原样保留；两支共用同一套成因判断，口径完全一致
```
