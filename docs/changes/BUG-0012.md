# BUG-0012 · 补录历史采购单，入库流水的时间戳却是「此刻」：历史窗口取不到本期加权均价，静默退回快照（2026-10-05 造数时发现，未修）

> 现场来源：**GOV-0005**。按真实服务函数补录 12 张历史采购单（单据日期 2026-09-19 ~ 10-04）之后，
> 上周（2026-09-28 ~ 10-04）窗口的「商品成本」**全部**走了快照口径（`cost_avg_lines=0 / cost_snapshot_lines=83`）——
> 明明这一周里进过货。把入库流水的时间戳夹回单据日期当天后，同一窗口变成
> `cost_avg_lines=69 / cost_snapshot_lines=14`。**同一批订单、同一份数据，只因为"什么时候录进去"不同，毛利就不一样。**

- **ID**：BUG-0012
- **类型**：BUG（写入端：流水时间戳与单据日期脱钩，且失败是静默的）
- **状态**：⏸ 待定（已定位、已实测；改法有两种，要用户拍板走哪一种）
- **Owner**：DSH 会话 `session-e94394d5-4f36-49dd-9ee1-446fcb7dee30`
- **开工日期**｜**关闭日期**：2026-10-05 ｜ —
- **Blast Radius**：**预估 L1～L2** —— 改 `purchase_service` 写入端（一行 `created_at`）会改**所有历史窗口的毛利读数**；
  若改成"加一个入库日期字段"则是 L2（迁移 + 入参 + 界面）。**本轮一行产品代码都没改**。

## ① 六问

**1. 现象是什么？**
- 补录 12 张采购单（`doc_date` 2026-09-19 ~ 2026-10-04）后，上周窗口的成本构成是
  **本期均价 0 行 / 快照 83 行**；这一周里明明有 18 条带价入库流水（夹回时间后为 28 条）。
- 也就是说：**这一周进过货，报表却认为"这一段没进过货"**，于是每一行都退回"下单那一刻的成本快照"。

**2. 根因在哪？**
- 采购单有 `doc_date`（单据日期 = 进货那天），但入库流水不看它：
  `backend/app/services/purchase_service.py:189` 建 `InventoryMovement(...)` 时**没有写 `created_at`**，
  于是由 `backend/app/models/base.py:36-38` 的 `TimestampMixin.created_at`（`default=utc_now_naive`）落成**"此刻"**。
- 成本口径恰恰按这个时间列开窗：`backend/app/services/cost_basis.py:74`（`hi = business_day_start_utc(until + 1)`）、
  `:82`（`created_at < hi`）、`:87`（`created_at >= business_day_start_utc(period[0])`）。
  ⇒ 补录的历史采购进不了"本期"，只能退到 ② 累计均价或 ③ 下单快照（三级口径见 cost_basis 模块 docstring）。
- **失败是静默的**：利润表只说「这一段没进过货 的 N 行按下单时的成本价算」，
  读这句话的人**没法知道**"这一段其实进过货，只是录进来的时刻晚了"。

**3. 还有第二处症状（同一根因）**
- 采购单 #11 / #12 的 `doc_date` 是 2026-10-04，但建单时刻是 **2026-10-04 19:06 UTC**（= 北京 10-05 03:06），
  10 条入库流水的**时间戳落在 10-05 这个业务日**，与单据日期不一致 ⇒ 10-04 那张单的进货永远不进 10-04 的窗口。
- 造数脚本自己的对齐守卫也曾被这一点绊倒：`backend/scripts/seed_ops_gap.py::align_history` 原来比的是
  **UTC 日期前 10 位**（`str(created)[:10] == str(when)[:10]`），10-04 的 `when` 与"此刻"的 UTC 日期撞上 → 静默跳过这 10 条。
  已改成比**业务日**（`(seen + timedelta(hours=8)).date() == day`）并重跑成功（打印「采购入库时间 10」）。
  ⛔ 这一段是**脚本侧**的修，不是产品代码的修。

**4. 影响是什么？**
- 「什么时候补录」直接决定历史毛利长什么样：同一个月，今天录进去和三个月前录进去，读数不同。
- 老板看到的「这一段没进过货，按下单时的成本价算」可能是一句**假话**。
- 成本覆盖率（`cost-coverage`）的「从来没带价进过货的商品」名册用的是**全量**入库流水（`change>0 and unit_cost not null`，`backend/app/services/reports/cost_coverage_query.py:61-87`），
  这一个**不受影响**（它不按窗口）—— 受影响的是"本期加权均价"这一级。

**5. 建议改法（两种，待拍板）**
- 方案 A（最小）：`purchase_service._add_line` 建流水时把 `created_at` 写成**采购单 `doc_date` 当天的业务时刻**
  （库里 UTC naive，用 `to_utc_naive(datetime.combine(doc_date, dtime(10, 0)))` 这种"业务日内的时刻"）。
  ⛔ 必须同时禁止"未来日期"的采购单，否则会写出未来的流水、污染未来的窗口。
- 方案 B（更贴业务）：给采购单补一个**入库日期**字段（默认 = doc_date），流水用它；界面与导入都要跟着加一格（L2）。
- 无论哪个方案：**录入时刻不再等于业务时刻**这件事要在口径说明里写清，且**不许静默**。

**6. 不许动什么？**
- 三级取价顺序（本期均价 → 累计均价 → 下单快照）与它们的金额算法——问题不在取价，在"流水落在哪一期"。
- `products.cost_price`（由 `_reprice_product` 维护的"最近一次带价入库价"）与 `product_cost_history`（溯源用）——它们本来就不参与毛利成本。
- 既有采购单与它们已生成的流水（本轮**一行不改**）；开发库里那 41 条被我夹回时间戳的行属于**开发库演示数据**，不是产品行为修正。
- 单测/探针里对 `created_at` 语义的既有断言（改写入端时它们会红，那是应该的）。

## ⑤ Data Contract

- **新增/改动哪些字段**：方案 A **零**（只写既有 `created_at` 的取值方式）；方案 B 新增 `purchase_orders.received_date`（默认 = doc_date）。
- **Owner 是谁**：采购域（`app/services/purchase_service.py`）。
- **什么时候写 / 什么时候不写**：只在建/改采购单行时写；⛔ 不改既有行。
- **是否允许 NULL**：`created_at` 非空（既有约束）；方案 B 的 `received_date` 允许空 = 取 doc_date。
- **历史数据怎么办**：**一个字节不动**。开发库里那 41 条被我夹回时间戳的行是"演示数据订正"，
  必须与产品修复分开记（脚本里的 `align_history` 已写明理由），⛔ 生产库里不许这么干。
- **迁移怎么做 / Rollback 怎么办**：方案 A 无迁移，回滚 = revert；方案 B 需迁移 + 回滚脚本。
- **删除本功能后历史数据还能不能解释**：能 —— 流水与采购单都在，只是时间戳又变成"录入时刻"。
