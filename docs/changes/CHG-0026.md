# CHG-0026 · 报表与账本的四个「读数口径」（2026-10-03 E2E 走查 P20 / P25 / P26 / P32）

> 走查原话（`_tmp/E2E测试报告.md`，逐字）：
>
> **P20 「营业指标」一张卡里混了两个时间口径**（`:119`）
> 页面：报表中心 → 营业纵览
> 实际：订单数 / 单均价 / 司机运费支出 是「今天」口径，而「待处理异常（近 30 天）52 单」是 30 天口径——四个数字并列，只有那一行带括号注明，容易读成「今天有 52 单异常」。
> 证据：`_tmp/w_biz.png`
>
> **P25 我的账本「我该付的」「我该收的」同额并列且没有一句解释**（`:86`）
> 页面：货主端 → 我的账本
> 实际：支出·我该付的 ¥85.5 与 收入·我该收的 ¥85.5 是同一个数（库里订单 551 只有一行 85.5），用户在页面上看不到任何说明，会以为被收了两遍钱。
> 根因：区分两者口径的解释句在 ui/shipper/ShipperLedgerScreen.kt:470-475，是一条 Hint；本机三台设备的提示开关都是关的（见「机制性发现」），所以那句话根本不渲染（滚动前后 dump 都没有）。
> 证据：`_tmp/w556_ledger.png` `_tmp/w556_ledger2.png`
>
> **P26 账本把「退货红冲」标成「已核销」**（`:92`）
> 页面：我的账本订单行
> 实际：退货后的订单行显示 已退货 + ¥0 + **已核销**。这一单并没有被核销（收讫），是被红冲冲平的。
> 根因：ui/shipper/ShipperLedgerScreen.kt:629 —— 只要 remaining 为 0 就写「已核销」，把「冲平」和「收讫」混成一词。
> 证据：`_tmp/w556_ledger3.png`
>
> **P32 客户经营「客单价」口径歧义**（`:174`）
> 客单价 ¥6670.3 与 订货总额 ¥6670.3 完全相同（客户数 1 家）。实现见 android/.../ui/dispatcher/ReportCenter.kt:595 —— 客单价 = 订货总额 ÷ **客户数**；而中文语境里「客单价」通常读作「每单均价」（这里 6670.3 ÷ 58 笔 ≈ ¥115），且「订货笔数 58 笔」就并排在上面。判定：**口径歧义，非硬缺陷**，建议改名为「户均订货额」或改成每单均价。证据 `_tmp/rep_cust.png`
>
> 结论：四条是**同一种病** —— 数字本身没错，错的是它旁边那句话：
> 窗口没写在标签上（P20）、分母没写在名字里（P32）、方向没写在词尾（P25）、状态词与真实成因不符（P26）。
> 所以这一批改的全是「界面上怎么称呼这些数」，**一个数字、一次查询、一个接口都不动**。
>
> ⛔ 两件明确不做：**不改后端那两个数的钱口径**（「全部」窗口下已撤销 / 未送达的单也计入「我该付的」，
> 这是既有的钱口径决策 —— 见 ⑨ Known Limitations，另立事项再议）；**不动提示开关机制**
> （P25 的根因之一是指示句走了 Hint、而总开关默认关；本次只把**这一句**改成常显，`core/HintPrefs.kt` 一行不改）。

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

**结论：Presentation。** 这一批改的是「界面怎么称呼这些数、把它们放在哪张卡里」，取值、查询与调用链一处没碰。

**五问依据**

- **输入**：仍是用户在报表页切时间药丸 / 切页签、在账本页切货主与时间窗口 —— 没有新增参数、没有新增端点。
- **状态**：没有任何新增界面状态（这一批连一个 `remember` 都没加）；四个改动都是纯表达式与文案。
- **边界**：P26 那一支的判据是**订单状态**（`o.status == "RETURNED"`）优先于金额（`remaining > 0L`），顺序由判据盯着。
- **失败**：不涉及请求失败路径（本批不发任何新请求）；页面原有的加载错误渲染一行未动。
- **依赖**：零新依赖（用的仍是既有的 `StatRow` / `SectionCard` / `Text` 与主题色）。

**核心改动声明**：无核心业务改动，故不设 Core / Extension / Infrastructure 三个边界行。

## ④ Behavior Contract

```text
Input:       用户在报表中心切到「营业纵览」或「客户经营」；批发商货主打开「我的账本」并选时间窗口。
Output:      营业纵览：本期四个数一张卡，「待处理异常」单独一张卡且标签写明近 30 天。
             客户经营：「户均订货额」与「每笔订货额」两行并列，分母各写各的。
             我的账本：两个数带方向；批发商段在两段之间多一句常显口径；退货单那格写「已退货 · 账已冲平」。
Success:     屏幕上四处的读法与事实一致：窗口、分母、方向、状态各自写实。
Failure:     不适用（本批不发请求、不写数据）。
Boundary Cases:
             · 客户数 = 1 家：户均 = 订货总额（看着像重复），每笔 = 总额 ÷ 笔数 —— 这正是 P32 要治的那个误会。
             · 分母为 0：两个数都走原有的 empty 守卫（all.isEmpty() / totalCount == 0 → ¥0.00）。
             · 只有货主（非批发商）：不渲染收入段，也不渲染那句口径说明（它在 `s.isMember` 分支里）。
             · 退货单：状态那一格优先看 RETURNED，金额为 0 也不再被说成「已核销」。
             · 未核销 / 已核销：两支都还在，金额与颜色沿用原样。
Side Effects: 无（一次读请求都不多发；页面渲染与改前完全相同的接口数据）。
Authorization: 不变 —— 仍是报表中心与我的账本那套既有权限，本批不碰 RBAC。
Compatibility: 不涉及接口兼容性（请求体与响应体一个字没改）。
```
