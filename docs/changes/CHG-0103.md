**① 用户要什么**（ref `m05399`，逐字）：

> 「顺便参考他这个样式啊，我们现在的商品管理。如果估清了。他那个卡片只会有一个沽清的状态，
>  但是并没有整体变灰的样式啊参考。他的样式啊，他当时就有一个整体变灰的变动啊啊，改一下吧。」

他同时给了一张**参考 App 的产品管理页截图**：顶部 `在售(99+)` / `已沽清(1)` 两个页签，左侧分类竖排，
右侧商品卡列表。**已沽清的那张卡**（「农家米粉肉」）整张发灰、降饱和，卡上叠了一个斜的「已沽清」
印章式水印；「改价」灰掉不可点，「取消沽清」仍可点，「编辑」白底描边仍可点。
未沽清的卡（卤水桂鱼、基围虾）是正常白底 + 绿色「改价」。

**② 现在是什么样**：这一页的商品卡在沽清之后**只多了一枚「已沽清」角标**
（`android/app/src/main/java/com/tapmoay/sorders/ui/dispatcher/ProductsScreen.kt` 原来那一行
`val soldOut: (@Composable () -> Unit)? = if (p.isActive) null else ({ ProductSoldOutBadge() })`
→ `ProductLine(badge = soldOut)`）：卡还是白的、图还是亮的、三个按钮还是可以点的。

**③ 为什么会这样**：这条口径**早就定过，只是没扩到这一页**。2026-10-07 用户在下单页选品弹层上
把「沽清」的含义从"贴个角标"改成了"**整卡变灰 ＋ 点不动**"（台账 **L-35** / `BUG-0017`，ref `m01347`，逐字）：

> 「灰掉了之后**就不能点**的哈……就是**整卡变灰**嘛……就是**拦住不让下**，
>  不可能是提示后他仍然可以下呀。」

那次只在 `ui/common/ProductPicker.kt::ProductRow` 里落地了，而且**明确留了一句注释说
"只在此处生效 —— 商品管理页与批量页的卡不受影响"**。于是同一件事在两个页面上是两套说法：
选品弹层是灰的、商品管理页是亮的。用户这一轮看的就是这个不一致。

**④ 应该改成什么样**：商品管理页的商品卡在 `is_active = false` 时
**① 换灰底 ＋ ② 整棵内容一起变暗**（图 / 名 / 数字 / 三个按钮 / 角标同一档），
并且灰卡上**看起来不能点的就真的点不动**：三个动作里只有「改价」被禁
（`enabled = !acting && p.isActive`）；「上架」与「编辑」**必须留着** —— 沽清不是终点，
禁掉这两颗，这件商品就再也回不到在售（参考图里「取消沽清」与「编辑」也是暗的但仍可点）。
灰卡与「已沽清」角标**并存**，它们是同一件事的两种说法（灰卡说"不能动"、角标说"为什么"），
不是"两个状态两个词"（那正是 `ProductsScreen.kt:421` 那段注释记着的既有病灶）。

**⑤ 改哪里**：两处（列表见 §②）。
① 新建 `ui/common/ProductSoldOutScrim.kt` —— 把"整卡变灰"的**两个数值**与卡壳做成共用件；
② `ui/dispatcher/ProductsScreen.kt::ProductCard` —— 用那个卡壳把整张卡包起来，并给「改价」加一道 `&& p.isActive`。
**为什么是这两处就够**：`ProductCard` 是这一页唯一的商品卡渲染处（列表里每一格都走它），
灰罩包住 `SectionCard` 就等于包住了卡上的每一个像素；数值只在共用件里定义一次，
以后别的页面（批量操作 / 库存 / 排序）要跟，引这一个文件即可。
⛔ 本次**没有**动 `ui/common/ProductCardKit.kt` 与 `ui/common/ProductPicker.kt` —— 那两个文件
正被并行的配色变更 `CHG-0102` 改着，同时动会撞车（原因见 §② Must Not Change 第 2 行）。

**⑥ 怎么证明改对了**：判据 `_tools/qa/_check_sold_out_card_grey.py`（静态，逐条钉住形状与数值）
＋ 反向验证 `_tools/qa/_reverse_verify_sold_out_card_grey.py`（≥8 条注入，每条都必须让判据变红）
＋ 全量静检与 gradle 单测回归 ＋ 真机取证（本轮由主会话统一做，见 §⑧）。

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

**结论：这是 Presentation 层的一处画法改动，Blast Radius = L0。**

- **不是 Core**：五问依据（规范 §三）逐条 —— ① 是否定义核心事实？**否**：核心事实是
  `products.is_active`（沽清 = 不能卖），本次一个字段都不动；② 是否改核心不变量？**否**：
  库存 / 订单 / 账本 / 权限 / 状态机都不经过这一次改动；③ 是否必须永久存在？**否**：
  把这一层删掉，`is_active` 的语义与所有后端行为**一个字都不变**，只是屏幕又回到"亮卡 + 角标"；
  ④ 是否可能出现多个实现？**可能，而且这正是本次要收口的**（选品弹层一处、商品管理页一处）
  —— 所以数值被收进一个共用件；⑤ 删除后 Core 是否仍成立？**成立**。
- **不是 Extension**：它没有新增能力、没有新端点、没有新工具，只是把已有事实换一种画法。
- **不是 Infrastructure**：不碰构建、不碰环境、不碰部署。
- **是 Presentation**：改的是一个 `@Composable` 的树形与两个不透明度常量。判据按规范 §三
  落在展示层（脚本在 `_tools/qa/`，只读源码文本、不编译、不跑 UI、不连设备）。

## ④ Behavior Contract

```text
Input           products.is_active（来自既有的 GET /products，字段与含义都不变）
Output          商品管理页里：is_active = false 的那张卡 → 灰底 + 整棵内容变暗（0.6）
                ＋ 仍然贴「已沽清」角标；is_active = true 的卡 → 一个像素都不变
Success         灰卡上「改价」点不动（按钮是 disabled 态）；「上架」仍打开确认弹层；
                「编辑」仍进编辑页；点图仍看大图（灰卡不夺走"看"的能力）
Failure         没有任何新的失败路径：这一层不请求、不写库、不抛异常。
                唯一的"失败"是**画不出来**（灰罩被删/数值被改坏），由判据拦
Boundary        is_active 只影响"怎么画"与"哪几个按钮可点"，不影响数据；
                角标文案仍是「已沽清」（唯一一份 ProductSoldOutBadge）；
                ProductCheckList 那一页不受影响（下架商品仍可勾）
Side Effect     无。不发请求、不写 DataStore、不改内存里的商品对象
Authorization   无变化：这一页本来就只对派单员开放
Compatibility   老包不受影响（纯客户端展示）；后端与出参零改动；深色主题下
                surfaceVariant 自带另一份值 —— 所以灰底不能写死一个灰（见共用件 KDoc）
```

## ⑤ Data Contract

**不适用。** 本次没有任何数据契约变更：

- 请求 / 响应字段：零新增、零改名、零改类型（`ProductDto.isActive` 早就在）。
- 唯一一处"沾数据"的地方是**读**：`p.isActive` 决定灰不灰，与 `ProductPicker` 里

  因为它们本来就有 `is_active = false` —— 这也是这次不需要任何数据动作的原因。

## ⑥ CHG 专章

### Before

沽清的商品在商品管理页上：**白卡、亮图、三个按钮全可以点**，唯一的变化是商品名旁边多一枚
「已沽清」角标。想判断"这一条现在能不能卖"，得先看见那枚角标、再读它的字。
同一件事在下单页选品弹层里已经是灰卡（`BUG-0017`），两页不一致。

### After

沽清的商品在商品管理页上：**整张卡灰掉**（卡壳 `surfaceVariant` 压到 45%）**且卡上所有内容一起变暗**
（图 / 名 / 数字 / 三个按钮 / 角标同一档 0.6）；「改价」按钮变成真正的 disabled（点不动），
「上架」「编辑」仍可点（灰卡上最需要的那两颗）。未沽清的卡**一个像素都没变**。

### Must Preserve

1. `products.is_active` 的语义与所有后端行为（沽清 = 不能卖，下单两道闸门不动）。
2. 「已沽清」角标的**形态与唯一文案**（`ProductSoldOutBadge`，无参、只有「已沽清」）。
3. 三个动作的文案、顺序、"一排等宽大按钮"的形态，以及沽清/上架的**二次确认弹层**。
4. 未沽清的卡：底色、内容不透明度、三个按钮的 `enabled`，与改前逐字一致。
5. 另外四个渲染商品的页面（选品 / 批量 / 库存 / 排序）本次**不受影响**。
6. 颜色 token（`ThemeGreen` / `#8B4A4A` / `QuickPriceGreen` / `ProductPurple` / `Success` / `error`）一个字不动。

### 为什么改这几处就够

`ProductCard` 是这一页唯一的商品卡渲染点（列表每一格都走它），所以"整卡"这件事只要
**包住这一个 `SectionCard`** 就成立 —— 不需要去改卡里的任何一行（图、名、数字、按钮都照旧画，
只是被外面那一层统一压暗）。数值只放在共用件一处，是因为它坏起来**不报错**：
`0.45f` 写成 `0.95f` 与写成 `0.05f` 都能编译、都能过单测，只有一处定义才钉得住。
「改价」那一道 `&& p.isActive` 必须单独写，是因为"灰"与"不能点"在 Compose 里是**两件事**
（`alpha` 不影响命中测试）—— 只做前者就是"看起来不能点、其实点得动"。
