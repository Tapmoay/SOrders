① 第 4 轮测试（方向 B · 金额口径连锁普查，测试台账 **TB-12**）实测：一张「已送达、还欠 173」的订单按商品**部分核销** 124（`order_product_ids` 只点其中几行）之后，这笔收款「撤销 → 恢复」一次，订单就变成 `paid=1`（**可它还欠 49**）。后果是三重的：剩下的 49 用逐单核销再也收不进（400「订单 xxx 已经收过款了…请改用滚动收款」）、滚动收款又不绑单（钱只进现金流、不冲这单）、`/reports/arrears-summary` 里这一行直接消失 ⇒ **这 49 永远挂在单上，而且欠款表上看不见**。
② 用户动作：账本 → 客户收款 → 登记（可只勾选某几行商品）→ 记错了点「撤销」→ 又点「恢复」。
③ 恢复时**写回 `orders.paid` 的条件**：从「这笔收款点过名的订单全部标已收」变成「只标撤销那一步确实翻过的那些」。
④ 不变量：① 逐单核销的创建侧判据一个字不改（`accounting_service.py:482` 的 `settling` 仍是"这一单被收清了"的唯一口径）；② 撤销侧行为不变（它本来就只翻 `paid=True` 的那些单）；③ 全额核销的「撤销→恢复」必须仍回到已收款；④ 恢复的四道门（订单不存在／在回收站／已撤销或已退货／现在已是已收款）全保留；⑤ 不新建表、不加列、不改出参；⑥ 钱的四个落点（订单、账本、现金流水、报表）计算方式一律不动。
⑤ Extension（一个既有恢复端点的判据修正）。它落在账本域，按规范 §八属于"钱"⇒ 走正式变更审查：本单配了判据 + 反验 + 三个单测 + 红证。
⑥ 判据 `_tools/finance/_check_receipt_restore_settling.py` 18 项全过、且在**改前源码**上跑 8 条不成立；反向验证 `_tools/finance/_reverse_verify_receipt_restore_settling.py` 7/7 全红且逐字节还原；单测 `backend/tests/test_receipt_partial_restore.py` 三例全绿，且把闸门拿掉后**部分核销那一例会红**（红证逐字：`恢复把还欠着 40 的单翻成了已收款（TB-12：这 40 永远收不回来）`）。

## ④ Behavior Contract

```text
Input           POST /api/v1/ledger/receipts/{receipt_id}/restore（这笔收款已在回收站里）
Output          200 + ShipperReceiptOut；被撤销的那几行 cash_flows 与收款单一起放回
Success        ① 撤销时被翻成未收的订单 → 恢复把它们翻回已收款（payment_method 按收款方式写回 cash/arrears）；
               ② 撤销时**没被翻**的订单（部分核销、本来就没收清）→ 恢复一个字段都不动它
Failure        四道门照旧：订单不存在 / 在回收站 / 已撤销或已退货 / 现在已经是「已收款」→ 400 并点名单号
Boundary Cases 找不到撤销名单（老数据、审计被清）→ **不翻任何订单**（宁可让用户再收一次，也不要把欠款藏起来）；
               同一笔收款撤销两次 → 第二次 400（幂等，BUG-0029 的老用例仍绿）
Side Effects   只动 orders.paid / orders.payment_method（名单内）、cash_flows.is_deleted、receipt.is_deleted、一行审计
Authorization  不变（仅派单员）
Compatibility  Compatible —— 没有任何字段/类型/文案变化；只是"恢复后订单是不是已收款"这个判定更准
```

## ⑥ CHG 专章

### Before

```text
① 已送达单 100（两行 60 + 40），按商品核销 60  →  paid=False（还欠 40）
② DELETE /ledger/receipts/{id}  →  204：流水软删，订单**没有**被翻（它本来就是未收）
③ POST /ledger/receipts/{id}/restore  →  200：流水放回，**并且 o.paid = True** ← 错在这里
④ 结果：这张单显示「已收款」，但它还欠 40；再想收那 40 会被 400 挡住
   （400 原文：「订单 xxx 已经收过款了（之前已经核销过），不能重复收款。如果是补差额，请改用「滚动收款」。」）
```

### After

```text
③ POST /restore → 200：流水放回；翻 paid 之前先取「撤销那一步翻过的名单」
   （审计 RECEIPT_CANCEL 的 payload.orders_rolled_back），只翻名单里的订单。
   部分核销那张单不在名单里 ⇒ paid 仍是 False、还欠 40，那 40 仍然收得进来。
```

### Must Preserve

```text
- 历史订单 / 历史金额 / 已冻结的 Pricing Fact（本单不碰）
- 历史 Provenance / Audit / Ledger（本单只**读**既有审计行，不写新类型 —— 除了一行 RECEIPT_RESTORE）
- 权限（仍是「仅派单员」）
- API compatibility（出参字段与类型不变）
- 本事项特有：创建侧的 settling 判据、撤销侧行为、四道门文案
```

### Blast Radius（L0～L3）

**L2** —— 契约/数据层：它决定「一张单算不算收清了」。按规范 §八（命中"钱"）走正式变更审查：判据 18 项、反向验证 7 条注入全红、单测 3 例（含把闸门拿掉后的红证）。

**最后一个问题**（规范 §三十五 / §三十六）：这条缺陷能活下来的原因，是**同一个不变量（"收清了才算已收"）在两个方向上各写了一遍**：创建侧写对了（`settling`），恢复侧凭直觉写成了"撤销的逆操作就是把标记翻回来"。
下一次同类的改动应当先问一句：**这个动作的逆操作，是不是真的等于"把字段翻回去"？** —— 撤销侧本来就只翻了它翻过的那些，逆操作却翻了全部，这个不对称就是病灶。
