## ② Must Change / Must Not Change

**Must Change**

- 补录照片必须有水印：**时间 + 地点 + 第三行补拍标识**（util/WatermarkText.kt 的 `lines()`）。
- 文案与行数**只有一个出处**：`WatermarkText.MAKEUP_TAG = "补拍 · 事后补录"`；界面上任何一处自己拼字面量都会被判据抓出来（「补拍」「补拍 · 事后补录」「送达地点」三个字面量在整个客户端只许出现在这一个文件里）。
- 地点口径**只有一处**：`OrderDetailScreen.watermarkText()`（实时定位 → 逆地理 → 订单地址 → 兜底），三条路都调它。
- 相册那条路必须**先画后传**（`Watermark.process(f, marked, …)` 之后 `vm.uploadPlacePhoto(marked)`）—— 画在一份没人传的副本上等于没画。
- 相机那条路必须画在**内存位图**上（`Watermark.markBitmap(bmp, f, …)`），不许先落盘一张无水印 jpg。
- 压图（2560 长边）与画水印都在 `Dispatchers.IO` 上（相册原图动辄十几 MB，不许卡主线程）。

**Must Not Change**

- ⛔ 送达照那条路：`Watermark.process(File(rawPath), out, wmText)` **逐字未变**，且**不许**带补拍标识 —— 当场拍的照片被标成「事后补录」是反向失真，比少一行更糟。
- ⛔ 上传接口与后端：`uploadPlacePhoto(file: java.io.File)` 一个字没动，没有新增字段 / 列 / 接口。
- ⛔ `Watermark.process` 的既有链路：EXIF 摆正 → 缩放 → 画 → JPEG 85，一个字没改坏（既有调用点因为 `tag` 有默认值而一个字都不用改）。
- ⛔ 订单详情页的其它卡片、其它页面、`OrderDetailViewModel` 的行为：零改动。
- ⛔ `util/Watermark.kt` 里不许出现裸色值（它同时是导出图表那条路的水印，见 `_tools/qa/_check_ledger_dashboard.py:123` 的白名单）。

## ③ Boundary

- **结论**：**PRESENTATION（客户端画在照片像素上的留痕）**，Blast Radius **L1**。
- **不改**：送达照那条路 / 上传接口与后端 / 数据模型 / 订单详情页其它部分。
- **不做**：① 不给「补拍」这件事加后端字段或数据库列（用户要的是**看得出来**，不是可查询）；② 不写进照片 EXIF；③ 不回溯处理服务器上已有的历史照片；④ 不做水印位置/字号的可配置项（沿用既有画法：底部半透明黑底白字）。
- **为什么这条边界解决不了**：水印是**客户端拍照那一刻**画在像素上的 —— 后端从头到尾只收到一个 JPEG，文件里没有任何「补拍」字段。所以判据只能守客户端这一侧的跨文件口径（文案一份 / 地点口径一份 / 三条路各画各的）。

## ④ Behavior Contract

- 在订单详情页**补传**一张照片（相册选 或 系统相机拍）⇒ 上传的那张图上，底部有两行或三行白字：时间 ｜ 地点 ｜ `补拍 · 事后补录`。
- **当场拍**的那张（「拍照送达」）⇒ 仍然只有**两行**（时间 + 地点），与本次改动之前逐字一致。
- 地点取不到（没有定位、逆地理失败、订单也没有地址）⇒ 第二行是 `送达地点`；地点超过 60 个字 ⇒ 截到 60 个字。
- 相册一次选多张 ⇒ 每张各画各的（文件名互不覆盖：`place_done_<ts>_<i>.jpg`）。
- 水印画失败（解码失败 / 写盘失败）⇒ 走既有的 `vm.error = "照片处理失败，请重试"`，不会传一张没水印的图上去。
- 历史照片、其它页面、后端返回的任何字段：一点变化都没有。
