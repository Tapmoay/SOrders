① 退货申请写错了一样商品、或者数量填多了几件，今天只能**驳回 → 让货主撤回 → 重新申请**一整轮。用户要的是**直接改**：改完只发一条通知告诉另外两方（原话：「不需要重新让货主撤销然后再重新申请一下，只不过我们会发个通知」）。

② 货主（批发商在库里也是货主那一侧）在「我的退货申请」里提一张申请 → 派单员在「退货待办」里看到它，点「办理退货」的那一刻才动库存 / 账本 / 退款（`backend/app/services/order_return_request.py::fulfill`）。在「办理」之前，这张申请单上的商品明细**没有任何改的口子** —— 仓里旧注释写的就是「数量锁死，要改数量只能驳回、让货主重提」（本轮已按用户新口径改写该注释）。

③ 三件事：**（a）** 退货申请明细（哪几行商品、各多少件）在「待处理」期间可被三方（派单员 / 货主 / 批发商）就地改写；**（b）** 新增**一条**消息 type `order.return_request.amended`（中文名「有改动」，通知标题「退货申请有改动」）；**（c）** 新增审计动作码 `ORDER_RETURN_REQUEST_AMEND`（App 审计卡片中文名「改退货申请明细」）与一条出箱事件 `returns.amended`。配套：一个写端点 `POST /return-requests/{id}/amend`。

④ 状态机四个既有 type 的语义（`order.return_request` / `.rejected` / `.done` / `.closed`）一个不改；⛔ 终态（已办理 / 已驳回 / 已自动关闭 / 已撤回）不许改；⛔ 钱 / 库存 / 订单状态一个不动（仍然只在 `fulfill` 那一刻变）；⛔ 不新增结构化字段、不做「每个字段一张表」；⛔ 已在申请里的凭证行**不删不重建**（只就地改数量）；⛔ 每次改动**只发一条**通知（不做每次字段改动发一条）；⛔ 不放宽任何既有判据（只追加窄例外并写明理由）；权限复用既有权限点 `order:return_request`，⛔ 不新建体系。

⑤ **EXTENSION IMPL**（在既有退货申请服务里加一个用例：既有权限点 + 既有校验函数 + 既有消息中心 + 既有出箱聚合根）。唯一落进核心区的是 `backend/app/models/enums.py` 的**追加式**动作码（见 §③ 声明行）。

⑥ 见 §⑧：后端 6 个用例真跑、Android 7 条单测真跑、判据脚本逐项通过、反验脚本 6 条注入全被抓（含逐字节还原 + sha256 自证）、`_check_dev_spec.py` / `check_reachability.py` / `_check_all.py` / `_check_core_freeze.py` 全绿。

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

- **结论**：**EXTENSION IMPL**（退货申请服务里加一个用例；接口层 / 消息层 / 界面层都是既有形状的追加）+ 一处 **CORE 的追加式改动**：`backend/app/models/enums.py` 的 `OperationAction` 新增一个成员。
- **五问依据**（规范 §三）：
  - ① 是否定义核心事实？**否** —— 「这张申请单上要退什么、退多少」是业务事实，但它的**定义处**是 `order_return_request_lines` 表与 `services/order_return_request.py`（不在核心清单里）；核心区只多了一个**取值**（审计动作码）。
  - ② 是否改变核心不变量？**否** —— 钱 / 状态 / 权限的不变量一个字没动；新动作码只是「多了一种可被审计的动作」。
  - ③ 是否必须永久存在？**是**（动作码一旦写进历史审计日志就不能回收 ⇒ 只能追加、不能改语义）。
  - ④ 是否可能出现多个实现？**否** —— 动作码的全项目唯一取值处就是 `enums.py`；改明细的用例也只有 `amend()` 一处。
  - ⑤ 删除后 Core 是否仍然成立？**是** —— 删掉 `amend()` 与这个动作码，退货申请照旧能提、能驳回、能办理，只是回到「要改只能重提」。
- **要改 Core 时的三问**（规范 §F1）：
  - 为什么现有 Extension 边界无法解决？审计动作码**没有** Extension 侧的定义处 —— 全项目就 `OperationAction` 一张表（`enums.py`，核心清单第 56 行「领域词汇表：状态 / 来源 / 审计动作码」），不追加成员就只能复用旧码。
  - 为什么修改 Core 是必要的？复用 `ORDER_RETURN_REQUEST` 会把「谁在什么时候**提**过这张申请」和「这张申请上的货后来被谁**改**成了什么」压成同一件事 —— 用户原话就是分开说的两件事；压成一个码的后果是派单员拿着货主最初的数量去退、申请单上却已经不是那个数量，**出了对账问题没有任何一层能回答数量是什么时候被谁改的**。
  - 修改后 Core 的不变量是什么？`OperationAction` 的既有取值**一个都没动**，只追加一个成员（`backend/app/models/enums.py:151`）；能力覆盖表 `backend/app/core/capability_audit_coverage.py:71` 把新码挂到既有权限点 `order:return_request` 下（⛔ 不新增权限点、⛔ 不新增能力）。
- **核心改动声明行**（改核心区文件时**必须**，写在 `AI_WORK_CLAIM.md`「进行中」）：
  `核心改动：backend/app/models/enums.py —— 为什么必须动核心：审计动作码（状态 / 来源 / 审计动作码）全项目只有这一张表，「这张申请单上的货是什么时候被谁改的」必须有自己的码才在审计页上问得出来；本轮只在 OperationAction 末尾追加一个成员，既有取值与语义一个都没动。`

               审计写一条 ORDER_RETURN_REQUEST_AMEND（改动前 / 改动后 / 改动人）；出箱一条 returns.amended；
               投递后**只产生一条通知**：派单员改 → 发给这张申请的货主；货主 / 批发商改 → 发给全部在职派单员。

## ⑤ Data Contract

- **新增/改动哪些字段**：⛔ 不加表、不加列、不加索引。改动落在**已有行**：`order_return_request_lines.quantity`（就地改）、本次不要的行 `DELETE`、新勾的行 `INSERT`（带 `product_name` 快照）。
- **Owner 是谁**：`backend/app/services/order_return_request.py::amend()`（这张申请单明细的唯一写入者；端点是薄壳，只做鉴权 / 取锁 / 出箱）。
- **什么时候写 / 什么时候不写**：只有 `status = pending` **且**调用者是三方之一时写；终态、越权、空明细、越界一律**不写**（校验在写之前，失败路径 `db.rollback()`）。
- **是否允许 NULL**：不涉及（没有新列）。
- **历史数据怎么办**：一个字不改 —— 历史申请单的明细、历史通知、历史审计日志原样可解释；⛔ 不回填、不迁移旧申请单。
- **迁移怎么做 / Rollback 怎么办**：**零迁移**（无 DDL）。Rollback = 回滚代码；库里只剩「申请单上的数量与最初提交时不同」这一事实，而这一点**本来就被审计行完整记录**（动作码 + 改动前 + 改动后 + 改动人）。
- **删除本功能后历史数据还能不能解释**：能。明细仍在 `order_return_request_lines`、改动仍在 `operation_logs`；删掉 `amend()` 只是少了一条**新的**改动途径，不会让任何历史事实失去解释。

## ⑥ CHG 专章（FEAT / GOV 不适用时写「不适用：<理由>」）

### Before

申请单提上去以后，商品明细是**死的**：货主填错了只能「撤回申请」再重提一遍；派单员发现数量不对，只能「驳回」（货主收到「被驳回」通知），再让货主重提。中间没有任何改的口子，界面上也没有那个按钮（旧注释写的就是「数量锁死」）。

### After

- 派单员在「退货待办」的那张单上多一个「改明细」按钮；货主 / 批发商在「我的退货申请」里那张单上多一个「改明细」按钮（**只在派单员还没确认时**出现 —— 三方共用同一句判据 `canAmendReturnRequest(req) = req.isPending`，界面不自己写状态判断）。
- 点进去是**同一个**弹层（两端共用 `ui/common/ReturnRequestsUi.kt:112`，填数量那一块复用全仓唯一那份 `ui/common/Components.kt::OrderReturnLines`）：上面写着「现在是：苹果×3、桃×1」、下面按订单行填新数量（能退的都填满 / 全清零两个快捷键），最下面实时显示「改后：…」。
- 确认后：明细真的变了、列表刷新、一条中文提示「改好了：现在是 …。已给货主和批发商发一条通知。」；**只发一条**通知（派单员改 → 货主收到「订单 SO-x 的退货申请被派单员改了：原来是 …，现在是 …。」；货主 / 批发商改 → 派单员收到「… 改了订单 SO-x 的退货申请：原来是 …，现在是 …。请按新的数量办理。」）。
- 终态的单子看不到这个入口；就算硬调接口也会被 400 中文挡回去（「已经办完了，不能改」）。
