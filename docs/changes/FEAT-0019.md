## ① 六问

1. **用户要什么**（2026-10-11 逐字）：「消息（底部 Tab）……要按消息类型做颜色区别，而且**只有未读状态才有这个样式**，已读所有消息样式一样」；「文字也要按风险程度着色……按风险程度分红 / 橙 / …（重要程度不同 → 文字颜色不同）」；「能查的消息点进去直达详情」。追加修正（同日晚）：「你的文字不能全部用颜色给他去搞出来……真正的重心是这几个字……**全是重点就是没有重点**」。
2. **现在是什么样**：`notifications` 只有 `category`（system / order / reminder）与 `type`（自由字符串）＋ 一整句纯文本正文；没有任何一处告诉客户端"这条消息有多危险""这句话里哪几个字是重点"。
3. **为什么现在不行**：① 严重度若由客户端按 `type` 猜，就有**两份判定**（后端文案或类型改了，客户端不知道）；② 客户端拿不到重点词就只能整行上色 —— 那正是用户否掉的做法（"全是重点就是没有重点"）；③ 每条消息的金额/单号只有发消息那一侧才知道，客户端硬编码关键词必然漂移。
4. **改成什么样**：后端在**发消息那一侧**给出两个**互相独立**的事实 ——`severity`（这张卡有多危险：`info` / `warn` / `danger`）与 `payload["emphasis"]`（这条消息里哪几个字 / 哪个数字是重点）。客户端只负责渲染：未读才上样式（竖条＋彩标＋只给被点名的片段按 severity 上色），已读整条灰调。**判定只有一处**：`backend/app/services/message_center.py::severity_for()`。
5. **怎么证明改对了**：判据 `_tools/qa/_check_notification_severity.py`（**77 项**）＋ 反向验证 `_tools/qa/_reverse_verify_notification_severity.py`（**7 条注入全部被抓**）＋ 单测 `backend/tests/test_notification_severity.py`（**8 条**）＋ 迁移判据 168 项。
6. **怎么回退**：`git revert` 两笔代码提交（+ 文书一笔）即可；数据面见第 ⑨ 节 Rollback（多出来的列与键对旧客户端是无害的附加信息）。

## ② Must Change / Must Not Change

**Must Change**
- `notifications.severity`：`String(8)`、`NOT NULL DEFAULT 'info'`、index；迁移 `032_notification_severity`（可重跑、ALTER 与索引分开建、**不回填**历史判断）。
- `NotificationOut.severity`：`GET /notifications`（以及走 `emit_notification` 的 socket 推送）必须带出来。
- **判定只有一处**：`message_center.severity_for()`；模型的**列默认值**（`severity_default`）委托给它 —— 于是 6 条绕过工厂的裸构造路径（`services/data_retention.py` ×3、`services/ledger_export_worker.py`、`api/v1/notifications.py` 的 `POST /price-notify` 与 `POST /notifications`）不必逐点改，也拿得到正确的档。
- **重点词**：`payload["emphasis"]` ＝ 本类固定的"新闻词"（`EMPHASIS_BY_TYPE`）＋ 调用方给的具体值（金额 / 人名）＋ 自动补的单号；**只保留真的出现在标题或正文里的词**；最多 4 处、单个词 ≤24 字。

**Must Not Change**
- ⛔ `speech_important` 的语义（那是"要不要念出来"的语音开关，与危险程度是两件事）。
- ⛔ 既有**未读角标**语义（`GET /notifications/unread-count`、`emit_unread_count` 的行为一字未动）。
- ⛔ `payload` 的**老字段**（`order_id` / `order_no` / `old_price` / `new_price` / 退货金额…）—— 旧 H5 的 `ShipperPriceNoticeBar.vue` 与 App 都在读，**只许追加键**。
- ⛔ `POST /notifications` 的既有行为（payload 由调用方给，本轮没有改它的构造）。
- ⛔ App 侧文件（`android/app/src/main/java/com/tapmoay/sorders/ui/messages/**` 是另一个会话的）。

## ④ Behavior Contract

- **Input**：`create_message(db, *, recipient_id, category, type, title, content, payload=None, speech_important=False, idem_key=None, emphasis=None)`；以及 6 条绕过工厂的裸构造路径。
- **Output**：`Notification.severity ∈ {"info","warn","danger"}`；`payload["emphasis"]: list[str]`（有序、去重、最多 4 条、每条 ≤24 字，且**每条都真的出现在标题或正文里**）。
- **Success**：`GET /notifications` 的每一行都带 `severity`；socket 的 `notification` 事件也带（同一个 `NotificationOut`）。
- **Failure**：表里查不到的 `type` → `info`（**不是**抛错，也不是"假装危险"）；列默认值取不到当前行参数（多行 INSERT）→ `info`（默认值绝不抛）。
- **Boundary Cases**：`type=None` / 空串 → `info`；重点词不在正文里 → 丢弃；重点词等于整条标题或整段正文 → 丢弃（用户否掉的"整行上色"）；超过 24 字 → 丢弃；超过 4 条 → 截断；`payload=None` 且无重点词 → **保持 None**（不许凭空造空字典 —— 客户端"没有 payload 就只读"的口径会被改掉）。
- **Side Effects**：写库多一列（迁移一次、索引一条）；`payload` 只会**多**一个 `emphasis` 键。
- **Authorization**：无变化（本轮没有动任何权限点/端点门）。
- **Compatibility**：旧客户端忽略新字段；旧 H5 读的 payload 老字段原样保留（判据第 7 组钉着）。

## ⑤ Data Contract

- **新增/改动哪些字段**：`notifications.severity VARCHAR(8) NOT NULL DEFAULT 'info'` ＋ 索引 `ix_notifications_severity`；出参 `NotificationOut.severity`；`payload.emphasis`（JSON 内新键）。
- **Owner 是谁**：`backend/app/models/notification.py`（词汇表 ＋ 列 ＋ 默认值）与 `backend/app/services/message_center.py::severity_for`（**判定的唯一来源**）。
- **什么时候写 / 什么时候不写**：建消息时写一次（工厂显式盖 ＋ 列默认值兜底）；**之后不再改**（标记已读不会改 severity；客户端只在未读时上样式）。
- **是否允许 NULL**：不允许（`NOT NULL` ＋ 服务器默认 `'info'`）。
- **历史数据怎么办**：升级前的存量行一律 `info` —— 拿今天的判定表**追认历史**，等于把"当时发出的那条消息"改写成"今天的判断"，所以**刻意不回填**。
- **迁移怎么做 / Rollback 怎么办**：`032_notification_severity.py`（可重跑；ALTER 与索引**分开**建 —— SQLite 不支持 `ALTER TABLE ... ADD COLUMN` 带索引）；回滚＝revert 代码即可，多出来的列/键对旧代码无害。
- **删除本功能后历史数据还能不能解释**：能 —— `severity` 只是每条消息的一个附加判断，删掉它不影响 `title` / `content` / `payload` 老字段的语义。

### 渲染规则（两条正交规则）
