① **「进一次货」这件事在系统里没有落点**：库存只认「一次一个商品的变动数量」（`POST /api/v1/inventory/movements`），供应商欠款要另开一次「新建应付单」。同一批货因此在两个页面各录一遍、中间没有任何连线 —— 录了入库忘了记应付，欠款就少一笔（供应商页显示「不欠」）；录了应付没录入库，库存与成本价都对不上。而进货价只有一个入口（入库时那句「进货价（选填）」），**录进去就订正不了**：没有改单，也没有「再记一笔冲销」能把它从加权均价里去掉 —— `backend/app/services/cost_basis.py` 的 `_weighted_avg` 分母只认 `change > 0 AND unit_cost IS NOT NULL`，冲销行（负数、无价或 0）天然进不了分母，再记一笔只会让旧价永远留在均价里。最后，「账上到底有多少收入算不出成本、是哪些商品没录进货价」在界面上一处也看不到。
② **当前流程（用户在界面上怎么做）**：派单员 → 库存页 → 选一个商品 → 填「变动数量」（正数＝入库）→ 填「进货价（选填）」→ 提交；然后 → 供应商页 → 选供应商 → 「新建应付单」→ 金额手工填成刚才那批货的钱 → 保存；付款时再在供应商页对那张应付单分次付。一轮采购要切两个模块、手填两次金额，两次之间没有任何校验。
③ **会变化的事实/能力**：(a) 新增一张单据（采购单：单头＋多行「商品 / 数量 / 单价」），保存时**同一个事务**写完三件事：库存流水（`inventory_movements`，新增来源线 `source="PURCHASE"`）、商品成本价与成本价历史（`record_cost`）、供应商应付单（`supplier_payables`）；(b) 进货价从「只能再记一笔」变成「**可以订正的那一笔**」—— 改单改写该行绑定的那条入库流水（而不是追加一条冲销）；(c) 报表中心新增第 9 格「成本覆盖」：这一段窗口的「算不出成本的收入 / 算得出成本的行数」＋「从来没记过进货价的商品」清单与补录入口。
④ **明确不能变**：成本口径（`cost_basis.py` 的三级口径与加权均价公式）一个字节不改；库存加减的原子 SQL 写法与「库存不足如实报 400」不变；`cost_history.record_cost` 是成本价的唯一写入口不变；欠款口径（Σ alive 应付单 − Σ alive 付款流水，唯一实现在 `supplier_service.py`）不变；付款/现金流水（`cash_flows`）一行不动；订单、账本、结算、计费规则一行不写；⛔ 不新建权限点（`backend/app/core/rbac.py` 的 `Permission` / `ROLE_PERMISSIONS` / `SCOPES` 一个字节不动）；⛔ 历史的手工入库流水**不回填**「它属于哪张采购单」（过去没有 provenance 就不许猜）。
⑤ **归属**：EXTENSION IMPL ＋ PRESENTATION。它不定义任何核心事实（库存流水、成本价历史、应付单都是既有的），只是把「一次采购同时产生这三件事」这条路径补上；也不改任何核心不变量 —— 恰恰相反，改单选择「改写绑定流水」而不是「再记一笔冲销」，正是为了保住 `Σ(movements.change) == products.stock` 这条不变量。删掉采购单页，库存 / 成本 / 应付三块照旧各自成立。
⑥ **证据**：判据 `_tools/qa/_check_purchase_orders.py`＋反验 `_tools/qa/_reverse_verify_purchase_orders.py`（注入破坏必须报红）＋ `backend/tests/test_purchase_orders.py`（建单 / 改单 / 撤行 / 撤销 / 恢复 / 并发 / 已付款拒绝）＋ 后端真实探针（建一张单，验库存、成本价、应付三处数字对得上）＋ 模拟器 5554 真机截图（采购单页、成本覆盖页、供应商页看到自动生成的应付）＋ 全量静检。详见 ⑦⑧。

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

- **结论**：EXTENSION IMPL（采购单这条路径）＋ PRESENTATION（报表中心第 9 格）
- **五问依据**（规范 §三）：
  - ① 是否定义核心事实？**否** —— 核心事实（库存流水、商品成本价与成本价历史、供应商应付单）都是既有的，本事项只是新增一条「同时产生它们三个」的路径，不新增任何金额口径。
  - ② 是否改变核心不变量？**否** —— `Σ(inventory_movements.change) == products.stock`、「欠款 = Σ alive 应付单 − Σ alive 付款流水」都不动；改单**改写**绑定流水（而不是追加冲销）就是为了保住第一条。
  - ③ 是否必须永久存在？**否** —— 采购单是「一次采购」的便利落点；没有它，三块事实照旧能各自手工成立。
  - ④ 是否可能出现多个实现？**否** —— 进货这条路径只有一条（采购单），建/改/删/恢复只有 `purchase_service.py` 一处实现。
  - ⑤ 删除后 Core 是否仍然成立？**是** —— 删掉采购单页与两张表，历史库存流水、成本价区间、应付单都还在，只是少了一条「这批货从哪来」的连线（应付单标题里那句「采购单 #N」仍读得懂）。
- **要改 Core 时的三问**：不适用：本事项的结论不含 CORE（不改任何核心不变量）。
- **核心改动声明行**（`AI_WORK_CLAIM.md`「进行中」里已写）：见声明块的「核心改动：`backend/app/models/enums.py`、`backend/app/api/v1/__init__.py`、`backend/app/models/__init__.py` —— 为什么必须动核心：新增动作码与路由挂载是词表 / 接线文件，不是新口径。」

Output         采购单对象：{id, supplier_id, supplier_name, doc_date, remark, item_count,

                items:[{id, product_id, product_name, unit, quantity, unit_cost, amount（服务端算）, movement_id}],
                created_at, updated_at}；⛔ 客户端不自己相减、不自己乘
Success        库存逐行 += 数量（原子 SQL）；成本价与成本价历史按 record_cost(source=PURCHASE) 更新；
               生成一张应付单（金额 = 单据合计、日期 = 单据日期、标题「<供应商> 采购单 #<id>」）并回填 payable_id；

               供应商不存在 / 日期空）；供应商被软删 → 400；
               库存竞态抢不到 → 400「库存不足…」或 409「库存刚刚被别的操作改过…」（与既有入库同一套话术）；
               改单后新合计小于该应付单**已付**金额 → 400（钱已经付出去，账不许改小到负数）；
               失败时**不**发生：库存不动、流水不写、成本价不变、应付单不建、审计不写（整事务回滚，不留半成品）

## ⑤ Data Contract

- **新增/改动哪些字段**：
  - `purchase_orders`：`id` / `supplier_id`（index，指向 `suppliers.id`）/ `doc_date`（Date，index）/ `remark`（String(256)，可空）/ `payable_id`（指向本单生成的 `supplier_payables.id`）/ `operator_id` / `created_at` / `updated_at` / `deleted_at`（`SoftDeleteMixin`）。⛔ 单头**不存** total（= Σ 明细，现算，避免同一个数两处算）。
  - `purchase_order_items`：`id` / `order_id`（index，指向 `purchase_orders.id`）/ `product_id`（index）/ `quantity`（Integer，与 `inventory_movements.change` 同一单位）/ `unit_cost`（Numeric(14,4)，与流水同精度）/ `movement_id`（指向本行写下的那条 `inventory_movements.id`）。⛔ 明细**不存** amount（= 数量×单价，现算）。
  - 既有表**一个字段都不加**。库存流水的 `source` 只是多一个取值 `"PURCHASE"`（列早就是 String(20)）。
- **Owner 是谁**：库存与成本侧属于库存线（本事项新增 `backend/app/services/purchase_service.py` 作为「采购单」这件事的唯一实现）；应付单的 Owner 仍是 `supplier_service.py`（本事项只调它的既有函数建单/软删/恢复，⛔ 不复制它的口径）。
- **什么时候写 / 什么时候不写**：只在建单 / 改单 / 撤行 / 删单 / 恢复五个动作时写，且与库存变动同一事务；只读端点（列表 / 详情 / 成本覆盖）**一个字都不写**。⛔ 不做「后台自动对账」「定时回填」。
- **是否允许 NULL**：`remark` 可空（默认空）；`payable_id` 建单后必回填（新数据不许为 NULL）；`movement_id` 在撤行后仍指向那条 `status="VOID"` 的流水（不置 NULL，置 NULL 就丢了「这一行曾经写下过什么」）；`deleted_at` 为 NULL = 未删。
- **历史数据怎么办**：⛔ **一行都不回填**。既有的手工入库流水（`source="MANUAL"` / `"WAREHOUSE"`）与既有的应付单（没有 `purchase_orders` 那一行指回去）都保持原样 —— 过去没有 provenance 就写「不属于任何采购单」，不许按今天的规则替它猜一张单出来（规范 §五 的原话：过去没有 provenance 就写 NULL/unknown）。
- **迁移怎么做 / Rollback 怎么办**：`backend/app/migrations/019_purchase_orders.py` **只建两张表**（一事一迁移）。Rollback = 撤掉端点与页面 + `drop table purchase_order_items, purchase_orders`：库存流水、成本价区间、应付单、付款流水都不受影响（采购单本身不持有任何金额真相）。
- **删除本功能后历史数据还能不能解释**：能。库存流水带 `source="PURCHASE"` 与 note 里那句「采购单 #N」，应付单标题写「<供应商> 采购单 #N」，成本价历史带 `movement_id` —— 三处各自都能说清「这笔是怎么来的」。

## ⑥ CHG 专章

### Before

要进一批货（比如 100 箱矿泉水、单价 12.5 元，供应商「XX 商贸」）：派单员在**库存页**输入商品 → 变动数量 100 → 进货价 12.5 → 提交；再切到**供应商页** → 选「XX 商贸」→ 新建应付单 → 标题「货款」→ 金额手工填 1250 → 保存。两次操作之间没有任何关联：忘了第二次，供应商页就显示「不欠这家钱」；填错金额，也没有任何一处会红。价格录错了（实际是 12.5，填成 15）：**系统里没有任何办法把它改回来** —— 库存可以再记一笔负数「调整」，但那笔 15 元的入库永远留在加权均价的分母里，成本价从此偏高。

### After

同样这批货：派单员打开**采购单**页 → 选供应商「XX 商贸」→ 日期（默认今天）→ 加两行「商品 / 数量 / 单价」→ 保存。系统在同一个事务里：库存 +100、成本价按 12.5 更新并记一条成本价历史、供应商应付单自动生成（金额 1250、标题「XX 商贸 采购单 #7」）。价格录错了：打开那张采购单，把 15 改成 12.5 再保存 —— 系统**改写**当初那条入库流水（而不是再记一笔），库存差额自动补齐，成本价按新的那一笔重算，应付单金额同步改成新的合计（已付的部分不许被改小到负数）。报表中心多一格**成本覆盖**：这一段窗口「有多少收入算不出成本 / 有多少行算得出」＋「从来没记过进货价的商品」清单，点进去就能补录。

### Blast Radius（L0～L3）

**L3**：一次保存同时改三处钱相关的事实（库存 → 成本价 → 供应商欠款），而且改单会**改写既有流水**、进而改变这一段窗口的加权均价与应付余额。按规范 §二十六，L3 要求：判据 + 反验 + 真实库探针 + 真机实测 + 全量静检，且每一条钱的口径都要有恒等式证据。
