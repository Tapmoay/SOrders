## ① 六问

① **解决什么问题？** `FEAT-0006` 只把 **z≥19** 换成了自备影像，因为当时认为"高德在 z18 及以下是清晰的"。
需求方看了真机之后否掉了这个前提，并要求实测 —— 实测结果是**高德在这个区域每一层都糊**：

| 层级 | 自备影像（高频能量） | 高德原生 | 差距 |
| --- | --- | --- | --- |
| z16 | 55.1 | 18.6 | **2.97×** |
| z17 | 44.6 | 15.6 | **2.85×** |
| z18 | 34.5 | **6.8** | **5.05×** |
| z19 / z20 | 22.1 / 11.9 | 「此区域无卫星图」灰底 | — |

⇒ 只换 z19/z20 解决的是最小的一块。本事项把范围扩到 **z≥15**。

② **当前用户 / 业务流程是什么？** 见 `FEAT-0006.md` ① —— 流程一个字不改，
本事项只改"地图上那几层影像从哪来"。

③ **哪个现有事实或能力会发生变化？** **`FEAT-0006` 声明过的行为契约变了**：
原来是「z≤18 交回高德」，现在是「z≤14 交回高德」。这就是本事项必须走 `CHG` 而不是 `FEAT` 的原因。

④ **哪些东西明确不能变化？** 见 ② 节的 Must Not Change。

⑤ **这个变化属于 Core、Extension 还是 Infrastructure？** **INFRASTRUCTURE**（与 `FEAT-0006` 同）。
五问：①否 ②否 ③否 ④**是** ⑤**是**（删掉它，地图退回高德影像，业务一字不变）。

⑥ **什么证据能够证明它完成？**

- 模拟器：z15/z16/z17/z18/z19/z20 **六层逐个截图**，都出的是自备影像（不是高德）；

## ④ Behavior Contract

```text
Input          高德 SDK 逐格调用 getTile(x, y, zoom)
Output         Tile(256, 256, jpegBytes) 或 TileProvider.NO_TILE
Success        z <= 14 -> NO_TILE（地图显示高德自己的影像）
               z = 15  -> 取 z16 的 (2x,2y)..(2x+1,2y+1) 四格，合成
               z = 16  -> 直取 z16
               z = 17  -> 取 z18 的四格，合成
               z = 18  -> 直取 z18
               z = 19  -> 取 z20 的四格，合成
               z >= 20 -> 直取 z20（>20 无基座，回落高德）
Failure        ⛔ 任何一步失败一律返回 NO_TILE（地图透出高德底图），
               **绝不**合成半张灰图、绝不抛异常、绝不返回空 Tile
Boundary Cases · 四格里只要有一格取不到（多边形边界）-> 整块放弃返回 NO_TILE
               · 不在三层的覆盖范围内 -> HTTP 404 -> NO_TILE（正常情况，不是错误）

               · 磁盘缓存写失败（空间不足 / 无权限）-> 只用内存，下次重新下载，不报错
Authorization  无（公开静态资源，与 FEAT-0006 同）
Side Effects   写磁盘缓存；不发通知、不写库、不改任何业务状态
Compatibility  Compatible：AmapPickerDialog 签名不变、三个调用点零改动、后端零改动
```

## ⑥ CHG 专章

### Before

用户在「地图选点」里**放大到 z19 及以上**时，看到的是自备高清影像；
**缩到 z18 及以下**，立刻变回高德 —— 而高德在这个区域**每一层都糊**（z18 实测比自备影像差 5.05 倍），
所以"缩一点就变糊"这件事从 z18 就开始了。

### After

**缩到 z15 才**变回高德。z15–z20 六层全部是自备影像（奇数层由相邻偶数层在客户端 2×2 合成）。
z14 及以下仍是高德。

### Must Preserve

```text
- 历史订单 / 历史金额 / 已冻结的 Pricing Fact
- 历史 Provenance / Audit / Ledger
- 权限
- API compatibility（后端零改动）
- ⭐ 选点的坐标语义：仍然只来自高德 GCJ-02 逆地理，⛔ 影像层不参与任何坐标计算
- ⭐ 路网注记层（zIndex=2）与它的全层级覆盖
```

### Blast Radius（L0～L3）

**L1** —— 只改一个地图图层的层级范围。
⛔ 不动任何数据契约、不动核心、不动钱 / 状态机 / 权限 / 审计。
**为什么不判 L0**：它改变用户在地图上看到的内容（同 FEAT-0006），且新增了 3.78 GB 服务端静态数据。

### ⑦.2 ⭐ 本轮抓到的真缺陷：没有负面缓存（已修）

`z=17` 上那 56 次 `NO_TILE` 里，**只有 2 个不同坐标**（`108051,54378` 与 `108051,54379`）——
它们是**数据边界的洞**（同列 54377/54380 都成功；核实过：这两格需要的 z18 子格在**本地源数据里也没有**）。
⇒ 「缺一张就整块放弃」的行为是对的，回落高德而不是合成半张黑图。

**但它暴露了一个真缺陷**：高德对拿不到的格子**会反复来问**（13 秒里 27 次/格），
而第一版代码**没有负面缓存** —— 每次重试都要「查磁盘缓存（miss）→ 发一次 HTTPS → 收 404」。
一屏 2 个洞就是 54 次白跑的请求；沿着覆盖边界拖地图时这个量会更大。

**修法**：`HiResTileLayer` 加一层负面缓存（`ConcurrentHashMap` + 10 分钟 TTL + 8192 上限），
⚠️ **只记 404**（后端明确说"没有"），超时 / 断网**不记**（那是暂时的，记下来会让一块本来有数据的
瓦片在 10 分钟里一直显示不出来）—— 为此把 `httpGet` 的返回值从 `ByteArray?` 改成 `(code, bytes)`。

**实测效果**：

```text
真实发出并收到 404 的次数 :   3
被负面缓存挡掉的次数      :  54
```

### ⑦.3 ⚠️ 顺手纠正上一轮（FEAT-0006）一句说过头的话

`FEAT-0006.md` 里写过「z18 时 `getTile` **调用 0 次**（SDK 连问都不问）」——
**那句话是错的**，因为当时的临时日志打在 `if (zoom < HI_ZOOM) return` **之后**，
量到的其实是"**通过门控**的次数"，不是"SDK 来问的次数"。

本轮把日志打在门控**之前**，真实数字是：**SDK 在每一层都会来问**，
z14 一次巡游里问了 **720 次**，我们全部立刻返回 `NO_TILE`。
⇒ 效果（回落高德）是对的，**"SDK 不问"这个因果说反了**。已在 `FEAT-0006.md` 与声明页里改正。
