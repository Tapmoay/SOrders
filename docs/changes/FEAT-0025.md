## ① 六问

① **要解决什么问题？** 用户要在 AI 聊天里设"第二个成本价"，AI 却回答**做不到** —— 真机截图里它说的是：
   「系统里每个商品只有一个成本价，你说的两个（进货成本、返点后成本）只能留一个 —— 报表里的毛利就是拿这一格算的。」
   用户原话（2026-10-11 逐字）：「我们要，**我们是可以设置多个成本价的**，**AI 也都可以调**。只不过我们一般情况下是默认按**一个成本价**，也就是**真实成本价**，按那个来计算的，一般订单都是按那个来计算的。当然，我们有时候计算的时候还有**第二个成本价** —— 这个成本价可能是**加了其他东西、或者比如说有补贴啊等等之后的成本价**。所以**一定要有多个成本价**啊。我在跟他聊天的过程当中，他就**没办法设置第二个成本价**。」

② **当前用户/业务流程？** 一个商品只有一个 `products.cost_price`（唯一写入口 `backend/app/services/cost_history.py:100`
   `product.cost_price = new_cost`，每次改都进 `product_cost_history`）。想记"返点后 / 补贴后"的成本，
   人工路径只能**覆盖**那一格 —— 覆盖之后订单与毛利的成本口径就跟着变了，这正是用户不敢做的。

③ **哪个现有事实会变化？** 多了一张表 `product_cost_prices`（每条 = 一个商品的一个**具名**成本口径）、
   五条端点、三条 AI 动作（`products.cost_price.set` / `.delete` / `.restore`）与商品编辑页的一个新弹层。
   **`products.cost_price` 自己没变**：它仍是"真实成本价"，仍是订单与毛利的唯一口径。

④ **哪些东西明确不能变？** ① `products.cost_price` 的语义与唯一写入口（`services/cost_history.py`）；
   ② 下单/派单定格：`services/order_flow.py:873` `cost_snap = prod.cost_price or Decimal("0")` ⇒ `:885` `cost_price_snapshot=cost_snap,`，
   `api/v1/order_products.py:226` / `:235` 同形；③ 毛利聚合 `services/reports/product_query.py:66`
   `cost, basis_src = basis.of(lp.product_id, lp.cost_price_snapshot)`（`services/cost_basis.py` 的口径判定）；
   ④ 报表里"毛利只按 `cost_price_snapshot > 0` 的行算 + 覆盖率说明"这套说法；⑤ 订单/账单/库存/权限的任何字段。

⑤ **属于 Core、Extension 还是 Infrastructure？** EXTENSION IMPL（新增一张只读参考口径表 + 三条 AI 动作 + 一个弹层）；
   核心区只**追加**了两处（见 §③ 的核心改动声明行）。

⑥ **什么证据能够证明它完成？** `_tools/qa/_check_product_cost_prices.py` **186 条断言全过**（含"默认口径仍取自
   `products.cost_price`"与"附加口径表没飘进任何算钱的文件"）；反验 `_reverse_verify_product_cost_prices.py`
   **19 条注入全部变红 + 逐字节还原**；`backend/tests/test_product_cost_prices.py` **16 passed**；
   `_check_core_freeze.py` 111 项通过（含本单那两行核心改动声明）。

## ② Must Change / Must Not Change

```text
Must Change:
- 数据：新增表 product_cost_prices（product_id / name / cost_price / sort_order + 软删列），
  (product_id, name) 唯一 —— 同名不许两条（用户要"能命名、能列多个、能排序、能删了再放回来"）；
- 接口：GET /products/cost-prices（列表；第 0 条是**合成的**默认那条）、POST /products/{id}/cost-prices
  （按名字 upsert：有就改价、没有就建，命中回收站那条就复活它）、PATCH /products/cost-prices/{row_id}
  （改名/改价/改顺序，只改传进来的字段）、DELETE .../cost-prices/{row_id}（**软删**）、
  POST .../cost-prices/{row_id}/restore（从回收站放回来）；
- AI：三条动作 products.cost_price.set / .delete / .restore —— **AI 必须能设第二条**（本单要治的痛）；
  卡片必须写清「哪个商品 / 哪条口径 / 改前 → 改后」，缺信息就问、⛔ 不许猜；
- App：商品编辑页加「成本价口径」弹层（能看 / 能加 / 能改名改价 / 能软删 + **手边有恢复入口**），
  默认那条**排最前**并标注"订单/毛利按它算"，其余标"参考口径"；
- 审计：四条动作码 PRODUCT_COST_PRICE_UPSERT / _UPDATE / _DELETE / _RESTORE ＋ 审计中心中文名。

Must Not Change:
- products.cost_price 的语义、唯一写入口与其历史（product_cost_history）；
- 订单/派单的成本定格（cost_price_snapshot 仍取自 products.cost_price）；
- 毛利聚合与成本口径判定（services/cost_basis.py、services/reports/**）；
- "毛利只按 cost_price_snapshot > 0 的行算 + 覆盖率说明"这套说法；
- 权限模型（仍是派单员可读可写，货主/司机读不到）；
- ⛔ 不给任何报表加"按第二个成本价看"的开关（钱的口径要用户拍板 —— 见 §⑥「下一单」）。
```

  - ③ 是否必须永久存在？**否** —— 删掉这张表与三条动作，人工路径仍能改 `products.cost_price`，订单与毛利照算。
  - ④ 是否可能出现多个实现？**是** —— "新建一张具名表"与"往商品上加 JSON 列"都做得成（本次选前者，理由见 §⑥）。
  - ⑤ 删除后 Core 是否仍然成立？**是**。
- **核心改动声明行**（两处，都是**只追加**）：
  - `核心改动：backend/app/models/enums.py —— 为什么必须动核心：` 审计动作码是全项目共用的取值表
    （`_tools/qa/_core_files.txt` 把它列为核心区），"谁加了/改了/删了/放回了某个附加成本口径"要留痕
    就只能在这里加码；本次只追加 4 个成员，既有成员一个没动，且这四条都**不写** `products.cost_price`
    （订单与毛利的成本口径仍旧是 `PRODUCT_CREATE` / `PRODUCT_UPDATE` 那两笔）。

    它是 AI 写闸门（`preview → 确认卡 → execute` 的唯一写入口），新开的写域必须在"动作 id → 处理器"

    （开关关着就不许传）—— 成本价一旦进模型上下文就会留在聊天记录里，这条正好是我们要的。

## ⑥ 专章

**不适用"改之前的行为"对比**：本事项是 FEAT（新增能力）。与它相邻的既有行为 —— 真实成本价的唯一写入口、
订单定格、毛利聚合、覆盖率说明 —— **一个字都没改**，见 §② Must Not Change；判据里有一节专门盯它们（§⑧）。

### 为什么选「新建一张具名的表」，而不是「往商品上加 JSON 列」

1. **要能命名、要能排序、要能一条一条删了再放回来**：JSON 列做不到"按名字唯一"（同名两条只能靠代码兜），
   也做不到"删掉第一条、保留第二条"这种行级软删 —— 而用户明确要的是"多个成本价"各自独立。
   唯一约束 `uq_product_cost_price_product_name` 把"同名不许重复"交给数据库，代码兜底只是第二道。
2. **钱的边界要一眼看得出来**：`products.cost_price` 那一格**没有动**，新口径在**另一张表**里 ⇒
   "订单与毛利的成本口径"与"参考口径"在数据层就是两样东西；判据因此可以写成一条**可机检的边界**
   （扫 `backend/app/**/*.py`：除了 5 个白名单文件，任何地方都不许出现 `ProductCostPrice` / `product_cost_prices`）。
   若走 JSON 列，这条边界就只能靠"约定"，判不出来。
3. **与既有软删规矩同形**：`is_deleted` + `deleted_at` + 一个 restore 端点，与全库其它名册一模一样
   （用户 2026-09-20 的硬规矩：删了必须能拿回来）。
4. **代价（明说）**：多一张表、多一次迁移、多五条端点；列表要合成一条"默认口径"给界面（见 §⑤）。
   换来的是"口径可比、可命名、可撤回、可机检"。

### 为什么"设置成本价口径"这条动作**没有撤回按钮**

`products.cost_price.set` 是"有就改、没有就建"：撤回到哪一条说不清（新建的那条该删掉？
改价的那条该改回原值？），所以它进了 `AiRevert` 的 UNDO_NONE 表，卡片上**明确写出**
"这条消息上没有「撤回」按钮，要改回去就跟我说一声"。删除与恢复则是**成对**的
（`AiResources.COST_PRICE`：`delete` ↔ `paired(restore)`，撤回锚是 `cost_price_id`）。

### 为什么这个功能是 L3（虽然一个字节的算法都没改）

因为它**紧挨着钱**：任何一次"顺手让第二个成本价参与计算"的改动，都会静默改变毛利。
本单的做法是把"不可能越界"写成**可机检的边界**：新增表在后端的合法落点只有 5 个文件
（模型 / 导出 / 迁移 / 接口 / schema），违约金的口径锚点（下单定格、写入口、毛利聚合）在判据里逐条钉死，
另有 19 条注入的反验证明判据真的能判红（其中第一条就是"把默认口径改成按第二个算"）。

### 下一单（建议，等用户拍板 —— 本单**没做**）

- **报表按第二个口径看**：例如"按返点后成本算的毛利"。这是**钱的口径**，需要用户先拍板：
  ① 是加一列（两个口径并列显示）还是切换；② 切换时覆盖率说明怎么写（`cost_price_snapshot` 仍是真实成本价，
  第二条口径是后来的价 ⇒ 历史订单没有这个数）；③ 权限（谁能看）。**本单刻意不做**，等拍板。
- **口径参与"调价建议"或"保本价"**：同样属于钱的口径，一起等拍板。
- **口径的历史**：现在改一条口径不留旧值（只有 products.cost_price 有 product_cost_history）。
  如果用户要"这条口径上个月是多少"，再照 cost_history 的样子补一张。
- **AI 侧**：目前 AI 能设/删/恢复，但**不能把订单或报表按第二个口径算** —— 若以后要，
  必须先在提示词里写清"默认口径是真实成本价"，再谈别的。
