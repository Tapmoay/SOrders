## ① 六问

1. **用户要什么**（2026-10-11 逐字）：
   > 「关于这个车辆年检提醒啊，到我给那个车子建档案的时候会填一下就是这车的**上牌日期**。
   >   或者说是**上一个年检日期**啊方便我们去做一个提醒」
   > 「**库存偏低**的话，我们**按百分比来算** —— 也就是说，他肯定会设置这个库存的报警嘛……
   >   然后我们在**报警的那个水平宽松一点**，就显示『库存偏低』，是这样子的。」

   两句合起来是**两件事**：①车辆只录**已经发生过的事实**（上牌 / 上次年检），"下次该检了"由系统算；
   ②「库存偏低」不新增任何字段，就在**已有的报警阈值上按百分比放宽**。
2. **现在是什么样**：`FEAT-0021` 把 `stock.near_low` 与 `vehicle.inspection_due` 登记了档位，却在
   `message_producers.NOT_PRODUCED` 里如实写着"没做"——理由都是**同一个形状**：**字段全库不存在**
   （`stock.near_low` 缺"建议水位"、`vehicle.inspection_due` 缺年检日期）。也就是说这两类
   **只会显示、不会自己出现**（消息中心里永远一条都没有）。
3. **为什么现在不行**：`vehicles` 表里**没有任何日期列**（`purchase_date` 是折旧用的购置日期，不是年检），
   所以"该提醒谁、提醒什么"没有输入；`products` 表里**只有 `low_stock_alert` 一个阈值**，
   没有第二根水位线，`stock.near_low` 就没有判定依据。
4. **这次改哪里**：给 `vehicles` 加两列（迁移 `033_vehicle_inspection.py`）；
   把"下次年检日期"落成**一处纯函数**（`services/inspection_due.py`，⛔ 不落库）；
   在 `message_producers.py` 里启用 `stock.near_low`（判档收敛到一个纯函数 `stock_band`）
   并新增 `notify_inspection` / `scan_inspection_due`；把两类从 `NOT_PRODUCED` 里**移走**。
5. **为什么不那样改**：⛔ **不加"下次年检日期"列** —— 那是派生量，落库就意味着"改了上次年检日期之后，
   算出来的旧值还留在库里"（与折旧额同一条纪律：派生量每次现算）；
   ⛔ **不给"库存偏低"新建一个水位字段** —— 用户要的是"在**已有的**报警水平上宽松一点"，
   多一个字段就多一处要维护、还会与阈值对不上（`FEAT-0021` 当时正是因为不想编一个阈值才如实没做）；
   ⛔ **不把 2/29 往后夹到 3/1** —— 见 ③ 的边界说明。
6. **做完什么样**：建车/改车时能填两格日期（可空），到期前 30 天派单员收到一条 warn「车辆年检将到期」、
   过期后收到 danger「车辆年检已逾期」；库存到报警阈值但还没跌破时收到 warn「库存偏低」、
   跌破时才收到 danger「库存不足」；每日扫描**连续跑两次第二次 0 条**。

### 三条边界（都写成了单测或注入，⛔ 别按"看起来更合理"改掉）

1. **库存恰好等于报警阈值 ⇒ 算「偏低」（warn），不算「不足」（danger）**。
   等于阈值说明**还没有跌破它**，与"已经跌破"是两件不同的事 —— 而用户要的正是"在报警的那个水平
   宽松一点"的这一档。判定线 = `阈值 × (1 + NEAR_LOW_RATIO_PERCENT%)`（阈值 10 件的商品：
   10~11 件报偏低、12 件起一个字都不发）。**比较一律走整数**（`stock * 100 < alert * (100 + 20)`），
   ⛔ 不用 `stock < alert * 1.2`：浮点在大数上会给出"差一件"的边界错，而这是"该不该补货"的判断。
2. **到期日当天算「临期」、不算「逾期」** —— 那一天车还能合法上路，说"已逾期"是错的话。
   分档与既有的 `payable_kind`（第 0 天 = 临期）**同形**：`left < 0` 才算逾期。
3. **2/29 落在平年时夹到 2/28**（`date.replace(year=+1)` 对 2/29 会抛 `ValueError`）。
   夹到 3/1 会让提醒比"满一年"**晚一天**，而这件事的两侧不对称：早一天只是多提醒一次，
   晚一天是让车主**可能过期上路**（罚款、扣车）。

## ④ Behavior Contract

**谁在什么时候收到什么**（收件人一律是 `message_center.active_dispatchers` —— 在用的派单员）：

| 触发 | 类型 | 档位 | 提前量 / 条件 | 幂等键 |
|---|---|---|---|---|
| 库存跌破报警阈值 | `stock.low` | danger | 库存 **<** `low_stock_alert` | `stock.low:{商品}:{日期}` |
| 库存**到了**阈值、还在 ×1.2 以内 | `stock.near_low` | warn | 阈值 ≤ 库存 **<** 阈值 ×(1+20%) | `stock.near_low:{商品}:{日期}` |
| 离下次年检 ≤ 30 天（含当天） | `vehicle.inspection_due` | warn | `left ≥ 0 且 ≤ 30` | `vehicle.inspection_due:{车}:{到期日}` |
| 已过年检到期日 | `vehicle.inspection_overdue` | danger | `left < 0` | `vehicle.inspection_overdue:{车}:{到期日}` |

- **两档库存互斥**：同一商品同一天**只会有一条**（不是两条）—— 判档只有 `stock_band()` 一处；
- **年检两类也互斥**：同一台车同一次到期只会有一条 —— 分档只有 `inspection_due.inspection_kind()` 一处；
- **两格日期都空的车一个字都不发**（那是"没录"，不是"没上牌"）—— ⛔ 不许拿"今天"或建档日期凑一个到期日；
- **两格都录了 ⇒ 以「上次年检日期」为准**，上牌日期只在从来没有年检记录时兜底；
- **停用（`is_active=false`）的车不催年检**（卖了 / 封存）；
- **年检没有事件钩子**：它不跟着任何一次写库走（"今天到没到期"与用户改了什么无关），
  所以 `run_daily_scan` 是它**唯一**的入口 —— 每日扫一遍全车队；
- **幂等**：一律走 `create_message(idem_key=...)` ＋ 数据库唯一索引 `uq_notifications_idem_key`，
  ⛔ 不靠"先查再发"。于是每日扫描**可以随便重跑**（进程重启 / 多 worker / 手工补跑都安全）。

文案（写进正文的那两句就是被点名的片段，⛔ 不许只在 emphasis 里出现）：

- 「商品「X」库存偏低：当前库存 11 件，已到报警阈值 10 件，请留意补货，别跌破阈值。」（点名：`11 件`、`10 件`）；
- 「车辆「赣A12345」的下次年检日期是 2026-11-05，还有 25 天，请提前安排年检。」（点名：车牌、`还有 25 天`）；
- 「车辆「赣A12345」的年检已逾期 3 天（下次年检日期 2026-10-08），请尽快安排年检。」（点名：车牌、`3 天`）。

## ⑤ Data Contract

**迁移 `033_vehicle_inspection.py`**（`VERSION = 33`）：

```sql
ALTER TABLE vehicles ADD COLUMN registration_date DATE NULL;
ALTER TABLE vehicles ADD COLUMN last_inspection_date DATE NULL;
```

- **两列全部可空、⛔ 不回填、⛔ 没有 DEFAULT**：NULL 的含义是「**没录**」，不是"没上牌"、也不是
  "从来没检过"。给一台没录过的车编一个上牌日期，后果是**系统会自己造一条假的年检提醒**出来
  （比不提醒更坏）；
- **没有索引**：这两列只随车辆行按主键读出（车辆的读法只有"列表 + 单行"），每日扫描是全表按
  "两格非空"过一遍小车队（几百行量级），建索引只会拖慢写入；
- **可重跑**：逐列判存在性、逐列执行（MySQL 的 DDL 隐式提交 —— 一条迁移可能改了一半才失败，
  下次重跑必须能接着往下走）；
- **自愈副本**：`core/schema_bootstrap.py` 里那段是同一句 DDL 的副本，给"迁移没跑过就直接起服务"的库兜底。

**出参 / 入参**：`VehicleOut` 多两格（原值，`null` = 没录；⛔ **不回**"下次年检日期" —— 那是派生量，
回一个算出来的日期会让客户端以为库里存着它）；`VehicleCreate` / `VehicleUpdate` 收这两格，
空串归一成 `None`（安卓 `explicitNulls = false` 发不出显式 null）。

**`PATCH /vehicles/{id}` 的语义（⛔ 这条最要命）**：逐格看 `model_fields_set` ——
**没传这个键 = 不动**、**传空串 = 清空这一格**。⛔ 不能用 `is not None`：老客户端与"只改车牌"的
常规编辑**根本不带这两格**，那样一次改车牌就会把用户录的年检日期**抹掉**（这是本条最坏的一种错法）。
两格是**互相独立**的：清空"上次年检日期"不该顺手把"上牌日期"也抹掉。
改动只在**真的变了**时写审计行（清空记 `→ （清空）`）：清空上牌日期等于"这台车从此不再提醒"，
而界面上只会少一个日期，看不出后果。

**三类新消息**用的是 `notifications` 现成列（`type` / `severity` / `payload` / `idem_key`），
⛔ **不加列、不建表**。
