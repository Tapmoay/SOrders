① 商品删除的三处弹窗/说明都承诺「列表顶端的『回收站』里可以把它恢复回来」（`ProductFormScreen.kt:325`、`:411-412`、`ProductBatchScreen.kt:290`），而商品管理页**从来没有那个回收站**：`ProductsScreen.kt` 里「回收站」零命中、`Apis.kt::listProducts` 连 `deleted_only` 参数都没有、`AppRepository.restoreProduct`（`AppRepository.kt:708`）在 `ui/` 下一个调用点都没有（只挂在 AI 撤回卡上）。用户 2026-09-20 定的硬规矩是「所有删除一律软删 + **界面上要有一个手边的恢复入口**」—— 商品这一格是欠账：删错了在界面上永久找不回来，只能调接口或找 AI。
② 用户动作：工作台 → 商品管理 → 某商品「编辑」→ 滑到「删除商品」（或底栏「批量操作」→ 勾几条 → 删除）→ 确认删除 → 商品从列表消失 → 想反悔时**没有任何入口**。（测试台账 TA-03 第 3 轮复现、TA-11 第 4 轮复现并升级为「堵死」。）
③ ① 后端多两个查询参数（`deleted_only` / `include_deleted`）与一条 403 门；② App 的 `ProductDto` 多一条取数路径（`deletedProducts()`），商品管理页顶部多一个「在用 / 回收站」档与一套恢复动作。能力上「已经从界面上消失的软删商品」第一次变得**可见、可恢复**。
④ 不变量：① 缺省查询（不带参数）**一个已删商品都不回**，与今天逐字一致（列表、选品页、AI 读通道、H5 全部走的就是缺省）；② `include_inactive` 的语义与那句描述（含 `已下架商品`）一字不改（被 API 快照与 `_check_wording_consistency.py:345` 钉着）；③ 恢复动作仍是既有的 `POST /products/{id}/restore`（含它自己的 `was_active` 回填口径），本单不碰；④ 权限不新建体系：进端点仍是 `order:create`，看回收站按既有的 `product:manage`；⑤ 不新增/不改动任何表、列、迁移。
⑤ Extension（既有一个只读端点加参数 + 展示层加一个档）+ Presentation（顶部那一排与文案）。不碰 Core：`products` 表早就有 `is_deleted/deleted_at`（`SoftDeleteMixin`），本单一个字节都不加。

## ④ Behavior Contract

```text
Input          GET /api/v1/products?deleted_only=true（回收站）｜ ?include_deleted=true（连回收站一起看）｜ 两个都不带（今天的缺省）
Output         200 + list[ProductOut]；无权者 403 + detail「无权查看回收站」（中文，不是结构体）
Success        deleted_only=true → 只回 is_deleted=true 的行，按 deleted_at 倒序（删除得晚的在前，同一时刻按 id 倒序）；
               include_deleted=true → 已删的也回，**排在最后**（活着的仍在售优先、手工排序、常用度、先创建的在前）；
               缺省 → 一个已删商品都不回（与今天逐字一致）
Failure        没有 product:manage 的角色带这两个参数 → 403，**不静默降级成「回收站是空的」**（那会把「你没权限」说成「没有已删商品」，两句完全不同的结论）；
               失败时**不**发生什么：不改任何一行、不写任何日志、不产生半成品事实（纯读）
Boundary Cases ① 已删商品一定 is_active=false（DELETE 强制下架）⇒ 回收站分支不许再套 is_active 过滤，否则恒空；
               ② 空回收站 → 200 + []（不是 404）；
               ③ include_deleted=true 且 include_inactive=false（App 的默认）→ 活着的只留在售、已删的照回：where(or_(is_active, is_deleted))；
               ④ 删了又恢复 → 该行回到缺省列表（is_deleted 已翻回 false）；
               ⑤ 两个参数同时给 → 按 deleted_only 理解（就是「只看回收站」）
Side Effects   纯读：不写库、不写 operation_logs、不动 outbox
Authorization  端点权限沿用 order:create（进得来）；两个新参数这道门沿用既有 Permission.PRODUCT_MANAGE（恢复端点用的同一把尺子）—— ⛔ 不新建权限点
Compatibility  Compatible —— 两个参数都默认 false；老客户端（选品页、订单详情改行、货主下单目录、AI 读通道、H5）不带参数时行为逐字不变
```

## ⑤ Data Contract

- **新增/改动哪些字段**：无新字段、无新列。只是 `products.is_deleted/deleted_at` 第一次**出现在查询条件与排序**里（`deleted_at` 只用于排序）。
- **Owner 是谁**：`products` 行归商品主数据（派单员维护，见 `rbac.py:183` 的 `product:manage: ("all", "商品是全局主数据，不分归属")`）。
- **什么时候写 / 什么时候不写**：本单**一个字节都不写** —— 回收站是读路径；软删标记仍由 `DELETE /products/{id}` 写、仍由 `POST /products/{id}/restore` 清。
- **是否允许 NULL**：不适用（`is_deleted` 是 NOT NULL 布尔；`deleted_at` 允许 NULL = 没删过，排序时它只出现在回收站视图中）。
- **历史数据怎么办**：⛔ 不回填、不修复。历史上被软删的商品本来就带着 `is_deleted=1/deleted_at`，它们**从本单起第一次可见**并可恢复；不做任何批量修改。
- **迁移怎么做 / Rollback 怎么办**：无迁移（不加列、不建索引）。Rollback = `git revert <实现提交>`：参数消失后端点回到缺省行为，已恢复的商品不受影响（恢复走的是既有端点）。
- **删除本功能后历史数据还能不能解释**：能 —— 本单不产生任何新的持久化事实；「某商品在哪一刻被谁删/恢复」仍由既有 `operation_logs`（`PRODUCT_DELETE` / `PRODUCT_RESTORE`）解释。


```text

```
