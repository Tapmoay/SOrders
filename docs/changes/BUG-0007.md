① **月末给司机结账时，结算单的金额与它下面的明细对不上 —— 那张单再也确认不了，司机这笔钱结不掉，只能改库。**

报错逐字（全量后端套件里三条长期红的用例，以及真机遇到时的同一条）：

```json
{"detail":"结算单金额 970.00 与明细合计 940.00 不一致，请核对"}
```

**根因不是「某个数字算错了」，是同一个账期里有两套取数口径**（backend/app/services/accounting_service.py）：

| 动作 | 改动前它怎么取明细 | 后果 |
| --- | --- | --- |
| 建单 create_settlement（改动前 :571） | 司机 + 月 + 类型 + status=OPEN + or_(order_id is NULL, 订单未软删) | order_id 为空的**历史孤儿明细也算进 amount** |
| 确认 confirm_settlement（改动前 :640） | 按 s.order_ids 重取（DriverBill.order_id.in_(...)） | 孤儿没有单号 ⇒ **永远取不回来** |

于是 amount（含孤儿）恒大于确认时算出来的 locked_total，差额正好是孤儿那几笔 ⇒ 确认接口必然 400。
**金额卡死 = 司机的钱卡死**：既确认不了、也付不掉，页面上那条明细永远是 OPEN，谁都没有出口。

**同一个病根还有另外三个出口**（都在同一条链路上，本轮一起收掉）：

1. **建单时孤儿被算进金额、却被从 order_ids 里丢掉**（改动前 :601 order_ids = [b.order_id for b in bills if b.order_id]）—— 两张脸对不上，是上面那个 400 的直接来源。
2. **手工改额必然确认不了**：DriverSettlementCreate.amount 是允许人工改的（改动前 :622-623 只改 amount），而确认时的恒等式是 amount == 明细合计 ⇒ 只要动过金额，这张单**从建出来那一刻就注定确认不了**，且报错里一个字都不提「你手工改过额」。
3. **作废解不开锁**：cancel_settlement（改动前 :755）的解锁块挂着门闩 if s.settle_type == PIECE and s.order_ids ⇒ 孤儿单（order_ids 为空）或月薪单在「作废单 + 明细已被它锁成 SETTLED」的竞态下**永远解不开** —— 那批明细既不在 OPEN 里、也不可付。

② **现状（读码 + 实测）**：全量后端套件里有 **3 条长期红**（backend/tests/test_full_loop_regression.py:174 / backend/tests/test_money_audit_trail.py:165 / backend/tests/test_timezone_family.py:109），单独跑这三个文件 **9 passed** —— 只有全量套件累积到那一步才红。
差额 **30.00** 的来源已经查明：backend/tests/test_driver_bill_recycled_scope.py 的 test_孤儿账单_订单号为空_不受影响 在共享测试库里留下一条 order_id IS NULL 的孤儿明细，而它**正是结算侧口径里该收的那种行** ⇒ 下一条用例建单时把它算进金额，确认时又取不到它。
活库（backend/sorders.db）实测**当前没有这种数据**：driver_bills 里 open/piece 303 行 ¥10837、settled/piece 8 行 ¥2700，**孤儿 0 行**；没有任何一组的「整月合计 ≠ 有单号行之和」；driver_settlements 54 行（1–50 draft、51–54 paid ¥675）。⇒ **不需要数据修复**，要修的是「一旦出现孤儿，那张单就永远确认不了」这条逻辑链路。

③ **变化：把这个账期「覆盖哪几行明细」在建单那一刻定死，并且让金额与明细全程同源。** 四处：
(a) **取数只有一处**：新增 backend/app/services/accounting_service.py:570 def settleable_bills(db, *, driver_id, settle_type, month) -> list[DriverBill]，软删口径（.outerjoin(Order, Order.id == DriverBill.order_id) + or_(DriverBill.order_id.is_(None), Order.deleted_at.is_(None))）搬进它体内；create_settlement（:611）与 confirm_settlement（:661）**都调它**，谁都不再手写条件。
(b) **建单当刻锁定**：新列 driver_settlements.bill_ids（JSON，可空）记下这几行的**主键**（含孤儿 —— 它们没有单号可列），create_settlement 里 :628 bill_ids = [b.id for b in bills]、构造器 bill_ids=bill_ids。确认时优先认它：:669 recorded = [int(x) for x in (s.bill_ids or [])] → if recorded: 按主键在**同一个取数函数**的当前结果里点名取行；少了就明确报错（「这张结算单锁定的 N 笔明细里有 M 笔已经不在了（被删除或已被别的结算单占用），请作废后重新结算」）。**老草稿没有 bill_ids，仍走老的两条分支**（按 order_ids / 按月口径），一行不废。
(c) **手工改额记差额**：新列 driver_settlements.adjustment（Numeric(12,2) NOT NULL DEFAULT 0），恒等式从 amount == 明细合计 变成 **amount == 明细合计 + adjustment** —— 确认（:714）与付款（:756）两处都用它；报错里点出那一笔（:716 tail = f"（本单另有手工调整 {adjustment:+}）"）。
(d) **作废解锁去掉门闩**：:798 cancel_settlement 改为无条件解锁 —— 按 DriverBill.settled_doc_id == s.id + DriverBill.status == DriverBillStatus.SETTLED 翻回 OPEN，不再看 settle_type / order_ids。

⑤ **Core**：backend/app/services/accounting_service.py —— 账本入账与欠款口径的唯一一处（取数与恒等式就在这里，两套口径正是病根）。
**Infrastructure**：driver_settlements 两列 —— **正式搬迁** = backend/app/migrations/017_settlement_bill_ids.py（VERSION 17，逐列判存在、可重跑、不回填）；**自愈副本** = backend/app/core/schema_bootstrap.py:1438-1459（「列不在才补」，重复启动幂等；应用启动只核对不改库，R3-01）。

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

- **结论**：**CORE**（accounting_service.py：账本入账与欠款口径）＋ **INFRASTRUCTURE**（两列 ＋ 迁移 017 ＋ 自愈副本）。
- **五问依据**：
  - ① 是否定义核心事实？**是** —— 「这张结算单覆盖哪几笔应付、它该付多少钱」是钱的核心事实。
  - ② 是否改变核心不变量？**是（把一条已经写坏的不变量改对）** —— 从「金额 == 确认时重取到的明细合计」（随时可能取不到）改成「金额 == 建单当刻锁定的明细合计 + 手工调整」。
  - ③ 是否必须永久存在？**是** —— 结算单要能事后解释自己的数字（这是审计与对账的前提）。
  - ④ 是否可能出现多个实现？**否** —— 取数只能有一处，这正是本条的修法。
  - ⑤ 删除后 Core 是否仍然成立？**否** —— 删掉 bill_ids 就退回「确认时按月重取」，月结数字当场失去可解释性。
- **要改 Core 时的三问**：① 现有 Extension 边界无法解决，是因为**取数与恒等式就在核心服务函数体内**，扩展点只能挂路由，改不了「这一单覆盖哪几行」；② 修改 Core 是必要的，因为病根是**同一个核心函数里的两半用了两套取数**；③ 修改后 Core 的不变量是「**一张结算单的 amount 在它诞生那一刻就与它的明细定死，之后每次校验都对着同一批行**」。
- **核心改动声明行**（已写在 docs/AI_WORK_CLAIM.md「已完成」）：
  - 核心改动：backend/app/services/accounting_service.py —— 为什么必须动核心：账本入账与欠款口径的唯一一处（取数与恒等式就在这里，两套口径正是 970/940 的病根）

## ⑤ Data Contract

| 列 | 类型 / 默认 | 谁写 | 含义 |
| --- | --- | --- | --- |
| bill_ids | JSON，nullable（无默认） | create_settlement（accounting_service.py:628 / 构造器 :643-656） | 建单当刻锁定的 driver_bills.id 列表（含 order_id 为空的历史孤儿） |
| adjustment | Numeric(12,2)，NOT NULL，server_default 0 | 同上（:641 adjustment = Decimal(body.amount) - amount，只在人工改额时非 0） | 人工改额与明细合计之间的差额；恒等式 amount == 明细合计 + adjustment |

- **什么时候写**：只在建单那一刻（create_settlement）写一次，之后**只读**；确认 / 付款 / 作废都不改这两列。
- **什么时候不写**：⛔ 迁移与自愈补列**不回填**老行（老行 = NULL / 0 = 「按老口径解释」）；⛔ 不改历史行的 amount / order_ids。
- **是否允许 NULL**：bill_ids 允许（NULL = 老单，走老路）；adjustment 不允许 NULL，默认 0。
- **历史数据怎么办**：老单保持原样；它的确认仍按 order_ids / 按月口径核对（旧行为不变）。过去没有 bill_ids 就写 NULL，**不许**按现在的规则猜过去。
- **迁移怎么做 / Rollback 怎么办**：python -m app.migrations upgrade（017，逐列判存在、可重跑）；回滚代码不删列 —— 两列对老单是惰性的（NULL / 0）。
- **删除本功能后历史数据还能不能解释**：能 —— bill_ids 记的就是当时那批行，删掉功能也仍然读得出来。
- **没有**新增 / 修改任何请求体字段或端点。

```text
                        确认优先按 bill_ids 点名取行、明细少了明确报错；恒等式 amount == 明细合计 + adjustment

                        老草稿（bill_ids 为 NULL）走老路；权限；出参既有字段名与形状；validate_month 上界。
Evidence:               见 ⑧ 的实测回填表（判据 / 反验 / 全量 pytest / 全量静检 / 真机）。
Known Limitations:      ① 迁移只在本机 SQLite 活库上真跑过，MySQL 分支没实跑；
                        ② 老单（bill_ids 为 NULL）仍按老口径核对 —— 若它本身带着孤儿明细，确认时依旧会报
                           「金额与明细合计不一致」（这是刻意的：不许拿新规则去改历史数字，处置入口是作废后重新建单）；
                        ③ 真机上没有制造「明细被抢走」的竞态（只在单测里覆盖）。
Rollback:               两笔提交各自可 revert；代码回滚后两列仍在库里（老单读 NULL / 0 即老行为），
                        ⛔ 不需要也不允许删列（删列会丢历史单的对账依据）。
Historical Data Impact: 无。迁移只加列、不回填、不改任何历史行的 amount / order_ids；
                        活库探针显示当前不存在口径不一致的结算单。
```

**最后一个问题**：这张单为什么会出现「金额比明细多」？—— 因为它建出来的时候把**没有单号的孤儿明细**算进了金额，而确认时却按单号去重取。现在这两半走的是**同一个函数**，覆盖哪几行在建单那一刻就写进了 bill_ids。
