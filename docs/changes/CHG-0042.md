① 派单员在**派单期**（货还在路上）发现这批货要换个人收：可能是整张单给别人、可能是**拆**一部分给别人、也可能是**并**进另一个货主已经在途的那张单。今天系统里没有这条路。用户 2026-10-05 口述（语音转写）：「假如 A 老板下了 50 单货、B 老板下了 40 单货，然后一起由一个司机直接发车，但 B 老板非常着急，所以派单员决定将 A 的 50 单货中的 30 单货和 40 单货**合并**在一起变成 70 单货给 B 老板，有时候可能是**全部货都直接给这个老板**；也有时候会把 A 的 50 单货**拆成 20 单和 30 单**，另外 30 单给另一个老板 C」。

② 当前流程：货主（或其代理）下单 → 派单员在派单池派给司机 → 司机接单 → 送达 → 结算。**货归谁在下单那一刻就定死了** —— 想换人只能「把原单作废 + 重新下一张」，于是原单的审计、它的库存预占、司机手上那张送货单全部要重来；而且重下的那张单与原来那张单之间**没有任何可追的关联**（"这批货本来是 A 的"这句话在系统里查不到）。

③ 会变的事实（**货的归属**这一格）：从今往后，一张单里的商品行可以带着「这件货是什么、多少件、什么价」整体或部分挪到**另一个货主**的名下，并且可在挪的同时**并进**目标货主已经在途的那张单。落点：
- 新命令 `order.transfer`（`backend/app/commands/order.py` 的 `transfer_lines`）＋ 新端点 `POST /api/v1/orders/{order_id}/transfer`（`backend/app/api/v1/orders_assignment.py:410-447`）；
- 新审计动作码 `ORDER_TRANSFER`（`backend/app/models/enums.py`，领域词汇表）；
- Android：订单详情页多一颗「转货」＋ 底部抽屉 `ui/order/OrderTransferSheet.kt`（选一位货主 → 每行填「转出几件」→ 确认）。

④ 明确不能变（逐条都在判据里）：
- **订单状态机**：本命令**一次都不写状态** —— 全仓唯一的状态写入点仍是 `backend/app/services/order_flow.py`（`_check_status_gate_locking.py` 的 `ALLOWED_STATUS_WRITERS`）；源单被搬空时**借既有的** `cancel_pending` 把它作废（`source_cancelled` 只作为回参告诉界面）。
- **钱**：源单的 `payment_method / paid / arrears_unit_* / collect_cash` 与「运费 / 司机计费」快照**一概不抄给目标单**（钱是源单与它的货主之间的事实，货走了钱不跟着走）；界面不算钱，行小计仍由后端按 `unit_price × 数量` 重算。
- **权限**：复用 `Permission.ORDER_DISPATCH`，不新建权限点、不新建能力族。
- **既有端点契约**：不修改任何既有请求/响应形状，只**新增**一个。
- **表结构**：不新增列、不新增迁移（`orders`/`order_products` 一行没动）。

⑤ **CORE**（订单域的命令 ＋ 它的领域词汇表）—— 这是一次**证据触发的例外**：证据是用户口述的真实业务场景（①）＋ 真库探针在真 schema 上跑出来的三处缺陷（⑦ 反向格）。不改 Core 的说法（"在下单那一刻用新货主重下一张"）会丢掉「这批货本来是 A 的」这条历史事实，并让预占/审计/司机手上的送货单三处对不上。

⑥ 见 ⑦ 测试表与 ⑧ 证据：**真库探针 80/80**（在 `backend/sorders.db` 的字节副本上跑产品代码）＋ 静态判据 64/64 ＋ 注入式反验 33/33 ＋ 全量静检 ＋ 模拟器 5554 真机端到端。

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

- **结论**：**CORE**（订单域的**命令**与它的**领域词汇表**）。理由：这里的"事实"是**货归谁** —— 它决定账本行落给谁、通知发给谁、司机手上那张送货单写谁；这不是展示层的取舍，也不能靠新增 Extension 解决（Extension 拿不到「把一行货从这张单挪到那张单」这一核心不变量）。
- **五问依据**（规范 §三）：
  - ① 是否定义核心事实？**是** —— 商品行的归属（`order_products.order_id` 指向哪张单）就是"这批货是谁的"。
  - ② 是否改变核心不变量？**否**（不变量一个没改）—— 不改状态机、不改金额算法、不改权限；新增的是一条**既有不变量之内的**新动作（货仍在"某一张在途单"上，只是那张单换了人）。
  - ③ 是否必须永久存在？**是** —— 只要还有"两个老板的货拼一个司机"这种真实场景，这条动作就得在。
  - ④ 是否可能出现多个实现？**否** —— 它读写的是同一批核心表（orders / order_products / operation_logs / outbox_events），换实现等于换核心事实的读写者。
  - ⑤ 删除后 Core 是否仍然成立？**是** —— 删掉这条命令，Core 退回"下单即定主"的旧样子（这正是它可回滚的原因，见最后一个问题）。
- **要改 Core 时的三问**（规范 §F1）：
  - 为什么现有 Extension 边界无法解决？`order.split` 只拆**同一个货主**的货（单号加 `-1`/`-2` 后缀、货主不变）；`PATCH /orders/{id}` 能改地址与联系人但**改不了"这批货属于谁"**；AI 写动作卡片是"一轮问一件事"，装不下"选一位货主 + 每行填件数"这种多行结构。三条既有边界都够不着这件事。
  - 为什么修改 Core 是必要的？不动核心就只有一条路：把原单作废、用新货主重下一张 —— 那样"这批货本来是 A 的"这条历史事实在系统里**永久消失**，且原单的预占、审计、司机送货单三处都要重来。
  - 修改后 Core 的不变量是什么？**"每一件在途的货都恰好属于一张单、且那张单只有一个货主"** 这条不变量不变；新增的是可在"同一件货的两张单"之间移动，移动必须留两条审计（out/in）与相应的库存预占变化。
- **核心改动声明行**（已写在 `AI_WORK_CLAIM.md`「进行中」）：
  `核心改动：backend/app/models/enums.py —— 为什么必须动核心：转货要在审计里与既有的「拆分订单」（ORDER_SPLIT，拆的是同一个货主的货）区分开 —— 复用 ORDER_SPLIT 会把「拆成两份」读成「货换主了」，而这两件事决定账本行落给谁、通知发给谁、司机手上的送货单写谁。`

- **什么时候写 / 什么时候不写**：只有在"派单期（待派单 / 已派单未接单 / 已接单）且不是终态"时才写；已送达 / 已撤销 / 已退货的单**一个字节都不写**（挡板 `order.status in (DELIVERED, CANCELLED, RETURNED)`）。

## ⑥ CHG 专章

### Before

派单员手上有 A 老板的一张待派单（或已派单）的单，B 老板临时把这批货要走了。他能做的只有：
① 把 A 的单**作废**（或在派单池里撤回）→ ② 打开"新增订单"，一位货主一位货主地重填一遍（地址、收货人、下单人、备注、每一件货与它的价）→ ③ 重新派单。
结果：A 的原单在系统里变成一张**作废的空壳**，"这批货本来是 A 的"这句话再也查不到；司机手上那张送货单要重打；原单的库存预占要先放再占。

### After

派单员打开那张单（详情页）→ 右下多一颗**「转货」** → 底部抽屉里：**选一位货主**（或填临时货主名；也可以**指名并进**目标货主已经在途的那张单）＋ **逐行填"转出几件"**（留空 = 不动，下面一颗「全部转出」＝整张给这一位）→ 「确认转货」。
- 还留着一部分：源单**原样留着**（少掉转走的那几件），目标单是一张新的待派单（并单时并进目标那张）；
- 全填满：源单被作废（界面上明说「源单已撤销」），目标单接走全部货；
- 目标单记着 `parent_order_id` 与内部备注「[转货 <时间>] 由 <源单号> 转入（操作人：…）」；
- 审计里两条：源单 `out`、目标单 `in`，各带商品、件数、单价快照；
- **钱不跟着走**：目标单的 `payment_method / paid / arrears_unit_*` 是它自己的（新建时为空），源单的钱口径一个字没改。

- ORDER_SPLIT 的语义（同一个货主拆单）与「撤回派单」「拆分」两条既有路的文案与行为
