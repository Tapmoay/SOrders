## ③ Boundary（Core / Extension / Infrastructure / Presentation）

- **结论**：CORE
- **五问依据**（规范 §三）：
  - ① 是否定义核心事实？**是** —— 「AI 用某个人的身份，在什么时候，对哪个动作发起了一次请求，成没成」是一条必须永久留存的审计事实；它是**旁路观测面**（`docs/DOMAIN_BOUNDARIES.md` §3.14 的 ai 域：调用量计数 ＋ 请求流水两张表都由上报端点与中间件直接落库，不接受任何域调用）。
  - ② 是否改变核心不变量？**否** —— 只读 `scope` 与响应状态、只 INSERT 一行到自己的表；订单状态、金额口径、权限判定、发件箱投递一条都没碰。
  - ③ 是否必须永久存在？**是** —— 它回答的是「当时到底发生了什么」，删功能也不能删历史行（与 `operation_logs` 同理）。
  - ④ 是否可能出现多个实现？**否** —— ⛔ 写入点只有 `core/ai_operation.py` 一处（挂载顺序也只有 `main.py` 一处），判据第 1 / 2 组钉着。
  - ⑤ 删除后 Core 是否仍然成立？**是** —— 它是旁路观测面，删掉之后业务、账本、审计、发件箱全部照常，只是没人答得上「AI 试过什么」。
- **要改 Core 时的三问**（规范 §F1）：
  - 为什么现有 Extension 边界无法解决？AI 的写动作走的就是**普通业务端点**（模型只能申请，用户点过确认卡才由 `AiWriteService.commit` 去调真实接口），所以没有任何「AI 路由」可以在扩展层挂一个装饰器；而既有的 `operation_logs` 写在业务事务里、只在写入成功之后落行 —— **被挡住的那一半它结构上就记不到**，这正是用户要的那一半。
  - 为什么修改 Core 是必要的？要「每一次请求都落一行（含失败）」，唯一的位置是**请求边界**（ASGI 中间件），而请求边界的顺序、上下文变量的生命周期都长在核心区（`main.py` / `core/request_id.py` / `core/client_origin.py`），`deps.py` 又是唯一知道「当前是谁」的地方。
  - 修改后 Core 的不变量是什么？**任何一次带 `X-SOrders-Origin: ai` 的请求，收尾时都会在 `ai_operation_logs` 里留下一行（成功 ok=1、失败 ok=0 且带 ≤500 字的原因）；这一行的写入使用独立会话，业务事务回滚不会把失败那一行带走；非 AI 请求一次数据库都不碰。**
- **核心改动声明行**（改核心区文件时**必须**，写在 `AI_WORK_CLAIM.md`「进行中」）：

  `核心改动：backend/app/deps.py —— 为什么必须动核心：AI 流水要写清「这一次是谁的身份」，而 get_current_user 是唯一知道当前用户的地方；只在 request.state 里记一个 user_id 给审计用，⛔ 不参与鉴权（拿不到就写 NULL，绝不因为审计失败而拦请求）。`

  `核心改动：android/app/src/main/java/com/tapmoay/sorders/ai/AiWriteService.kt —— 为什么必须动核心：commit 时把「这一次是哪个动作」（p.actionId）一并交给 ClientOrigin.asAi(...)，否则流水只记得下 PATCH /orders/{} 而看不出改的是联系人还是运费。`

## ④ Behavior Contract

**动作：AI（模型代某个人）发出一次请求**
- Input：请求头 `X-SOrders-Origin: ai`（App 侧只有 `ClientOrigin.asAi` 会带）＋ 可选的 `X-SOrders-Ai-Action`（值形如 `orders.create`，字符集白名单 `[A-Za-z0-9_.:-]`、截断 64 字、非白名单字符一律当没给）。
- Output：**库里多一行**（成功与失败都写），写的是 谁（user_id / user_name） / 何时（created_at，UTC naive） / 哪个动作（action，可空） / 哪个端点（method ＋ path） / 成没成（ok） / 为什么（error，可空） / 哪一次（request_id） / 多久（duration_ms）。
- Success：成功那行 `ok = 1`、`error` 为 NULL；界面绿徽「成功」。
- Failure：失败那行 `ok = 0`、`error` ＝ 响应体 `detail`（非字符串则 JSON 序列化、截断 500 字）；界面红徽「失败 · <状态码>」＋ 那行原因；**没有走到响应**（异常）时写「（这次请求没有走到响应）」；响应体没有 `detail` 时 `error` 为 NULL，界面如实写「后端没有留下原因（看状态码）」。
- Boundary Cases：非 AI 请求**零开销放行**（一次 DB 都不碰、响应逐字不变）；写流水本身失败**不许影响业务响应**（异常全吞 ＋ `logger.warning("AI 操作流水写入失败：%s", exc)`）；请求被取消（`asyncio.CancelledError`）**原样抛**、不吞；未登录 / 鉴权前就被挡回来的请求 `user_id` 为 NULL，界面写「未登录请求」；没带动作头的只读查询 `action` 为 NULL，界面写「未标动作（只读查询）」。
- Side Effects：一次**独立会话**（`SessionLocal()`）的 INSERT —— ⛔ 不用请求那条会话，因为业务事务回滚时「失败那一行」正好也没了（判据第 2 组第 1 条钉着）。
- Authorization：读端点是 `Depends(require_permission(Permission.OPERATION_LOG_READ))`（只有派单员）；本单**不新增权限点**；写侧没有任何客户端可调入口（只有中间件）。
- Compatibility：请求头是**新增**的，老客户端不带也照常工作（`action` 为 NULL）；响应新增字段走 DTO 默认值，老 App 忽略即可。

## ⑥ CHG 专章

### Before

AI 用某个人的身份改数据，走的是**普通业务端点**；全链路唯一区分得出来的只有请求头 `X-SOrders-Origin: ai`，而**没有任何一处**把它记下来。既有的 `operation_logs` 记的是「数据被改成了什么」，写在业务事务里、只在写入成功之后落行 —— AI 试一次被 403 / 422 挡回来，库里一行都没有。于是用户最想问的那句「**AI 是不是悄悄试过什么、被挡住了**」在今天的系统里答不上来；即使成功那几次，光看 URL 路径也读不出「`PATCH /api/v1/orders/{}` 到底改的是联系人还是运费」。

### After

**每一次**带 `X-SOrders-Origin: ai` 的请求收尾时都落一行 `ai_operation_logs`（成功也写、失败也写），派单员在「AI 助手 → 设置 → AI 操作流水」一页里按时间倒序看：谁 / 何时 / 哪个动作 / 哪个端点 / 成没成 / 失败原因 / 请求号 / 耗时。三态都验过：**全部**、**只看失败**（走服务端 `ok=false`，⛔ 不是本地过滤）、**一直往前翻**（`skip` 是真游标，每页 60）。AI 侧的能力面**一点没变**：读这一页的权限沿用 `OPERATION_LOG_READ`，且该端点在 `_tools/ai/_read_coverage.py` 里**显式排除**给模型 —— 审计面不是业务能力，开给模型＝让被审计的一方自己念记录。

### 取证途中撞上并修掉的两处
