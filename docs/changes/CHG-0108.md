## ① 六问

**问（用户逐字，2026-10-10）**：

> 既然我们的图标改成了这个颜色那我们手机桌面上的图标也要改一下包括加载动画也就是我们一开始进app的那个预加载动画也要改一下。

同一条消息前面还附了一张图：登录页那枚 LOGO —— **淡绿圆角方块 ＋ 墨绿货车**。

**为什么现在才提**：App 里的绿是 CHG-0091（"整体基调从蓝变绿"）换的，之后
CHG-0101/0102/0105/0107 又调了四轮；桌面图标和启动画面**一次都没跟过**。

**病灶**：`res/drawable/ic_launcher_background.xml` 里写的是旧蓝 `#D9E8FF`、
`ic_launcher_foreground.xml`（货车）写的是旧藏蓝 `#0A3168`、
`values/colors.xml` 里甚至还是**更早的橙金** `#FFB020`（早于 CHG-0091，一直没人动）。
于是用户看到的是：**桌面上一个蓝方块，点开先闪一屏白底蓝图标，然后进 App 才是绿的。**

**改法**：四个字面量全部改成登录页那两枚 token 的**现值**——
底色 = `PrimaryContainer` `#DBE8E1`，货车 = `OnPrimaryContainer` `#0E3021`；
并给 API 31+ 的启动画面显式指定底色，让"预加载"那一屏也是同一块淡绿。

**判据**：新建 `_tools/qa/_check_app_icon_green.py`（26 项）＋ 反向验证
`_tools/qa/_reverse_verify_app_icon_green.py`（12 条注入）。

**不这么改会怎样**：桌面图标与 App 内配色长期两套；而因为**没人会天天看桌面图标**，
下一次换色还会漏——这正是本单要立判据的原因。

## ⑥ CHG 专章

### 启动画面是怎么回事（这决定了改动落在哪）

用户嘴里的「一开始进 app 的那个预加载动画」＝ **Android 12（API 31）起系统强制的启动画面**
（SplashScreen）。它不是我们画的：每次冷启动，系统先画一屏
「底色 ＋ 应用图标」，等第一帧出来才让位。两条属性决定它长什么样：

| 属性 | 默认取什么 | 本单之前的表现 |
|---|---|---|
| `android:windowSplashScreenBackground` | `windowBackground`（本主题没写 ⇒ 系统白） | 一屏**白** |
| `android:windowSplashScreenAnimatedIcon` | 应用图标（`@mipmap/ic_launcher`） | 旧**蓝**方块图标 |

⇒ 在白底上放一枚蓝图标。**把图标改绿**就同时修好了启动画面的图标那一半；
底色那一半要显式指定，所以有了 `splash_background` 与 `values-v31/themes.xml`。

### 为什么主题要拆成 `.Base` ＋ v31 覆盖

`android:windowSplashScreen*` 是 API 31 才有的属性，只能写在 `values-v31/` 里。
而资源覆盖是**整份 style 替换**，不是合并——如果 v31 里直接写
`parent="android:Theme.Material.Light.NoActionBar"`，就得把状态栏那两条**再抄一遍**，
于是"改基础项"变成两处。所以拆一层：

```text
values/themes.xml      Theme.SOrders.Base   ← 基础项（状态栏）唯一一份
                       Theme.SOrders        ← API<31：只是继承
values-v31/themes.xml  Theme.SOrders        ← API 31+：继承 .Base ＋ 两条启动画面项
```

判据钉住「两层都指向 `.Base`」与「v31 不出现 `statusBarColor`」，
所以下次有人想改状态栏，改一处就够。

### 值从哪来（不是手挑的）

| 位置 | 值 | 来源 |
|---|---|---|
| 背景层 / `ic_launcher_background` / `splash_background` | `#DBE8E1` | `Color.kt` 的 `PrimaryContainer`（登录页 LOGO 那个方块的底色） |
| 前景层（货车） | `#0E3021` | `Color.kt` 的 `OnPrimaryContainer`（登录页 LOGO 里货车那个色） |

判据**读 Color.kt 现算**，不把值抄一份到自己里面——否则下一次换色，判据会和资源
一起过期，等于没有判据（反向验证第 ① 条专门证明这件事：改 `Color.kt` 的
`PrimaryContainer`，判据必须跟着红）。

### 已知代价

1. `#DBE8E1` 是很浅的绿，在白色壁纸上**显眼度一般**——和 CHG-0091 之前那版
   `#D9E8FF` 是同一量级的浅色，属于"和登录页一致"这个已定口径的直接结果，
   不是这次新引入的问题。用户看的就是这枚（消息里那张图）。
2. API < 31 的设备**没有**系统启动画面，冷启动那一瞬仍然是 `windowBackground`
   （系统白）。本单**故意不动** `windowBackground`：`MainActivity` 的注释里写着
   「没画背景的页面会露出窗口底色」，把它改成淡绿会让那些页面跟着变绿——
   那是另一个可见后果，不在本单范围内。

## 附：为什么这单值得立判据

「桌面图标」是本项目里**唯一一个用户不会在日常使用中看到、却每次装完都会看到**的界面。
`ic_launcher_background.xml` 的注释里其实早就写着「用户 2026-09-19 说：把 App 图标
换成登录界面的图标」——那条口径本身执行得很好，**但它是"抄一份值"而不是"读同一个 token"**，
于是 CHG-0091 换色之后它就静默失效了将近一个月，直到用户自己看出来。

判据的做法因此不是"再抄一份现值"，而是**拿 Color.kt 的现值去对资源里的字面量**。
这一条比本单改的那四个十六进制值重要得多。
