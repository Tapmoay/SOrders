# BUG-0013 · 两个实例同时启动时，自举锁只等 60 秒，而并发下某条建表迁移偶发要 ~59 秒：慢的那一方启动失败（2026-10-05 跑全量静检时抓到，未修）

> 现场来源：**全量静检唯一那条红**。台账里 `python _tools/ops/_migration_tests.py --concurrent` 记着 ✅，
> 实跑却退出 1：两个子进程退出码 `[1, 0]`，失败那个是
> `app.core.file_lock.FileLockTimeout: 拿不到文件锁 …\Temp\sorders_bootstrap.lock（等了 60.0s）`。
> 单进程空库迁移 **8/8 都快（~2s）**；并发下**赢的那一方**某条建表迁移偶发跑到 **59077 / 59140 ms** ——
> 输的一方刚好差几十毫秒没熬过 60 秒预算。

- **ID**：BUG-0013
- **类型**：BUG（启动期并发：锁等待预算 < 最坏一条迁移的耗时；失败形态是"这个实例起不来"）
- **状态**：⏸ 待定（已稳定复现、已把卡点缩到"不在 Python 层 sqlite execute"；根因未定论，改法有两种，要用户拍板）
- **Owner**：DSH 会话 `session-e94394d5-4f36-49dd-9ee1-446fcb7dee30`
- **开工日期**｜**关闭日期**：2026-10-05 ｜ —
- **Blast Radius**：**预估 L1** —— 方案 A 只动一个等待常量（+ 它的注释与判据）；方案 B 可能动连接/提交语义。
  **本轮一行产品代码都没改**（只新增本文件）。

## ① 六问

**1. 现象是什么？**
- `python _tools/ops/_migration_tests.py --concurrent` **偶发**退出 1：
  `两个进程退出码 [1, 0]（分别在第 61.1s / 61.3s 结束，从启动算起）`；
  版本表仍 `1..22` 每版一行、`重复记账：没有` —— 也就是说**迁移本身没做错、锁也没破**，
  只是慢的那一方**起不来**。
- 失败原文：`app.core.file_lock.FileLockTimeout: 拿不到文件锁 C:\Users\OPTIMI~1\AppData\Local\Temp\sorders_bootstrap.lock（等了 60.0s）`。
- 用例自己的注释早就写着这件事：「这条用例偶发红（2026-10-04 实测 8 次里红 2 次）」（`_tools/ops/_migration_tests.py:152-153`、`:175-177`）。

**2. 根因在哪？**（分层：先排掉不是它的，再说缩到哪儿）
- ❌ **不是"有人长期握着锁"**：干净态下 `FileLock(BOOTSTRAP_LOCK_FILE, wait_s=1.0)` → `lock free: acquired in 0.00s`。
- ❌ **不是并行负载造成的假红**：单进程空库迁移 `8/8` 全快（`1.7 / 0.9 / 1.9 / 1.8 / 1.9 / 2.1 / 1.8` 秒）；
  库放 `%TEMP%` 还是放仓库 `_tmp` 无差别（`2.3 / 1.9 / 1.8` 秒）⇒ 与杀软扫描、磁盘位置无关。
- ✅ **缩到这一点**：并发下**赢的那一方**会有**一条建表迁移**长跑 ~59s，而它是"哪一条"不固定 ——
  `_tmp/_probe_mig_race2.py` 实测 `迁移 020_invoices 完成（59077 ms）`，另一次是
  `019_purchase_orders 完成（59140 ms）`，其余（001~019、021、022）全是 `0 ms`。
  ⇒ 输的那一方 60.0s 的等待预算**刚好差一点点**，于是抛 `FileLockTimeout`。
- ❓ **仍未定论**：这 59 秒**不在 Python 层的 sqlite `execute` 里** ——
  埋点（`_tmp/instr/sitecustomize.py` 打 `sqlite3.Cursor.execute`，>0.4s 才记）在两次慢跑里**一条都没打出来**。
  怀疑在 `Connection.commit` / 连接建立 / Windows 文件锁语义；但第一版埋点没打
  `sqlite3.dbapi2.connect`（SQLAlchemy 走的正是 `sqlite3.dbapi2`），而同时埋 connect+execute+commit 的
  `_tmp/_probe_mig_trace.py` 因运行期限被掐、**没取到数据**。⇒ 要定论必须先抓到一个慢跑的栈。
- **代码锚点**：`backend/app/core/schema_bootstrap.py:220 def prepare_schema(engine) -> None` →
  `:232 with FileLock(BOOTSTRAP_LOCK_FILE): _prepare_locked(engine)` → `:236 def _prepare_locked(engine)`
  = `apply_runtime_self_heal(engine)` + `run_migrations(engine)`（自愈与迁移**同一把锁**）；
  `backend/app/core/file_lock.py:36 DEFAULT_WAIT_S = 60.0`、Windows 分支 `:102-119`（`msvcrt.locking(LK_NBLCK, 1)`
  每 0.05s 轮询到 deadline 抛 `FileLockTimeout`）；
  `backend/app/migrations/_runner.py:420 class _lock` → `:429 self._impl = FileLock(LOCK_FILE)`（同一个 60s 缺省）、
  `:364 with _lock(), _db_lock(engine):`、`:371-401` 逐条迁移 `started = time.monotonic()` → `duration_ms`（「完成（N ms）」的出处）、
  `:304 class _db_lock`（非 MySQL 直接返回：SQLite 是单机文件库，如实不做跨主机锁）。

**3. 还有第二处同源风险（现在看不见）**
- 生产是 MySQL：`_db_lock` 走 `SELECT GET_LOCK(:n, :t)`，而 `file_lock.py:36` 的注释自认
  "与 `_db_lock` 的 `GET_LOCK` 同口径 60 秒" ⇒ **"一条迁移最坏要跑多久"这个数从来没被量过，
  却同时决定了两个 60s 预算够不够**。本次只是 SQLite 单机把这个缺口跑出来了。
- 对应的真实场景正是 `docs/MULTI_INSTANCE_READINESS.md:94` 记着"还没做"的那一格：
  多实例同时发布时，慢的那一方会**直接启动失败**（不是重试、不是降级），要靠编排层重启兜底。

**4. 影响是什么？**
- ① **闸门偶发红**：台账（`docs/R3_FAILURE_DRILL.md:98`、`docs/R3_CONSTRAINTS.md:433`、`docs/R3_PROGRESS.md:231`）
  把这条用例记成 ✅，于是 `_tools/qa/_check_report_facts.py` 偶发报「1 条不成立」。
  本仓 2026-09-25 就"偶发红的闸门"拍过板：**一个会偶发红的闸门等于没有闸门**，宁可拿时间换确定性。
- ② **发布风险**：两个实例同时启动 ⇒ 慢的一方起不来；这条路**从未在生产上真跑过**（`docs/R3_FAILURE_DRILL.md:98` 备注）。
- ③ 现象是**静默偏斜**的：快的那一方毫无异常，只有慢的那一方报一条锁超时 —— 容易被当成"偶发环境问题"糊过去。

**5. 建议改法（两种，待拍板）**
- **方案 A（把预算花在余量上，最小改动）**：给 `schema_bootstrap` 的自举锁显式定一个
  "迁移最坏耗时 + 余量"的等待常量（例如 300s），并把"为什么不是 60s"写进 `file_lock.py:36` 的注释与
  `_db_lock` 的 `GET_LOCK` 参数；配一条判据盯住"等待预算 ≥ 实测最坏耗时 × 余量"。
  代价：真卡住的实例会**等更久才失败**（但这次这类"慢而不是死"的情形会成功）。
  ⛔ 不许把"两个进程都必须退出 0"改成"允许一个失败"。
- **方案 B（先量后改）**：先把 59s 卡点钉死（同时埋 `sqlite3.dbapi2.connect` + `Connection.commit` + `PRAGMA`，
  或在慢跑上挂 `faulthandler.dump_traceback_later` 取栈），再决定是改连接/提交语义、还是只改预算。
  代价：要先能稳定复现（目前大约 1/2 ~ 1/3 的概率），可能要跑多轮。
- 两个方案都要守住三条不变量：**两个进程都退出 0 / 版本表每版恰好一行 / 不重复记账**。

**6. 不许动什么？**
- 锁序：**本机 flock → 服务端 `GET_LOCK`**（`_runner.py:364` 的注释写明：反着写会和 `--workers 2` 死锁）。
- "自愈与迁移必须同一把锁"（`schema_bootstrap.py:232` 的注释：R3-01 抓到过窗口期 DDL 相撞；同进程重入不死锁）。
- `checkfirst=True` 的可重跑语义与版本表记账方式（`backend/app/migrations/020_invoices.py:28-33` 等）。
- 用例的判据强度与它的失败输出（⛔ 不许为了让闸门变绿而放宽"两个进程都必须退出 0"）。
- 台账里那三条 ✅ 的历史记录（要改的是"现在能不能稳定跑通"，不是"当时有没有跑通"）。

**最后一个问题**：为什么"没做错任何事"的迁移会让一个实例起不来？——
因为"迁移要跑多久"这个最坏值从来没人量过，而"实例愿意等多久"已经被写死成 60 秒；
两个数各自都合理，**放在一起就成了发布期的偶发悬崖**。
