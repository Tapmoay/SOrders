① 三个页签的「分类」是**三种互不相同的画法**，其中两种是坏的：

1. **联系人**档是常驻左栏：`ContactCategoryPane` 里 `MasterRail(…, Modifier.width(112.dp).fillMaxHeight())` + 右边一个列表。
   1080 宽的屏上先被削掉 112dp，剩下给卡片的宽度里还要塞三行信息（名字 / 电话 / 分类标签）+ 两枚圈底动作 —— 这正是用户点名否掉的那句「右边的卡片的信息被挤压了不是很好看」。
2. **地点**档有分类名册（`place_categories`），但**只能进表单才能选**：列表上看不出哪一条属于哪一类，也筛不了。
3. **线路**档**根本没有分类**：`ShipperAddress` 没有 `category` 列、没有名册、没有端点。用户要「三档一致」，那就得先把这一档的分类**建起来**。

④ 这一批要的不是新功能按钮，是**三档同一个位置上的同一个控件**：标题（「常用线路」/「联系人」/「地点」）与右侧「新增 X」之间的那个位置放一个**分类胶囊** —— 当前是全部就显示「全部」，选了某一类就显示那一类的名字；点它，**从左侧滑出一个抽屉**，抽屉里就是分类列表（「全部」+ 每一类 + 末行「管理分类」）。

② 派单员 / 货主进「工作台 → 地址与联系人」，三个页签回答的是同一类问题：「我常跑的那几趟，收发货人、地点、线路分别有哪些」。
真实的动作是「我这一趟要送城东那几家」：先看这一类的**分组**，再在组里找那一条，点卡片上的「编辑」或「删除」，或者点右上「新增 X」。
所以分类在这里**不是筛选器**，是**分组**：用户要先**看得见有哪几类**、**知道现在在看哪一类**（胶囊上写着），再**一键换类**（抽屉）。
这也解释了为什么不能做成表单里的下拉（下拉只表达"这一条属于哪类"，表达不了"现在在看哪类"），也不能做成常驻左栏（那会把卡片挤窄）。

③ 变化分三块：

- **画法**：联系人的常驻左栏拆掉，三档统一成「标题行一个胶囊 + 点开左侧抽屉」；「管理分类」从"左栏最后一格"变成"抽屉最后一格"，点它仍**在同一屏**换成管理面板（第二层），不新开路由。
- **新能力**：线路分类名册（表 / 迁移 / 五个端点 / DTO / 仓库层 / 管理面板），以及线路表单里的「分类」下拉 —— 没有这个入口，名册建了也是死的。
- **数据**：`shipper_addresses.category`（`VARCHAR(32) NOT NULL DEFAULT 空串`）+ 索引；老线路一律落空串 = 未分类（**不回填**）。

④ 不动的东西（逐条见 ② 的 Must Not Change）：另外五份名册的端点与字段、`/api/v1/shipper/addresses` 的既有语义（**线路不是 upsert**、软删 + `restore` + `set-default`）、权限与既有审计码、列表顺序与稳定 key、
搜索框占位语（路线那档的「搜线路：收货人 / 电话 / 地址」被 `_tools/ai/_check_ai_guardrails.py:4073-4074` 逐字钉着）、空状态文案、删除后的撤回行、卡片画法与 `CardTag` 这个私有类名。
还有一条**用户裁定**必须继续守：抽屉里**一格都不显示「N 条」**（2026-09-19「那个分组下面不要显示有多少条啊，这是多余信息」）—— 条数只留在**管理面板**里（那里删之前要看影响面）。

⑤ **Contract / Data（L2）+ Presentation**。给这一档补分类名册，动的是**接口契约与库表**（新表、新列、新端点、新 DTO），这一层不是渲染问题；同时三档同形的胶囊与抽屉是纯 Presentation。
为什么不是 **L0**：接口与库表真的变了（老客户端不看新字段不受影响，但它们确实多出来了）。
为什么不是 **L3**：不碰钱、不碰账本、不碰订单生命周期、不碰权限边界 —— 线路分类只影响"这一屏看得见哪几条"，删一个分类后端还会拦（还挂着线路就拒绝，并如实说有几条）。

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

**CONTRACT + DATA（L2）**，夹着一块 **PRESENTATION**。判断依据：

- 线路分类名册是**新的持久化事实**：一张表、一列、五个端点、五个 DTO。后端之外（别的端、别的角色、报表）都能看见它 —— 这不是"只发生在渲染层"的改动，所以不能算 L0。
- 但它落在**扩展/外围**那一侧：分类只决定"这一屏看得见哪几条"，不参与计价、不参与结算、不参与订单生命周期，也不改变任何既有权限判定。所以不是 L3。
- 三档同形的胶囊与抽屉（`CategoryTriggerChip` / `CategoryDrawerSheet`）是纯渲染：换个画法而已，把它下沉到任何别的层都无处安放。
- 唯一一处"离开这一屏"的新东西是共用零件 `ui/common/CategoryDrawer.kt` —— 它属于 UI 公共层（放的是"分类怎么显示"这一条画法），与 `PersonDrawer`（`ui/common/PersonPicker.kt:140`）同一层级、同一路子。

## ⑤ Data Contract

**新增一张表**（`backend/app/models/route_category.py`）：

```text
route_categories
  id            PK
  shipper_id    FK users.id（index）      —— 每个货主/派单员自己那一份名册
  name          String(32)（index）        —— 分类名（去空格，最 32 字）
  sort_order    Integer default 0（index） —— 整份顺序（与另外五张名册共用同一套校验）
  created_at / updated_at
  UNIQUE (shipper_id, name)  name=uq_route_category_owner_name
```

**新增一列**（`backend/app/models/shipper.py::ShipperAddress`）：

```text
shipper_addresses.category  VARCHAR(32) NOT NULL DEFAULT 空串  （index: ix_shipper_addresses_category）
```

口径与联系人 / 地点**逐字同形**：**空串 = 未分类**；这一格存的是**分类名**（自由文本），不是名册 id —— 名册管顺序，字符串管归属。

**新增五个端点**（`backend/app/api/v1/route_categories.py`，前缀 `/api/v1/route-categories`，角色门与 `shipper.py` 同一份）：

| 方法 | 路径 | 干什么 |
| --- | --- | --- |
| GET | `` | 自己那一份名册（按 `sort_order`），每项带 `address_count`（管理面板要看影响面） |
| POST | `` | 建一个分类（重名 → 409；超 200 个 → 400） |
| PATCH | `/{category_id}` | 改名 / 改顺序（**改名同一事务级联**改掉挂着的线路，含回收站） |
| POST | `/reorder` | 整份顺序一次提交（必须覆盖自己全部现存分类，走共用那份 `ordered_ids`） |
| DELETE | `/{category_id}` | 删（204）；**还有线路挂着 → 400**，并把条数说清楚 |

**兼容性与迁移检查**：迁移 013 只**加列 + 加索引**，可重跑（已存在就跳过），不建表（新表由 `create_all` 建）、**不倒数据、不回填**；
老线路的 `category` 落空串 = 未分类，前端对空串的处理就是「全部」下的普通一条；出参多一个 `category` 字段对老客户端是无害的增量。
客户端新增的 DTO：`RouteCategoryDto / RouteCategoryCreateRequest / RouteCategoryUpdateRequest / RouteCategoryReorderRequest`，`AddressDto` 与 `AddressCreateRequest` 各多一格 `category`。
