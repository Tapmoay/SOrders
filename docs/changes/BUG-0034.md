① 开销记错一笔（金额写错 / 记重）之后，**全系统没有任何出口**：`DELETE /api/v1/expenses/54` → 404，开销只有 `GET` 与 `POST` 两个端点，App 侧连「撤销」两个字都搜不到 —— 这一笔会永久留在账上，并进入车辆成本表、利润表的期间费用与报表导出。

② 派单员在「账本管理 → 开销管理」里记开销（单独一页 `Routes.EXPENSE_CREATE`），记录区按分类名册分组、右上角时间药丸选窗口。发现记错时的既有业务流程是：**没有流程** —— 用户只能再记一笔反向的「冲正」开销，但那笔冲正会同时污染分类名册的笔数，而且原笔仍在合计里。

③ 变化的是「开销这件事能不能撤」：新增 `DELETE /api/v1/expenses/{id}`（204，软删）与 `POST /api/v1/expenses/{id}/restore`（200，原样放回）；`GET /expenses` 新增 `deleted_only` 档；出参新增 `is_deleted`/`deleted_at`；**凡是从 expenses 取数的地方**都改成不再算已撤销的那一笔。

④ 明确不能变：**金额算法一个字节都不许改**（`accounting_service.py` 的 `create_expense` 与钱的口径、订单/账本/收款链路）；撤销**不是物理删**（用户 2026-09-20 定的硬规矩：所有删除一律软删 ＋ 必须有恢复路径）；历史开销的含义不变（默认列表、缺省出参、既有报表口径在「没有撤销过任何一笔」时与今天逐字一致）；开销与它写下的那条 `cash_flows` 的关联方式不变（`party_type="expense"` ＋ `party_id`，⛔ 不许改成按金额+日期猜）。

⑤ 属于 **Extension Point / Presentation**：软删这一层是仓库里已有的通用能力（`SoftDeleteMixin` ＋ `schema_bootstrap` 幂等自愈段），本单是把它挂到 `expenses` 这一张表上；取数处改的是各口径的 where 子句，不改算法本体；App 侧是展示层。**两处核心区**（`backend/app/core/schema_bootstrap.py` 加列段、`backend/app/models/enums.py` 两个审计动作码）按「核心冻结」流程写了声明。

⑥ 证据（详见 ⑧）：单测 `backend/tests/test_expense_soft_delete.py` **10 passed**（含「删前 − 这一笔 = 删后」的等式）＋ 判据 `_tools/finance/_check_expense_soft_delete.py` **81 项全过** ＋ 反验 `_tools/finance/_reverse_verify_expense_soft_delete.py` **21/21 全红且逐字节还原** ＋ 两条 AI 门禁 `EXIT=0`。

## ④ Behavior Contract

```text
Input          DELETE /api/v1/expenses/{expense_id}；POST /api/v1/expenses/{expense_id}/restore；
               GET /api/v1/expenses?deleted_only=true|false（缺省 false）
Output         DELETE → 204 无体；restore → 200 ExpenseOut（含 is_deleted=false、deleted_at=null）
Success        撤销：开销单打标记 + 它写下的那条 cash_flow 打标记 + 写一条 EXPENSE_DELETE 审计
               恢复：两处标记都摘掉 + 写一条 EXPENSE_RESTORE 审计；此后每一处口径的合计都比撤销时**正好多这一笔**
Failure        ① 撤销一个不存在的 id → 404「这笔开销不存在」；
               ② 重复撤销 → 400「这笔开销（#N）已经撤销过了，不用再撤一次」；
               ③ 恢复一笔没撤过的 → 400「这笔开销（#N）没有被撤销，不需要恢复」。
               （失败时**不**发生什么：不写审计、不改任何标记、不产生半成品事实 —— 四道门都在改数之前判完）
Boundary Cases ① 老库没有这两列：DDL 自愈补列并回填 0，缺省查询结果与补列前逐字一致；
               ② 重复执行 DDL：不报错（duplicate / already exists 被忽略）；
               ③ 已撤销的开销仍在库里（行、金额、分类、driver/vehicle/order 一个字段都没动）；
               ④ 回填脚本不给已撤销的开销补流水；
               ⑤ 出参默认值：老后端不带 is_deleted 时客户端按 false 画（正常开销不许被画成「已撤销」）
Side Effects   两条审计日志（操作日志页可见中中文名）＋ 撤销/恢复各自刷新客户端列表与分类名册
Authorization  两个端点都只要 DispatcherUser（与既有开销写入口同一把尺子）；⛔ 不新建权限体系
Compatibility  Compatible：GET 缺省行为与出参旧字段逐字不变（只多两个带默认值的键），
               DELETE/POST 是新路径，不动既有路由
```

## ⑤ Data Contract

- **新增/改动哪些字段**：`expenses` 表新增 `is_deleted BOOLEAN NOT NULL DEFAULT 0` 与 `deleted_at DATETIME`（＋索引 `ix_expenses_is_deleted`）；出参 `ExpenseOut` 新增 `is_deleted: bool = False`、`deleted_at: datetime | None = None`。
- **Owner 是谁**：`expenses` 表归开销管理（`app/api/v1/expenses.py` ＋ `accounting_service.create_expense` 写入）；软删这两列的写法与仓库既有的 `SoftDeleteMixin` 家族一致（归属表见 `docs/R4_CORE_EXTENSION_MAP.md` §3/§4）。
- **什么时候写 / 什么时候不写**：只在两个新端点上写（撤销置 `True`/时间戳，恢复置回 `False`/`None`）；`create_expense` 一个字都不改（新建走列默认值 0）；⛔ 任何 PATCH/PUT 路径都不许碰这两列。
- **是否允许 NULL**：不允许（`NOT NULL DEFAULT 0`）；`deleted_at` 只在 `is_deleted=True` 时有值，恢复时置回 `NULL`。
- **历史数据怎么办**：老库补列后回填 `is_deleted = 0`（**不是留 NULL**）—— 留 NULL 会让历史开销整体从账上消失；`deleted_at` 对历史行保持 `NULL`（过去没有撤销过任何一笔，不许按现在的规则猜一个时间出来）。
- **迁移怎么做 / Rollback 怎么办**：DDL 写在 `schema_bootstrap.py` 的幂等自愈段（`app.migrations upgrade` 之外的那条线，两条都幂等）；Rollback = 回滚提交 ＋ 删掉两个端点（两列可以留着：`is_deleted=0` 时对既有口径完全等价）。
- **删除本功能后历史数据还能不能解释**：能。撤销过的开销仍在库里、字段原样，`deleted_at` 就是「哪一天撤的」；审计里 `EXPENSE_DELETE`/`EXPENSE_RESTORE` 两条成对存在，谁撤的、什么时候撤的、当时那笔流水是哪条都查得到。

## ⑥ CHG 专章（FEAT / GOV 不适用时写「不适用：<理由>」）

### Before

派单员在开销列表上发现一笔记错的（金额 123.45 记成 1234.5、或者同一笔记了两遍）：行上只有「详情」，点进去只有明细；`DELETE /api/v1/expenses/54` 返回 404；界面上「删」「撤销」两个字零命中。用户唯一的办法是再记一笔反向的开销，于是分类名册的笔数、车辆成本表、利润表的期间费用三处同时被两笔污染，而原笔永远留在账上。

### After

同一个动作：在「开销管理」里那一行上点**「撤销」** → 走既有危险确认控件（`DangerConfirmDialog`，二次确认）→ 这一行从列表里消失，snackbar 提示「已撤销」并自带「撤回」；列表顶上的标题行出现**「显示已撤销」**档，点进去能看到这一笔（灰显、标着撤销时间），行上有**「恢复」** → 点一下，它原样回到在用列表，并且**车辆成本表、利润表期间费用、分类名册在用笔数、报表导出、收支页**五处的合计都同时**正好多回这一笔**。

### Must Preserve

```text
- 历史订单 / 历史金额 / 已冻结的 Pricing Fact
- 历史 Provenance / Audit / Ledger
- 权限
- API compatibility
- 本事项特有的：accounting_service.py 的金额算法本体与 biz_map 映射；开销 → cash_flows 的关联方式
  （party_type="expense" + party_id）；缺省查询与缺省出参的逐字行为
```

### Blast Radius（L0～L3）

**L2** —— 契约面变化：新增两个写端点（DELETE/POST restore）、`GET /expenses` 新增可选参数 `deleted_only`、出参新增两个带默认值的键。**不到 L3**：不动钱的口径算法、不动表关系与订单生命周期、不新建权限点、不跑数据回填迁移（只补列 + 回填 0）。L1 部分：五处取数口径各加一个 where 过滤（列已存在、语义唯一）。L0 部分：App 展示层（一行按钮 + 一个档 + 二次确认）。
