## ⓪ 需求方原话

> 「（车辆属性）**是要算钱的**。不过主要的一些是不会算的，主要的是**吨和方**这种
>  即便（计量）单位……我们在计算的时候**可以直接拉取这些属性，然后直接进行单位换算**。」

`FEAT-0001` 只做了**前半截**（把这组属性登记到车上）。这一件做后半截：
把属性**读出来**、替掉（或优先于）现在那条全库通用的换算规则。

⛔ 为什么当时没有一起做：规范 §二十五（不许扩大战线）。它会穿孔到
下单页 / 订单卡片 / 订单明细 / 账本小卡**四个显示消费点**，
而它又依赖一个 `FEAT-0001` 回答不了的问题。

---

## ⛔ 唯一阻塞项（需求方拍板之前不许开工）

```text
「一车 = 多少方」—— 这一单算的是哪辆车？

事实：订单上没有车辆字段，只有司机（orders.driver_id）；
      车辆挂在司机名下（vehicles.driver_id，一辆车最多一个司机）。
      而一个司机可能换过车，一辆车也可能换过司机。

  甲）按下单时选的**那一辆车**（下单页新增"选车"）
  乙）按**派单那一刻**那个司机当时名下的车（快照进订单）
  丙）按**商品行**各自选一辆（一单多车，比如 3 车沙子分两辆车拉）
```

三种答案导出的接口、界面与历史口径**完全不同**：

| | 谁受影响 | 历史怎么解释 |
| --- | --- | --- |
| 甲 | 下单页要加一个选择器；货主也得会选车（而货主**看不到**车辆台账） | 老单没有车辆 → 退回通用规则 |
| 乙 | 派单时要**快照**车型/容积进订单（与 `driver_rule_snapshot` 同一个做法） | 老单没有快照 → 退回通用规则 |
| 丙 | 下单页每一行都要选车；订单卡片/明细/账本小卡每一行都要显示不同的换算 | 同上 |

⚠️ **不要猜**：猜错的后果是"两个数都对、但没人知道哪个是这一单的"，
而这类错**不报错**（与单位换算第一版那四条判据要防的是同一类问题）。

## ① 六问（草案，等拍板后补全）

① **解决什么问题？** 现在「1 车 = 8 方」是**全库一条**（`unit_conversions`），
   而现实里一辆 8 方、另一辆 12 方 —— `FEAT-0001` 已经把"每辆车多少方"登记好了，
   但**没有任何一个消费点在读它**。

② **当前流程是什么？** 下单页/订单卡片/订单明细/账本小卡四处都调
   `ui/common/Units.kt::qtyWithUnitConverted(qty, unit, conversions)`，
   数据源是 `UnitConv.rows`（登录时拉一次 `GET /unit-conversions`）。

③ **哪个现有事实会变化？** `1 车 = 8 方` 从"全库一条"变成"**看这一单是哪辆车**"。
   通用那条仍然在（兜底），所以它是**叠加**不是替换。

④ **哪些明确不能变？** 见 Must Not Change（下面是草案）。

⑤ **属于 Core 还是 Extension？** 判据侧是 Extension（读能力），
   但**消费点取值口径**属于契约 ⇒ L2，要兼容性与迁移检查。

⑥ **什么证据能证明完成？** 判据 + 反向验证 + 四个消费点各一张真机截图；
   ⛔ 判据必须能证明"**没有车辆属性时逐字节退回今天**"（否则老单会显示错）。

## ③ 与 `FEAT-0001` 的接口（已经具备的条件）

- `VehicleOut.attrs` 里 `load_tons` / `volume_cubic` 是**字符串**（去尾零），客户端用 BigDecimal 接；
- 后端 `services/vehicle_attrs.py::CAPACITY_KEYS` 明确写着"**参与换算的就是这两项**"，
  判据钉着它（谁挪出去都会红）；
- 车辆的读取入口现成：`GET /vehicles`（仅派单员）——
  ⚠️ 但**货主端看不到车辆台账**，这一条会在拍板时直接影响甲/乙/丙三个方案的可选性。

## ④ Behavior Contract（草案）

```text
Input          换算请求：单位（如"车"）+ （可选）这一单的车辆（某个 vehicle_id 或一份属性快照）
Output         折算率（多少方 / 多少吨）+ "这个数是按哪辆车来的"（要能说出来）
Success        车上有这一项（容积/载重）且 > 0 → 用它；⛔ 不用 1、不用 0 顶
Failure        ① 没有车辆 ② 车上没量过这一项 ③ 单位不是"车"
               → **全部退回今天的行为**（读 unit_conversions 那条通用规则；再没有就不显示）
Boundary Cases 有车有值 / 有车没值（退回通用）/ 没车（退回通用）/ 通用那条也没有（不显示换算）
Side Effects   只读：本事项**不写任何库**（快照进订单是乙方案的事，见 ⓪ 的三个选项）
Authorization  沿用既有：谁的界面谁看得见；⛔ 不让货主去读车辆台账（车辆接口现在只有派单员）
Compatibility  ⛔ **必须证明"没有车辆属性时与今天逐字节相同"** —— 否则老单会显示错
```

## ⑤ Data Contract（草案）

- **不新增任何列**：数据源就是 `FEAT-0001` 已经落库的 `vehicles.load_tons` / `volume_cubic`

  与 `orders.driver_rule_snapshot` 同一个做法，届时这里要改写）

## ⑥ CHG 专章

**（不适用：这是 FEAT）** ⚠️ 但它确实会**改变既有四个显示点的取值来源**，所以要说清边界：

- 变的是"**在有车辆属性时**显示哪个数"；
- **不变**的是"没有车辆属性时的显示结果"（必须逐字节相同，这是本事项的头号兼容判据）；
- ⛔ 钱始终不动：换算只作用于**数量的显示**（单价 / 行金额 / 账本 / 报表全按原来的单位算）——
  这条是 2026-09-24 定死的，本事项不重新讨论。
