① 现在的整套界面是**高饱和的绿主题**（CHG-0091 定的：主操作 / 派单作业 / 信息一律 `#00A870`），
21 格模块色里还有亮青 `#48F0F0`、黄绿 `#8EC714`、荧光橙 `#FF6B2C` 这类**很跳**的颜色。
用户 2026-10-09 连发三张图（`m02471` 订单卡 / `m02472` 工作台宫格 / `m02473` 整体配色方案），
逐字说（`m02474`）：「按照它的配色方案进行一下修改以及我给你的那个照片」；
又补一句（`m02545`）：「这是新任务吼也就是改我途中给你发的那些样式」。
**真正做到一半时他又专门钉了一句（`m02683`，本单的硬约束，逐字）**：
「继续继续，但**我不希望整体太过于灰**啊」—— 这一句把本单从"照抄参考图的低饱和"
变成了**一对约束**：既要不刺眼，又**不能整片发灰**（见 ⑥ 里那条 15% 地板）。
他要的是：**主操作色改成深红棕 `#8B4A4A`**、**商品 / 订单信息块改成红棕 `#B5726B`**、
状态色与 21 格模块色统一换成**低饱和的雾感色**（绿 / 蓝 / 青 / 棕 / 橄榄 / 紫 / 砖红）。

② 用户实际怎么用：派单员 / 货主 / 司机三端各自打开工作台（21 格 / 7 格 / 2 格宫格），
靠**颜色**找功能（`ModulesEntryTest.kt:92-93` 写明了这条定位规则：「老人靠颜色找功能」）；
订单卡上商品行是一块一块的圆角胶囊，数量标签压在主操作色上；底部按钮是"确认接单"这类主操作。

③ 变的是**语义色的值**与**模块色本身**：
`Color.kt` 里 `ThemeGreen` / `ThemeGreenDeep` / `ProductRowTint` / `MemberGold` / `MessageRed` /
`MoneyOrange` / `SupplierBlue` 等 token 的**数值**，以及 `Modules.kt` 里三张表逐格的 `color =`。
**token 的名字、数量、引用关系一个都不动**（`NavBlue = ThemeGreen`、`InfoBlue = ThemeGreen`
这类别名继续成立），所以改的是"这套色长什么样"，不是"这套色怎么组织"。

④ 明确不能变：
- **能力、路由、权限、账本口径、订单状态机**一个字不动（本单只碰颜色）。
- **单色的语义分工**不动：账本仍然是"钱的色"、消息仍然是"要跳出来的色"、
  退货申请仍然是"这条线自己的色"（跨端同功能同色这条约定照旧）。
- `ModulesEntryTest.kt` 里那两条**真的**在量的判据：
  `:210 账本管理入口页 7 格两两颜色分得开`（≥60）、
  `:104 AI 的底色必须和货主同屏其它入口分得开`（≥60）；
  以及 `:91 同一个工作台里不许出现两块一模一样颜色的图标`（完全同色）。
- `ui/theme/AiBrand.kt` 的 AI 品牌渐变（`AiBlue→AiPurple→AiPink`）是**品牌标识不是语义色**，
  被 `ModulesEntryTest.kt:56/:58` 钉着 —— 不在本单范围内。
- 商品的**数量拼法**、订单卡商品块的**布局结构**（一条 `Row`、只有 `verticalArrangement`）不动 ——
  那是 CHG-0091 真机抓到过"0 高回归"的地方，本单只换颜色，不碰布局。

## ⑥ CHG 专章

**Before**：主操作 / 派单作业 / 信息 = 主题绿 `#00A870`；商品块 = 淡绿底 `#E6F7EE` + 深绿数量块 `#0E7A50`；
21 格里有亮青 `#48F0F0`、黄绿 `#8EC714`、荧光橙 `#FF6B2C`、金 `#F5A623`。
用色处另有 **159 处硬编码**直接写着这些旧色（`Color(0xFFFF9500)` 这种），换 token 碰不到它们。

**After**：主操作 = 深红棕 `#8B4A4A`；商品 / 订单 = 红棕 `#B5726B`；成功 / 完成 = `#567A5F`；
提醒 / 重要 = `#C8A56A`；普通 / 信息 = `#6B7F99`；禁用 / 辅助 = `#9B8F88`；背景 = `#F7F6F3`；
21 格按用户图二的量测色（雾绿 / 雾蓝 / 卡其 / 橄榄 / 雾紫 / 砖红 …）。
**45 个 token 换值、159 处硬编码跟着换、40 个旧色值全仓一处不留**（判据真的在数它们）。
换色后的饱和度：新方案 49 个用色**最低 8%（浅底，不算图标色）/ 中位 37%**；
旧方案饱和度中位 **86%** —— 那正是用户说"太亮、刺眼"的那套。参考图 21 格实测最低 11% / 中位 31%。

**⚠️ 本单唯一的取舍（两张图之间真有量化冲突，见 ⑨ Known Limitations ①）**：
图一的"成功 `#567A5F`"与图二的"代理下单 `#6E876C`"距离只有 30.2，
"提醒 `#C8A56A`"与"批发商管理 `#CEA772`"距离只有 10.2 —— 同一套色板放不下两张图。
**采信规则：图一 / 图三 = 语义色规范（7 个 token 逐字照采）；图二 = 21 个模块身份色（逐格照采）**。
两张图各自内部一致，冲突只在"拿图一的角色去套图二的格子"时才出现，而那是本单**不需要**做的映射。

**⚠️ 第二条取舍（`m02683` 那句"不要太灰"落地成什么）**：
参考图 21 格**本身**就很灰（最低 11%），照抄会把 `AccountBrown #97897F`（15% 饱和度）带进来 ——
所以地板定为 **`SAT_FLOOR = 0.15`**：严格高于参考图最灰的两格（11% / 13%），
又容得下他画的整个家族；**不许往上提**（提到 22% 就会逼着"账户管理"那格偏离他给的灰棕 ——
那是用尺子改设计，不是执行他的要求）。

**Must Preserve**：语义分工、路由、能力、布局结构、数量拼法、AI 品牌渐变。

**Blast Radius**：L0 —— 展示层。改的是 `Color.kt` 的数值、`Modules.kt` 的逐格颜色、
以及 27 个界面文件里硬编码的色值，不触碰任何业务逻辑；唯一的风险是"某两格看着像同一个色"，
而这条有单测真的在量（`ModulesEntryTest` ＋ `ThemePaletteTest`）。

## 附：为什么改这几处就够（落点判断）

用户三张图给的是**两套东西**：

1. **7 个语义色**（图一 / 图三的"整体配色方案"）—— 只管"主操作 / 商品块 / 状态"这几件事。
   本项目里这些角色全部由 `Color.kt` 的 token 承担，用色处写的是 `Color(ThemeGreen)` 这种**引用**，
   所以**改 token 的值 = 全 App 换色**，不需要去每个界面改（这也是 CHG-0091 换色的同一手法）。
2. **21 个模块身份色**（图二的宫格）—— 这些**不是语义色**，是"一色一功能"的身份标识，
   落在 `Modules.kt` 的三张表里，只能逐格换。

⇒ 落点就是「`Color.kt` 换值 + `Modules.kt` 换逐格色」这两处，加上随动的判据与文书。
