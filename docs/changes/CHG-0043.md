# CHG-0043 · 转货跟司机：新开的那张单直接派给原来那位司机（换的是货主，不是这一趟活儿）

> 上一份：CHG-0042（转货本体：拆 / 并 / 整单转出）。**这一份只改一件事**：新开的单**归谁跑**。
> 起因：goal round 1 拿 objective 逐条对 CHG-0042 的落地做审计，字面缺口是 objective 那句

> 静静躺在池子里，司机那边什么都没发生：货在他的车上，单却不在他手上。

## ① 六问

| | 回答 |
| --- | --- |
| **What** | 转货时若源单**在司机手上**（已派单 / 已接单），新开的那张目标单**直接派给这位司机**（走 `services/order_flow.py::assign_driver`，与派单员手点「派单」是同一条路）；并进既有单时**不动**（那上面本来就有司机）。 |
| **Why** | 司机已经在跑这一趟活儿了。货主换人只是账面归属变了，"谁把这批货送到"没变 —— 让新单回池子等人再派一次，等于同一趟活儿被派两遍、司机手上还多出一张要重新接的单。 |
| **Who** | 派单员（`Permission.ORDER_DISPATCH`，不新建权限）；司机那边的文案由事件名决定（`orders.assigned`）。 |
| **When** | 只在「转货这一步**新开**了一张单」且「源单当时在某位司机手上」时；三个前置不满足（司机账号找不到 / 已不是司机 / 已停用）就**如实跳过**，不拦整笔转货。 |
| **How much** | L1 —— 行为变更 + 多发一个既有事件（`orders.assigned`），**无迁移、无表结构、无新端点、无钱口径变化**；比 CHG-0042 的 L2 低一档：它改的是同一命令**内部**的下一步动作，对外契约只**加**两个可空字段。 |
| **If not** | 货主的货转过去了，司机手机上却没有这张单：他会继续按原来那张（已经少了几件、甚至已经作废的）单送货；派单员以为转完就完事，直到司机在门口打来电话。 |

## ② Must Change / Must Not Change

**Must Change**
- `backend/app/commands/order.py::transfer_lines`（:870-925）：新开的单在**行搬完之后**派给源单的司机（顺序：落盘 → 源单该作废的作废 → 派单 → **再落一次盘** → 目标单预占对账）。
- 派单这一步**不许包 SAVEPOINT**：`assign_driver` 在「这一单刚被别人派走」那条路上自己 `db.rollback()`（`services/order_flow.py:171-173`），而 SQLAlchemy 的 `Session.rollback()` 回滚的是**整笔事务**（`db.begin_nested()` 那个存档点一起被放掉）—— 包了照样把已搬好的行整段丢掉、函数还接着写审计与发件箱并 commit（真库探针实测：库里留下一句"新订单待派单"而那张单根本不存在）。正确形状是**失败即整笔失败**：`except ValueError` → `raise CommandError(…, 409)`，没有 commit ⇒ 源单没动、货也没搬。
- 发件箱新增一支：跟上了发 `orders.assigned`（**不是** `orders.edited`，更不是 `orders.created` —— 那两句文案分别是"订单被改了"和"新订单待派单"，对一张司机从没见过、也不在池子里的单，两句都是假的）。
- `orders.assigned` 在 `backend/app/commands/registry.py` 的 `order.transfer` events 里声明（域地图 `docs/DOMAIN_BOUNDARIES.md` 的订单域 events 行本来就认领着它）。
- 契约加两个**可空**字段：`followed_driver_name` / `follow_skipped_reason`（schema → 路由 → DTO → 结果文案）。
- 界面：抽屉里一行只读的「新单归谁跑」（跟原司机 <名字> / 进待派单池），静态规则写进既有的 `Hint`。

**Must Not Change**
- 状态机：**一句 `status =` 都不许写进命令层**（派单只走 `order_flow.assign_driver`，含它的 CAS 与派单审计）。
- 钱：转货一个钱字段都不抄（CHG-0042 立的规矩，这一份没动它）。
- 已送达 / 已撤销 / 已退货的单仍然一个字节都不写（挡板只有一处）。
- 并进既有单时不替那张单做决定：它有自己的司机，或者上面还压着别的货。
- 失败语义分两层：**可预期**的三种跟不上（找不到司机 / 已不是司机 / 已停用）在派单之前就挡掉，**不拦整笔转货**（货主之间的事实已经成立），只把原因如实带回去；派单当场抛（如 CAS 失败）则是**整笔失败** —— 见 Must Change 第二条。

- **Extension**：`commands/order.py`（转货命令）、`commands/registry.py`（事件声明）、`schemas/order.py` + `api/v1/orders_assignment.py`（两个可空字段）。

- **Presentation**：`ui/order/OrderTransferSheet.kt`（一行只读 + 一句 Hint）、`ui/order/OrderDetailViewModel.kt`（结果文案）、`data/remote/dto/Dtos.kt`（两个字段）。

## ④ Behavior Contract

```text
Input          与 CHG-0042 同（POST /api/v1/orders/{order_id}/transfer）
Output         { …, followed_driver_name: str|null, follow_skipped_reason: str|null }
Success        新开的目标单：status=DISPATCHED、driver_id=源单司机、dispatched_at=现在、
               driver_billing_mode_snapshot / driver_rule_snapshot 按这位司机现算、
               预占按整张单的净额写一笔（auto_stock_out）；内部备注带"[派单指派 …]"前缀；
               审计：ORDER_DISPATCH 一条（目标单）+ ORDER_TRANSFER 两条（out/in 都带跟随事实）；
               发件箱 orders.assigned {driver_id, order_id}（司机一条"新派单"站内信）。
Side Effects   跟上了：不再发 orders.created（那张单不在池子里，发出去派单员会扑空）。
Failure        三种前置（找不到司机 / 不再是司机 / 已停用）→ 只跳过跟随，转货照常成功，
               follow_skipped_reason 带一句人话；assign_driver 自己抛（如"这一单已经被派过了"）
               → **整笔失败**：抛 CommandError(409)「这笔转货没有完成（源单没动、货也没搬），请重试」
               （Session.rollback() 回滚的是整笔事务，SAVEPOINT 是假保险 —— 真库探针实测）。
Boundary Cases ① 源单待派单（没司机）→ 不跟，新单进池（CHG-0042 的原有行为）；
               ② 源单已派单 / 已接单 → 跟；
               ③ 整单转空（源单被作废）→ 跟（司机的活儿在目标单上继续）；
               ④ 并进目标货主既有单 → 不跟（那张单有自己的司机，走 orders.edited）；
               ⑤ 司机离职 / 停用 → 不跟 + 如实说明。
Compatibility  Compatible（纯新增两个可空字段 + 一个既有事件的新发点）；老客户端不读这两个
               字段时行为与 CHG-0042 完全一致。
```

## ⑤ Data Contract

- **新增/改动哪些字段**：**没有新字段、没有新表、没有迁移**。用到的既有列：`orders.driver_id` / `orders.dispatched_at` / `orders.status`（跟随派单写的正是派单员手点「派单」写的那几格）。
- **什么时候写 / 什么时候不写**：只在"这次是新开的一张单 + 源单在司机手上 + 那张单还没有司机"时写。
- **历史数据怎么办**：一个字都不动。"这批货当年是转过来的"仍由 CHG-0042 的三点（`parent_order_id` / 内部备注 / 两条审计）解释；**历史转货单不会因为这一份而改变司机**。
- **Rollback**：revert 实现提交即可（跟随只是转货内部多走一步；已经派出去的司机不会自己变回池子 —— 那要靠「撤回派单」这条既有的路）。

## ⑥ CHG 专章

### Before（CHG-0042 立下的口径，逐字）

- CHG-0042.md:157「还留着一部分：源单原样留着（少掉转走的那几件），目标单是一张新的**待派单**（并单时并进目标那张）」。
- CHG-0042.md:109-110 Side Effects 列的是「orders.created（新建目标单时，带 order_id）+ orders.edited / orders.cancelled / orders.pending_pool_changed」—— **没有** orders.assigned。
- CHG-0042.md:171 Must Preserve「库存预占与总账的平：转走的行必须把源单的预占放掉、**目标单（派单那一刻）才占**」。

### After

- 目标单**看源单当时在谁手上**：在 → 直接派给这位司机（`status=DISPATCHED`，连带费用快照与 `auto_stock_out` 预占）；不在 → 原样进池（不变）。
- 发件箱多一支 `orders.assigned`（跟上了才发），`orders.created` 只在"新单确实进了池子"时发。
- CHG-0042.md:171 那条 Must Preserve **仍然成立**：跟随就是"派单那一刻"，预占仍由 `auto_stock_out` 按整张单的净额写；命令层随后那句 `_resync_stock_if_assigned(db, target, …)`（:928）只是**复核**（差额 0，写不出第二笔占用）—— 但它**之前**必须先 `db.flush()`（:927）：会话是 `autoflush=False`（`backend/app/database.py:110`），派单刚写下的预占流水不落盘，SQL 算出来是 0、复核会照着 want 再写一整笔（真库探针实测：该占 4 件被写成 8 件）。

### Must Preserve

```text
- 状态机：状态写入点仍只有 services/order_flow.py（跟随走的就是那个函数，命令层一句 status 都没有）
- 库存预占与总账的平（目标单在"派单那一刻"才占 —— 跟随只是把那一刻提前到转货里）
- 钱：转货不重算价格、不抄源单的钱（CHG-0042 的 MONEY_FIELDS 一条没碰）
- 历史订单 / 历史审计 / 既有端点与 DTO 的向后兼容（两个新字段可空）
- CHG-0042 已有的行为：拆 / 并 / 整单转出、搬空作废、两条审计、待派单池刷新
```

### Blast Radius

**L1 —— Behavior + 一个既有事件的新发点**：改的是同一命令内部的下一步动作，对外只**加**两个可空字段与一个既有事件（`orders.assigned` 早已在领域地图里认领、`backend/app/main.py` 早就有处理器），无迁移、无钱口径、无权限变化。之所以不是 L0：司机那边会**多收到一条站内信**，且客户端要读两个新字段才会说清"新单归谁跑"。
