## ① 六问

① **解决什么问题？** 代理下单页里那一行「从联系人里选收货人」与**页面最上面的「请选择货主」**
   功能重叠：派单员先选货主，收货人这一套跟着货主/线路来，再给一行"从名册里挑"就是两个入口做同一件事。
② **当前用户 / 业务流程是什么？** 见 ⑥ 的 Before。
③ **哪个现有事实或能力会发生变化？** 见 ⑥ 的 After。
④ **哪些明确不能变化？** 见 ②。
⑤ **属于 Core / Extension / Infrastructure？** **PRESENTATION**，不碰 Core。
⑥ **什么证据能证明完成？** 见 ⑧。

## ② Must Change / Must Not Change

```text
Must Change:
- 那一行**只在货主自下单时出现**（`if (!proxyMode)`）；代理下单页**不显示**

Must Not Change:
- ⛔ 货主自下单（货主端「下单」）**保留**那一行 —— 他自己那本联系人名册是常用路径
- ⛔ 挑选弹层仍是共用的 `ContactPickerSheet`、回填仍走 `fillReceiver`（一个字不动）
- ⛔ 代理下单页最上面的「请选择货主」与它带出的一切（`setShipper` → 收货人/下单人）
- ⛔ 收货人名称/电话、下单人、备注那几行
- ⛔ 后端一个字节不动
```

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

**PRESENTATION**，**L0**。五问：①否 ②否 ③否 ④否 ⑤**是** ⇒ 不涉及 Core。

## ④ Behavior Contract

```text
Input          界面渲染（同一个下单页，两种进法）
Output         货主自下单 → 「联系信息」第一行是「从联系人里选收货人」
               代理下单   → 这一行不渲染，第一行直接是「收货人名称」
Success        代理下单页照旧能下单；收货人仍可从线路/地点带出来
Failure        不适用：纯展示，没有失败路径
Boundary Cases 两端共用同一个页面（`proxyMode` 一个开关），所以判据要能分辨这两种进法
Side Effects   无
Authorization  不适用
Compatibility  Compatible：不改接口、不改数据
```
