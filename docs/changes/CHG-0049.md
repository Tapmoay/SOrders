**① 我要解决什么问题？** 用户要的「撤销」有两个毛病：**派单员撤不了「派单中」的单**（界面上没有那颗按钮），
以及**连点两下就报失败、失败还把整页列表换成红字错误页**（用户读成「撤多了就失败、连接不上」）。

**② 当前用户 / 业务流程是什么？** 撤销 = 把一张还没送达的订单变成「已撤销」并**通知货主与司机**（后端
`cancel_order`，允许的状态是 `PENDING_DISPATCH` / `DISPATCHED`）；它有三个容易混的兄弟动作 ——
**撤回派单**（`recall_dispatch`，回**待派单池**、要填原因、司机收通知）、**退回池子**（`release_dispatch`，静默、货主无感）、
**编辑**。四个入口都在客户端：货主列表卡片、派单员待派单池那一档、派单员订单列表（本事项新增）、订单详情页。

**③ 哪个现有事实或能力会发生变化？** 客户端的行为：① 派单员订单列表对 `CANCELLABLE` 的订单多一颗「撤销」；
② 详情页的撤销门从写死的 `role == Role.SHIPPER` 改成问 `Capabilities`（两个键任一）；③ 四条撤销路各加一行
`if (acting) return`；④ 失败从**页面级 `error`** 改成**弹层级** `dialogError` / `cancelError`；
⑤ 两处撤回文案改成「**待派单池**」；⑥ 共用件 `DangerConfirmDialog` 多一个带默认值的 `enabled`。

**④ 哪些东西明确不能变化？** `CANCELLABLE` 的取值（仍是 `PENDING_DISPATCH` / `DISPATCHED` 两个）；
后端接口、权限、状态门、通知面**一个字不改**（本事项零后端改动）；撤回派单的落点仍是 `PENDING_DISPATCH`；
三个动作的既有语义与入口位置；`DangerConfirmDialog` 既有调用方的行为（默认值兜住）。

**⑤ 有没有更小的改法？** 有，而且被台账否掉了：只改详情页那一行（台账的 C 案）—— 用户得先点进详情页才够得着，
而他抱怨的正是「撤不了」；本事项按台账**推荐的 B 案**做（主列表入口 + 详情页按能力开门），
⛔ 没动「已完成派单」那一档（按司机分组、卡片已挤）。

**⑥ 如果什么都不做，会发生什么？** 派单员仍然只能「撤回派单 / 退回池子 / 编辑」，用户会继续认为**系统撤不了单**；
而连点两次仍会**撤两遍请求**（第一次成功、第二次 400），失败仍把列表顶掉 —— 用户会把「撤多了」与「连接不上」
当成同一个毛病（这正是 L-13 三处互锁的合成现象）。

## ④ Behavior Contract

```text
Input:
  派单员在订单列表（DispatcherOrdersScreen）对 order.status in OrderStatusModel.CANCELLABLE 的卡片点「撤销」；
  或 任何角色在订单详情页点「撤销订单」——门 = Capabilities.can(role.key, "order:cancel_shipper") ||
  Capabilities.can(role.key, "order:cancel_dispatcher")，且 order.status in OrderStatusModel.CANCELLABLE；
  或 货主在「我的订单」卡片点撤销；或 派单员在待派单池那一档点撤销（既有入口，位置未变）。

Output:
  成功：订单变成「已撤销」（后端 cancel_order），货主在「已撤销」里能看到；司机 / 货主收到 orders.cancelled 通知；
        弹窗关闭；派单员列表那句回执 actionResult = "订单已撤销"，列表重新加载。
  失败：弹窗**不关**，失败原因画在弹窗**自己里面**（dialogError / cancelError → FormErrorLine），用户可以改主意再点一次。

Success:
  一次点击只发一次请求：进入 confirmCancel()/cancel() 后第一行 if (acting) return —— 请求在途时再点 N 下都不再发；
  确认键在在途期间显示为禁用（enabled = !vm.acting）；成功后才 showCancelDialog / cancelTarget 收场并 load()。

Failure:
  任何 HTTP / 业务异常都走 toApiException(e).message 写进**弹层级**字段，⛔ 不写页面级 error
  （派单池那张页 error != null 会把整页换成 ErrorView、列表先没了；2026-09-23 真机抓到过这一幕）。

Boundary Cases:
  · 状态不在 CANCELLABLE 里（待派单池之外的其他档）⇒ 界面上**没有**撤销键（详情页同时要能力与状态两个条件）；
  · 派单员在「已完成派单」那一档（按司机分组的 DispatchedList）⇒ 本事项**没有**加撤销键（见 ⑨ Known Limitations）；
  · 在途期间连点 N 次 ⇒ 仍然只有一次请求；
  · 打开弹层又关掉再打开 ⇒ 上一次的失败原因已经被清掉（openCancel / dismissCancel / onCancelClick 各清一次）；
  · 后端拒绝（例如已被别人撤掉）⇒ 走 Failure 那条：弹层里出红字，弹层留着。

Side Effects:
  后端既有行为原样（状态流转、orders.cancelled 发件箱、待派单池变更）；客户端只多两个界面态文本与一个默认形参。
  ⛔ 不写账本、不发通知、不改权限、不改状态集合。

Authorization:
  单一真源仍是 core/Capabilities.kt（order:cancel_shipper / order:cancel_dispatcher；dispatcher 在 BYPASS_ROLES 里）；
  后端照旧按 Permission.ORDER_CANCEL_SHIPPER / ORDER_CANCEL_DISPATCHER 与状态门执行 —— 两层都在，
  客户端这次只是把**入口**补齐到与后端 / 能力表一致，⛔ 没有放宽任何判定。

Compatibility:
  对既有调用方是加法：DangerConfirmDialog 的 enabled 有默认值 true，所有既有调用方行为逐字不变；
  四个撤销入口的位置与语义不变（只在派单员订单列表**新增**一颗）；撤回派单 / 退回池子 / 编辑三颗按钮位置未动。
```

### Must Preserve

- **三个动作的语义与位置**：撤销（不可逆 + 通知）／撤回派单（回池子 + 填原因 + 司机收通知）／退回池子（静默 + 货主无感）
  —— 四颗按钮的所在位置与文案区分未被改动，只有派单员订单列表**多**了撤销这一颗。
- **客户端只认状态模型**：`OrderStatusModel.CANCELLABLE` 逐字未动；详情页与三个列表的撤销门都仍由它把关。
- **后端零改动**：状态门（`orders_delivery.py:370-378`）、权限（`ORDER_CANCEL_SHIPPER` / `ORDER_CANCEL_DISPATCHER`）、
  通知发件箱、`recall_dispatch` 的落点（`order_flow.py:621 status=OrderStatus.PENDING_DISPATCH,` + `driver_id=None`）原样。
- **共用件的既有调用方**：`DangerConfirmDialog` 的 `enabled` 有默认值 `true` ⇒ 其它调用方行为逐字不变。
- **没被顺手动的东西**：派单池「已完成派单」档（`DispatcherPoolScreen.kt:287 DispatchedList`）没加撤销键；
  `ApiClient` 的超时与文案原样（「撤多了连接不上」的另一条路，见 ⑨ Known Limitations）。

### Blast Radius（L0～L3）

- **L0（共用件）**：`ui/common/Components.kt::DangerConfirmDialog` —— 只多一个**带默认值**的形参 `enabled`。
- **L1（主，局部行为）**：撤销这一个动作的四个入口与四个 VM 方法
  （`DispatcherOrdersScreen/ViewModel`、`DispatcherPoolScreen/ViewModel`、`ShipperOrdersScreen/ViewModel`、
  `OrderDetailScreen/ViewModel`）。
- **L2（同族动作的文案）**：撤回派单的两处文案（同一屏、同一动作族，改的是**说法**不是行为）。
- **L3**：无 —— 没有 Core、没有后端、没有数据库、没有权限点、没有钱、没有状态机、没有账本。
