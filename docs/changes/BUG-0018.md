② 正常路径是「记一笔开销」：`POST /api/v1/expenses` → `backend/app/api/v1/expenses.py` 的 `create_expense` 路由 → 服务层 `backend/app/services/accounting_service.py` 的 `create_expense(db, body, operator_id)` → 建 `Expense` **并写一条 `CashFlow(OUT)`**。而 `backend/scripts/seed_demo_data.py` 当年那条路是 `for _ in range(30): db.add(Expense(...))` —— **直接 insert，跳过第二步**（`db.add` 不经过任何业务函数），于是那 30 笔只活在"开销管理"页上。
③ 三件事变了：① **播种脚本改走服务层** —— 以后不会再有新的"看不见的开销"；② **开发库存量补齐** —— 一次性脚本给那 30 张各补一条 OUT 流水（幂等、默认预览）；③ **记账口径收成一处** —— 分类名 → 现金流水 `biz_type` 的映射从 `create_expense` **函数体内**提到模块级 `EXPENSE_BIZ_TYPES` ＋ `expense_biz_type()`，并抽出 `write_expense_cash_flow()`：记账与回填**共用同一个函数**（原来回填脚本只能抄第二份映射，抄出来的那份一旦走散，同一张开销单会有两条口径不同的流水）。

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

```text
结论：Core 的既有不变量被坐实（账务写入单源）＋ Infrastructure 的一次性回填；
      没有 Extension、没有 Presentation 改动。
```

**五个问题逐个答：**

1. **这个变化属于哪一层？** `backend/app/services/accounting_service.py` 是账务服务（Core 的既有单源），`backend/scripts/` 是一次性运维脚本（Infrastructure）。
2. **是不是在扩展点上加东西？** 不是。没有新增能力、没有新增端点、没有新增字段、没有新增配置开关。
3. **有没有改界面？** 没有。Android 一行没动 —— 页面上多出来的金额，是流水补齐后**既有页面自己算出来的**（这正是"数据修好了"与"界面改了"的区别）。
4. **有没有碰领域类型 / 权限模型 / 后端契约？** 没有。`ExpenseCreate`、`Expense`、`CashFlow` 的字段与枚举一字未改。
5. **那为什么还要写"边界"这一节？** 因为"记账必须同时写流水"这条不变式原来**只在正常路径上成立**（服务层写，脚本绕过），本单把它变成"任何路径都走同一个函数"。这属于既有 Core 不变量的**坐实**，不是新增边界。

**核心改动声明行**：本单唯一的核心行为是 `accounting_service.py` 里抽出 `write_expense_cash_flow()` 并把 `create_expense` 改成调它 —— 记账路径的**输出**不变（同样的流水、同样的字段、同样的分类口径），变的是"只有一个地方写流水"。存量补写由 `backend/scripts/backfill_expense_cash_flows.py` 完成，它只调用核心的同一个函数。

## ⑤ Data Contract

1. **新增 / 改动哪些字段？** 一个都没有。`Expense` / `CashFlow` / `ExpenseCreate` 的字段与枚举未动；本单只**新增了行**（开发库 30 条 `cash_flows`）。
2. **Owner 是谁？** `accounting_service.py`（账务单源）是"开销 → 流水"这条口径的 Owner；`backfill_expense_cash_flows.py` 只是它的一次性调用方。
3. **什么时候写？** ① 正常路径：`create_expense` 里 `db.flush()` 拿到 `expense.id` 之后立即写（同一事务）；② 存量：手动跑一次回填脚本（`--yes`）。
4. **是否允许 NULL？** 既有列的 NULL 语义未动；`doc_id` / `party_id` 回填时一律写 `expense.id`（回填正是按它认"有没有流水"）。
5. **历史数据怎么办？** 就是本单做的事：30 张历史开销补写流水。补齐后「开销管理」与「账本 / 收支」第一次对得上（53 / 53，¥44560.51）。
6. **迁移与 Rollback？** 没有 schema 迁移（不加列、不改表）。回滚 = 还原代码 ＋ 必要时按下面的方式撤掉补写的流水（见 §⑨）。
7. **删除后历史数据还能不能解释？** 能：回填的流水与开销单一一对应（`doc_id = expenses.id`），删掉开销单时既有软删/级联规则不变，流水的 `party_name` 存的是分类快照 —— 与既有 23 张的形状完全一致，不引入新的解释难题。

## ⑥ CHG 专章

### Before

- 记账（`accounting_service.create_expense`）里有**一份**分类 → `biz_type` 映射（写在函数体内），`CashFlow(...)` 也在函数体内手拼；
- 播种脚本 `seed_demo_data.py` **自己 `db.add(Expense(...))`**，跳过服务层 ⇒ 30 张历史开销没有流水（¥35840.00 在钱那一侧不存在）；
- 没有任何机器判据盯着"开销单与流水必须成对"，也没有回填手段（想补只能手写脚本、再抄一份映射 —— 那正是第二种口径的来源）。

### After

- 模块级 `EXPENSE_BIZ_TYPES` ＋ `expense_biz_type()`：**全后端唯一一处**"哪个分类算哪个口径"；
- `write_expense_cash_flow(db, expense, operator_id=None)`：**记账与回填共用的同一个函数**，字段全部取自落库的那张单；
- `create_expense` 只负责建单 + 调它（`CashFlow(` 在 `accounting_service.py` 里只出现一次）；
- 播种脚本改走 `create_expense(db, ExpenseCreate(...), dispatcher.id)`；
- 新增一次性回填脚本（幂等、默认预览、`--yes` 才写）＋ 4 个 pytest ＋ 新判据与新反验；
- 开发库真跑一遍：30 → 0，53 张开销单与 53 条流水逐张对齐（¥44560.51）。

### Must Preserve

- 8 类 16 键的**取值**与"认不出落 OTHER、不抛异常"的行为；
- `POST /api/v1/expenses` 的入参 / 返回与权限；
- `cash_flows` 表结构与报表（`/cash-flows`、`breakdown`、`summary`）的口径；
- 历史开销单行本身与既有 23 张流水（一条都不碰）；
- 其它记账路径（收款 / 结算 / 货损 / 退货）与审计。

### Blast Radius（L0～L3）

| 维度 | 影响 | 判据 |
|---|---|---|
| L0 日志 / 静默 | 无（脚本有 print，日志无新增噪声） | 判据第 4 节 |
| L1 局部行为 / 界面 | 界面一行未改；页面上多出来的金额是流水补齐后的既有算法结果 | 判据第 2、3 节 |
| L2 数据 / 状态 | 开发库 `cash_flows` **新增 30 条 OUT**（¥35840.00）；开销单行未动 | 开发库实测：53/53 对齐 |
| L3 钱 / 账 | 「账本 / 收支」与现金流量表的**支出合计变大 ¥35840.00**（原来漏算的历史开销）；⛔ 算法未改 | 真机 5554 取证 |
