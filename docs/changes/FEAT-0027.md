① **消息中心的消息只在 App 里存在**：库存预警、应付到期、收款、设备登录、公告这些站内信，只有打开 App 才看得到；退到后台/锁屏，用户对它们一无所知。用户的原话是「你光在自己软件里谈消息没什么用的，有时候你要**在软件外**谈消息」。
② 服务端产生消息 → 走 socket `notification` 事件（或断线重连时的 `sync` 回补）→ 安卓 `core/RealtimeHub.kt` 收到 → 现在只更新未读数、刷列表、必要时落一条**静默**的普通通知（`postMessage`，且点它只回到首页）；消息中心页（`ui/messages/MessagesScreen.kt`）点击卡片才按 `noticeRoute` 跳转。
③ 三条能力发生变化：⒜ 消息**会进系统通知栏**且按 `severity` 分重要性（danger→HIGH、warn→DEFAULT、info→LOW）；⒝ **点通知直达那条消息对应的页面**（与 App 内点击同一份路由）；⒞ 一次来多条时**合并成一条摘要**（"有 N 条新消息"），并新增一个「消息进通知栏」开关。
④ 不能变：司机新单那条链（渠道 `orders_alert`、语音播报、按 order_id 去重、点通知进单）**一个字不动**；站内消息本身**不许被丢掉**（关开关只是不弹系统通知）；消息中心页的既有样式与既有路由映射（深链只能复用 `MessageGrading.noticeRoute`，不许有第二套）；后端与数据库零改动。
⑤ **Presentation ＋ Infrastructure（客户端）**：它不定义任何新的领域事实，也没有服务端契约变化 —— 改的是"同一条已经在库里的消息，在客户端还应该发生什么"。
⑥ 证据：单测 `MessageNotifyTest`（severity→渠道、id 去重、前台不弹、开关关掉不弹、多条合并、深链与 App 内路由逐条一致）；判据 `_tools/qa/_check_message_system_notify.py`；反验 `_tools/qa/_reverse_verify_message_system_notify.py`（≥6 条注入必须让判据变红）；司机那条链的红线 `_tools/ai/_check_notify_guardrails.py` 与 `_tools/qa/_check_alert_ringback.py` 仍全绿；`gradle :app:compilePhoneDebugKotlin` ＋ `:app:testEmuDebugUnitTest --tests "*Notify*"`。

## ④ Behavior Contract

```text
Input          一条站内信：id / type / severity / title / content / payload（socket 的 notification 或 sync 回补两条链）
Output         通知栏：单条一格（标题＝消息标题，正文＝消息正文；折叠行按 60 字截断，展开是全文）；
               或一条摘要"有 N 条新消息"（窗口内 ≥2 条时）
Success        点通知 → App 直达那条消息对应的页面（与消息中心里点这张卡是同一份路由）；摘要 → 消息中心
Failure        拿不到通知权限 / 开关关掉 / App 在前台 / 这条 id 已经弹过 → **不弹**，
               但**消息一条都不丢**（列表、未读数、已读都照旧由原有链路维护）
Boundary Cases ① id 缺省（≤0，老调用点或异常负载）：不去重、照弹（宁可重复也不静默不提醒）；
               ② 认不出 type 或 payload 缺键 → 路由为 null → 点通知只把 App 打开（不瞎跳）；
               ③ 一批里混着 danger 与 info → 摘要按**最高**那一档选渠道（别把 danger 埋进一堆 info 里）；
               ④ App 在前台：不弹系统通知（应用内列表本来就会刷新，不重复打扰）
Side Effects   写本机 SharedPreferences（开关 ＋ 已弹过的通知 id），不发任何网络请求
Authorization  不需要新的权限点：读的是**发给我的**消息（`PushTrust.acceptNotification` 已在上游过滤）
Compatibility  Compatible：通知渠道只**新增**（老渠道一个不删，旧版 App 行为不变）；
               接口与字段零改动，老客户端的消息中心照常工作
```

## ⑤ Data Contract

- **新增/改动哪些字段**：**服务端零字段**。本机新增两条 SharedPreferences 键（`alerts` 这个 XML）：`message_notify`（bool，默认 true）、`message_seen_ids`（"通知id@时间戳;…"，去重窗口 24 小时、上限 128 条）。
- **Owner 是谁**：本机设置与去重记录 = 客户端自己（`core/AlertPrefs.kt` 是这两条键的唯一读写处）。消息本身仍归服务端（`notifications` 表）。
- **什么时候写 / 什么时候不写**：只在**真的落了一条系统通知**之前写 `message_seen_ids`（去重后）；开关那一行由用户在「我的 → 消息提醒」里拨。
- **是否允许 NULL**：不适用（布尔与字符串，字符串缺省是空串）。
- **历史数据怎么办**：`message_seen_ids` 是空串起 —— 旧版本弹过的消息在新版本里会**再弹一次**（升级那一下），之后不再重复；这是有意选择（宁可多提醒一次，也不好推断"过去弹过哪些"）。
- **迁移怎么做 / Rollback 怎么办**：不需要迁移（键缺失时按缺省值走）。回滚 = 换回旧 APK：新渠道与两条键留在机器上不再被读，消息中心与司机那条链不受影响。
- **删除本功能后历史数据还能不能解释**：能 —— 删掉它只是"消息不再进系统通知栏"，消息本身与它的时间线都在服务端与消息中心里。

## ⑥ CHG 专章（FEAT / GOV 不适用时写「不适用：<理由>」）

> 本事项是 FEAT；按 `_TEMPLATE.md` 的要求仍保留四小节，写清用户看到的变化。

### Before

库存预警 / 应付到期 / 收款 / 设备登录 / 公告这些消息到达时：App 在后台的话，通知栏里只会出现一条**静默**的普通通知（渠道 `messages_alert`），且**点它只把 App 打开**（`setContentIntent(openApp(null))`），用户还得自己进消息中心翻；一次来 10 条（每日扫描那种）就是 10 条通知刷屏；App 在前台时也会照弹一条（与界面里的刷新重复打扰）。

### After

同样的消息到达时：① 按 `severity` 分档 —— danger 走「消息」（HIGH，有横幅）、warn 走「消息提醒（一般）」（DEFAULT）、info 走「消息（低）」（LOW，安静）；② **点通知直达那条消息对应的页面**（`MessageGrading.noticeRoute` 算出的整条路由，与消息中心里点这张卡同一份）；③ 1.5 秒窗口内来了 ≥2 条 → 合并成一条「SOrders 有新消息 / 有 N 条新消息」，点它进消息中心；④ App 在前台时不弹（应用内本来就会刷新）；⑤ 「我的 → 消息提醒」多一行「消息进通知栏」，关掉**只不弹系统通知**，站内消息一条不丢。

### Must Preserve

```text
- 司机新单那条链（orders_alert 渠道、语音、按 order_id 去重、点通知进单）
- 站内消息本身：列表 / 未读数 / 已读 / 删除 / 保留期，一个都不变
- 消息中心页的样式与 noticeRoute 那份路由映射（深链只能复用它）
- 后端与数据库（零改动）
- 通知权限那条链（NotifyPermission 的唯一读法、首页硬提示与这一页那句话逐字相同）
```

### Blast Radius（L0～L3）

**L1**：改的是安卓客户端"消息到达时做什么"与本机提醒设置；不碰服务端、不碰数据库、不碰金额与订单口径。之所以不是 L0：它新增了两个通知渠道 id 与两条本机键，并改了"点通知去哪一页"这一行为；之所以不是 L2：没有任何持久化契约或跨端字段变化。
