① **我要解决什么问题？** 三件事，缺一件都不算修完：
   - **建单时的「锁」是假的**：`create_settlement` 只写 `DriverSettlement` 一行（`order_ids` / `bill_ids` / `amount`），**一个字节都不碰明细**；明细仍旧 `open`、`settled_doc_id` 为空 ⇒ 第二张草稿单照样把它收走。冲突被发现的时间被拖到「确认第二张单」的时刻。
   - **报错把两种成因糊成一句**：`（被删除或已被别的结算单占用）`。明细真被删了，用户会以为是被别的单占着；被别的单占着，用户又会去查明细是不是丢了。而且**一个单号都不给**，用户只能自己去翻列表。
   - **注释与行为相反**：`backend/app/api/v1/driver_settlements.py:93` 写着「建结算单＝把一批「待结」明细**锁进**一张单子（钱虽未出，但已经不能再被第二张单占用），必须留痕。」——与本单要修的行为同时成立时，这句话是**反的**。注释是这一半 bug 的载体：它让下一个人以为不用查。

② **当前用户 / 业务流程是什么？** 派单员按月给司机结算：`driver_bills`（一笔订单一条，或按月的「孤儿明细」）处于 `open` ⇒ 建草稿结算单（把这个月司机 3 的 `piece` 明细收进一单）⇒ `confirm`（明细转 `settled` 并绑 `settled_doc_id`）⇒ `pay`（写 `cash_flows` 的 PAYMENT 行）。界面上司机明细列表与结算单列表都会显示明细的 `settled_doc_id`；用户在「建单」这一步期待的心理模型就是注释里那句话：**收进来的明细已经被这张单占住了**。

③ **哪个现有事实或能力会发生变化？**
   - `driver_bills.settled_doc_id` 的含义扩了一档：从「这张明细结算给哪张**已确认**的单」扩成「这张明细**已被哪张未作废的单占用**」（草稿也写）。
   - 「建单」从**一个不可能的失败**（这个月没待结明细）变成**两种失败**（没待结明细 / 待结明细都被别的单锁着——后者点名到单号）。
   - 「确认失败」的文案从一句糊话变成按成因逐笔分句（占用 / 已删除 / 状态已变）。
   - 作废草稿单的解锁范围扩大：除了 `settled` 的行，**本单锁着的 `open` 行**也要放回 `settled_doc_id = NULL`。

④ **哪些东西明确不能变化？**
   - **已确认 / 已付款的结算单在接口层不可撤销**（全仓没有 unsettle / 红冲端点，`cancel` 只放开给 `draft`）——这是设计，本单一个字节都不动。
   - **钱的口径**：`cash_flows` 只在 `pay` 时写；`s.amount == 明细合计 + adjustment` 这个恒等式在确认与付款两处都必须继续成立。
   - **取数只有一处实现**（`settleable_bills`）：建单 / 确认 / 作废都从它取数（BUG-0007 的判据 `_tools/qa/_check_settlement_single_source.py` 会逐字核对它）。
   - **作废解锁不许复活被保留任务作废的明细**（`backend/app/services/data_retention.py:231-245` 会把过 3 年物理清理订单的 `open` 明细翻成 `cancelled`）——解锁条件里不能出现 `CANCELLED`。
   - 表结构 / 迁移 / `schema_bootstrap` / 接口出参 / `bill_ids` / `adjustment` 的语义（BUG-0007 那批字面量与 8 条回归用例继续原样通过）。

⑤ **这个变化属于 Core、Extension 还是 Infrastructure？** **Infrastructure**（`backend/app/services/accounting_service.py` 的取数口径、锁的落点与失败语义；接口层只是把 `ValueError` 翻成 400）。它是**核心区文件**（`_tools/qa/_core_files.txt` 收录：账本入账与欠款口径），所以本单在 `docs/AI_WORK_CLAIM.md` 里按规矩声明了一行 `核心改动：`。

### R4-BOUNDARY-JUSTIFICATION：为什么边界解决不了这件事

用户看到的两个症状（「两张草稿单都能收同一笔钱」与「报错分不清两种成因」）都**不能靠边界修**：

- 前端可以在建单前先查一遍「这笔明细是不是挂在别的草稿单上」，但那要靠**新的查询能力**（当前接口按 `bill_ids LIKE '%12%'` 拼字符串才能反查，`driver_bills` 出参里的 `settled_doc_id` 在草稿期是空的）——等于把锁的真相搬到客户端，且**并发下必然漏**（两个派单员同时建单）。
- 「报错分开说」更不能在边界做：接口层拿到的只是一个 `ValueError` 字符串，成因（被占用 / 已删除 / 状态已变）只有查过 `driver_bills` 的服务层知道。
- 因此最小改动就是**在唯一取数实现 `settleable_bills` 上把这个口子收口、在建单当刻真的落锁**——这也是本单动到核心区文件（`accounting_service.py`）的全部理由。⛔ 明确**没有**走「给 `driver_bills` 加一列 `draft_doc_id`」那条路：那要迁移 + `schema_bootstrap` + 模型 + 核心区三处同改，不是最小改动；`settled_doc_id` 这一列在草稿期本来就是空的，语义扩一档即可。

## ④ Behavior Contract

```text
B1 建单当刻就上锁：create_settlement 成功后，本单收进来的每一笔明细 settled_doc_id == 本单 id，status 仍是 open。
B2 一笔 open 明细同时最多被一张「未作废」的结算单占用；被占用时建单 400 并点名（明细 X 在结算单 #Y（状态）），本单不创建。
B3 没有任何待结明细（也没人被锁）时，仍是老句「{month} 无待结算明细（请先生成账单）」。
B4 确认只认本单锁住的明细：取数 = 「没人锁的」+「本单锁住的」；被别的单占用的行**不会被本单悄悄抢走**。
B5 确认时明细「不在了」要按成因分开说：被别的结算单占用（X 笔，附单号）/ 已被删除（Y 笔）/ 已不是待结状态（Z 笔），文案保留「已经不在了」与「请作废后重新结算」。
B6 作废草稿单把本单锁住的行放开：status ∈ {settled, open} 的行 → open + settled_doc_id = NULL；cancelled 的行不动。
B7 付款仍只认「settled_doc_id == 本单 id 且 status == settled」的行，金额恒等式不变。
B8 注释与行为一致：接口层那句「锁进一张单子」说的是真的，且写明锁落在 settled_doc_id 上。
```

## ⑤ Data Contract

- `driver_bills.settled_doc_id`：**语义扩一档** —— 「这张明细被哪张单据占用（`draft` / `confirmed` / `paid`）」。草稿单存续期间允许出现 `status = open` ＋ `settled_doc_id` 非空（`BUG-0024` 之前这一组合只可能由脏数据造成）。
- `driver_bills.status`：取值不变（`open` / `settled` / `cancelled`）；建单**不改**状态，确认才 `open → settled`，作废解锁 `settled → open`（只限本单锁住的）。
- `driver_settlements.bill_ids` / `order_ids` / `amount` / `adjustment`：语义与取值一字未改（BUG-0007 的契约）。
- **老数据（legacy）**：库里已存在的草稿单（本单之前建的）没有锁，其 `bill_ids` 为空的老单走「按 `order_ids` / 按月重取」两条老分支，现在这两条分支也会跳过被别人锁住的行 ⇒ 老草稿继续能用，但不能抢新单的锁。
- 迁移：**无**。没有新列 / 新表 / 新索引；`settled_doc_id` 与 `status` 都已有单列索引。

### 这次怎么做的

1. **锁真的落下去**：`create_settlement` 在 `db.add(s)` 之后 `db.flush()` 拿 id，再逐行 `b.settled_doc_id = s.id`（状态保持 `open`：钱还没出，明细仍「待结」但**已被占用**）。
2. **取数收口在唯一的 `settleable_bills` 上**：默认只取「没人锁的」；确认时传 `doc_id=s.id` 把「本单自己锁住的」算回来；`include_claimed=True` 只给建单报错时点名单号用。
3. **建单就会 400**：这个月的待结明细都被别的单锁着时，直接报 `{month} 的 N 笔待结明细已经被别的结算单锁住了（明细 12 在结算单 #57（草稿））；请先作废那张单再来建单，本单未创建`。
4. **确认按成因分句**：`_why_gone` 按 `settled_doc_id` 与本单 id 的关系三分桶（被别人占用 / 查不到=已删除 / 其余=状态已变），报错形如「这张结算单锁定的 1 笔明细已经不在了：1 笔已被别的结算单占用（明细 344 在结算单 #57（已确认））。请作废后重新结算」。
5. **作废解锁**：`settled_doc_id == s.id` 且 `status ∈ {settled, open}` → `open` + `settled_doc_id = NULL`（`cancelled` 的保留任务作废行不复活）。
6. **注释与行为对齐**：接口层那句注释扩写成「锁落在 `settled_doc_id`、状态仍是 open、作废放回、为什么要 flush」。

```text
Known Limitations
```
- 草稿期明细仍是 `open`（钱未出、可继续参与报表），因此「待结金额」类报表**不会**因为被草稿单锁住而变小 —— 这是刻意的（锁只挡第二张结算单，不改钱的可见性）；如果以后要让报表也能看出「被草稿单占住」，那是另一单。
- 老草稿单（本单之前建的、没锁的）不会追溯补锁：它们的 `bill_ids` 仍指向当时那批明细，确认时按新规则重新校验（被别人锁住的行会被跳过并报错）。
- 结算单列表页**没有**新增「这笔明细同时挂在 N 张草稿单上」的提示（那是 TB-08 期望里的另一条备选修法；现在这条路已经不可能发生，因为第二张单建不出来）。

```text
Rollback
```
- 单文件回退：`git revert` 本单的实现提交即可（`accounting_service.py` 与接口注释；新增的三个文件删掉不影响运行）。
- 数据回滚：`settled_doc_id` 是既有列，回退后草稿单锁着的行会残留非空 `settled_doc_id`（回退前先把这个库里的 `status='open'` 行的 `settled_doc_id` 清成 NULL 即可，未确认的草稿单本来就该是空的）。
