② **当前用户 / 业务流程是什么？** 用户（需求方）与 AI 会话多个并行改同一仓库；此前唯一的流程约束

与 R1～R4 的整改文档里，**没有一份"一个事项从立项到关闭"的规范**。

③ **哪个现有事实或能力会发生变化？** 「一个开发事项的身份与流程」这件事本身：
从"没有统一 ID / 没有定义文件 / 没有 Blast Radius / 没有关闭六格"变成"有，且有机器判据"。

④ **哪些东西明确不能变化？** 见 ② 与 ⑥ 两节。

⑤ **属于 Core、Extension 还是 Infrastructure？** 都不是 —— 它是 **GOV**（改规则本身），
零运行时改动。

⑥ **什么证据能够证明它完成？** `python _tools/qa/_check_dev_spec.py` 绿 +

### ⑧.1 本事项顺手抓到的两个真缺陷

⛔ 这两条**不是**"顺手改一下"：它们都落在本事项的范围内（"确保每次开工都读得到"），
都当场修了、都有判据钉着、都在上面那张表里有证据。

**① 39 份文档从入口到不了 —— `check_reachability.py` 报孤儿。**
那份检查早就写好了、质量也高，但它**从来没被跑过**（它在 `backend/scripts/`，
不在 `_tools/*/_check_*.py` 的自动清单里）。跑一次的结果是：
**R3 / R4 的全部证据页与报告，从 `AGENTS.md` 出发都到不了** —— 对新会话等于不存在
（与本项目那份沉睡 5 个月的 94 KB 项目地图是同一种病）。
本事项把它接进必跑清单（`_check_doc_reachability.py`），并在 INDEX 里补「全量文档目录」。
顺带修出 **4 条断链**：

| 断链 | 性质 | 处置 |
| --- | --- | --- |
| `DOMAIN_BOUNDARIES.md` → ```../../backend/app/commands/order.py``` | **真断链**（该文件在 `docs/` 下，多写了一层 ``../``） | 已改正原文（另一条 registry.py 同） |
| `R4_EXTENSIONS.md` → ``../backend/app/extensions/`` | **判据假阳性**（目标是真实存在的**目录**，解析器只认文件） | 解析器放宽为"文件或目录存在即可"—— ⛔ 不存在的目录照样算断链 |
| `R4_CONTRACTS.md` → ``../backend/app/core/contracts/`` | 同上 | 同上 |

**② 这份反向验证自己第一版被抽出来的是「0 条」。**
`_check_reverse_verify_anchors.py` 靠**元组字面量**的形状把注入锚点抽出来做静态核对；
第一版写成 `s_xxx(sb)` + `sb.replace(...)` 方法调用，
结果锚点**一条都没被核对** —— 而"抽不出来"看起来是**绿的**（没有锚点可核对 = 没有报错）。
已改成表驱动的字面量形状，现在抽得出 **10 条**，锚点一腐烂当天就报红。
