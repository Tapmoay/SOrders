## ① 六问

### 问 1：用户看到的是什么？期望是什么？

| 走查项 | 实际（走查原话） | 用户期望 |
| --- | --- | --- |
| P19-a 计费规则卡 | 同一张卡既写「按单计件 · 小货车 **每单 22 元**」，又写「**还没勾价目** —— 派给这个司机的单会进「待定价」」 | 一眼看出「每单 22 元」是**给司机的工钱**，不是这单的运费；再看出没勾价目时运费根本还没出来 |
| P19-b 结算页 | 真实送达的那一单在「司机运费结算」里查不到，钱藏在 运费模板 → 待定价 里，两页没有互相链接也没有角标 | 结算页上直接看见「还有 N 单运费没定价」，点一下就到待定价页 |

### 问 2：现状为什么是这样？（各自的根因）

- **P19-a**：`ui/dispatcher/DriverBillingRulesScreen.kt:209-311` 的 `RuleCard` 把后端的 `rule.summary`（「按单计件 · 小货车 每单 22 元」）平铺出来 —— 那笔钱是**司机侧口径（工资）**；同一张卡下半句「还没勾价目 —— 派给这个司机的单会进「待定价」」说的是**货主侧口径（运费）**。两笔钱同屏、同排版、都没有口径标签 ⇒ 卡面读起来像「每单 22 元已生效」。价目缺没缺这件事，卡上只有一句条件文案，没有可扫的标记。
- **P19-b**：`ui/dispatcher/FreightSettlementViewModel.kt` 的 `load()` 只取「已送达且已计价」的运费单（明细行 `"运费 ¥"` / `"运费 待定价"` 两种写法都只在 `@freightFee != null` 的那批里出现）；后端的 unpriced 过滤（`backend/app/api/v1/orders_query.py:160-166` 与 `:210-215` 两条互不相干的查询路径各一份）刻意把 `DELIVERED` 也算进来（`backend/app/services/accounting_service.py:187` 有注释「`GET /orders?unpriced=true` 刻意把 DELIVERED 也算进来」），但**结算页从来没有请求过它**。待定价页 `ui/dispatcher/FreightPricingScreens.kt:195 fun UnpricedOrdersScreen(` 与结算页之间没有任何入口关系（模板页 `ui/dispatcher/FreightTemplatesScreen.kt` 那一格 `"待定价"` 是唯一的门）。

### 问 3：改完用户看到什么？

- **结算页**：司机选择行下面多一行 `errorContainer` 底色的提示条 —— 「还有 N 单运费没定价 —— 不分司机，也不在上面这张表里」，右侧「去定价 ›」点进运费待定价页。
- **规则卡**：名字同一行右侧多一个红字小胶囊「缺价目」（**只在这条规则一份价目都没勾时出现**）；摘要上方多一行灰字「给司机的钱」；空价目那句原话后面多一句「「给司机的钱」是工资；运费按价目算，没勾价目运费就出不来（点「编辑」勾上）」。

### 问 4：不改会怎样？

卡面继续读起来像「每单 22 元已生效」⇒ 派单员以为这单的运费已经算好，遇到结算页查不到单会当成数据丢了（走查就是这样写下来的）；待定价的钱继续只藏在一个与结算无关的页面里，结算页看起来像「这个月一单都没送达」。

### 问 5：怎么证明改对了？（两条腿）

- **机器判据 + 反验**：`python _tools/qa/_check_freight_pricing_clarity.py`（25 项）＋ `python _tools/qa/_reverse_verify_freight_pricing_clarity.py`（逐条注入「改坏了」的版本，证明判据会红）。
- **人眼真机截图**：5554 派单员三张 —— 规则卡缺价目态、结算页那一行提示、「去定价」落到的待定价页。

### 问 6：会不会伤到别处？

- 结算页多**一次只读请求**（复用 `container.repo.unpricedOrders()`，与待定价页同一个方法）；`loadUnpriced()` 自带 try/catch，失败就按「没有」处理（提示条不显示），**不许把整页拖红**（主表 `load()` 的失败语义一个字没动）。
- 结算页的 `PersonTriggerRow(` **仍然只有一处**：那一行提示**不复用** `PersonTriggerRow`（它写死了「选择」二字，而且 `_tools/qa/_reverse_verify_freight_settlement_ui.py:86` 的注入锚点正是 16 空格缩进的那一行 —— 多一处会让反验 MISS）。
- 新增的两个 Text 都**不带** `maxLines = 1`（`_tools/qa/_adaptive_squeeze_baseline.txt:20` 的 `FreightSettlementScreen.kt 4` 只许降不许升）。
- 规则卡改动落在 `RuleCard` 内部（`_check_billing_rule_form.py:88` 的切片是 `fun DriverBillingRulesScreen(`，不含它）；冻结句一字未动（见 ② 的 Must Not Change）。
