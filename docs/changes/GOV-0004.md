## ① 六问

① **解决什么问题？** 每份 `_tools/qa/_check_*.py` 的模块 docstring 里常写一句
「配套：python `_tools/qa/_reverse_verify_x.py`（**N 种破坏方式**全被抓）」—— 那是这份判据
「被多少种破坏证明过」的**唯一说明**。而那个 N **原来没有任何判据在管**：后来给反向验证补注入的人
不会回头改这句话，于是它安静地烂成**第二份真相** —— 读起来像「这条红线有 N 种破坏在守着」，
其实那个 N 早在几次补注入之后就过期了，最离谱的一处写着 8、真实是 28（差 20 条）。

2026-10-04 把仓库里所有这类声明跟配套脚本的注入表逐条对账，**8 处声明里 6 处是错的**：

### 为什么不能只把那六个数字改对（老毛病：只擦这一次）

因为数字**会再次过期** —— 而且这次实测就是证据：同一句话在 6 个文件里都烂掉了，
其中一处差 20 条。只擦数字 = 把下一次腐烂留给下一个人；所以「改对数字」与「上锁」
必须在同一个逻辑改动里做完：`_check_reverse_verify_anchors.py` 现在每次都会把仓库里所有这类声明
跟配套脚本的表长核一遍，写错就红。

## ④ Behavior Contract

- **输入**：无（静态扫仓库：`_tools/*/_check_*.py` 的源码文本 + 被指到的反向验证脚本的 AST）。
- **新增输出**：一行 `顺带核对了 N 处「配套：…（N 种破坏方式）」说明书条数（M 处拿得到对照表）。`
- **成功**：0 处对不上 → 这一支**不**增加失败（退出码不受它影响）。
- **失败（退出码 1）**：
  - 任一处「写的 N ≠ 配套脚本表长」→ 打印 `❌ K 处「配套说明书」的条数与脚本对不上（它是一份会安静过期的第二真相）：`，「  · 文件:行号 写着 N 种破坏方式，而 <rv> 的表里是 M 条」，并给修法提示「把那个数字改成真实的表长（只改数字，不动判据）」；
  - 声明里还写了 `a/b` 时，要求 `a == b` 且分母等于表长或表长 +1；
  - 声明指着一份**不存在**的配套脚本 → 报「指着一份不存在的配套脚本」；
  - `M < MIN_CLAIMS (8)` → 报「抽取失效了，先修这个 —— 别让这一节安静地什么都没查」。
- **幂等 / 只读**：不写任何文件；同一份仓库跑两次结果一致。
- **不适用**：无 API Contract、无权限、无审计码（这一支不产生业务事件）。
