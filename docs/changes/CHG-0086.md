## ③ Boundary（边界：为什么这件事不该在代码边界以外解决）

结论：**这条线的落点只能是 AI 的能力面**，不能推给「让用户去页面点」或「后端再开一个专用端点」。

五问依据：

1. **用户侧**：派单员已经在用 AI 干活（登记票据、对齐台账是同一批活儿）；六条端点早就在，缺的只是「AI 说不说得出来」。
2. **代码侧**：六条端点在 `data/repo/AppRepository.kt:872-896` 与 `data/remote/api/Apis.kt:2068-2108` 齐备 —— 数据层一行不用改，本单只写 `ai/` 这一层。
3. **重复侧**：手工页面与 AI 走的是**同一套端点**，不存在两套业务逻辑；卡片上的话由 `AiWriteAction` 的 blurb/details 承担说明责任（这一层就是「说明书的唯一出处」）。
4. **风险侧**：发票是**占号 + 进税汇**的东西，登记 / 开具 / 作废三条撤不回来 —— 所以三条都给 HIGH 风险 ＋ 确认卡 ＋ `UNDO_NONE` 理由（风险拿不准往上一档，见 `AiWrite.kt:28`）。
5. **能力侧**：定位必须落到**确定的编号**上（`resolveInvoice` 五件套 → 命中唯一一张才允许动），不靠模型记 id —— 这是账本 `resolveEntry` 已经定下的同一口径。

**核心改动声明**：`android/app/src/main/java/com/tapmoay/sorders/ai/AiWriteService.kt` —— 为什么必须动核心：数据源接口（7 个方法）与处理器注册表都在这个文件里；发票域按既有域的形状接进去，不另起一层框架（`AiWriteInvoices.kt` 只提供规格与处理器，接线点全在核心文件里）。**没有动 README 之外的任何 Core 文件**：`data/`、`backend/`、数据库、权限点都零改动（前后对比见 ⑧ 证据表）。

## ④ Behavior Contract

```text
Input:
  - 登记：direction（OUTPUT/INPUT，必填）＋ amount（必填）＋ 进项要 supplier + purchase_orders（至少一张）、销项要 customer；
          invoice_no / date / tax_rate / tax_amount / note 可选；票号没拿到可以先空着。
  - 改票 / 开具 / 作废 / 撤票：五件套定位（invoice_no 最准；或 date + amount；或 party 对方名；direction 可收窄）—— 至少给一个能收窄的。
  - 改票另外给要改的值（new_invoice_no / new_date / new_amount / new_tax_rate / new_tax_amount / note），一个都不给就拒绝。
Output:
  - 一张确认卡（NeedConfirm）：卡上逐字段写着「现在是什么 → 要改成什么」，以及这次做完会发生什么。
  - 确认之后：Done（带 undoToken 与 undoLabel）或 Done（undoToken = null，撤不回来的三条）。
Success:
  - 端点返回 2xx：登记返新票编号；改 / 开具 / 作废 / 撤票 / 恢复无返回体（幂等键由框架带上）。
Failure:
  - 参数缺失/格式错 → Rejected（如「缺少 supplier：这张进项票是谁开给我们的？（供应商名册里的名字）」）；
  - 定位 0 条 → Rejected ＋ 列最近几张候选；>1 条 → Rejected ＋ 列候选（票号最准）；命中回收站 → Rejected（先说「恢复这张票」）；
  - 进项票逐张核采购单，不存在 → Rejected（「采购单 #12 不在系统里（编号对不对？）」）；
  - 后端非 2xx → 由框架转成给用户看的话（不吞错）。
Boundary Cases:
  - 票号撞不出来：日期比对含**前后 31 天**（与账本同一窗口），一次最多拉 100 张（后端默认分页）；
  - 只给税率、没给税额 → AI 算出来（taxOf）并显式进 payload；只给税额没给税率 → 拒绝；
  - 税额 > 价税合计 → 拒绝（「这两个数是不是填反了？」）；
  - 改票「说的和现在一样」→ 拒绝（不产生空改动）；「没说要改什么」→ 拒绝；
  - 销项票挂采购单 / 进项票填客户 → 拒绝（各自说清为什么）；
  - 一处最多挂 50 张采购单（卡片可读性上限）；票号长度上限 64（与后端一致）。
Side Effects:
  - 台账行新增/改动/撤下；撤票是**伪装删除**（行还在、is_deleted 置位），恢复逐字段照搬；
  - 三条撤不回来的动作（登记/开具/作废）**不留撤回路径** —— 卡片上直说，不允许出现「事后可以撤」的假承诺。
Authorization:
  - 六条全部只给派单员（AiRole.DISPATCHER）；不进 SHIPPER_ACTIONS；「恢复发票」undoOnly = true（模型看不到）；
  - 权限点仍由后端把关（AI 只是调用者）—— 越权会在后端被拒，AI 侧不另做一套授权。
Compatibility:
  - 动作总数上界 165 → 171；说明书上限 27000 → 29000（实测 27807）；
  - 既有 165 个动作的 id / 参数 / 卡片文案一个字不改；货主清单 44 条不变。
```
