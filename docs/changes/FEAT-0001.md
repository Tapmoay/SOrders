## ⓪ 需求方的原话（本事项的唯一依据）

> 「可以给一辆车**固定一个属性**。因为他不是有对应的车子吗，还有车牌，其实给这辆车固定属性，
>  他的属性是不是**不可能变**；也就是说，在**创建车辆的时候就需要填相应的属性**。
>  **不同的车型会需要填的属性是不同的**，比如说大车要填的大车属性不同；
>  挂车，他要填挂车的属性不同。别说有可能是个**平板车**、有可能是一个**自卸车**。」
>
> 「（车辆属性）**是要算钱的**。不过主要的一些是不会算的，主要的是**吨和方**这种
>  即便（计量）单位……我们在计算的时候**可以直接拉取这些属性，然后直接进行单位换算**。」
>
> 「**属性清单可以啊，就可以就这样子**。」（属性清单获批）

⇒ 四句话把这件事定死：

| 需求方的话 | 落到设计上 |
| --- | --- |
| 给一辆车固定一个**属性** | 属性挂在**车辆**上（不是挂在换算表上） |
| 属性**不可能变** | 它是**建车时定下的事实** —— 所以改属性是"整份说清改成了什么"，不是逐项打补丁 |
| **创建车辆时**就要填 | 新增车辆的弹层按型式长出对应的输入项 |
| **不同车型填的属性不同** | **车身型式**决定属性集（箱式车 / 平板车 / 自卸车 / 挂车） |
| 主要的是**吨和方** | `载重(吨)` / `容积(方)` 是**参与换算**的两项（其余只是台账信息） |

### ⛔ 已作废的那一版（写在这里，免得下一个人照它做）

第一版设计是「`unit_conversions` 加一列 `vehicle_id`（可空，空 = 通用），取值优先级：
指定车辆 > 通用」。它**能**表达"一车等于多少方逐车不同"，但需求方要的不是这个 ——
他要的是**车辆自己带着容积/载重**。两者的区别不是实现风格，而是 **Owner 在哪**：

- 作废版：容积住在**换算表**里（一辆车的容积是一条换算规则）；
- 现版：容积住在**车辆**里（"一车 = 多少方"是**读车辆属性**得到的结果）。

### ⭐ 由此得到的两个字段（本事项最重要的一个判断）

| 字段 | 取值 | 它回答什么 | 谁在用 |
| --- | --- | --- | --- |
| `vehicles.vehicle_type`（**没动**） | 小货车 / 大货车 / 挂车 | **这辆车按什么算钱** | 司机计费规则 / 运费模板 / 司机应付 / `resolve_billing_mode` |
| `vehicles.body_type`（**新增**） | 箱式车 / 平板车 / 自卸车 / 挂车 / 未设置 | **这辆车能填哪些属性** | 只有车辆台账自己 |

⛔ **为什么不去扩 `vehicle_type` 的取值**（这是本事项做过的最重要的一次"停下来"）：

`vehicle_type` 不是"这辆车长什么样"，而是"怎么给它算钱"。同一套取值被**五处**共用，
其中 `models/user.py::resolve_billing_mode` 里那一行 ——

```python
return "PIECE" if vehicle_type == "trailer" else "SALARY"   # 挂车按单计费、其余固定工资
```

**是钱**。往里塞 `box` / `flat` / `dump`，等于让「箱式车按什么算钱」变成一个
**从来没有人回答过**的问题；而答错了不报错，只会让某些司机从固定工资悄悄变成按单计费。
这正是规范 §三十三 第④条「同一个业务事实出现两个 Owner」要停下来重设计的形状，
所以本事项改成**另起一个字段**，而不是扩取值 —— 代价只是界面上多一行选择器，
收益是那条钱的口径一个字都没动（判据里有两条专门钉着它）。

### 属性清单（需求方逐条批准的那一张，**照它做**）

```text
所有车都有：车高(米)、车宽(米)、净重(吨)
          载重(吨) ⭐、容积(方) ⭐        ← 吨/方 对每一种型式都开放，见下
箱式车    ：车厢长(米)、车厢宽(米)、车厢高(米)
平板车    ：台面长(米)、台面宽(米)          ← 没有「台面高」（清单里就没有这一项）
自卸车    ：车斗长(米)、车斗宽(米)、车斗高(米)（容积在这一档叫「斗容」）
挂车      ：轴数(个)
```

⚠️ **一处解释性扩大，必须说清**：需求方给的清单里 `载重(吨)` 只写在平板车 / 自卸车 / 挂车下面、
`容积(方)` 只写在箱式车 / 自卸车 / 挂车下面。但他在同一段话里说了「**主要的是吨和方**这种计量单位」——
这两个是**任何一辆货车都有**的容量事实，缺了它，"一车 = 多少方"对某些车就凭空没有依据，
而那正是他要这些属性去干的事。所以本事项把吨/方放进**通用档**（仍然**选填**）。
⛔ 这是"**多给一个选填框**"，不是"改口径"：一个字节的钱都不在这里算。

### 「车厢长 / 台面长 / 车斗长」是**同一个事实**，所以是**一列**不是三列

它们都是"**载货区长**"，只是不同车的叫法不同。拆成三列之后，"这辆车载货区多长"会有
**三个 Owner**，改一处漏两处（规范 §三十三④）。所以库里是 `cargo_length_m` 一列，
**叫法**由 `services/vehicle_attrs.py` 按型式给（界面上显示"车厢长(米)"/"台面长(米)"/"车斗长(米)"）。

## ① 六问

① **解决什么问题？** 车辆台账现在只有「车牌 / 车型 / 挂的司机」三样，**没有任何一辆车自己的
   物理事实**。"一车 = 8 方"只能是一条**全库通用**的换算（`unit_conversions`），
   而现实里一辆 8 方、另一辆 12 方 —— 一条通用规则表达不出来。

② **当前用户 / 业务流程是什么？** 派单员在「车辆管理」里登记车辆（车牌 + 车型 + 绑司机），
   之后这辆车只会出现在司机的那张卡上。它**没有任何属性**。

③ **哪个现有事实或能力会发生变化？** `vehicles` 从"三样身份信息"变成
   "三样身份信息 + 一组这辆车自己的物理事实"。⛔ **既有三样一个字不改**。

④ **哪些明确不能变化？** 见 ② 节（Must Not Change）。

⑤ **属于 Core、Extension 还是 Infrastructure？**
   五问：①定义核心事实？**否**（车辆台账是主数据，但车辆属性不影响任何既有口径）
   ②改变核心不变量？**否** ③必须永久存在？**否** ④可能出现多个实现？**是**
   ⑤删除后 Core 是否仍成立？**是** ⇒ **Extension**。
   ⛔ 但它要**改线上库结构**（加 10 列），而那是 L3 —— 不是因为改了核心语义，
   是因为"改线上库结构"这个动作本身。

⑥ **什么证据能够证明它完成？** 见 ⑧：判据 107 项 + 反向验证 25 条 + 单测 32 条 +
   API 端到端 17 条 + 真机（模拟器 5554）6 条。

## ③ Boundary 与 L3 文书

**结论**：**EXTENSION IMPL（车辆台账的属性侧）+ L3 数据库迁移**。

### 要改库结构时的三问（L3 必答）

- **为什么现有 Extension 边界无法解决？** 不是边界问题，是**要加列**；
  而线上老库加列的唯一合法入口就是迁移（`app/migrations/`）——
  `migrations/README.md` 的分工：「正式变更走 migrations/、运行时自愈走 bootstrap」。
- **为什么必须动它？** 因为只有它能加列。⛔ 不是为了"方便"。
- **改完之后 Core 的不变量是什么？** **不变**。本事项不碰钱、不碰状态、不碰权限、
  不碰任何既有读写的出参口径（只是每辆车多回几个字段）。

### Old / New Invariant · Why · Migration · Compatibility · Regression · Rollback

```text
Old Invariant:  vehicles 只有身份三样（plate_no / vehicle_type / driver_id）+ 启停用；
                一辆车没有任何"它自己能装多少"的事实
New Invariant:  vehicles 多一组可空属性；「这辆车有什么属性」由 body_type 决定，
                判据是 vehicle_attrs.fields_for(body_type)，全项目只此一份
Why:            需求方「一车 = 多少方逐车不同」——一条全库通用的换算表达不出来；
                而属性是这辆车的事实，就该住在这辆车上
Migration:      app/migrations/010_vehicle_attrs.py：10 列，逐列判断幂等；
                body_type NOT NULL DEFAULT 空串（空串 = 未设置，是**正式取值**），
                其余 9 列可空。⛔ 不回填、不猜老车（与 009 那条「千万不要猜着补快照」同源）
Compatibility:  Compatible —— 纯新增可空列 + 纯新增可选入参；
                老客户端不传 body_type/attrs 时行为与今天**逐字节相同**
                （判据里有一条：AI 的 vehicle.update 只发 plate_no/vehicle_type/active，
                 不传 attrs = 不动属性）
Regression:     ① 既有 15 辆车读出来照旧（属性为空 = 没量过，卡片只是不显示那一行）；
                ② 车型（计费口径）的校验与取值不变；
                ③ 司机计费 / 运费模板 / resolve_billing_mode 一个字没动
Rollback:       删列即回到今天。属性不参与任何既有计算路径，数据零损失；
                唯一的损失是"已经量过的那些数"，所以回滚前先导一次 vehicles
```

答：**可以，而且就是用 Extension 解决的** —— 本事项没有往任何核心 service 里加判断，
新增的是一个纯函数模块 + 一个迁移。**动核心的只有"加列"这一个动作**，
而那个动作在架构上本来就只有一个合法入口。

## ④ Behavior Contract

```text
Input          （可选）body_type + attrs{属性键: 数值}
Output         这辆车能填哪些属性（按 body_type）、以及填过的值
Success        型式合法、每一项都属于这个型式、都是 > 0 且不超过上限 → 落库 + 写一条审计
Failure        型式认不出 / 键不认识 / 这一项不属于这个型式 / 不是数字 / ≤ 0 / 超上限
               → 400 + **一句能照着改的中文**（⛔ 不是 pydantic 的英文结构体）
Boundary Cases ① 完全不填属性（合法：没量过的车照样要能登记）
               ② 换型式时旧属性不属于新型式 → 400 并**点名是哪几项**，
                  在同一个请求里把属性改对即可（界面上是先剔除、并且说出剔除了什么）
               ③ 传空对象 attrs 为空 = 全部清空（⛔ 这正是不能用 is not None 判的原因）
               ④ 老车（body_type 为空）= 只能填通用那几项，不是错误
Side Effects   写 vehicles 会写一条 VEHICLE_UPSERT 审计日志（与既有 CRUD 同形），
               changes 里逐项写出"哪一项从多少改成多少"，清空也记（→（清空））
Authorization  沿用既有车辆台账的体内角色判断（仅派单员），⛔ 不新建权限点
Compatibility  Compatible：多两个可选入参 + 出参多三个字段
```

## ⑤ Data Contract

- **新增字段**：`vehicles.body_type`（VARCHAR(16) NOT NULL，缺省空串）+ 9 个属性列
  （`height_m` / `width_m` / `curb_weight_t` / `load_tons` / `volume_cubic` /
  `cargo_length_m` / `cargo_width_m` / `cargo_height_m` / `axle_count`）
- **Owner**：车辆台账。⛔ 不复制到订单/账本/司机上（要用的地方按 id 读这辆车）
- **什么时候写 / 不写**：建车时填；改车时**整份替换**（没写进去的清空）
- **是否允许 NULL**：允许，且 NULL 的语义是明确的「**这一项没量过**」，不是"忘了填"
- **历史数据怎么办**：现有车辆**全部留空**；⛔ 不许按车型猜一个容量出来
- **迁移 / Rollback**：见 ③
- **删除本功能后历史数据还能不能解释**：能 —— 删掉这 10 列，"这辆车"就回到只有身份三样，
  历史订单、账本、司机计费全都不依赖它

**真机证据（模拟器 5554，2026-09-28）**：

1. 卡片上出现**两个独立 chip**：「小货车」（车型）+「未设置」（车身型式）—— 老车照旧能读；
2. 新增车辆弹层：未选型式时**只有 5 项通用属性**（车高/车宽/净重/载重/容积）；
3. 选「箱式车」后**当场变成 8 项**，且叫法变成「车厢长(米)/车厢宽(米)/车厢高(米)」；
4. 填 车高 4 / 载重 12 / 容积 8 → 保存 → 卡片出现「**载重 12 吨 / 容积 8 方**」；
5. 再打开编辑 → 三项值**原样回填**（说明整份替换的往返是对的）；

## 留给下一件事（已经不在本事项范围内）

需求方那段话还有**后半截**没做：「我们在计算的时候**可以直接拉取这些属性，
然后直接进行单位换算**」。

那一步**不能顺手做**，因为它要先回答一个本事项回答不了的问题：

```text
「一车 = 多少方」——这一单算的是哪辆车？
  订单上没有车辆，只有司机；而车辆挂在司机名下（vehicles.driver_id）。
  ⇒ 是"按派单时那个司机当时名下的车"？还是"下单时先选车"？
     还是"每条商品行各自选一辆"？
```

三种答案会导出三种完全不同的接口与界面，而且会穿孔到下单页 / 订单卡片 / 订单明细 /
账本小卡**四个显示消费点** —— 按规范 §二十五（不许扩大战线）单独立案：

→ **`FEAT-0005` 车辆属性接进单位换算**（见 `docs/changes/FEAT-0005.md`）。
