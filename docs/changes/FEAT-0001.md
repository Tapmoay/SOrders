## ⓪ 需求方 2026-09-27 晚补充的口径（**本事项据此调整**）

> 「可以给一辆车**固定一个属性**。因为他不是有对应的车子吗，还有车牌，其实给这辆车固定属性，
>  他的属性是不是**不可能变**；也就是说，在**创建车辆的时候就需要填相应的属性**。
>  **不同的车型会需要填的属性是不同的**，比如说大车要填的大车属性不同；
>  挂车，他要填挂车的属性不同。别说有可能是个**平板车**、有可能是一个**自卸车**。」

⇒ 三句话把本事项从"换算率绑车"改成了**车辆台账的属性模型**：

| 需求方的话 | 落到设计上的意思 |
| --- | --- |
| 给一辆车固定一个**属性** | 属性挂在**车辆**上（不是挂在换算表上） |
| 属性**不可能变** | ⭐ 它是**建车时定下的事实**，不是随时可编辑的偏好设置 |
| **创建车辆时**就要填 | 新增车辆表单要按车型长出对应的输入项 |
| **不同车型填的属性不同** | 车型 → **属性集**不同（大车 / 挂车 / 平板车 / 自卸车各一套） |

⛔ **这否掉了我原来那版设计**（"给 `unit_conversions` 加一列 vehicle_id"）——
理由写在 ③ 里的那条偏离说明现在**作废**：需求方要的不是"换算率按车区分"，
而是"**车辆自己有一组属性**"。本事项按新口径重写。

### ⭐ 2026-09-27 深夜：需求方又补了两句，**L 级别定了**

> 「（车辆属性）**是要算钱的**。不过主要的一些是不会算的，主要的是**吨和方**这种
>  即便（计量）单位……我们在计算的时候**可以直接拉取这些属性，然后直接进行单位换算**。」

## ① 六问

① **解决什么问题？** 「单位换算」现在只有**一条全局规则**
（`unit_conversions`：from_unit / to_unit / factor）。而"一车 = 多少方"**逐车不同**
（用户原话：「这个一车是可以绑定的，绑某辆车」）—— 一辆 8 方、另一辆 12 方，
一条全局规则表达不出来。

② **当前用户 / 业务流程是什么？** 派单员 / 货主在「单位换算」页维护「1 车 = 8 方」；
下单页、订单卡片、订单详情、账本小卡四处按它显示「10 车 ≈ 80 方」。

③ **哪个现有事实或能力会发生变化？** `unit_conversions` 从"一对单位一条规则"
变成"一对单位**可以有多条规则，各自指定适用于哪辆车**"。

④ **哪些明确不能变化？** 见 ② 节。

⑤ **属于 Core、Extension 还是 Infrastructure？** 五问：①定义核心事实？**否**
②改变核心不变量？**否** ③必须永久存在？**否** ④可能出现多个实现？**是**
⑤删除后 Core 是否仍成立？**是** ⇒ ④⑤为是、①②③为否 ⇒ **Extension 候选**，
与既有 `unit_conversion` 扩展同一位置。
⛔ 但它要**改线上库结构**，而 `schema_bootstrap.py` 是核心区文件
（`_tools/qa/_core_files.txt`）⇒ Blast Radius 是 **L3**。

⑥ **什么证据能够证明它完成？** 见 ⑧：判据 + 反向验证 + 真机。

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

- **结论**：**EXTENSION IMPL（换算规则的数据侧）+ L3 迁移**。
- **⚠️ 与需求方口径的一处偏离，必须说清**：Q2 选的是「每辆车一个容量」，
  我实施成 **换算表加"适用车辆"一列**，而不是 **vehicles 加容量列**。理由：
  后者会让"一车等于多少方"出现**两个 Owner**（换算表一条通用 + 车辆一条容量），

  换算率本来就住在换算表里（已有 CRUD / 软删恢复 / 四个消费点 / 判据）。
  ⛔ 如果需求方要的是"容量登记在车辆台账上"，**说一声，本事项调整后再开工**。
- **要改 Core 时的三问**（L3 必答）：
  - 为什么现有 Extension 边界无法解决？—— 不是边界问题，是**要加一列**；
    而加列的唯一合法入口就是 `schema_bootstrap.py`（线上迁移唯一入口）。

  - 修改后 Core 的不变量是什么？—— **不变**。本事项不碰钱、不碰状态、不碰权限。

### Old Invariant / New Invariant / Why / Migration / Compatibility / Regression / Rollback

```text
Old Invariant:  (from_unit, to_unit) 在同一条"活着的"规则里唯一
New Invariant:  (from_unit, to_unit, vehicle_id) 唯一；vehicle_id 为 NULL 时按 (from_unit, to_unit) 唯一
Why:            用户「一车可以绑某辆车」——一车装多少逐车不同，一条全局规则表达不出来
Migration:      schema_bootstrap 加列（可空），现有行全部保持 NULL（= 通用）。
                ⛔ 不猜历史、不回填、不改历史
Compatibility:  Compatible —— 纯新增可空列；不传 vehicle_id 的老客户端行为完全不变
Regression:     既有全局规则仍能换算；四处消费点的输出逐字节不变
Rollback:       列可空且不参与任何既有计算路径 → 删列即回到今天（数据零损失）
```

- **核心改动声明行**（必须写在 `docs/AI_WORK_CLAIM.md`「进行中」）：
  「核心改动：backend/app/core/schema_bootstrap.py —— 为什么必须动核心：单位换算要按车辆区分，唯一合法加列入口」
- ⚠️ 这只是"干净核"的一行声明。它**不是**证据档文件（`socket_io.py` 才要写全四格）。

## ④ Behavior Contract

```text
Input          换算请求：from_unit / to_unit /（可选）vehicle_id
Output         命中规则的 factor（+ 这条规则绑的是哪辆车）
Success        指定了 vehicle_id → 用绑那辆车的那条；否则用通用那条
Failure        一条都没有 → 如实说"没有这条换算"，⛔ 不拿 1 或 0 顶
Boundary Cases 只有通用 / 只有车辆 / 两者都有（车辆优先）/ 两者都没有
               vehicle_id 指向已停用或已删的车 → 当作"没有这条"，退到通用
Side Effects   写 unit_conversions 会写一条审计日志（与既有 CRUD 同形）
Authorization  沿用既有 UnitOwner = shipper + dispatcher，⛔ 不新建权限点
Compatibility  Compatible：多一个可选入参；不传 = 今天的行为
```

## ⑤ Data Contract

- **新增字段**：`unit_conversions.vehicle_id`（整数、可空、引用 `vehicles.id`）
- **Owner**：单位换算（该表由它使用）。车辆是核心主数据，这里**只引用 id、不复制容量**
- **什么时候写 / 不写**：管理页选了车才写；不选就是 NULL（= 通用）
- **是否允许 NULL**：**允许**，且 NULL 是"通用"的正式语义，不是"没填"
- **历史数据怎么办**：现有行**全部保持 NULL**（它们本来就是全库通用那条）；
  ⛔ 不许按现在的规则猜某辆车该填什么
- **迁移 / Rollback**：见 ③ 的 Migration 与 Rollback
- **删除本功能后历史数据还能不能解释**：能 —— 删掉 vehicle_id 只是回到"一条通用规则"
