## ⑥ CHG 专章

### 病灶：结论对、明细错，而且**没有任何代码在算这个明细**

模型拿到的是**原始行**，它自己在回答里拼了一份"退货红冲 8 笔：−431.50"。拼错的机制有两层：

1. **按单拼**：它先按订单号把行归堆，再决定哪些算"退货红冲"。窗口里 10 笔行里，有 2 笔（450/451）挂在**已软删**的单上 ——
   模型的 `orders.list` 里没有这两张单（回收站里的单不进已送达清单），于是它按单拼出来的明细里就"少了两笔"，
   而它并不知道自己少了两笔（它以为明细就是全部）。
2. **口径没说**：即使它把 10 笔都列出来，用户拿库里的原始数据核对时仍会问"为什么这 2 笔你的账本里没有"。
   库里的规则是 `ledger_scope.visible_ledger_clause()`：**进了回收站的单整条排除**，那种单的 ORDER 行与 RETURN 行
   成对存在、净额 0 —— 两边都不计。这层口径从来没有哪一句话讲给用户听过。

### 这次怎么做的（三件事，都在代码里）

1. **明细由代码算**：runner 按 `来源` 把 `ledger.list_entries` 的行分组，算好每组的笔数与金额（`ledger_detail`），
   再把 `source = return` 那一档单拎出来：笔数、金额、逐行明细（订单号 / 日期 / 金额 / 商品 / 货主）、
   以及**哪些是整单退**（订单号不在本次已送达清单里 ⇒ 整单退；在 ⇒ 部分退）。模型只负责把这份算好的明细讲出来。
2. **口径由代码给**：`const val SCOPE_NOTE` —— "只算**没进回收站**的单的账。进了回收站（已删除）的单，它的自动行与
   退货红冲行在库里成对存在、净额 0，账本与营业额两边都不计 —— 拿库里的原始数据核对时笔数会对不上，**那不是漏账**"。
   这一句话既进结论（只查全时），也作为 `scope_note` 键交给模型。
3. **纪律进提示词**（第 13 条接三行）：明细照 `ledger_detail` / `returns` 说、⛔ 不许自己按单拼明细、不许自己加总；
   有人核对笔数时先讲 `scope_note` 那条口径。

另：`core/LedgerSourceLabel.kt` 原来只认得 `order / manual / refund`，`return` 会**原样透传**成英文 ——
账本图例与 AI 记账卡上都会露出 `return`。这一档补上（`"return" -> "退货红冲"`），并且判据**禁止**执行器里再抄一份来源表。

### 判据与反验（这一单的红线，坏一处就必须红）

- 判据第 12 节（`_check_ai_workflow.py`）：分组、四键、来源中文走唯一那份表、`bySource[SOURCE_RETURN]`、
  `sumMoney` 合计、`isWholeOrderReturn(row, seen)` 与 `return no !in seen`、逐行五键、`const val SCOPE_NOTE` 与
  口径正文（没进回收站 / 成对存在、净额 0 / 那不是漏账）、`val conclusion = if (incomplete) … else … + returnsCn + SCOPE_NOTE`、
  6 个新键、提示词三行纪律、`"return" -> "退货红冲"`、4 个单测档位；**以及 absente 检查：执行器里不许出现第二份来源表**。
- 反验 14 条注入：明细不再按来源分组 / 来源名另抄一份 / 退货红冲不单拎 / 整单退货改成猜的 / 口径掏空 /
  「那不是漏账」删掉 / 没查全也照样说明细 / 不再交 `ledger_detail` / 不再交 `scope_note` / 提示词纪律删掉 /
  来源表删 `return` / `BUG-0019.md` 缺一节 / 登记簿改单号 / 工作声明改单号。
