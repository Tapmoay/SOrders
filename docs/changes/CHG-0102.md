① CHG-0101 把整套配色换成了用户三张参考图里的低饱和雾感色。换完之后用户看着真机说了一句
（`m04527`，逐字）：

> 「呃我觉得饱和度还是太低了一点不也不说饱和度吧，应该说太灰了一点。整天都饱和度或者说
> 是明度吧，应该叫做明度。他们并不是完全都是一致的只是在一个区间内。就像是色彩理论一样
> 啊，我们现在一看好看的话，它所有的呃比如说我们一般评价一个画它比较偏低，饱和但是整体
> 的色调又统一且看的舒适是这样子的这样，它又是怎么做到的呢？我们就以工作台的所有那些功能
> 的图标为例子，你做一份简单的html样式做给我看并且最后呃发送给我网站地址」

**量出来之后发现他的判断比"整体太灰"更准**：CHG-0101 那 19 格的明度极差只有 25.6（比
CHG-0091 的 51.8 已经好很多），但彩度从 **8.1 到 58.4** —— 最灰的 `账户管理 #97897F` 只用到
它那个色相在那个明度下能给到的 **11%**，最艳的 `消息中心 #CA454E` 用到 **58.4**，
**同屏差 7.2 倍**。所以病根不是"整体发灰"，是**灰的特别灰、艳的还挺艳** —— 也就是他说的
"他们并不是完全都是一致的，只是在一个区间内"。

要的是：**低饱和，但同一屏里每一格都还有颜色，而且颜色之间的"浓淡"落在同一个区间里**。

② 用户实际怎么用：派单员 / 货主 / 司机三端各自打开工作台（19 格 / 7 格 / 2 格宫格），
靠**颜色**找功能（`ModulesEntryTest.kt:92-93` 写明了这条定位规则：「老人靠颜色找功能」）；
同一屏里相邻的格子必须一眼分得开，否则"一色一功能"这条定位手段就失效了。

③ 变的是**值的集合**，不是组织方式：

- `Color.kt` 里 **12 个模块语义 token** 换值（`MgrGreen` / `ProgressYellow` / `ShipperTeal` /
  `MemberGold` / `ProductPurple` / `InventoryTeal` / `MoneyOrange` / `ArrearsTangerine` /
  `ReportIndigo` / `MessageRed` / `AccountBrown` / `DriverLime`），外加 **4 个派生值**
  （`DestOrange` / `SuccessGreen` / `Success` / `Tertiary`）。
- `ui/nav/Modules.kt` 里三张表逐格的 `color =`（派单端 8 个字面量 ＋ 账本页 7 格 ＋ 货主端 7 格）。
- `ui/**/*.kt` 里 **30 个文件 166 处**写死在用色处的同一批色值（`ReportCenter.kt` 一个大户）。
- 新增一页一档的**机器判据**（`PaletteUniformity.kt` ＋ `PaletteUniformityTest.kt`）。

**token 的名字、数量、引用关系一个都不动**（`NavBlue = ThemeGreen`、`InfoBlue = ThemeGreen`
这类别名继续成立，`AiTone*` 四个别名也继续成立）。

④ 明确不能变：

| 1 | `ThemeGreen = 0xFF8B4A4A`（主操作色）及其族 | 那是用户第一张图**亲手画的**主操作色，白字对比度 6.61:1，CHG-0101 的核心成果 |

## ③ Boundary（Core / Extension / Infrastructure / Presentation）

**结论：全部落在 Presentation。**

- `ui/theme/Color.kt` / `ui/nav/Modules.kt` / `ui/**/*.kt` 全是 Compose 渲染层。
- `ui/theme/PaletteUniformity.kt` 是**纯函数**（不 import `android.*`，JVM 单测直接跑得起来）——
  它是"给判据用的量尺"，不是业务逻辑；**为什么不是 Extension**：Extension 是为业务加能力，
  这里没有新能力，只有"把已有的颜色量一遍"。
- **为什么不是 Core**：没有任何领域规则变化，`core/` 目录一行未动。
- **为什么不是 Infrastructure**：不碰后端、不碰数据库、不碰构建与发布。
- 唯一跨界的一点：`ProductCardKit.DEFAULT_PRODUCT_NAME_COLOR` 是**数据兜底值**
  （后端没给 `name_color` 时新渲染用的），改的是"以后新渲染长什么样"，
  **库里已有的值一个字节不动**（见 ⑤）。

## ⑥ CHG 专章

### Before

- CHG-0101 那套：19 格 L\* 47.4~73.1（极差 **25.6**）、C\* **8.1~58.4**（差 **7.2 倍**）。
- `账户管理 #97897F` 在它那个色相那个明度下只用到 **11%** 的可用彩度 —— 屏幕上就是一块灰。
- 用户在真机上看到之后说「太灰了一点」；同时又提醒"他们并不是完全都是一致的，只是在一个
  区间内"。

### After

- **H 档**（用户在页面上从三档里点名的那一档）：**相对彩度 0.62 / 明度带 58±5 / 彩度夹 28~44**，
  生成口径 `C = min(max(0.62 × C*max(L, h), 28), 44, C*max × 0.94)`。
- 19 格 L\* 52.9~63.0（极差 **10.0**）、C\* **27.9~44.2**（差 **1.58 倍**）。
- 色相去重：把间隔 <20° 的相邻色相推开（最多 ±11°，19 格里推了 **17 格**）——
  原来 `退货申请` 36.4° 与 `挂账单位` 39.1° **只差 2.7°**，靠彩度差撑着，彩度一拉平必然撞。
- 两张子表的硬约束**继续满足**：账本页 7 格最差 **67.2**（≥60）、货主端 AI 与其它格最差 **60.7**（≥60）。
- `Color.kt` 16 处、`Modules.kt` 46 处、`ui/**/*.kt` 30 文件 166 处，全部落地；
  CHG-0101 那 30 个色值**全仓一处不留**。

### Must Preserve

- `ThemeGreen = 0xFF8B4A4A` 与其族；暖砂白四层；`SheetSurface`；AI 品牌三色；
  token 的名字 / 数量 / 别名关系；`ModulesEntryTest` 的两条 ≥60；暗色主题。

### 为什么改这几处就够

语义色走 token ⇒ 换 token 就换掉全 App；**但模块身份色只能逐格换**，
而真正的第二半是 `ui/**/*.kt` 里 **166 处写死的色值** —— 只换 token 会一半新一半旧
（CHG-0101 已经吃过这个亏：`ReportCenter.kt` 一个文件 75 处）。
