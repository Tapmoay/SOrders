## ④ Behavior Contract

```text
Input      : 派单员在五个名册页选中某一类；或在名册面板建/改名/排序/删一个分类；
             或在账号/车辆表单里选一格分类（可以现场新建）。
Output     : 左栏（抽屉）里那一格高亮；列表只剩这一类；名册面板里那一行带上「N 个账号 / N 辆车」；
             账号/车辆详情里 `category` 回显。
Success    : 200/201/204；选中格立刻生效（本地过滤，不往返后端）；
             建号/建车带了一个名册里没有的分类名 → 自动补进名册（排到最后）。
Failure    : 重名 409「分类「X」已经存在了」；超过 200 个 400「分类最多 200 个，请先清理一些」；
             排序少传一行 400（`ordered_ids` 说清少了几个）；删还有东西挂着的分类 400
             「还有 N 个账号挂在这个分类下，先把它们改成别的分类（或改个名）再删」；
             非派单员写 403（读 200）；非派单员改账号分类 403「仅派单员可修改账号分类」。
Boundary   : 空串 = 未分类（选中「全部」= 不过滤，与「未分类」不是同一件事）；
             账号名册的「在用」**不含回收站**（号码带 `_del{id}` 后缀的那些），
             车辆名册的「在用」**含停用的车** —— 两套口径故意相反，各自写在端点注释与单测里；
             名册里没有的分类名不是错误（老数据、别的路径写进去的），列表照样要显示它。
Side Effects: 三个写动作各写一条审计日志（USER_CATEGORY_* / VEHICLE_CATEGORY_*）；
             改名是**一项事务**：名册行与所有挂着的账号/车辆一起改（含回收站里的账号）。
Authorization: 写 = `Permission.USER_MANAGE`（今天只有派单员有这个点）；读 = 登录即可。
Compatibility: 只加列与加表，老客户端不受影响；`category` 缺省空串。
```


**最后一个问题**：回滚之后，哪些历史事实必须保持不变？

答：① 账号与车辆的既有字段（手机号、角色、车型、车身型式、属性、司机关联、启用状态）一个都不能变；

「谁在什么时候把这一类改成了什么」，回滚代码不该抹掉历史）；
③ 分类列里的值可以留着（老代码读不到它、也不受影响），但**不许**因为回滚就把它清空或改写。
