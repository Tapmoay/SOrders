① 一句话：**被取消的那一趟取数把「协程被取消」当成业务失败写进了页面级 error，渲染门当场把整个列表顶掉。**
机制是两件事叠起来：`load()` 里 `loadJob?.cancel()` 之后，被取消的那一趟**仍然会跑完它的 catch** ——
`CancellationException` 正是 `Exception` 的子类，于是「取消」被当成业务失败写进 `error`（改前
`DriverOrdersViewModel.kt:326`）；而取数**不在主线程上返回**（OkHttp 的回调从网络线程续回主线程），
那个 catch 于是**排在新一趟的 `error = null` 之后**落地 —— 页面级 error 一旦有值，

| 层 | 这一单动了什么 | 为什么它在这层 |
|---|---|---|
| Core | **零** | 全仓唯一的取数入口 `AppRepository`、推送源 `RealtimeHub`、`AppContainer` 都不需要动：这件事只跟「这一页怎么落笔」有关 |

| Infrastructure | `_tools/qa/_check_cancellation_not_error.py`（五组 23 项）＋ `_tools/qa/_reverse_verify_cancellation_not_error.py`（13 条注入） | 判据与反验是机器可跑的检查设施，不参与业务；写它们是为了让「取消不是失败」这条**时序**红线以后坏一处就当场红 |
| Presentation | `ui/driver/DriverOrdersViewModel.kt` 一处（`load()` 的落点判定 ＋ 取数接缝）；单测与两行测试依赖 | 屏幕上是这一页被顶掉，落笔的判定也只能在这一页的 ViewModel 里做（`DriverOrdersScreen.kt` 一个字节不动） |

### R4-BOUNDARY-JUSTIFICATION：为什么边界解决不了这件事

1. **「取消」是协程自己的信号，外围拦不住、也不该拦。** 在 Screen 层按字符串过滤（把这句异常串认出来、不当成错误）
   等于把**异常文案当协议**：换一个协程实现或换一处调度器，串就变了，而且真失败的文案也在同一格。
   只有产生这个 catch 的那一层才知道「这一趟是被谁打断的」—— 所以取消分支只能加在 `load()` 里。
2. **只加取消分支还不够。** 真机证据里这个 catch 之所以能留在屏上，是因为它**排在新一趟的 `error = null` 之后**落地
   （取数从网络回调续回主线程）。所以同一个窗口里必须有「谁能让页面动」的判据 —— 光加 `catch (CancellationException)`
   堵不住「过期那趟**没**被取消、只是回来得晚」那一格（契约 ③：晚失败也不许盖掉新结果）。
3. **不能靠「把取数挪到 IO 调度器上」解决。** 那是把**触发条件**改掉，不是把**落点判定**改对：真机上取数就是从网络回调
   续回主线程的；而且 `data/` 下全仓没有一处 `withContext` —— 顺手加一个等于改数据层的线程语义，
   超出 L1 半径（也超出这一单的授权范围）。判据把这条写成红线。

## ④ Behavior Contract

```text
取数（DriverOrdersViewModel.load() —— 司机端「我的订单」页；三个调用点：init / 顶部刷新与错误页「重试」/ 实时推送收集器）
- 打断：新一次 load() 会先 loadJob?.cancel() 掉旧的那一趟（这个打断语义**保留**）
  被取消的那一趟 ⇒ **静默结束**：不写 error、不闪错误页、不把新一趟的 loading / refreshing 收掉
  新那一趟 ⇒ 照常 loading / 取数 / 写 orders 与 ordersTab
- 真正的失败（网络断、HTTP 4xx/5xx、解析失败）⇒ 照旧：error = toApiException(e).message，屏上显示错误页 ＋「重试」，
  点「重试」＝ vm.load()（这条**不许改差**）
- 过期（没被取消、只是回来得晚）的那一趟 ⇒ **不写任何状态**：
  成功回来的数据不覆盖新结果（成功路径守卫）／失败回来的错误不覆盖新结果（通用 catch 里的守卫）／
  finally 不收新一趟的加载态（if (mySeq == loadSeq)）
- 世代号在**挂起点之前**取（loadJob?.cancel() 之后、viewModelScope.launch 之前）：
  viewModelScope.launch 在 Dispatchers.Main.immediate 下**可能当场内联执行**，那一刻 loadJob 还指着**旧** Job ——
  按 Job 同一性判「我是不是当前那一趟」会当场判错
- 顺序不变：写 orders 与写 ordersTab 仍然**相邻**（中间不许出现任何挂起点）

边界与近似（如实说）
- 这一条只解决「落点判定」：loadJob?.cancel() 的打断语义、取数在哪条线程上返回、推送要不要节流，本单一律不动。
- 世代号是 Int、只在主线程上递增（load() 的三个调用点都在主线程）：**不需要**原子类型；也不跨进程、不落盘。
- 「只有当前那一趟能写状态」**不等于**「最后一次点的一定赢」：两次取数都在飞、都成功时，屏幕上是**最后落地**的那一趟 ——
  本单保证的是**过期的那一趟不写**，不是「按点击顺序决胜」（那需要另一套取消/去重契约）。
```

## ⑥ CHG 专章

### 病灶：取消被当成失败，而且那一趟还能抢在新一趟之后落地

改前 `android/app/src/main/java/com/tapmoay/sorders/ui/driver/DriverOrdersViewModel.kt:304-333`
（`git show HEAD:android/app/src/main/java/com/tapmoay/sorders/ui/driver/DriverOrdersViewModel.kt` 可逐字复核）：

```kotlin
    fun load() {
        loadJob?.cancel()
        // ⚠️ **在挂起点之前**把"这一趟是给哪一栏取的"钉死：取数期间用户又切了一次 tab 的话，
        //    拿回来的是**旧那一栏**的数据 —— 那时若按新 tab 记 [ordersTab]，就又把两件事混成一件。
        val wanted = tab
        loadJob = viewModelScope.launch {
            loading = orders.isEmpty()
            error = null
            try {
                val statuses = if (wanted == 0) OrderStatusModel.DRIVER_OPEN else FINISHED_STATUSES
                val fetched = statuses
                    .flatMap { container.repo.orders(status = it, dateFrom = if (wanted == 1) dateFrom else null, dateTo = if (wanted == 1) dateTo else null) }
                    .sortedByDescending { it.createdAt }
                // ⚠️ 这两句**必须相邻**（中间不许出现任何挂起点）：orders 与 [ordersTab] 是同一个事实的两半
                orders = fetched
                ordersTab = wanted
            } catch (e: Exception) {
                error = toApiException(e).message
            } finally {
                loading = false
                refreshing = false
            }
        }
    }
```

**`catch (e: Exception)` 是这一单的全部病灶**：`CancellationException` 是 `Exception` 的子类，
所以「被新一次取数 / 推送打断」这条**正常**结局从这里流进了页面级 `error`；而 `finally` 无条件收加载态，
于是过期那趟还能把新一趟的转圈一起关掉。真机上看到的就是这两件事的合成：
`DriverOrdersScreen.kt:104` 的 `vm.error != null -> ErrorView(vm.error.orEmpty(), onRetry = { vm.load() })`
把列表整页顶成四行（dump 原文 `_tmp/test_round3/evidence_ta04_before.txt`）。

### 这次怎么做的

1. **取数接缝（只为可测，不改语义）**：`DriverOrdersViewModel` 的构造加两个带默认值的参数 ——
   `fetchOrders: suspend (wanted: Int, from: String?, to: String?) -> List<OrderDto>`（默认实现就是原来那两句
   `container.repo.orders(...)` 的 flatMap + 排序）与 `refreshSignals: Flow<Unit>`（默认 `container.realtimeHub.refreshOrders`），
   `init` 改成 `viewModelScope.launch { refreshSignals.collect { load() } }`。
   为什么必须开这个口子：JVM 单测里造不出 `AppContainer`（构造函数就求值 `context.applicationContext`，
   而且 `appScope = CoroutineScope(SupervisorJob() + Dispatchers.Main.immediate)` 是**急切**初始化），
   仓库既有先例是 `ai/AiAgentLoopTest.kt` 的 `FakeTransport` 接缝。接缝只是把真实来源换成替身，**判定逻辑一个字没换**。
2. **世代号（契约 ③ 的落点判定）**：`private var loadSeq = 0`（`:122`）；`load()` 里
   `loadJob?.cancel()` 之后立刻 `val mySeq = ++loadSeq`（`:353`，**在挂起点之前**）。
   为什么不按「`loadJob` 是不是我」判：`viewModelScope.launch` 在 `Dispatchers.Main.immediate` 下可能
   **当场内联执行**，那一刻 `loadJob` 还指着**旧** Job，拿它判会当场判错；世代号在 `launch` 之前取，与调度器怎么排无关。
3. **取消不是失败**：`catch (e: CancellationException) { throw e }` 排在通用 `catch (e: Exception)` **之前**（`:370-376`），
   原样重抛（协程的取消靠它传播）—— 与仓库既有惯例一致（`ui/shipper/ShipperOrdersViewModel.kt:188` 同一写法，
   那句注释原文：「本项目栽过一次同类坑：把 CancellationException 当成业务失败」）。
4. **三处守卫**：成功路径写 `orders / ordersTab` 之前 `if (mySeq != loadSeq) return@launch`（`:364`）；
   通用 catch 写 `error` 之前同一道守卫（`:380`）；`finally` 里 `if (mySeq == loadSeq)` 才收
   `loading / refreshing`（`:385-388`）。
5. **测试依赖**：`android/gradle/libs.versions.toml` 与 `android/app/build.gradle.kts` 各一行（`kotlinx-coroutines-test`，
   版本跟既有的 `coroutines = "1.10.1"`）；仓库此前**没有任何**单测用过 TestDispatcher（全仓 0 处 `runTest` /
   `Dispatchers.setMain`，也**没有任何一个测试构造过 ViewModel**），本单是第一次 —— 用 `StandardTestDispatcher` 把
   「取数挂在别的调度器上」造出来（正是探针里唯一看得见这一格的形状）。
6. **钉住**：单测 3 档（`DriverOrdersLoadCancelTest.kt`）；判据 `_tools/qa/_check_cancellation_not_error.py`（五组 23 项）；
   反验 `_tools/qa/_reverse_verify_cancellation_not_error.py`（13 条注入）。
