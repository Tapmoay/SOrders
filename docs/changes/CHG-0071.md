① 用户要「**商品可以打折、订单可以打折**」，并且「**对应的商品可以固定价格，就是不参与打折**」（原话 ref **m01280**，逐字：「我们要加个新功能就是商品可以打折，就是订单它可以给订单进行打折，然后我们对应的商品是可以固定价格的，就是不参与打折。」）。今天系统里**没有任何一处能打折**：改单只能改地址 / 收货人 / 备注，改价只能改商品档案或批发商专属价（那是**永久价**，不是一次促销）。商家要抹零、要减 10%，今天只能靠改商品单价 —— 而那会改到**所有人的报价**，且看不出「这一单为什么便宜」。

② 今天的业务流程：货主 / 批发商下单（价格由 `PriceRule` 专属价或商品默认价**唯一决定**，下单页没有单价输入框）→ 派单员在「订单管理 → 编辑」里改地址 / 收货人 / 备注（`PATCH /orders/{id}`，`Permission.ORDER_EDIT`）→ 派单 / 送达 / 收款 / 退货。**收款与毛利全部按行金额（`order_products.line_total`）算**：`backend/app/services/order_money.py:134-136`，`goods_amount = Σ line_total`，账本 / 营业额 / 毛利都读它。

③ 变化的现有事实有两处：**（a）行金额 `line_total` 不再是「单价 × 数量」** —— 折扣不摊到行，`goods_amount = Σ line_total` 这条恒等式当场破（这正是台账否掉变体 B 的理由）；**（b）退货金额**从「按 `unit_price` 退」改成「**按折后实付退**」（口径补充 **m13365**）。另外多出两个快照事实：这一单**打了什么折、谁在什么时候打的、为什么**，以及商品级的「不参与打折」。

④ 明确不能变（逐条见 §②）：报价体系（`price_rules` 的专属价 / `OrderCreateViewModel.priceFor`）一个字不动；`canChargeToArrears` / `canSettle` 等既有谓词与挂账、核销、收款单、资金流水全部不动；**下单与货主自助那一侧不许出现打折**（`price_rules.py` 不许被当成折扣的落点 —— 那是把一次性促销写成永久价）；历史订单的行金额、账本、审计一律不改写。

⑤ 结论 **EXTENSION IMPL ＋ 数据契约（贴着 Core 的订单金额）**：折扣算法本身是**一份实现**（`services/order_discount.py`），但它写的是核心事实 `order_products.line_total`（`docs/R4_CORE_EXTENSION_MAP.md` 里行金额归订单金额的口径）。因此本单按 **L2** 做，并遵守「行金额只能由**一处**算出来」这条既有纪律。

⑥ 证据（细节见 §⑦ / §⑧）：① 新判据 `python _tools/qa/_check_order_discount.py` 必须能判红，配 `_tools/qa/_reverse_verify_order_discount.py` 逐条破坏；② 四条口径的机器可验形态（整单 / 勾选两档 × percent / amount 两种、理由进日志、退货按折后实付退、`no_discount` 的商品不许被勾进折扣）；③ 全量 `_check_all.py` ＋ `check_reachability.py` ＋ gradle 编译 / 单测；④ 真机 emulator-5554 打折前后的对照截图。

- **结论**：EXTENSION IMPL ＋ 数据契约（贴着 Core 的订单金额口径，故按 L2 走）

## ④ Behavior Contract

```text
Input          派单员对一单调 POST /orders/{order_id}/discount，body = {kind: "percent" | "amount", value, line_ids: [订单行 id]（空 = 整单）, reason?}；或 DELETE /orders/{order_id}/discount（取消这一单的折扣）。
Output         折扣后的 OrderOut（行金额已写成折后值）＋ orders 上的七个折扣快照列。
Success        行金额按折扣重算：percent = 按比例减（抹到分）、amount = 总额抹零（余额摊到参与行，保证 Σ 行金额 = 折后总额）；订单详情显示「已优惠 ¥X（减 10% / 抹零 ¥X）」与操作人 / 时刻；write_log 记 kind / value / 金额 / 范围 / 理由。
Failure        （失败时**不**发生什么）金额非法（percent 不在 0~100 / amount <= 0）、勾了不参与打折的商品、空范围、终态单（DELIVERED / CANCELLED / RETURNED）、已收款单 —— 一律 4xx 且**行金额与 orders 一个字节都不改**（整条事务回滚，不留「改了一半」的单）。
Boundary Cases ① 折扣后某一行为 0 元（抹零把整单抹平）② 参与行只有一行 / 全部行 ③ 折后金额出现半分（按分四舍五入 + 余数摊回）④ 整单折扣后再改成只勾一行 ⑤ 打了折的单再改数量 / 单价（折扣必须跟着重算，不许被「单价 × 数量」抹掉）⑥ 打了折的行退货（按折后实付退）⑦ 取消折扣后行金额回到 单价 × 数量 ⑧ 商品在打折之后才被标成「不参与打折」——**已发生的折扣不回溯**，下一单才生效
Authorization  `Permission.ORDER_EDIT`（沿用派单员改单那一扇门，⛔ 不新建权限点）
Compatibility  Compatible —— 新端点、新列（可空 / 有默认值）；老客户端不发这两条请求；老订单 `discount_kind IS NULL` 即「没打过折」，行为与今天逐字一致。
```

## ⑤ Data Contract

- **新增/改动哪些字段**：
  - `orders`（七个折扣快照列）：`discount_kind` VARCHAR(16)（`percent` / `amount`）、`discount_value` NUMERIC(14,4)（10 = 减 10% / 3.50 = 抹 3.50）、`discount_amount` NUMERIC(14,4)（**这次一共减了多少钱**，快照）、`discount_lines` JSON（**数组**，每项 `{"line_id": …, "before": "…", "after": "…"}` —— 参与行 / 打折前金额 / 打折后金额，金额存**字符串**以免 JSON 的 float 改写 NUMERIC 精度；整单就是全部行）、`discount_reason` VARCHAR(255)、`discount_by_id` INT、`discount_at` DATETIME。
  - `products`：`no_discount` BOOLEAN NOT NULL DEFAULT 0（先例：同文件 `:25 is_active`）。
  - `order_products.line_total`：**字段没变，写法变了** —— 折扣生效的那些行写折后值。
- **Owner 是谁**：`order_products.line_total` 与订单金额口径的 Owner 是**订单金额（Core）**（`docs/R4_CORE_EXTENSION_MAP.md` §3/§4）；折扣算法与七个快照列的 Owner 是本实现（`services/order_discount.py`）；`products.no_discount` 的 Owner 是商品主数据（与 `is_active` 同一位）。
- **什么时候写 / 什么时候不写**：只在 `POST /orders/{order_id}/discount` 与 `DELETE …` 里写；没打折的订单**七个列全是 NULL**（⛔ 不写 0 —— 0 会被读成「打过折但减了 0 元」）；改地址 / 备注 / 派单 / 收款 / 送达一律不碰它们。
- **是否允许 NULL**：允许（未打折 = NULL）；`no_discount` 非空、默认 0。
- **历史数据怎么办**：历史订单七个列全 NULL =「这一单没打过折」，**不回溯、不补算**。⛔ 不许把今天才有的折扣规则套到昨天的单上。
- **迁移怎么做 / Rollback 怎么办**：走**正式迁移** `backend/app/migrations/025_order_discount.py`（VERSION 25；`create_all` 建新库、老库在这条迁移里 `ALTER TABLE`，先例 `009_freight_rule_snapshot` / `024_product_visibility_targets`）。⛔ **不写** `core/schema_bootstrap.py` —— 那份文件只管「运行时自愈」，加列是正式变更（`_check_silent_release.py` 第 5 条钉着这条分工；025 的 docstring 里写了为什么不两边都写）。Rollback = 撤掉代码后列留着不管（新列全是 NULL，老代码不读它们）。
- **删除本功能后历史数据还能不能解释**：能 —— 「行金额 = 当时成交的钱」这条读法不变，折扣快照列就是当时的 provenance。

## ⑥ CHG 专章（FEAT / GOV 不适用时写「不适用：<理由>」）

### Before

派单员想给一单便宜 10 元，今天只有三条路，三条都坏：**（a）** 去商品档案改单价 —— 改的是**所有人的报价**，下一单、别人那一单全跟着变，而且看不出这一单为什么便宜；**（b）** 给批发商配 `price_rules` 专属价 —— 那是**永久价**，等于把一次促销写死进报价体系，还会影响他以后每一单；**（c）** 什么都不做 —— 账上多收他 10 元，商家自己去线下找补。系统里**没有任何字段**记录「这一单打了折、减了多少、谁批的、为什么」，退货时也只能按原单价退（多退给客户）。

### After

派单员在「订单管理 → 编辑」弹窗底部多一块**折扣**：

- **范围**：整单（默认）／只打勾选的行 —— 勾选列表里**标了「不参与打折」的商品不可选**（灰掉并写明理由）；
- **方式**：**减百分比**（10 = 减 10%）／**抹零**（减一个金额，如 3.50）；
- **理由**：选填一句话（如「老客户抹零」）。

点「应用折扣」→ 那几行的行金额变成**折后实付**（整单折扣就摊到每一行），订单金额跟着变，订单详情出现一行「**已优惠 ¥X（减 10% / 抹零 ¥X）· 理由 · 张三 10-07 06:4x**」。操作日志（`write_log`）记下这次折扣的 kind / value / 金额 / 范围 / 理由。取消折扣（`DELETE`）把行金额还原成「单价 × 数量」。此后这一单的**收款、账本、毛利、退货全都按折后实付走**（退货按折后单价退，不多退）。

### Must Preserve

```text
- 历史订单 / 历史金额 / 已冻结的 Pricing Fact
- 历史 Provenance / Audit / Ledger
- 权限
- API compatibility
- 报价体系：price_rules 专属价与 OrderCreateViewModel.priceFor（下单页仍无单价输入框）
- goods_amount = Σ 商品行 line_total、goods − returned = (settled − refunded) + arrears 两条恒等式
- 挂账 / 核销 / 收款单 / 资金流水 / 账本入账的实现与话术
```

### Blast Radius（L0～L3）

**L2** —— 动到**表的列**（`orders` 七列 ＋ `products.no_discount`）、**钱的算法**（行金额的第三种来源）与**退货口径**（按折后实付退），并且算法要在四个「重算行金额」的站点保持一致。⛔ 但**不碰核心区文件**、不改任何恒等式、不改权限体系、不改历史数据。
