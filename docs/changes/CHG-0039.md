# CHG-0039 · 派单池加「已完成派单」分页（按司机分组）+ 派单员可把已派的单静默退回派单池（货主端无感）

> **用户原话（语音转写）**：「在派单词（=派单池）再加一个分页为**已完成派单**，这个已完成派单跟派单词是一样的。但是有一点不（=不同），就是拍（=派）单完成之后，他会进入到这里订单」「派单员可以对订单进行修改…**司机一个卡片是一个司机，然后司机里面有很多小卡片，小卡片就是订单**，然后派单员可以点进去，对这些订单进行修改」「比如说一个司机接了 2 个货主的订单，他同时送 2 个货主，派单员可以将某一个货主调整为一个货主…这些货物先送这个货主的」「如果是这样操作的话，那**原来的那个货主的货物就会重新回到派单池**，然后派单员又可以重新对这个派单进行操作、进行派单」「**这一点要注意**：这个操作**货主端是不会显示的** —— 货主端如果派单了之后，派单员执行这个操作，货主端仍然会显示状态为**已派单**或者说**司机已接单**；订单的状态会**默默**发生改变，**不会有任何的消息提醒**。这个操作**只限于派单员**，货主不会有任何的交易提醒，而且**货主也不需要知道这个**」。
>
> ⇒ 这是两条同源的诉求：① 派单池多一档「已完成派单」，读法＝按司机分组（一个司机一张卡，卡里是订单小行）；② 派单员把某张已派的单**退回派单池**（司机立刻看不到），而**货主端一个字都不变**。
> ⇒ 第 ② 条动了订单状态跃迁（已派单 / 已接单 → 待派单）、新增一列库结构、新增一个端点 ⇒ 按规范 §二十六，本事项是 **L3**（Order Lifecycle + Database Schema + Authorization 边界），走规范 §二十七 的正式变更审查。

**① 我要解决什么问题？**
派单池只有一档「待派单」：单一旦派出去就从这个列表里消失，派单员再也看不到「我派出去的单现在都在谁手上」，也就没有任何入口把一张派错的单**收回来**（唯一的 `recall` 会把整张单撤回并**通知货主**，用它来做「司机带太多单，先退一张回头再派」会把一件内部调度的事变成货主可见的事件）。
⇒ 要解决的是两件事：**看得见**（已派的单按司机分组列出来）与**取得回**（退回派单池，且货主端无感、零提醒）。

**② 当前用户 / 业务流程是什么？**
派单员在「派单作业 → 待派单池」里逐单派给司机；司机接单后在「我的订单」里看到；货主在自己的「我的订单」里看到「已派单 / 已接单」，并会收到 `orders.revoked` 这条站内信（撤回时）。
派单员的实际作业是**批量**的：一位司机一次带好几张单，路上发现带不动了，需要把其中一张退回来**当天再派给别人** —— 而这件事在今天的系统里没有落点。

**③ 哪个现有事实或能力会发生变化？**
- 订单状态机会多一条跃迁：`DISPATCHED | ACCEPTED → PENDING_DISPATCH`（动作码 `ORDER_RELEASE_SILENT`，与 `ORDER_RECALL` 分开）。

## ⑥ CHG 专章

### Before

- 派单池只有一档「待派单池」：已派的单从列表消失，派单员没有任何「按司机看已派单」的视图。
- 想把一张已派的单收回来，唯一手段是「撤回」（`recall`）：它会把整张单撤回并**给货主发站内信**（`orders.recalled`）—— 一件内部调度的事变成货主可见的事件。
- 库里也没有地方记「货主最后看到的状态是什么」，所以任何「真实状态改了但货主看着不变」的做法都无法落地。

### After

- 派单池页两档：待派单池 / 已完成派单；后者按司机分组（组头名字 + 电话），组间按组内最新单 id 倒序。
- 每张已派单的卡左侧有「退回池子」→ 弹层（说明 + 可选原因）→「确认退回」，成功提示「已退回派单池，货主端不会有任何变化」。
- 退回的真实效果：`orders.status → PENDING_DISPATCH`、`driver_id / dispatched_at / driver_acknowledged_at / driver_piece_amount / driver_commission_rate` 一起清空、`shipper_status_hold = <退回前的状态>`、`auto_stock_release`、审计 `ORDER_RELEASE_SILENT`、司机收到 `orders.revoked` + 池子变更事件。
- 货主侧：出参按冻结值显示「已派单 / 已接单」，列表仍在该档、只出现一次；消息中心零新增；订单详情流转记录无「退回」字样。
- 审计页（派单员 → 报表中心 → 异常与审计 → 审计）能回看：`退回派单池（货主无感）` / `原因 chg0039-e2e`（这是货主无感之后**唯一**能事后回看的地方）。

### L3 必答（规范 §二十七）：为什么不能通过新增 Extension / Contract 解决？

```text
1. Extension 是什么：给第三方/外部接入用的扩展面。本事项是「派单员内部把一张已派的单收回池子」，
   没有任何外部参与方；把内部状态跃迁挂到扩展点上，等于让扩展面成为状态机的第二个写入口。
2. Contract 是什么：既有接口对客户端的兼容承诺。本事项要新增的是**一条跃迁**与**一列事实**，
   不是既有接口的形状变化 —— 新增端点本身不破坏任何旧契约，但光加端点不写跃迁是空壳。
3. 状态的唯一真相在 order_flow.py：绕开它另写一处 status 赋值，就等于把并发防重与派单/撤回的既有
   不变量拆成两份（判据 _check_order_commands.py 直接数「API 层直写状态 0 处」）。
4. 货主出参的唯一出口在 order_response.py：写在别处会出现同一条口径两个实现（列表一个样、详情另一个样）
   —— 这正是「静默」最容易漏的地方（漏一处就等于把内部调度暴露给货主）。
5. 领域词汇表是共用的：不新增 ORDER_RELEASE_SILENT 动作码，审计里就分不清「通知货主的撤回」与
   「不通知的退回」，事后无法回答「这单是被撤回过还是被静默退回过」。
6. 库结构只能走迁移：shipper_status_hold 必须可空、不回填、不设默认值；走 create_all 之外的任何
   旁路都会在新老库之间产生两种结构。
```
