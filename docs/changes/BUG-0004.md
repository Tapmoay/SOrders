# BUG-0004 · 派单这条路上的三个洞：档位按布尔分、带出换人不出声、订单详情页没有派单入口

> 走查自 2026-10-03 三端真机 E2E 报告（`_tmp/E2E测试报告.md`）P8 / P9 / P12。
> 三个洞不是三件事，是**一份能力长错了地方**：整份「派单」弹窗体只长在「待派单池」这一页里，
> 分类只认一个布尔量（`pickVehicle` = 大车组 / 挂车组）；订单详情页要用它，只能再写一份；
> 而收货人那两栏被「带出」覆盖时也没人出声 —— `ui/common/ContactFill.kt` 只管**填什么**，不管**说一声**。

   **P12** 订单详情页底部只有 现场支付 / 挂账 / 拆分订单 / 删除订单，**没有派单** ——
   要看一张单派给谁、要改派，只能退回「派单作业」Tab 的待派单池里翻（`_tmp/d_detail2.png` / `_tmp/m_detail2.png`）。

② 现在的样子：司机分**三种**（小车 / 大车 / 挂车，见 `docs/plan-driver-freight.md`），本仓库唯一的标签函数是
   `ui/dispatcher/UsersManageScreen.kt:587 internal fun driverKindLabel(vehicleType: String?): String`
   （`small -> 小车司机` / `large -> 大车司机` / `trailer -> 挂车司机`；同文件 :583 的注释还记着「这里原来把 small 写成大车司机」那笔旧账）。
   可派单弹窗体整个长在 `ui/dispatcher/DispatcherPoolScreen.kt:177` 起：`var pickVehicle by remember { mutableStateOf(false) }`（:196），
   两个页签点是/否，下拉过滤写成 `vm.drivers.filter { (it.vehicleType == "trailer") == pickVehicle }` —— 一个布尔量扛三种车型，
   于是 `small` 被吞进「大车组」，标签也写成 `Text(if (pickVehicle) "挂车司机" else "大车司机")`，**不跟选中的人走**。
   收货人这两栏有四个来源（手打 / 选联系人 / 选线路 / 选地点），`ui/common/ContactFill.kt` 只回答「带出时填什么」，
   被覆盖的一方**没有任何人负责说一句**。派单能力这边，`ui/order/OrderDetailViewModel.kt` 里只有拆分与完成，一行派单都没有。

③ 变化：三处，一个方向 —— 把「派单」从一页里**抽出来变成一份共用件**，把「分类」从布尔量改成**真值**，
   把「被换掉了」这件事**说出来**：
   (a) 新增 `ui/dispatcher/AssignDriverDialog.kt`（272 行）：一份弹窗、两个入口共用；档位**数据驱动**
   （`driverKindLabel` 说的三档，只画真的有人 的档位）、过滤按 `vehicleType` 真值、标签经 `driverKindLabel` 跟着选中的人走、
   错误行走共用件 `FormErrorLine`；池页面自己那份弹窗体（含运费模板子弹窗）整体搬进来。
   (b) 订单详情页底部动作区加「派单」主按钮（闸门与拆分**同源**：`OrderStatusModel.ASSIGNABLE`），
   借用池子那份 ViewModel 但传 `autoLoadPool = false`（只为弹一个框，不该顺手拉整池），名册改成按需 `loadDrivers()`。
   (c) `ui/common/ContactFill.kt` 新增纯函数 `receiverSwapNotice(before, after, source): String?`（三句话：被清空 / 带出 / 换人），
   线路与地点两条支路都调用它，画在**收货人两栏正下方**，用户一动手（手改名称/手改电话/挑联系人/预填）就清掉。
④ 不能变：司机档案的三种车型与 `driverKindLabel` 的三个返回值；「带出」的规矩本身
   （线路/地点带出优先、来源空着的那栏不许清用户填的、手改永远能覆盖）；派单的既有链路
   （`repo.assignOrder` / `batchAssign`、运费与「收取现金 / 内部备注」字段、`confirmAssign` 的校验口径）；
   两个角色的权限（只有派单员能派单与挂账，货主/司机端不显示）；待派单池既有的批量派单与筛选；
   收货人名称/电话仍然可选；后端与数据库**一个字不动**。
⑤ 结论：**Presentation ＋ 局部行为（Local Behavior）** —— 弹窗怎么分组、标签写什么、按钮放在哪、提示画不画；
   没有新事实、没有新契约、没有新写入、没有迁移。⇒ Blast Radius **L1**。

## ⑤ Data Contract

- **新增/改动哪些字段**：**无**。零字段、零表结构、零迁移、零后端改动。
- **Owner 是谁**：弹窗状态与名册的 Owner 是 `DispatcherPoolViewModel`（`drivers` / `selectedDriverId` / `openAssign` / `confirmAssign`）；
  那句话的 Owner 是下单页的 `OrderCreateViewModel.receiverNotice`（语义 = 设计规范里的 `formError` 同类：**表单一侧的提示**），
  ⛔ 它**不**承担页面级 `loadError`（那一格仍然只有 `load()` 写，整页 ErrorView）。
- **什么时候写 / 什么时候不写**：`receiverNotice` 只在**带出成功覆盖**时写（线路支路 / 地点支路各一处）；
  用户一动手就写 `null`（手改名称 :578 / 手改电话 :953 / 挑联系人 :968 / 预填 :982）。
  `selectedDriverId` 只在用户选人时写（切页签顺带选人算用户动作）；`drivers` 只在 `loadDrivers()` 里写。
- **是否允许 NULL**：允许 —— `receiverNotice = null` 的语义是「现在没有话要说」，界面上不占位、不留空行。
- **历史数据怎么办**：**什么都不做**。本事项不写库、不读库；旧的订单派给谁、收货人是谁，一个字不改。
- **迁移怎么做 / Rollback 怎么办**：**无迁移**。Rollback = 池页面把弹窗体收回去、删掉详情页那颗按钮与 `AssignDriverDialog` 调用、
  删掉 `receiverSwapNotice` 与其两处调用（或只摘 UI、把纯函数与单测留下）。
- **删除本功能后历史数据还能不能解释**：能 —— 派单记录、账目、收货人全不受影响，只是退回「详情页没有派单入口」的旧样子。
